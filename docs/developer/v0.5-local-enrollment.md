# Transactional local enrollment

Astra #42c2 provides the persistence and online Host primitives for [initial bootstrap and local principal lifecycle](v0.5-architecture.md#2c-privileged-initial-owner-bootstrap-product-decision-2026-09-01-owner-002). [Owner recovery transactions](v0.5-owner-recovery.md) extend these primitives in #42d1. The [protected handoff foundation](v0.5-owner-handoff.md) supplies artifact delivery. The [offline coordinator](v0.5-offline-coordinator.md) implements privileged preparation and the [local security RPC adapter](v0.5-local-security-rpc.md) binds online completion. The [production Host service](v0.5-host-service-composition.md) exposes this adapter. The [ordinary-client composition](v0.5-client-security-composition.md) is implemented; [real multi-user ceremony qualification](v0.5-windows-local-security-qualification.md) now covers the composed Windows boundary.

## Authority and transaction boundary

Every repository operation owns a non-pooled, existing-database-only SQLite connection and an immediate writer transaction. The caller retains the machine-wide Host/offline lease. Ordinary clients have no project path to this repository. The online Host adapter receives authenticated connection state and trusted native identity from the local TLS composition. An incoming request cannot supply its own actor evidence or native identity.

Enrollment creation and non-Owner revocation recheck the actor's HostId, principal ID, native identity, current public key, Active state and Owner flag inside the write transaction. A previously authenticated Owner snapshot cannot authorize after a credential change. No grant, OS group or administrator status substitutes for this check. Ordinary operations cannot revoke, replace or demote the Owner. This unit issues no capability grants.

The offline bootstrap preparation persistence primitive requires an actual privileged, lease-holding caller; it is deliberately absent from the online adapter. It refuses an initialized Host and any unexpired live bootstrap authorization. An expired predecessor is invalidated atomically with preparing its replacement. The offline coordinator enforces actual OS privilege, machine exclusivity, credential setup and protected handoff delivery.

First bootstrap consumption checks the intended native identity, keyed verifier, expiration, valid public key, Uninitialized state and absence of an existing principal for that identity. Initial Owner registration, Initialized transition, ticket consumption/result and audit event commit together. Any failure rolls everything back.

Additional enrollment creates one new non-Owner row or reactivates the exact retained Revoked row authorized by the ticket. A new-row ticket cannot overwrite any existing row; a reactivation ticket cannot overwrite an Active row. Every state transition invalidates other unconsumed enrollment and dependent Owner recovery tickets in that same transaction, including recovery candidates prepared when the target had no row. Snapshot equality alone cannot revive a ticket after a revoke/reactivate/revoke cycle.

Revocation retains the row, clears its public key, invalidates dependent tickets and both Host/server grant forests, and audits atomically. Grant invalidation follows descendants from grants held by the revoked principal; unrelated trees remain unchanged, including independent root grants that the prior Owner issued to other actors. The issuer field is historical attribution, not another provenance parent. Repeated revocation of an already-revoked row is a no-op. Reactivation never restores invalidated grants.

## Secrets and retries

The online adapter only retrieves a previously provisioned 32-byte key from `ISecureCredentialStore`, named `local-enrollment-verifier-v1-<HostId in N format>`. The name is nonsecret. The key is independent of the rotatable TLS identity credential and must be retained for the lifetime of the recorded tickets, including consumed ones. Missing or invalid key material fails closed; online requests never generate, replace or delete it. Offline provisioning is still #42d.

Verifiers use HMAC-SHA256, domain-separated by version, HostId, purpose and ticket ID. The exact ASCII prefix is `PSM.LOCAL.ENROLLMENT/1\n<HostId:D>\n<purpose decimal>\n<ticketId:D>\n`, followed by the presented secret bytes. Purpose values are InitialOwner=1, AdditionalPrincipal=2, OwnerRotation=3 and OwnerRehome=4; the latter two serve the recovery transactions. Raw codes and HMAC keys never enter persistence APIs. The online adapter generates 32 random bytes for an additional enrollment and gives the Owner a redacted secret object for explicit out-of-band delivery; its first-consumption lifetime is 15 minutes. The persistence boundary rejects creation lifetimes beyond 24 hours. Client presentation/encoding and offline handoff composition remain later work.

Wrong-code attempts on a live additional-enrollment ticket increment a durable counter, capped at ten. At ten, even a correct first consumption is refused; only a freshly authorized ticket can proceed. Immediate writer transactions serialize concurrent attempts and consumption. Native mismatch or stale state never creates authority. Expiration gates only first consumption.

A correct secret for a consumed ticket returns its recorded principal ID at any later time, even after expiration or subsequent revocation. It never re-registers a key, restores authority, consumes again or appends a second completion audit. A different submitted public key is ignored on that read-only retry. The client must retain its original unbound key until the result is bound, as the existing credential-store contract requires. Wrong secrets and wrong native identities are always refused. Initial Host initialization does not block this consumed-result exception.

`LocalEnrollmentVerifier` and returned bearer objects redact normal text, public-property destructuring and diagnostic JSON. Verifier export is explicitly for the database. Audit events use fixed event kinds and bounded nonsecret summaries, never request-controlled free text or a verifier. Raw buffers explicitly extracted by a trusted cryptographic consumer remain that caller's cleanup responsibility.

## Evidence boundary

Isolated tests cover concurrent bootstrap and reactivation, rollback on audit failure, exact expiration, indefinite consumed-result retries, durable concurrent ten-attempt lockout, new-row duplicates, revoked-target ABA, dependent recovery-ticket invalidation, both grant forests, current Owner/native/key checks, client proof after enrollment, revocation of an existing connection, missing/corrupt secure-store key, cancellation and redaction. These fixtures run under unique leases with synthetic identities; they do not replace the final real Windows service/two-user bootstrap and Owner-recovery acceptance tests.
