# Owned Windows discovery receiver

Trial reference: #44ab, within #44. `WindowsLanDiscoveryReceiver` implements the neutral `ILanDiscoveryReceiver` lifetime and public-hint callback. Its public constructor requires an explicit port from 1 to 65535 and binds an exclusive IPv4 UDP socket. There is no default installed discovery port, sender, Host generation wiring or local-client action in this unit.

The receiver requires [Windows IPv4 packet information](https://learn.microsoft.com/en-us/windows/win32/winsock/ip-pktinfo), verifies that the option is enabled and obtains the actual incoming interface and source from the socket result. A payload cannot select its own source address. Every candidate uses a fresh [Windows hardware/subnet eligibility observation](v0.5-windows-lan-policy.md); no old interface index or cached eligibility grants admission. An unreadable or disappearing adapter is excluded by the native policy. An unexpected exception escaping inventory terminates the receiver and is observable through `Completion`.

Empty packets, packets over 512 bytes, truncated data/control information and missing/invalid IPv4 source/interface metadata are dropped before inventory or callback work. The receive buffer has one extra byte, and a Windows message-size error is also dropped. All receive attempts, including malformed traffic, incur a 10 ms delay: at most 100 receive attempts and policy reads per second, with no catch-up burst. A fixed socket buffer and one serial worker bound queued work. Discovery remains best effort under floods; these limits do not guarantee availability or authenticate a sender.

Each admitted callback gets independent payload storage, the actual interface/source and an owner cancellation token. Callbacks run serially, and already admitted callbacks belong to shutdown even if they ignore cancellation temporarily. `DisposeAsync` closes the socket, requests cancellation and waits for the worker, callback and cancellation callbacks to finish. Repeated disposal observes the same completion/failure. Unexpected receive, policy and callback failures also close the socket. Worker and cancellation failures remain observable after cleanup. The Host owner must observe `Completion` and await disposal; a callback must not await its own receiver's disposal/completion.

The ordinary `--windows-lan-receiver-probe` uses real loopback UDP and packet metadata through an internal constructor that can bind only loopback. Its synthetic admission hook exercises fresh refusal and callback mechanics independently of production hardware eligibility; the public constructor always uses the native Windows policy. Tests cover empty/513-byte/4096-byte drops followed by a complete 512-byte packet, independent payload storage, changing admission, serialized blocked callbacks, concurrent disposal, policy/callback/cancellation failures (including simultaneous worker and cancellation failures), null callbacks, invalid production ports, bind contention and exclusive rebinding after cleanup. Real production construction is checked without sending physical-LAN traffic. Loopback evidence does not certify multiple machines, real LAN broadcast or physical adapter changes.

The callback carries unverified hints for the [Host discovery directory](v0.5-host-discovery.md). It cannot create trust, grants or authoritative identity; actual pairing and negotiated TLS remain required. The [availability boundary](v0.5-discovery-availability.md) distinguishes known, cleanly drained native failures from callback/cleanup faults; it adds no automatic retry. The [constrained sender](v0.5-windows-discovery-sender.md) supplies one owned broadcast round. The [Host runtime](v0.5-host-discovery-runtime.md) owns periodic sending and receiver recreation. Generation/installed configuration and local authorization follow. Linux remains gated on Windows parity.
