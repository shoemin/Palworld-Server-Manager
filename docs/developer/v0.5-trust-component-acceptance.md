# Trust revocation component acceptance

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28). This is the isolated experiment's aggregate acceptance of PRs157–182, built on accepted credential storage (#27), peer transport (#44) and authorization (#45). Canonical issue and Project status are unchanged. Completion means the authorized Host trust component is ready for migration and later UI consumers; it does not mean the whole product is ready for release.

## Acceptance evidence

| Issue criterion | Implemented behavior and qualification |
|---|---|
| Online two-sided unpair works and is idempotent | Canonical local commit is unconditional. An already prepared authenticated connection sends a bounded best-effort notice; the receiving canonical transaction revokes only the original sending peer. The exact receipt permits a read-only duplicate on the retained original session, never a fresh stale handshake. `ReciprocalUnpairTests`, `PeerUnpairRpcTests`, live connection/coordinator tests and four actual receiving-process delivery/fault cases cover confirmation, lost reply, hang and death. |
| Offline local revocation immediately blocks stale credential reuse | `RevokeLocalPeerTrust` and `RevokeRemotePeerTrust` share one immediate transaction, clearing pins/rotation/recovery, retaining a tombstone and invalidating the exact grant forest. Notification neither opens a connection after commit nor delays the transaction. Actual process tests reopen the database and refuse stale reconnect. |
| Reconnect cannot silently restore Active trust | Canonical admission checks current trust and original key pair/incarnation. Revoked/PeerBound/recovery traffic cannot obtain ordinary authority. A fresh request claiming the same HostId enters the explicit replacement gate. Native negative/reconnect cases and original-session ABA tests cover this boundary. |
| Re-pair establishes a fresh relationship | Fresh PAKE evidence binds candidate key, local key and relationship incarnation. Only the current actual local Owner approves replacement; old grants remain invalid and current configured defaults create fresh roots. Native same-key revoked re-pair and simultaneous own-key recovery both complete genuine ceremonies and independent Owner approvals. |
| Dependent grants follow exact provenance only | `PeerTrustRevocationTests.AtomicForestsTombstoneAndAudit` and remote administrator cases select grants issued to or by the peer and their single-parent descendants. Already-invalid roots cannot hide live descendants. Replacement uses the same canonical forest rules. |
| Unrelated grants remain intact | Exact before/after grant, trust, pending-candidate and completion tables are compared before commit; unexpected successful-audit side effects roll back. Tests retain unrelated grants of the same capability and target and preserve their effective permission. |
| Owner remains unaffected and unrevokable remotely | Actual local Owner identity is preserved by canonical policy and integrity checks. Remote self-revocation has only the narrowly verified committed-result exception. Replacement is local-Owner-only. The originating local Owner still cannot bypass the receiver's independent machine ceiling. |
| Audit is complete and secret-free | Each changed authoritative transaction writes and verifies its bounded success audit in the same transaction; no-op duplicates write nothing. Audits identify actors, semantic peers, counts and incarnations, without keys, codes or secrets. Failure/late-effect tests prove rollback; actual two-Host and process tests check independent local audits. An unreceived best-effort notice cannot produce a remote success audit. |

## Complete paths and limits

The [local trust RPC](v0.5-local-peer-trust-rpc.md), [receiving remote administration RPC](v0.5-peer-trust-administration-rpc.md) and [originating local-user route](v0.5-originating-user-trust-route.md) derive actors from their actual protected sessions. The originating Host checks the current user's exact-destination permission before contact, before command and before reporting; the receiver separately checks its machine ceiling. No client carries the Host private key. Denied local requests make no outbound contact.

[Local network actions](v0.5-local-trust-network-actions.md) explicitly prepare a live unpair connection before revocation. Missing preparation does not weaken offline revocation. [Unpair coordination](v0.5-unpair-coordinator.md) retains at most32 actual workers for at most two minutes; delivery is bounded to three seconds and generation shutdown awaits actual transport disposal. This is ephemeral security work, not a durable remote-command queue. Each Host commits independently, so reply loss or a later local refusal cannot undo an already completed remote effect.

[Owner replacement](v0.5-owner-peer-replacement.md), [recovery confirmation](v0.5-recovery-completion-confirmation.md), [recovery contact](v0.5-recovery-contact-retry.md) and [offline continuity](v0.5-offline-recovery-completion-continuity.md) preserve exact approval/key/incarnation evidence. Offline recovery never restores old authority; the compromised/lost key cannot authenticate its own replacement. Genuine [repair](v0.5-native-repair.md) and [own-key recovery](v0.5-native-own-recovery.md) are distinguished from fixtures with historical verified bindings. [Unpair](v0.5-unpair-process-qualification.md) and [recovery](v0.5-recovery-process-faults.md) fault tests use actual disposable receiving processes.
