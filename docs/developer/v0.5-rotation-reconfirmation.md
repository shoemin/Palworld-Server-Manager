# Retained rotation status and Owner reconfirmation

Trial reference: #44m, within #44. This supplies the trusted Host persistence boundary for a live check of an already-staged rotation. The [negotiated status RPC](v0.5-rotation-status-rpc.md) now supplies the transport; the promotion-receipt exchange, global cutover/retirement engine and local/service composition remain required. Public request/reply records are correlation data, never proof of identity, key possession or a fresh exchange.

`BeginPeerRotationStatusQuery` captures the exact Active, non-recovery peer's Current, Pending, RotationId and original deadline. It creates a random query ID and a twenty-second monotonic, single-use in-memory context owned by that repository instance. Restart, another repository, expiry or a failed/ambiguous completion requires a new live query. No context is persisted or reconstructed from wire input. Non-null Owner intent means an explicit local approval for that retained candidate, with the actual authenticated Owner/native/verifier tuple checked when the query begins. An opportunistic query has no renewal authority.

The trusted status transport sends the captured request on this Host's own fresh exchange, verifies the negotiated peer UUID and exact echoed correlation tuple, and obtains the actual fingerprint from completed mutual TLS. `CompletePeerRotationStatusQuery` rechecks Active/non-recovery trust and all captured pending fields inside one write transaction. A changed deadline, replacement stage, prior promotion or lost/revoked trust makes the context stale. Single use and original-deadline comparison prevent replaying an earlier approval after the same rotation lapses again. Monotonic freshness is checked after lock acquisition and again after audit before commit, so wall-clock rollback or a delayed transaction cannot revive an old exchange.

Only the already-trusted Old credential can resolve status here. Old-authenticated Staging/ReadyForCutover renews a lapsed stage to thirty minutes and clears its reconfirmation flag only with captured explicit Owner intent and a fresh exact Owner/native/verifier check in the transaction. Current, Pending fingerprint and RotationId stay unchanged. An unexpired stage is not extended. A passive query cannot renew. The renewal audit names the local Owner. Old-authenticated Aborted/Unknown clears only those Pending fields with a remote-peer audit, including for an opportunistic query. Accepted proposal replay history and customized grants remain intact.

Old-authenticated CutOver/Completed content never promotes, renews or clears the retained stage; it can only cause normal lapse maintenance. Actual New presentation uses the existing ordinary completed-TLS observer, independently of any status claim or Owner approval. That observer's promotion makes this captured Old/pending context stale, so status completion cannot clear its outstanding promotion receipt. No reply can introduce a new candidate.

The sender's `ReadRoutineRotationStatus` is read-only and independently matches the connection's actual local fingerprint to current durable Host identity, then checks the requested rotation's exact public Old/New tuple. A known proposal's immutable tuple must also match; legacy state may answer from its durable credential references without inventing proposal ordering. Staging/Ready/Aborted require Old still presented; CutOver/Completed require New. Unknown means the requested identity is absent; malformed, inconsistent, uninitialized or nonmatching state is denied. The wire adapter authenticates the requesting Active peer before exposing this read.

Six ordinary scenarios cover fresh Owner authority, passive/non-promoting status, exact correlation and retained tuple, monotonic expiry despite wall rollback, concurrent renewal, repeated lapse, failed audit and deadline-crossing rollback, recovery/changed-stage/promotion races, legacy public state and current presentation. Persistence inputs are synthetic at these trusted seams; this unit does not claim new wire proof, service composition or physical/process-crash evidence. Full #44 remains incomplete.

Status completion now also matches the actual local TLS fingerprint to the captured and current local Host credential inside the transaction. A local credential change invalidates that exchange.
