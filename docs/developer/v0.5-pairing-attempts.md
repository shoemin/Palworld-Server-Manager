# Host pairing attempt lifetime

Trial reference: #44b, within #44. `PairingAttemptCoordinator` is an internal Host responder component. It owns invitations and inbound SPAKE2 exchanges, now connected by the separate [first-contact Host stream](v0.5-peer-pairing.md) to the actual socket source address. Request-provided addresses are never acceptable. The future local handler must authorize invitation creation. Durable trust and pinned activation have separate implementation seams; terminal database audit delivery and periodic cleanup are now owned by the pairing runtime; installed-service composition, local dispatch and rotation remain outstanding.

An invitation contains ten uniformly generated ASCII decimal digits and a public random invitation UUID. Host retains the code only in an opaque, explicitly disposable secret buffer. The returned secret is a separate copy for the authenticated local delivery path. Diagnostic JSON and formatting redact it; cryptographic consumers must clear explicitly extracted buffers. No code is written to disk.

The five-minute lifetime uses monotonic elapsed time. UTC expiry is informational for display. Both a one-second cleanup timer and every operation check expiry, including after expensive native calls. Moving the wall clock backwards cannot extend the code. A Host crash loses every invitation and exchange; startup cannot recover them from an old UUID.

Each invitation allows one simultaneous exchange. Each new exchange gets a fresh 32-byte nonce and a fresh native handle. A failed or disconnected exchange counts once against the invitation, regardless of repeated calls on its old object. Ten failures lock the code for its remaining lifetime and erase the retained secret. Successful authenticated identity binding consumes the code and disposes the native exchange. Reusing the successful attempt object is rejected; downstream durable finalization must use its verified result and enforce its own transactional idempotence. The result is neither PeerBound nor Active and confers no authority.

Source backoff is shared across invitations, normalizes IPv4-mapped IPv6 addresses, and allows only one active exchange per source. Failures impose delays of one, two, four, eight, sixteen and then at most thirty seconds. History lasts ten minutes after last activity. A success also imposes a one-second creation delay. Unknown invitation IDs, unavailable invitations and failed initialization are rate-limited. Malformed cryptographic input, cancellation and disconnect conservatively consume a live exchange's failure budget; a local initialization error never verifies a guess but still backs off its source.

Residency is bounded to sixteen invitations and 256 source records. Unexpired source records are not evicted to admit address churn; a full table refuses new sources until records age out. This is an availability tradeoff, not protection against a distributed denial of service. Each invitation's single exchange also bounds native work below the wrapper's global 128-session limit. Cancellation, explicit invitation cancellation, transport disconnect, timer expiry and coordinator shutdown dispose owned native exchanges. The caller continues to own the provider and disposes it after the coordinator.

The coordinator callback carries only an attempt UUID and an outcome enum. `IdentityVerified` reports the cryptographic handoff, not terminal pairing success or Active trust. Exceptions from a consumer cannot prevent cleanup. The later [owned terminal audit journal](v0.5-pairing-audit.md) persists failed/expired outcomes, closes admission on write failure, and maintains pending trust with its existing audit transaction. The standalone coordinator itself has no database writer. No local authorization capability, ordinary management route, Host credential access or client dependency is added.

Three ordinary lifecycle scenarios cover failure counts/concurrent admission/backoff, monotonic expiry/restart/in-flight cleanup, and bounded residency/cancellation/audit failure. An additional actual native probe completes reciprocal Host identity binding, rejects a different code and verifies single-use cleanup. These extend the separate sixteen wrapper scenarios; synthetic lifecycle collaborators are not used as cryptographic evidence. Run the ordinary suite or `--pairing-lifecycle-probe`, and run the native `--spake2-wrapper-probe` described in [the wrapper documentation](v0.5-spake2-wrapper.md). Exact local/CI and two-pass reviews are recorded in the trial ledger.
