# Nonblocking unpair notification coordinator

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28).

`PeerUnpairCoordinator` owns only ephemeral [prepared unpair connections](v0.5-live-unpair-delivery.md). `Prepare` is an explicit Host action while trust is Active, separate from revocation. It admits at most 32 unfinished workers, with at most one preparation available per peer. Preparation and retention share a two-minute lifetime; the underlying factory additionally bounds connection establishment to 15 seconds and delivery to three seconds. No address, notice or retry is persisted.

The local and remote permission facades first complete the canonical revocation transaction with their fixed authenticated actor, expected authorization revision, target and relationship incarnation. Only afterward does `Notify` perform an in-memory lookup and signal an asynchronously continued worker. It never connects, sends inline, waits for acknowledgement, invokes cancellation callbacks or disposes transport on the return path. The synchronous result therefore remains the committed local result even if the peer is offline or delivery fails.

`RevokePeerWithNotification` returns the local result and a separate observational task. Missing, still-preparing, unchanged or stopped entries yield `NotAttempted`. A ready entry yields `Confirmed` or `Unconfirmed` after the scoped delivery and cleanup finish. These outcomes confer no authority. The existing `RevokePeer` facade uses the same notification path and returns only the local result. Denied, stale, canceled-before-commit and disposed-facade calls cannot signal delivery. Incoming reciprocal notices use the separate receiver and never trigger an echo.

A preparation removed by revocation cannot later become ready. A notified or removed entry still counts toward the worker limit until its actual task completes, including transport cleanup. Starting work suppresses ambient request execution context; the actor and facade stay inside the synchronous command. All completion signals use asynchronous continuations, and transport callbacks execute outside the registry lock.

Full Windows network composition shares one same-Host coordinator between local and remote runtimes and the network generation. Cross-Host wiring is refused. Generation shutdown closes preparation, signals and cancels workers, and drains all actual tasks before releasing its certificate. Cleanup still drains workers when cancellation callbacks throw. The local-only installed profile has no coordinator and reports notification as not attempted.

## Evidence and limits

Ten focused scenarios cover actual encrypted two-Host delivery through local/remote facades, a local result returned while a Host-side response adapter is held, denied/stale/bad-key/canceled/disposed calls leaving a ready connection unused, missing and deliberately unfinished preparation, no echo, cross-Host wiring refusal, capacity including removed workers, exact retention expiration, cancellation-callback failure with completed cleanup, both authenticated dispatchers routing notification, and real generation shutdown with certificate/timer cleanup. Capacity and timer tests use explicit lifetime adapters; dispatcher fixtures use production signing/verifiers with simulated transport context. The held response is a Host-side adapter around actual TLS, not evidence of a remote-server hang.

This unit does not add a public revocation RPC, automatic connection preparation, or UI. Full initiating-command orchestration, actual remote hang/drop qualification and fresh Owner-approved re-pair remain subsequent #28 work. The existing delivery guard continues to require the original connection proof and exact current committed tombstone. Ordinary outgoing administration still requires the originating user's independent local authority. Six creator permissions and limits are unchanged; accessibility certification remains **WAIVED, never PASS**. Physical-PC/Palworld/parity/Linux/release qualification is not claimed.
