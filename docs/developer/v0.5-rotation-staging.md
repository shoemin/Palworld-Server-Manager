# Durable rotation proposals and peer staging

Trial reference: #44l, within #44. This unit supplies public protocol metadata and the trusted persistence boundaries for staging. It does not send proposals, define a new wire feature, implement live reconfirmation or the remote receipt exchange, cut over Current, or retire keys. Those transport/rotation-engine steps remain required before full #44 acceptance.

After [material preparation](v0.5-rotation-material.md) and the Owner-authorized transition to Staging, `PrepareRoutineRotationProposal` rechecks the exact active Owner/native/verifier tuple and current pre-cutover rotation. It allocates one immutable proposal identity and monotonic SQLite AUTOINCREMENT sequence, recording its public Old/New fingerprints with the Owner audit in the same transaction. Concurrent or repeated calls return the same proposal. Audit failure rolls allocation back. A trusted Host can read that already-prepared proposal for retransmission, but only while the same rotation remains Staging/ReadyForCutover and Old is still Current. Aborted or post-cutover rotations cannot be sent through this path.

`StagePeerRotation` requires actual completed mutual TLS under the receiver's currently trusted Old fingerprint and an Active, non-recovery relationship. The future wire adapter must independently match the negotiated peer UUID and actual connection fingerprint; a public proposal DTO is never proof. PeerBound, an unknown peer, a local self-claim, a pending rather than current key, invalid sequence, same Old/New key or a changed proposal identity is refused. Staging never creates Active trust or applies defaults/grants.

The receiver atomically stores the accepted proposal, Pending fingerprint/rotation ID and a thirty-minute deadline with its authenticated-peer audit. Old stays Current. Repeating the same accepted proposal returns its retained deadline without extending it. A distinct, higher-sequence proposal can replace an unexpired pending stage. Previously accepted IDs/tuples remain immutable, older sequences cannot overwrite a newer stage, and a removed/overwritten accepted attempt cannot be silently staged again. Ordering is scoped to the peer UUID and its authenticated current-key fingerprint; a separately established fresh trust anchor has a distinct key epoch. Accepted rotation IDs remain retained across epochs as replay evidence.

A lapsed existing stage is marked for reconfirmation atomically and returned as blocked, without accepting a new proposal or changing either pin. A promoted peer still retaining a rotation ID for receipt confirmation also blocks fresh staging until that acknowledgement is resolved; no proposal can erase the outstanding receipt. These are explicit return dispositions, not permission to refresh or promote. The [completion observer](v0.5-peer-rotation-completion.md) still requires actual live New presentation, and only the separate Owner-approved live reconfirmation path can renew a lapsed deadline.

Migration 4 adds only public sender/receiver proposal tables. It does not infer a sequence, remote acknowledgement, proof, deadline or grant from older state. A retained legacy stage without recorded proposal ordering stays recognizable live and can complete using the existing observation/receipt rules, but cannot be overwritten/refreshed through this staging primitive. The separate live-status/reconfirmation boundary can resolve that exact retained tuple without inventing its proposal ordering. Credential history remains fingerprints/times only; the proposal replay ledger is separate and never substitutes for the retained promotion receipt ID.

Five ordinary scenarios cover concurrent sender allocation, Owner freshness, audit rollback, concurrent receiver idempotence, stale/changed/overwritten proposals, original deadlines, lapse and receipt blocks, current-key epochs, invalid identity/state, grant retention and a real schema-3-to-4 upgrade without invented metadata. Public fingerprints and accepted Active states are synthetic inputs at these trusted seams; actual wire proof is tested separately by the TLS components and is not claimed as a new proposal exchange here. Full #44 and physical/process-crash acceptance remain incomplete.

[Retained-rotation status and Owner reconfirmation](v0.5-rotation-reconfirmation.md) now provide the bounded persistence foundation. [Live status RPC](v0.5-rotation-status-rpc.md) is now implemented; [Proposal RPC and acknowledgement history](v0.5-rotation-proposal-rpc.md) are also implemented; promotion-receipt RPC and full rotation remain later work.

Actual staging transport now also supplies the receiver-local TLS fingerprint, rechecked against current Host metadata inside the staging transaction.
