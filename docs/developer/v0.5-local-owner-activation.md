# Protected local Owner activation and retry

Trial reference: #44aj, within #44. The full-network local runtime offers additive `LocalOwnerPeerActivation` (11) with local protocol 1.9. `ActivatePeer` requires that feature and local principal security, actual native-bound authentication and a current Owner. Pairing-only negotiation cannot enable activation; local-only composition does not advertise it. Requests contain only the expected peer Host UUID and a bounded reachable host/peer port, never an actor or private credential.

The current generation owns a fresh pinned mutual-TLS activation attempt with the existing fifteen-second deadline. Before network work and in acknowledgement preparation, the Host checks the exact captured Owner identity/verifier. Actual local and peer fingerprints, Host identities, pending expiry and trust state remain mandatory. The final immediate writer checks the Owner again after acquiring the writer, before any Active transition or mandatory hook effect, including an AlreadyActive retry. It rechecks the Owner after hook/audit work and observes cancellation before committing. No transaction spans network. The hook remains mandatory and transactional; #45 owns production default issuance.

The remote Host can activate before the initiating Host receives its acknowledgement. A changed local Owner can therefore leave remote Active and local PeerBound. The local transaction is refused without rolling back the independent remote state. A freshly authenticated authorized Owner can retry over pinned TLS without the old code; the remote AlreadyActive response and local final commit complete the transition. AlreadyActive retries do not repeat hook effects or grants. Unknown local/remote result values are refused, remote error detail/trailers are replaced with fixed local text, and no failure erases durable pending trust.

Four ordinary scenarios cover exact actor and readonly-retry guards, post-hook Owner/cancellation/failure/expiry rollback, fresh authorization or cancellation after real writer contention, and protected local RPC capability/native/Owner/input/unknown-peer boundaries. Genuine native qualification pairs two fixture Hosts, changes the initiating Owner verifier during the remote activation hook, proves remoteActive/localPeerBound, reauthenticates with a real replacement client key and completes/repeats pinned activation with one fixture effect per Host and zero real grants. These test hooks are not a shipped grant provider. Local loopback qualification is not installed-service, physical-LAN or process-crash acceptance.

Installed remote enablement with the concrete #45 hook/provider/configuration, safe old-key retirement and remaining crash/physical qualification are still outstanding. Existing trusted inbound/system activation paths retain their protocol and behavior; they do not gain a fictitious local Owner actor.
