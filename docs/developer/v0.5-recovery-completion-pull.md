# Bounded reverse recovery client

Trial #28r connects the [receiving offer surface](v0.5-recovery-completion-offer.md) to a Host-only client. `PeerRecoveryCompletionRpcClient.PullAsync` retrieves a peer's original pending acknowledgment, records the local canonical receipt, and confirms that receipt over a fresh authenticated connection. `HostNetworkGeneration.PullRecoveryAsync` owns the entire awaited exchange through the existing traffic lifetime. Automatic contact triggers have separate qualification below; public initiating commands remain #28 work.

Both phases share one15-second cancellation deadline and use actual Windows native mutual TLS, exact HTTP/2,16KiB messages and a known root HTTPS URI. The caller must retain the Host generation and borrowed certificate until the call, including actual native callback/channel/transport disposal, returns. Shutdown closes admission, cancels and drains the whole exchange before releasing that key. No incoming source port is treated as a peer listening address.

The first connection captures the actual current local and peer keys and original relationship incarnation once. It negotiates explicit features15 and16, checks the semantic remote Host and reads the offer. A peer lacking16 returns `Unsupported`, distinct from `NoPending` and `Confirmed`; a capable older-minor backport is supported. A well-formed differing acknowledged fingerprint reaches the existing canonical mismatch audit and returns `KeyMismatch` without confirmation. Malformed identifiers, fingerprints or replies fail before local receipt effects.

A matching offer goes through canonical `ReceiveAuthenticatedRecoveryCompletion`. That local transaction may clear recovery and advance the local incarnation. The client preserves the exact approval, actual keys and this specific result incarnation, then fully disposes the first transport. It never refreshes or reuses that session's proof. The second connection must capture exactly the expected actual keys and result incarnation. A new read-only `RequireRecordedRecoveryCompletion` validates the exact latest durable receipt under current initialized Owner/trust/key state before and after sending the positive attestation. It refuses a superseded receipt without rewriting it. Only closed, exactly correlated `Confirmed` or `AlreadyConfirmed` responses qualify success.

Each Host commits independently. A dropped offer leaves the original remote obligation pending. A dropped connection after the local receipt but before remote confirmation preserves that receipt; a later pull processes the original acknowledgment as an exact duplicate and retries confirmation. If the peer committed confirmation but its response was lost, this attempt fails; a later read can return `NoPending`. It does not fabricate a recovered success response. Likewise, a local trust, credential or receipt change after the peer commits causes local refusal without claiming to undo the remote transaction. No extra durable token or offline command queue is added.

Ten test groups cover actual two-way independent recovery with fresh native connections; exact read-only receipt validation; controlled loss at each of three phases followed by listener restart and runtime recreation; original local keys/incarnation/Owner and remote approval changes; receipt supersession; malformed offers and canonical mismatch audit; malformed confirmation and post-commit local change; explicit features/backports/no-pending/input bounds; generation shutdown while the second actual TLS callback is held; a single real deadline spanning delayed first and held second responses; and eight concurrent clients with one receipt/confirmation audit. These historical-binding/canonical-approval fixtures and controlled Host-side response faults do not replace the separate genuine native PAKE scenarios or actual remote process/network fault qualification.

The client itself never triggers another retry. The separately qualified [contact coordinator](v0.5-recovery-contact-retry.md) connects existing fixed security clients to opportunistic retry. A denied ordinary administration request must still make no outbound contact, preserving originating local-user authorization and the independent remote machine ceiling. Public initiating commands and actual remote hang/drop remain #28 work. Creator six/limits are unchanged; accessibility/screen-reader certification remains WAIVED, never PASS. No physical Palworld run, Windows parity, Linux production or release acceptance is claimed.

The Astra trial used no external GitHub Codex reviewer. Astra was responsible for both implementation and technical review.
