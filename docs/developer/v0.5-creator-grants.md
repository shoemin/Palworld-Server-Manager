# Approved remote creator permissions

Trial reference: #45f. The Owner explicitly approved six automatic permissions for a successfully created server: ViewServer, StartStopRestart, EditSettings, ManageBackups, TransferExport and DeleteServer. ManageServerSharing is excluded, and both delegation flags are false. This supersedes the earlier seven-permission proposal. No permission is added to an existing server or unrelated peer, and no Host administration permission is created.

The [canonical policy](v0.5-authorization-foundation.md) expands exactly six fresh server grants for the creating peer and the new local Host-qualified ServerRef. The peer must currently hold CreateServer for this exact Host. The approved automatic policy issues current Owner roots through IssueServer, with null parents; it never converts a Host capability into a server-scoped parent or fabricates authenticated Owner credentials. Pure candidate construction writes nothing and proves no creation occurred.

`CommitConfirmedRemoteCreation` is a trusted Host-only finalization seam. Its mandatory callback persists the Host's already-confirmed successful creation metadata on the supplied connection and transaction. It is not a request-supplied success Boolean, server executor or network endpoint. The caller holds the Host lease; callback code must perform only database finalization, without external work, nested commit or rollback. The later operation/creation workflow must establish actual success before invoking it and integrate this seam; the present slice does not claim that workflow is implemented.

Before the callback, the immediate transaction checks actual completed TLS/negotiation evidence, current Active non-recovery peer, accepted remote pin, current local credential, exact relationship incarnation and expected authorization revision. Evidence is supplied by trusted Host transport, never deserialized from a request. Current or already trusted pending credential presentation retains the accepted rotation rules. The peer needs exact CreateServer authority, and both inventory and historical server grants must be absent for the proposed identity. A duplicate finalization or reuse of an identity with grant history refuses before the callback.

After the callback, the exact new inventory row must exist and current authority must still match. The six grants are timestamped after confirmation, inserted and audited with the actual remote peer, true current Owner issuer, exact server/capability and a Host-generated creation-event correlation ID. That ID groups confirmation-related grant audits; it is not a durable server-operation identity. No paths, display names, fingerprints or verifier material enter these audits. Final inventory, peer proof/incarnation, Owner, revision and exact grant checks precede cancellation and commit. Any callback failure, missing registration, audit failure, authority mutation or cancellation rolls back registration and all grants together.

These are machine-level ceilings. Each initiating user still needs independent local permission on the originating Host; no local-user permission is automatically created here. Revoking CreateServer later prevents future creation without revoking the independent Owner-root management grants already issued for existing servers. Ordinary sharing requires separately authorized delegation.

Eight pure/actual SQLite scenarios cover exact six-entry membership/no sharing/delegation, post-confirmation timestamps/real actor audit, failed/missing/duplicate/reused identity, wrong peer/local pins/incarnation/revision/CreateServer target, confirmation and final audit mutations including Owner and grant changes, eight competing writers, independent local-user ceilings, trusted pending pins and cancellation. Fixtures simulate Host-confirmed creation; they do not run Palworld or prove installed creation/remote routing. No schema, wire, dependency, OS or server-operation implementation is added. The [remote grant writers](v0.5-remote-grants.md) reuse the current peer-proof check. Remaining #45 authenticated Host adapters/enforcement retain their gates. Accessibility is waived; physical parity, Linux and release qualification remain downstream.

[Pre-write permission denial auditing](v0.5-permission-denials.md) now commits a denial-only record for an authenticated policy refusal before any requested mutation. No requested grant/default/history/invalidation/creation effect commits on refusal. Authentication, malformed/stale/cancelled requests and later mutation/audit failures retain their separate rollback paths.
