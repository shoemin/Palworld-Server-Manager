# Authorized Host settings observations

`SettingsSnapshotReader` is a trusted synchronous Host engine combining the managed file reader, strict project-owned parser, semantic DTO mapper and private content revision repository. It is not a production RPC and is not yet activated in Host composition. Future local and peer handlers must share one reader for the Host lifetime and preserve its ordering with future saves; independent per-request readers would not serialize file observation order.

The request names a fully qualified ServerRef on this Host. Current ViewServer is checked before waiting and again after acquiring the cancellable ordering gate, before inventory or file reads. Registration must exist. The managed adapter binds its recorded path to the exact profile's fixed files. No read creates an active file or infers installation defaults/effective values. EditSettings does not imply read authority.

Each file is parsed with PreservedPalworldConfigFile. Only catalog entries positively classified as nonsecret have values retrieved and decoded through the existing PalworldConfigParser.Unquote helper. Secret/unknown keys retain metadata with no configured/default/effective values. Duplicate positively nonsecret keys are rejected as ambiguous, without assigning new runtime semantics; repeated secret/unknown keys are deduplicated as metadata. Sources and aggregate DTO bounds are checked before revision effects. Raw file bytes are disposed/cleared on success and failure; parser copies and strings remain subject to managed-memory lifetime, not complete erasure.

The content observer hashes the active bytes and issues the existing canonical decimal revision. The optional defaults are independently observed and do not determine that active-file token. Unchanged content retains its revision; observed changes, including change-and-revert, advance it. This cannot detect an unobserved change-and-revert or freeze the filesystem.

Before metadata effects and again before commit, a supplied read-only validator checks current authenticated local/peer evidence and exact ViewServer inside the observer's owned SQLite transaction. `GrantPolicyRepository.ValidateLocalServerCapability` and `ValidateRemoteServerCapability` reuse the canonical current proof and scope policy but never open a nested writer, write a denial audit or commit. Connection/transaction and exact authoritative database binding are checked. Initial canonical authorization retains its normal denial audit. Permission facades retain callback thread, lifetime and cancellation guards. Local outbound still requires Active destination plus the local grant; incoming peers may target only this Host and need current TLS fingerprints/incarnation/Active non-recovery proof. Neither path grants the other ceiling.

The same transaction also validates the registered inventory observation, including exact path, creation time and all recorded fields. Rebinding, deletion, pending credential/grant changes or final cancellation refuse and roll back the observation transaction. Existing inventory strict type/UTC/initialized-Host/single-Owner checks remain intact. A final canonical authorization and cancellation check runs before returning the DTO. A refusal after the metadata commit can retain a private observation row; no file write, grant or response is produced. This is an observation, not an atomic file save.

Tests cover View-only local/peer success and Edit-only/no-grant refusal before IO; qualified targets and missing registration; secret/unknown suppression; original nonsecret decoding and optional defaults; unchanged/reopened/changed/ABA revisions; credential/grant/registration races; SQL-trigger changes seen by final validation and rolled back without denial-audit commits; malformed/ambiguous/oversized projections and platform failures before metadata effects; queued and final cancellation; concurrent reads; exact transaction binding and current/staged peer proof; guarded facade lifetime/thread/cancellation. Existing real service file qualification remains separate from this Host engine's synthetic registered file source.

Future RPC work still needs additive negotiated contracts, bounded transport sizing, both remote ceilings and Host network-generation lifetimes. Future saves require EditSettings, fresh byte reconciliation before token comparison, verified stopped lifetime, durable Host operation locks and filesystem recovery. No production settings RPC/save, game execution, Windows parity, Linux or release qualification is claimed here.
