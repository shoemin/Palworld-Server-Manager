# Fixed authenticated recovery completion RPC

Trial #28k exposes the [canonical exact-key receipt](v0.5-recovery-completion-receipt.md) through the existing Host-owned Windows mutual-TLS HTTP/2 peer service. `NegotiateRecovery` and `ReceiveRecoveryCompletion` are fixed security operations. The receiving Host derives the approving peer, actual local/remote public fingerprints and original relationship incarnation from its own completed TLS connection. The request supplies only the intended receiving Host, approval ID and acknowledged receiving key. It cannot select an actor, grant, incarnation or ordinary-authentication bypass.

## Admission and negotiation

The peer listener additionally admits a known current or durably staged key belonging to an `Active` peer whose recovery flag is set. This separate read-only certificate predicate does not authorize an RPC. Unknown, revoked and `PeerBound` recovery keys remain refused at TLS admission. The existing ordinary certificate predicate and ordinary authentication are unchanged. Completed recovery negotiation independently requires the actual current local credential, exact claimed peer's Active current/pending key, valid rotation metadata and current relationship incarnation. It performs no observation/promotion, replacement approval, grant issuance or recovery write.

The current peer offer is protocol1.13. Feature15 `PeerRecoveryCompletion` is advertised **only** by the fixed recovery hello. Its negotiated intersection contains no activation, rotation, unpair or permission-dispatch feature even if the remote hello requests every known feature. Both normal and recovery negotiation share the connection's single-attempt guard, so a recovery connection cannot switch to ordinary mode after recovery clears. Compatible-major/minimum-minor negotiation follows the existing explicit capability contract: an explicitly supported backport is accepted; missing features and unknown authorization-relevant result values fail closed. Product version is display only. New immutable `host-v1-13.pb` and `peer-security-v1-13.pb` descriptors retain all prior history.

## Receiving and retry behavior

The runtime-owned receiver requires HTTPS/HTTP2, its own live connection, the negotiated completion feature and exact recipient. It links caller cancellation to request abort, serializes through the connection gate and invokes the existing atomic receipt writer with actual session evidence. That writer rechecks current keys/incarnation and exact final state/audit before commit. Reply correlation covers receiving and approving Host IDs, approval ID, acknowledged fingerprint and the closed `Recorded`, `AlreadyRecorded`, `KeyMismatch` outcome. Shape/correlation validation is not authentication; `KeyMismatch` never proves successful completion and cannot qualify a future sender confirmation.

A matching receipt clears only the receiving relationship's recovery flag and preserves grant/rotation state. A mismatch leaves recovery set and records its canonical audit. A lost reply can be retried over a fresh authenticated recovery connection using the same approval ID; exact duplicate receipts are read-only. The original pre-clear connection cannot perform a new receipt. Routine promotion deliberately retains its relationship incarnation: the actual promoted key may still replay its exact receipt, while the retired old key is refused. A changed local credential, replaced/revoked relationship or unrelated incarnation transition invalidates held evidence. Recovery completion never silently reactivates historical grants.

## Qualification and remaining work

Nine ordinary test groups include immutable wire history, real Windows TLS with recovery set on both peers, eight concurrent deliveries and fresh-connection lost-reply retry, every ordinary peer RPC refused before/after clear, normal negotiation refused during recovery, internal permission dispatch refused on the restricted session, malformed/oversized/legacy/backported hello cases, real unknown/revoked/PeerBound TLS refusal, changed actual keys and incarnation, current/staged keys after rotation lapse, transaction rollback for audit abort/deletion, bounded errors and owned-runtime/cancellation/disposal checks. The fixture establishes prior independently verified bindings and activates over real TLS; it is not a full native PAKE and two-Owner recovery ceremony.

This unit provides receiving transport only. [Exact pending and confirmation persistence](v0.5-recovery-completion-confirmation.md) is qualified separately. The [fixed native sender](v0.5-recovery-completion-sender.md) now has separate awaited-scope qualification. Generation-owned invocation/retry coordination, public initiation and the full fresh-PAKE/both-Owner-approval recovery acceptance remain #28 work. No ordinary management wire API, generic offline command queue, installed deployment, physical Palworld run, Windows parity, Linux implementation or release acceptance is claimed. Accessibility/screen-reader certification remains WAIVED, never PASS.
