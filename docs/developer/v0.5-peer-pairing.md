# First-contact Host pairing RPC

Trial reference: #44g, within #44. This unit connects the [guarded native SPAKE2 provider](v0.5-spake2-wrapper.md), [attempt coordinator](v0.5-pairing-attempts.md) and [durable PeerBound repository](v0.5-peerbound-storage.md) through an actual Host-owned gRPC stream. The peer stream remains a trusted Host composition seam; the protected local Owner entry point is described below, while installed remote startup remains outstanding.

First contact uses a separate endpoint from [pinned activation](v0.5-peer-grpc.md). Both sides prove possession of usable P-256 TLS credentials under the existing TLS 1.2/1.3, HTTP/2, validity and no-resumption policy. The first-contact endpoint cannot initially pin an unknown peer, so TLS possession alone establishes no trusted identity. The endpoint maps only `PeerPairingProtocol.Pair`; activation and ordinary management are unavailable there. Only a successfully code-confirmed, MAC-protected public identity whose SHA-256 SPKI fingerprint exactly matches the actual TLS peer can reach trust storage. Storage also checks the actual local TLS fingerprint against the Host's current durable credential. A claimed Host UUID or certificate alone cannot create trust.

The public wire schema uses explicit `PeerPairing` capability, extended in #44y with protocol 1.7 and `PeerPairingAdvertisedInvitation`. Immutable descriptor history preserves the earlier 1.3 shape. The ordered stream starts with either a public invitation UUID or the negotiated advertised-invitation selector, followed by responder nonce/share, initiator share/confirmation, responder confirmation/binding, initiator binding and a bounded result. No code, private key or authentication key crosses the peer wire. Native SPAKE2 validates points, confirmations and bindings. The receiver requires request EOF before storing; both sides deny unexpected frame types, lengths, trailing frames and unknown results. Message size is four KiB; each call has a twenty-second total deadline. Existing TLS handshake, connection and stream limits still apply.

An actual TLS connection permits one attempt, including after a malformed first request. The responder supplies the coordinator with the socket's actual source address. The coordinator's five-minute invitation limit, ten-failure budget, fresh nonce, shared source backoff and bounded resident state remain in force. Disconnect, cancellation and failure release the native exchange. The internal outbound Host helper owns a fresh transport/channel per attempt and clears the copied code bytes immediately after native initialization. Ordinary clients have no dependency or Host-key access through this path. The caller owns the runtime, native provider and credential lifetimes; listeners and calls must finish before those owners are disposed.

The two Hosts commit independently. The initiator stores verified PeerBound before sending its own binding; the responder stores only after verifying that binding and receiving request EOF. A later stream failure can therefore leave one durable PeerBound and the other side without it. That pending row is retained with its original deadline and zero authority; no transport exception deletes it or implies Active trust. If both rows became durable, pinned mutual TLS can finish activation without the old code. A side that crashed before persistence must do fresh pairing; repeating pairing against an existing matching PeerBound resumes the original deadline. Matching Active trust reconfirms without rewriting grants; different/revoked credentials create the existing Owner-approval candidate, and recovery remains gated. There is no cross-Host transaction.

The required diagnostic callback reports coordinator lifecycle outcomes only. `IdentityVerified` means native cryptographic verification, which occurs before final TLS-identity matching, EOF and storage; it is not terminal pairing success. The owned [terminal audit journal](v0.5-pairing-audit.md) now records failed/expired outcomes and handles write failure with bounded public retry state and closed admission. PeerBound creation and other durable trust transitions include their repository audit transaction. Request logging and detailed remote exceptions are disabled, and framework size/deadline/cancellation refusals retain bounded status codes without payload details.

Two ordinary tests exercise actual TLS and gRPC admission, protocol/size/frame refusals, disconnect cleanup, one-attempt connection lifetime and the absence of activation on this endpoint. Their tracking provider cannot verify identities and is only a lifecycle fixture. The separate native probe uses the pinned production Windows DLL with real synthetic CNG credentials and two SQLite stores: successful reciprocal binding and same-key retry, zero authority before separate pinned activation, consumed and wrong code refusal, a valid native MAC for the wrong TLS key, and a valid binding followed by a forbidden extra frame. The full native CI command includes this probe. These are actual loopback tests, not process-kill, reboot, multiple-machine or production service acceptance.

The concrete Host generation now supports safe credential completion/retirement. The canonical Active default hook remains #45's responsibility. For cumulative component evidence and downstream limits, see the [#44 acceptance inventory](v0.5-peer-component-acceptance.md).


The [shared Host traffic lifetime](v0.5-host-traffic-lifetime.md) now supplies pre-TLS connection admission/draining and a whole-operation wrapper for outgoing work, with actual local/peer/partial-handshake evidence. The [generation owner](v0.5-host-network-generation.md) now composes its listeners, outgoing helpers and pairing background cleanup; the [Host transition coordinator](v0.5-host-generation-transitions.md) serializes replacement and explicit recovery, while installed authorized dispatch remains outstanding. A drained lifetime does not bypass final cutover eligibility.

## Address and code selection

The Host client accepts an HTTPS address/port and the one-time code without an internal invitation UUID. A start-frame flag selects the responder's most recently created live invitation under the same lock as source/invitation admission. Cancellation, expiry, successful identity verification and ten-failure lockout clear the selection; no older invitation becomes advertised automatically. Older live invitations remain reachable only by their explicit UUID. Creating a newer invitation does not cancel an already admitted exchange on the older one, and completing/cancelling that older exchange cannot clear the new selection.

Both sides must negotiate `PeerPairingAdvertisedInvitation` for this path. Supplying both selectors, supplying neither, or using advertised selection without the capability fails before native proof processing. Existing explicit-UUID pairing still requires only `PeerPairing`. The minor and product version strings do not substitute for capabilities. No separate invitation lookup RPC, code field, new rate-limit bucket, proof change or trust shortcut is added. Address/code work uses the same generation and transition admission/cleanup ownership.

Ordinary tests cover selection consumption/cancellation/expiry/lockout, no fallback, concurrency, frame/capability refusal and closed ownership helpers. Native qualification exercises actual address/code first contact, wrong code, consumed selection and lost reply, while retaining explicit-ID retry and raw hostile binding/EOF cases. The local Owner entry point and address/discovery foundations are linked below; installed remote enablement remains outstanding.

The [address/discovery foundation](v0.5-host-discovery.md) now provides manual host/IP plus port parsing and a bounded directory of unverified advertisements. Its metadata never substitutes for the actual PAKE/TLS identity proof. The [concrete Windows discovery configuration](v0.5-windows-discovery-configuration.md) supplies an explicit opt-in factory.

The [local Owner pairing foundation](v0.5-local-owner-pairing.md) now supplies generation-bound authenticated invitation/discovery/address-code actions and a fresh Owner check inside final outbound binding persistence. The protected local RPC below uses those methods; installed enablement remains outstanding.

The [protected local pairing RPC](v0.5-local-owner-pairing-rpc.md) now supplies explicitly negotiated, native-bound Owner initiation in full-network composition. Installed remote enablement and the remaining qualification gates are still outstanding.

The [protected local activation/retry action](v0.5-local-owner-activation.md) can complete durable PeerBound over pinned TLS without the old code, with fresh Owner authorization through the final activation transaction.

The [native PeerBound process recovery qualification](v0.5-peerbound-process-recovery.md) establishes both bindings through the actual selected provider, terminates the initiator process after durable PeerBound, and requires pinned activation/retry after restart with PAKE disabled. The separate [pre-PeerBound process case](v0.5-peer-precommit-process-crash.md) covers the initiator before its writer. The [responder process case](v0.5-peer-responder-process-crash.md) separately targets an asymmetric durable binding; mid-commit, physical and installed qualification remain distinct.
