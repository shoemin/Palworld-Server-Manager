# Local Owner approval of peer replacement

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28).

`GrantPolicyRepository.ApprovePeerReplacement` implements one local, audited replacement transaction. The caller must supply actual current local Owner evidence and the expected authorization revision. The selected [verified candidate](v0.5-replacement-candidate-evidence.md) must be unapproved, permanently uninvalidated, unexpired within its original bounded window, and still match the exact peer state, current pin, original incarnation and verified local Host fingerprint. Any staged pending fingerprint blocks approval. A leftover rotation ID without a pending fingerprint is cleared as obsolete metadata.

Approval invalidates the old peer's exact grantee/grantor provenance forests, preserves unrelated grants and historical IDs, marks this candidate approved by the actual Owner, and permanently invalidates unapproved siblings. It retires old pairing metadata, binds the proposed key to the same stable Host ID, captures the final new incarnation, records fresh local binding evidence, and applies the currently configured defaults as new canonical current-Owner roots. Factory defaults remain empty. No prior grant is revived or automatically reissued.

The peer's independent `PeerRecoveryRequired` flag is preserved. Local approval of that peer's credential does not prove that the other Owner approved this Host's credential. A private transaction-scoped approval context qualifies only the exact newly approved Active recipient for default root issuance. It rechecks the current Owner, recorded approval, local/peer fingerprints and resulting incarnation, then uses the existing typed `AuthorizationPolicy.IssueHost`/`IssueServer` rules and default validator. It is never exposed as ordinary authorization. Normal policy reads, manual grant issuance, ordinary activation and remote proof checks still reject a recovery-pending peer, so these newly stored roots remain unusable until separate authenticated exact-key completion clears recovery. No temporary flag clear or Owner substitution is used.

Schema 15 records one latest `PeerReplacementCompletions` security marker per peer, tied to the exact approved candidate, approved key and source/resulting incarnations. The local fingerprint at approval is historical provenance. No address or business command is stored, no historical marker is backfilled, and this unit sends nothing. A later replacement supersedes the marker; revocation cancels it in the same transaction with an exact timestamp and audit count. Generic trust state/key changes also invalidate it. Repeating an already approved current request creates no new grants or audits; a later relationship or canceled/superseded marker cannot reactivate that request.

After all writes and audits, the writer rechecks the current Owner and local credential, authorization revision, complete expected grants, trust/candidate/binding/proof/pairing/receipt/marker rows, default configuration and every success audit. Late cancellation or changed effects roll back the whole transaction. Neither a remote acknowledgement nor any network operation participates in local approval.

## Evidence and remaining work

Nine persistence scenarios cover Active/revoked/PeerBound approval, exact grant invalidation and fresh configured roots, benign leftover rotation metadata, retained recovery with ordinary use/manual issuance/ordinary activation denied, rejection of a late recovery clear, stale/expired/unproven/non-Owner requests, unconditional staged-key refusal, idempotent retry and later same-key replacement without grant revival, sixteen late-effect/audit rollback cases, concurrency/cancellation and an empty schema upgrade. These fixtures exercise the canonical writer and policies with explicit database identities; they do not certify a complete PAKE-to-Owner-approval network ceremony or field installation of this command.

The durable completion receiver/sender must still authenticate exact current keys, reject old-key acknowledgements, handle recovery-related incarnation changes, and retry only bounded security completion state. Public command routing, actual remote hang/drop and complete re-pair qualification remain subsequent #28 work. Six creator permissions and limits are unchanged; accessibility is **WAIVED, never PASS**. Physical-PC/Palworld/parity/Linux/release qualification is not claimed.
