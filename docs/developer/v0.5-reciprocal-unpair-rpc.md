# Negotiated reciprocal unpair receipt

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28).

`PeerSecurityProtocol.ReceiveUnpair` exposes the [atomic reciprocal receiving transaction](v0.5-reciprocal-unpair-receipt.md) over the existing encrypted HTTP/2 peer service. Both peers must negotiate `PeerUnpair` (feature14); the current peer offer is protocol1.13 after the [fixed recovery transport](v0.5-recovery-completion-rpc.md) addition. Immutable host/peer-security1.12 descriptor snapshots preserve this unpair schema revision. Product version is display information only.

`PeerUnpairNotice` names only the intended receiving Host. It contains no peer target, fingerprint, incarnation, Owner flag or permission. The internal runtime-owned receiver verifies HTTPS, HTTP/2, connection association with that exact runtime and the negotiated feature, then supplies the original connection's authenticated peer/local fingerprints and original incarnation to the canonical repository. The receiving Host is checked explicitly; the peer being revoked is always the actual connection peer. Initial receipt requires current Active/non-recovery trust, with no management grant needed for this intrinsic surrender.

The dedicated receiver uses only the repository's narrow completed-receipt duplicate rule. It does not relax ordinary request authentication or TLS admission. A duplicate may succeed on the original already-authenticated connection while the exact receipt/tombstone remains current. It cannot create a new connection, restore trust, affect a later relationship or cancel a newer pending Owner replacement. A change to the receiving Host's current credential also rejects old receipt evidence. Connection disposal and both request cancellation sources guard the transaction; cancellation after the commit cannot undo local revocation.

The bounded reply contains receiving/unpaired semantic Host IDs and only `Recorded` or `AlreadyRecorded`. No authorization revision, grant count, fingerprint or internal incarnation is disclosed. `PeerUnpairWire.ValidateReply` requires both expected identities and denies unspecified/unknown outcomes; it is shape/intent validation, not transport authentication. An eventual sender must obtain the expected identities from its authenticated exchange. Storage, authentication and precondition errors use the existing bounded RPC status mapping, without underlying exception text.

## Evidence and limits

`PeerUnpairRpcTests` uses actual Windows mutual TLS, HTTP/2 and gRPC on loopback with independent Host stores and real activation RPCs. Initial verified pairing bindings are explicit fixtures; these tests do not claim a new PAKE ceremony. Eight concurrent notices on one negotiated connection produce one receipt/audit and seven duplicates. A later pending replacement is preserved, a stale activation RPC is refused, and a new connection is rejected with a real transport/TLS failure cause. Other tests cover missing/legacy negotiation, malformed/wrong recipient, PeerBound/recovery, changed current local credential, old-session refusal before and after a later artificially restored relationship is independently unpaired, and complete rollback with bounded status after an injected audit failure. Artificial restoration is negative session/incarnation evidence only, not positive Owner-approved repair.

Separate adapter tests deliberately simulate transport facts to check foreign runtime, missing/insecure/non-HTTP2/closed connection and request cancellation refusal without claiming another real handshake. Public wire tests cover serialization, explicit feature negotiation and unknown/mismatched replies. The full suite retains canonical grant-forest/Owner/audit checks, receipt migration, all prior RPCs and immutable protocol history.

This unit qualifies the receiving RPC. The [scoped live delivery client](v0.5-live-unpair-delivery.md) can use a retained authenticated connection after local revocation. Nonblocking command orchestration, hanging/dropped/offline behavior and full fresh Owner-approved re-pair remain subsequent #28 work. There is no cross-Host atomic commit or offline command queue. Ordinary outgoing administration still requires the originating user's independent local permission. The six approved creator permissions and limits are unchanged. Accessibility remains **WAIVED, never PASS**; physical-PC/Palworld/parity/Linux/release qualification is not claimed.
