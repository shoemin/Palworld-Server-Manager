# Reciprocal self-unpair receipt

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28).

`GrantPolicyRepository.ReceiveAuthenticatedPeerUnpair` lets an authenticated Active peer surrender its own relationship. Unlike [remote administration](v0.5-remote-trust-revocation.md), this intrinsic relationship action needs no management capability and cannot select any other target. Trusted Host composition supplies original completed TLS/negotiation evidence; no request-body identity, fingerprint or incarnation is accepted as authentication. Initial receipt requires current Active/non-recovery trust, both actual credentials and the original relationship incarnation. PeerBound stays activation-only.

The first notice uses the same immediate local [revocation transaction](v0.5-local-trust-revocation.md): clean retained tombstone, permanent exact grant-forest and pending-replacement invalidation, actual-peer audit and final identity/state/revision/audit checks. It also writes a received-unpair receipt in that transaction. Missing or altered receipt/audit evidence rolls back every effect. The audit distinguishes `Origin=ReceivedUnpair` from `Origin=Administration`; neither origin is caller-controlled text.

Schema13 adds one `PeerUnpairReceipts` row per peer: original and revoked incarnation, original public peer/local fingerprints and receipt time. The resulting incarnation has a cascading foreign key to the existing never-reused incarnation table. A later trust/recovery/pairing-incarnation change removes the receipt immediately. The old source incarnation intentionally has no foreign key because revocation itself retires it. Migration starts with an empty table and manufactures no prior receipt, authority or successful revocation.

A duplicate may return the current no-change result only when the original proof matches that receipt, the authoritative Host still uses the same local credential, and the exact clean tombstone, receipt time and resulting incarnation remain current. This branch changes no trust, grants, audit, timestamp or pending replacement. In particular, it cannot cancel a new Owner replacement candidate created after the first notice. A repeat after independent administrative revocation with no matching receipt refuses authentication. The local security outcome remains Revoked regardless of whether a notice reply can be returned.

The receipt is completed security evidence, not an active credential pin, an outgoing job or an offline command queue. It is never consulted by TLS handshake admission or ordinary management authorization. A revoked credential cannot establish a new authenticated connection using this row. Repository recreation can inspect a committed receipt using trusted evidence, but this does not claim that an old network connection survives a process restart. The [negotiated receiving endpoint](v0.5-reciprocal-unpair-rpc.md) uses the narrow duplicate branch only with original evidence from its already-authenticated connection, never to rebuild authentication from the notice payload.

## Evidence and remaining work

`ReciprocalUnpairTests` covers intrinsic self-only revocation with no management permission, exact atomic effects, duplicate/repository-reopen behavior, preservation of a newer pending Owner decision, ordinary-authentication refusal, changed current local credential, old-session refusal after later relationship restoration, nine late receipt/audit/state faults, eight concurrent deliveries with one effect, cancellation after writes, additive schema12-to13 migration and cascading invalidation on a pairing-incarnation rewrite. Artificial Active restoration is negative ABA evidence only, not a completed repair flow. The shared test snapshot includes the new receipt table.

This persistence unit is consumed by the [negotiated receiving RPC](v0.5-reciprocal-unpair-rpc.md). A [scoped live delivery client](v0.5-live-unpair-delivery.md) now holds an authenticated connection across a matching local revocation. [Nonblocking coordination](v0.5-unpair-coordinator.md), [local inspection/revocation RPC](v0.5-local-peer-trust-rpc.md) and [genuine native re-pair](v0.5-native-repair.md) have separate qualification. [Local Owner replacement inspection/approval](v0.5-local-owner-replacement-rpc.md) also has separate qualification. [Protected local network actions](v0.5-local-trust-network-actions.md) now provide online unpair preparation and Owner recovery initiation. The [originating-user route](v0.5-originating-user-trust-route.md) now supplies independent local and remote administration checks; [aggregate trust acceptance](v0.5-trust-component-acceptance.md) records the complete #28 evidence. Actual unpair process faults have [separate qualification](v0.5-unpair-process-qualification.md). No receipt may delay the initiating Host's local revocation. The six creator permissions and independent local-user ceiling remain unchanged. Accessibility remains **WAIVED, never PASS**; no physical-PC/Palworld/parity/Linux/release or external-review claim is added.
