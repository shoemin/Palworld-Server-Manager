# Protected local Owner pairing RPC

Trial reference: #44ai, within #44. The full-network Windows composition binds its local security runtime to the exact owning generation before listener startup. The installed local-only composition remains unchanged. Only the full-network runtime offers additive `LocalOwnerPairing` (10), introduced with local protocol 1.8. Each connection must negotiate both that feature and `LocalPrincipalSecurity`, authenticate its actual native-bound local principal, and pass the [Owner action](v0.5-local-owner-pairing.md) checks. Legacy negotiation and existing security RPCs remain compatible; a client claim alone cannot enable local-only pairing.

`CreatePairingInvitation` returns the invitation identity, expiry and ten code bytes through the protected local channel. Response construction runs within the generation's invitation ownership scope: construction/cancellation failure cancels the invitation and disposes its secret. Temporary mutable code copies are zeroed. A lost network reply is not proof of delivery or an atomic cross-Host transaction; an undisclosed invitation expires through the existing ephemeral lifecycle. `CancelPairingInvitation` requires the current authenticated Owner and an exact nonempty UUID.

`DiscoverPairingHosts` returns unverified hints in pages of at most 32, from the bounded 256-entry cache. Offset must be 0–256; limit 0 means 32, otherwise 1–32. Next offset 0 means the end of that response's snapshot. The cache can change between calls, so pages may omit or repeat hints; they carry no trust authority. Replies include claimed identity, actual observed reachable source, listener ports and advertised protocol. Every reply is checked against the local 16 KiB message limit. Actual protocol and identity are still negotiated/proven during pairing.

`PairHost` accepts only a bounded reachable host, port 1–65535 and ten ASCII digit bytes. The local Host performs the entire existing TLS/PAKE exchange, retaining its private key. The Owner is rechecked in final binding persistence. The response identifies the verified peer and explicit local/remote pairing dispositions, plus local pending expiry/replacement identity where applicable. No ordinal cast or unknown local disposition is accepted; the peer client also rejects unknown remote results. No management grant or automatic activation is added. A remote failure returns fixed local text without forwarding its detail/trailers; ordinary local transport metadata may still be present. Failure after durable local PeerBound can require retry and does not erase that record.

Ordinary tests use real named-pipe TLS, actual Windows caller identity and real client-key proofs for capability/local-only/legacy/anonymous/non-Owner/stale refusals, all 256 hints through bounded pages, request validation, invitation cancellation and failed response construction. Native qualification adds local-client-to-local-Host-to-peer-Host pairing, wrong-code refusal and idempotent retry, with real PAKE and zero grants. Local fixtures do not establish installed-service remote enablement or physical-LAN acceptance. The mandatory #45 activation hook, installed configuration/provider packaging, retirement and remaining crash/physical qualification are separate work.

The [protected local activation/retry RPC](v0.5-local-owner-activation.md) adds a separate negotiated feature in local protocol1.9; pairing-only negotiation still does not authorize activation.
