# Windows native TLS cache (#42b1)

The Product Owner approved a Windows Schannel native key container as a derived TLS-use cache of the machine credential. SQLite's opaque reference and the DPAPI secure store remain authoritative. The cache neither creates a new HostId nor supplies recovery credentials. This bounded slice supplies the Host-side platform primitive; the [offline coordinator](v0.5-offline-coordinator.md) and [production Host service](v0.5-host-service-composition.md) now compose it with the channel and durable authority. Ordinary peer rotation remains later scope.

`IHostTlsCredentialCache.LoadAsync` always retrieves the referenced secure-store PFX first. Only ECDSA NIST P-256 is accepted. The private source is imported ephemerally, with transient export permission solely for the in-memory PKCS#8 transfer to the Microsoft Software Key Storage Provider. Temporary managed private buffers are cleared. The persisted machine key is finalized with export disabled, a protected security descriptor, and no interactive unlock. No plaintext application file or certificate-store installation is used.

A deterministic name consists of a versioned product prefix, semantic HostId, and SHA-256 of the bounded opaque reference. It contains no secret. Creation does not overwrite an existing key. Every reuse verifies provider security, actual key-file security, export policy and public-key equivalence with authority. Missing authority, wrong key, unexpected permissions, ownership, path/reparse state, curve or provider failure stops the caller. Unsafe state requires privileged repair; the cache never silently adopts or repairs it.

The only allowed owners/access principals are the dedicated Host service SID, elevated Administrators and SYSTEM. Provider and file DACLs are protected and must include all three with full access and no outsiders. Non-exportability limits accidental API export; it does not defend against a privileged machine owner, memory inspection, disk rollback or copies already made. Provider-managed Windows software-key storage is an additional persisted secret representation, not an in-memory-only claim. Application diagnostics contain no private material.

## Caller lifecycle

The trusted Host or exceptional offline caller must hold the existing machine exclusivity lease throughout use. Stop and dispose every TLS connection, server and certificate handle before reconciling retirement. This seam does not acquire a second authority lease or determine rotation policy. Callers serialize authority changes with load/reconciliation; cancellation is not a transactional rollback of an already finalized cache entry.

Before serving connections, derive the complete retained reference set from authoritative identity/rotation/recovery state and call `ReconcileAsync`. It enumerates only this HostId's exact product namespace, validates each owned key, and deletes entries outside the retained set. Missing entries are reconstructed only when loaded from authority. Retire abandoned/stale keys before exposing the corresponding completed/aborted/recovered state, alongside secure-store retirement and descriptor reconciliation. The offline and startup coordinators implement this ordering; no cross-store atomicity is claimed.

Run native-provider work on an independent worker before the channel becomes ready. Never invoke it synchronously inside, or wait for it from, the SCM start callback: Microsoft documents a service-start deadlock hazard for these APIs. The earlier synthetic fixture waits for an elevated harness to observe Running; the production callback returns immediately while its independent worker initializes, allowing SCM to reach Running without a readiness signal or additional service permissions. SCM Running alone must never be interpreted as application authentication readiness.

## Evidence and scope

The privileged integration fixture uses a real virtual service account and two fresh non-elevated Windows users; its credentials and endpoints are synthetic. The worker holds the existing runtime lease and publishes only public readiness data in the protected fixture directory. Tests cover provider/file ACLs, non-exportability, authority mismatch/missing authority, unsafe ACL rejection with restored positive baseline, actual Schannel TLS, cache retention/removal/reconstruction, service and elevated-offline access, normal/crash restart, and ordinary/activation-member denial. A medium-token local run cannot stand in for these tests. Exact successful SHAs/runs belong in the trial ledger.

There is no production authentication handler, principal grant, bootstrap ticket, remote transport, Linux implementation or release/reboot qualification in this slice. The separate [Windows local security qualification](v0.5-windows-local-security-qualification.md) covers full #42; Windows feature parity remains a later gate.

Native definitions are checked against the installed Windows SDK and [NCryptImportKey](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/nf-ncrypt-ncryptimportkey), [NCryptSetProperty](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/nf-ncrypt-ncryptsetproperty), and [CNG key storage providers](https://learn.microsoft.com/en-us/windows/win32/seccng/cng-key-storage-providers). The [transport preflight](v0.5-local-ipc-preflight.md) records the measured .NET 8 Schannel constraint.

## Native-directory provisioning

A real virtual-account run reached native key finalization and failed with NTE_PERM (0x80090010), while the elevated test succeeded. The machine KSP's shared key directory permits privileged creation by default. `WindowsNativeTlsProvisioning` therefore supplies an explicit elevated setup step under the stopped-Host lease: add only `CreateFiles` (plus Windows' implicit synchronization right) for the dedicated virtual-service SID on that directory itself, with no inheritance. It preserves existing unrelated ACEs; unexpected existing grants for this service SID require repair. It grants no read/write/delete rights on another key, no directory deletion, and no ACL/ownership administration. Cache files are still finalized with their own protected approved ACL.

Installation/removal of this grant is owned by the privileged composition caller, never ordinary clients or `LoadAsync`. Setup is idempotent. An owned grant is removed explicitly after stopping the service and retiring caches; the fixture verifies removal instead of restoring a stale snapshot of a global ACL. The production installer composition belongs to #42b2. Concurrent external administrative ACL edits are outside the supported provisioning transaction; administrators must serialize configuration changes.

The verified creation sequence sets only DACL_SECURITY_INFORMATION (4) before finalization. Windows assigns the creator's default owner; the cache verifies it afterward. Setting OWNER as well caused NTE_PERM under the actual service token and is not used. Creation-time ACL selection and post-finalization owner/provider/file validation are separate checks. Failed creation is never returned as a usable credential; an unsafe remaining provider entry blocks reconciliation and requires privileged repair. The fixture's exceptional cleanup of known synthetic entries is not a production repair path.
