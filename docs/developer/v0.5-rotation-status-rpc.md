# Pinned live rotation-status RPC

Trial reference: #44n, within #44. The existing Host-owned peer endpoint now offers `ReadRotationStatus`, gated by explicit `PeerRotationStatus` capability 6. The status feature was introduced at protocol 1.4; earlier activation traffic remains additive and separately gated. Immutable host-v1-4 and peer-security-v1-4 descriptor snapshots retain every earlier snapshot. Pairing-finalization negotiation still permits PeerBound, but status dispatch requires fresh Active, non-recovery trust on the actual connection. This status-only capability does not enable proposal, promotion-receipt, management or grant operations.

The outgoing Host captures [the exact retained rotation query](v0.5-rotation-reconfirmation.md) before opening one new mutual-TLS HTTP/2 connection. It uses the same pinned Windows transport, disabled proxy/redirects, fixed message limits and actual post-handshake observation as activation. Each exchange has a fifteen-second cancellation deadline; the persistence intent also enforces its independent twenty-second monotonic lifetime. Negotiation must match the expected peer UUID and status capability. The actual local connection fingerprint must still match current Host metadata, and an Old-status completion rechecks it against both captured and current metadata in the write transaction.

A response under actual Old is converted through a closed enum mapping and must echo the complete captured query ID/HostId/RotationId/Old/New tuple. The persistence completion performs fresh trust, exact retained deadline and Owner checks. Owner-approved Staging/Ready can renew a lapsed stage; opportunistic Aborted/Unknown clears it; no unexpired stage is extended. A claimed CutOver/Completed under Old cannot promote. If the connection actually presents retained New, ordinary completed-TLS observation promotes before status processing; the caller reports New observed and preserves the outstanding receipt, without using a status claim to change trust.

The server rechecks negotiated capability and Active trust on every RPC, even on an existing connection. It returns only the exact requested rotating Host tuple through the trusted read, bound to its actually presented current local credential. Unnegotiated, PeerBound, revoked/recovery, wrong Host identity, malformed IDs, unknown enum replies and inconsistent public tuples fail closed. Requests and replies remain capped at 16 KiB, detailed server errors stay disabled and no private key, pairing code or local Owner credential is serialized.

Five ordinary integration scenarios exercise real Kestrel/HTTP2/mutual TLS: passive lapse and Owner renewal, unexpired no-extension, unreachable then fresh abort cleanup, actual New proof after a synthetic global cutover, incomplete-handshake refusal, missing capability, fresh PeerBound/recovery checks on an existing connection, wrong/malformed request identity, closed response enums and local credential changes. A test transport alters a real server response only after actual TLS has completed: wrong correlation, unknown state, false Old-key cutover and Owner change all preserve pending trust. This fault injection never fabricates a successful handshake. The global cutover row used to present New is synthetic; this does not claim a complete cutover engine or physical multi-machine/process-crash evidence.

Installed service/local Owner RPC composition, automatic opportunistic scheduling, promotion-receipt transport and full per-peer progress, global cutover/retirement and complete #44 qualification remain outstanding. A failed or canceled check leaves durable pending state available for a new bounded exchange, except that an independently valid actual New observation may already have promoted it. Customized grants and activation defaults remain untouched.

[Proposal delivery and first acknowledgement history](v0.5-rotation-proposal-rpc.md) now use a separate capability on the same endpoint, whose current hello is 1.5.
