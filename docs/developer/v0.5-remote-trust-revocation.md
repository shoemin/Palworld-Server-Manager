# Authenticated remote trust revocation

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28).

`GrantPolicyRepository.RevokeRemotePeerTrust` uses the same private atomic transaction as [local revocation](v0.5-local-trust-revocation.md). A peer administrator needs `ManageTrustedManagers` for exactly the receiving Host. Pairing alone, `ManagePermissions`, a foreign-Host grant and a request's claimed identity do not authorize revocation. Trusted Host composition supplies the original completed TLS peer/local fingerprints and relationship incarnation. The repository requires current `Active`, non-recovery trust and the receiving Host's current unretired credential before policy checks or effects.

The target is a remote relationship in that receiving Host's own database. Revoking another peer leaves the acting peer authenticated through commit. An administrator can intentionally revoke itself; only that exact actor/target equality replaces the now-impossible final `Active` proof with verification of the complete expected clean tombstone and newly advanced incarnation. The original proof is still required before mutation. No caller can supply a post-write validator or select this exception independently of its authenticated identity. It cannot identify, demote or replace a local Owner.

An actor may also lose a capability delegated through the peer it revokes. The original capability authorizes the transition, and exact final grant/trust state verifies the intended loss. All unrelated state, pending replacements, current Host credential, revision and success audit retain the local unit's checks. Audit actor fields record the real acting peer; the summary separately identifies the revoked target. Late actor-key/recovery/incarnation changes and altered or missing audit rows roll back the entire revocation, including self-revocation.

The internal `LocalPermissionCall` and `PeerPermissionCall` expose `RevokePeer` without exposing actor evidence or the repository. Their existing authenticated-channel, runtime association, negotiated feature, synchronous callback lifetime and cancellation guards apply. Peer dispatch first performs canonical current-credential observation. If a verified staged credential is promoted, its separate security transition can advance the authorization revision before the requested revocation; an outdated request then refuses and must refresh. A later revocation independently rechecks proof and current policy.

Revoking another peer is idempotent while the caller remains authorized and refreshes current revision/incarnation. After self-revocation, its old authenticated connection cannot issue ordinary retries or regain authority; that refusal is intentional. A later fresh relationship cannot be affected by the old session. Reciprocal surrender without administrative permission is a distinct security notice, not this administrator action.

These are adapter and persistence tests, not a new installed RPC ceremony.

This unit installs no wire endpoint or new protocol feature. Actual outgoing administration must independently enforce the originating local user's permission and the remote machine ceiling.
