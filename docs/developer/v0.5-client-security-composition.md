# Ordinary client security composition

Trial #42d3c2 compiles the same security coordinator into the ordinary CLI and Avalonia. Its Windows factory uses the fixed product service, named pipe, protected public trust directory, current-user DPAPI credential store and intended-user Owner handoff reader. Avalonia constructs it lazily for later authorized screens; this unit adds no feature UI. Neither client gains a dependency on Host, Core, persistence or Host platform projects.

Each command opens a fresh pinned HTTP/2 gRPC session and checks the exact Host identity, protocol version and local-security capability before transmitting credentials. Only a precisely classified absent pipe permits query/start activation. TLS failures, malformed negotiation and generic RPC failures cannot trigger activation. Mutations are not automatically retried. Identity and Owner status come from a proof with the current user's key; they do not imply capability grants.

Completion first resumes the exact persisted Host/ticket/purpose/key-choice context. An active re-home target selects its existing key only after successful proof; an unknown or revoked target can prepare a fresh key. A lost result resumes the pending choice before consulting the now-stale current key. Preparation persists before submission. The returned principal must authenticate with the prepared key before durable confirmation; Owner ceremonies also require current Owner status. Handoff deletion occurs only after confirmation. Lost replies, cancellation, failed confirmation and failed deletion preserve the appropriate retry state.

The ordinary CLI exposes:

- `identity`
- `invite --user-sid SID`
- `revoke --principal UUID`
- `complete-enrollment --ticket UUID`, reading one bounded base64 code from standard input
- `complete-handoff --ticket UUID`, reading the protected current-user artifact

Invitation output deliberately delivers a bearer code to the authorized Owner for secure out-of-band transfer. It is not diagnostic output. Completion never takes a secret in process arguments. Errors expose fixed classifications, not input, RPC details or exception text. Owned secret/private-key buffers are cleared; runtime protobuf/string copies are never logged, without claiming full-heap zeroization. No command prepares offline recovery, sets Owner directly, selects arbitrary endpoints or writes Host state locally.

Six ordinary test groups use actual pinned TLS/RPC, DPAPI and Host transactions for bootstrap, enrollment, rotation, re-home, lost replies, key-proof refusal, confirmation/deletion ordering, activation classification and safe errors. Synthetic account setup and malformed post-transport handshake fixtures are explicitly identified. These tests do not establish final two-user acceptance with the shipped client: #42d3c3 still requires that actual Windows evidence, and full #42 remains incomplete.
