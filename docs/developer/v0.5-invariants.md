# v0.5 invariant registry

This registry exists because [#19](https://github.com/shoemin/Palworld-Server-Manager/issues/19) exposed repeated cross-section contradictions in the v0.5 architecture even when individual correction requests were followed correctly. A large prose document is a poor structure for keeping requirements consistent across many rounds of editing — a short, numbered, checkable list is not.

**This registry is normative.** Detailed design documents (`docs/developer/v0.5-architecture.md`, future implementation docs) explain and elaborate these invariants; they do not override them silently. If a design document and this registry ever disagree, the design document is wrong and must be corrected — not the other way around, and not by quietly editing this file to match a design decision without recording why.

Every `§`-numbered Source citation below refers to sections of [`docs/developer/v0.5-architecture.md`](v0.5-architecture.md), the [#19](https://github.com/shoemin/Palworld-Server-Manager/issues/19) deliverable.

Each invariant has a stable ID. IDs are never reused or renumbered — a retired invariant is marked retired, not deleted, so historical references (issues, commits, review reports) stay meaningful.

Every applicable-invariant claim in an issue or PR must cite IDs from this table, not paraphrase them.

## How to use this registry

- **Planning an issue**: list every invariant ID the work could plausibly touch (see the preflight requirement in `docs/developer/agent-workflow.md`) — err toward including a borderline one rather than omitting it.
- **Reviewing an issue before Review Required**: audit the resulting whole against every applicable ID with a compact PASS/FAIL matrix (`docs/developer/agent-workflow.md` defines the required format) — not just the specific delta that was changed.
- **Writing a new invariant**: keep it short, normative, and checkable. If it takes a paragraph to state, it's a design decision, not an invariant — put the paragraph in the architecture doc and link to it from a one-line invariant here.

## Registry

| ID | Statement | Source |
|---|---|---|
| `ARCH-001` | The existing v0.4 WPF application remains completely frozen. No v0.5 refactor or feature work touches it; critical bug fixes are allowed only when separately authorized. | [#17](https://github.com/shoemin/Palworld-Server-Manager/issues/17), [#16](https://github.com/shoemin/Palworld-Server-Manager/issues/16), `v0.5-architecture.md` §1 (`Core`'s bounded legacy carve-out) |
| `ARCH-002` | `PalworldServerManager.Lan` remains a legacy v0.4 compatibility dependency for the frozen WPF application during v0.5. It is not renamed into or reused as the new `Contracts` assembly, and new v0.5 Host/Avalonia/CLI code does not depend on it. | `v0.5-architecture.md` §1 |
| `HOST-001` | Exactly one authoritative machine-wide Manager Host exists per physical PC. | [#17](https://github.com/shoemin/Palworld-Server-Manager/issues/17), `v0.5-architecture.md` §2 |
| `HOST-002` | All normal server/process/filesystem/profile mutations execute through the authoritative Host — never directly by a client. | [#17](https://github.com/shoemin/Palworld-Server-Manager/issues/17), `v0.5-architecture.md` §2 |
| `PERSIST-001` | The Host is the sole *online* writer of authoritative Host state. The offline recovery CLI may write only under the same machine-wide exclusivity lock, and only while the Host is not running. | `v0.5-architecture.md` §5a |
| `CLIENT-001` | Every ordinary local client (`Client.Avalonia`; `Client.Cli` as of `CLIENT-003`) has no dependency path to `Core`, `Host`, `Host.Persistence`, or any Host-side `Platform.*` project. | `v0.5-architecture.md` §1 |
| `CLIENT-002` | No ordinary local client (`Client.Avalonia`; `Client.Cli` as of `CLIENT-003`) ever possesses the machine Host's private identity credential. | `v0.5-architecture.md` §4c |
| `CLIENT-003` | Ordinary local CLI and Avalonia clients authenticate through the same server-authenticated local channel and per-user `LocalPrincipal` credential boundary. Privileged `Host.Cli` is offline bootstrap/recovery only and never substitutes for ordinary local-client authorization. | `v0.5-architecture.md` §1, §2c, §5a |
| `IDENT-001` | A stable, semantic Host identity (`HostId`) is separate from its rotatable authentication credential. | `v0.5-architecture.md` §4a |
| `IDENT-002` | Every server identity that crosses a Host boundary is collision-safe and Host-qualified: conceptually `ServerRef(AuthoritativeHostId, ServerProfileId)`, never a bare, unqualified server ID. | [#17](https://github.com/shoemin/Palworld-Server-Manager/issues/17) §11, `v0.5-architecture.md` §4d |
| `IDENT-003` | Routine Host-credential rotation is staged. A new credential cannot become current until every remaining Active peer has durably accepted it, or an Owner explicitly revokes/excludes peers that have not. Peers accept old and new credentials during the bounded transition; routine rotation never silently strands an Active trusted peer. | `v0.5-architecture.md` §4a-i |
| `LOCAL-001` | Each authorized local OS user maps to a distinct, persisted `LocalPrincipal`. Every *initialized* Host has exactly one active Owner. Before initialization completes, the Host is `Uninitialized` and exposes no ordinary authority surface — only the privileged bootstrap-completion path is permitted. | `v0.5-architecture.md` §3a, §2b, §2c |
| `LOCAL-002` | A local principal's private credential is held client-side, by that user; the Host stores only the verifier/public side. | `v0.5-architecture.md` §3a |
| `LOCAL-003` | OS transport/group eligibility never authorizes `LocalPrincipal` enrollment or re-enrollment. Non-Owner enrollment/reactivation requires explicit Host-side Owner authorization, and revocation remains durable until explicitly reauthorized. | `v0.5-architecture.md` §3a |
| `LOCAL-004` | Every local client authenticates the authoritative Host and uses an integrity-protected local channel before transmitting credentials, enrollment/bootstrap secrets, authentication signatures, or operational RPCs. | `v0.5-architecture.md` §3b |
| `OWNER-001` | Remote actors and ordinary local operations cannot revoke, demote, or replace the Owner. OS Administrator/root has only the explicit, exceptional offline recovery path. | `v0.5-architecture.md` §2b |
| `OWNER-002` | Initial Owner establishment requires explicit Administrator/root-authorized machine bootstrap bound to the intended OS principal. OS-group membership, transport access, or first connection can never claim Owner authority. | `v0.5-architecture.md` §2c |
| `REMOTE-001` | Outbound administration routes `Avalonia -> local Host -> remote Host`. `Client.Avalonia` never connects to a remote Host as the machine identity directly. | `v0.5-architecture.md` §4c |
| `REMOTE-002` | Outbound remote administration requires **both** local-principal authorization and independent remote `PeerHostId` authorization. A remote grant is a machine-level ceiling, not automatic authority for every local user. | `v0.5-architecture.md` §4c |
| `PAIR-001` | Pairing/trust and authorization are separate concerns. Being paired grants no server/admin authority by itself. | [#17](https://github.com/shoemin/Palworld-Server-Manager/issues/17), `v0.5-architecture.md` §5 |
| `PAIR-002` | A `PeerBound` trust state permits only pairing-finalization/activation-recovery traffic on that relationship — not ordinary management. Ordinary management requires `Active` trust. | `v0.5-architecture.md` §4b, §4c |
| `PAIR-003` | Pairing and revocation logic never assumes an atomic transaction spanning two Hosts. Each Host commits only its own local state. | `v0.5-architecture.md` §4b, §8 |
| `PAIR-004` | After proof of the currently trusted Host credential is lost, a newly paired credential claiming an existing `HostId` cannot replace trust or inherit authority automatically. Explicit local-Owner-approved credential replacement is required, and prior grants never silently reactivate. | `v0.5-architecture.md` §4b-i |
| `AUTH-001` | Host-capability and server-capability grants are type/scope valid by construction. A Host-level capability can never become a server-scoped grant. | `v0.5-architecture.md` §5 |
| `AUTH-002` | Delegation authority is explicit. Every non-root delegated grant records exact provenance (`DerivedFromGrantId`), and downstream validity follows the single-parent grant forest — never a multi-parent DAG unless that's a deliberate future design change. | `v0.5-architecture.md` §5 |
| `AUTH-003` | No indirect path — role preset, default template, migration, Owner adoption/re-home, remote-creator auto-grant, or any other UI convenience — may manufacture authority that bypasses the canonical grant-issuance rules. | `v0.5-architecture.md` §5 (`DefaultGrantTemplate`/role-preset fix) |
| `AUTH-004` | Shipped factory pairing defaults are least-privilege. A Host's *currently configured* defaults may differ from the shipped factory defaults, and changing them never retroactively rewrites grants already issued. | `v0.5-architecture.md` §5, §4b-i |
| `AUTH-005` | Every `HostCapabilityGrant` targets exactly one authoritative `HostId`. A Host-level authorization check must match that `HostId` exactly, and delegated `HostCapabilityGrant`s cannot change the target `HostId`. | `v0.5-architecture.md` §5, §4c |
| `PROTO-001` | Protocol compatibility uses explicit version/capability negotiation, never app-version-string comparison. An unrecognized authorization-relevant enum value is denied by default, never permitted by default. | `v0.5-architecture.md` §13 |
| `OPS-001` | A stale write to an editable resource is rejected via a revision/version check — never silently merged or overwritten. | `v0.5-architecture.md` §9 |
| `OPS-002` | Incompatible or destructive work acquires a Host-owned operation lock, visible to every connected client, not just the initiator. | `v0.5-architecture.md` §9 |
| `OPS-003` | A long-running operation belongs to its own Host-owned operation identity, not to the client connection that started it. | `v0.5-architecture.md` §9 |
| `RECOVERY-001` | An operation interrupted by a crash is classified explicitly (safe-to-retry / safe-to-resume / requires-manual-review / safe-to-discard) — destructive work is never blindly resumed by default. | `v0.5-architecture.md` §10 |
| `SEC-001` | Secret material is protected at rest per the accepted platform threat model for its OS, and never appears in logs, audit records, or diagnostic bundles. | `v0.5-architecture.md` §7 |
| `MIG-001` | v0.4 → v0.5 migration is non-destructive copy-and-validate. Source v0.4 state is left untouched, and multiple OS users' independent v0.4 stores are never silently merged. | [#17](https://github.com/shoemin/Palworld-Server-Manager/issues/17) |
| `PLATFORM-001` | OS-specific behavior lives behind explicit platform seams and a single composition root per executable — never scattered `OperatingSystem.IsWindows()` branches through shared code. | `v0.5-architecture.md` §1, §11 |
| `PLATFORM-002` | Interactive shell/UI actions execute in an interactive client session, never inside the machine-wide Host service/headless daemon. Host may authorize and return only bounded resource information required for a local client action. | `v0.5-architecture.md` §11, §11a |
| `LINUX-001` | No Linux-specific production implementation begins before explicit Windows Avalonia/Host feature-parity acceptance. | [#17](https://github.com/shoemin/Palworld-Server-Manager/issues/17) Gate E, [#20](https://github.com/shoemin/Palworld-Server-Manager/issues/20)/[#21](https://github.com/shoemin/Palworld-Server-Manager/issues/21) |

- 2026-09-01 — second Codex review of PR #57 found two gaps in the just-landed `LOCAL-003`/`PAIR-004` mechanisms themselves (fixed inline, no new invariants — an `EnrollmentCode` binding for `PendingLocalPrincipalEnrollment`, and a durable `Revoked` tombstone state for `TrustedManagers` instead of row deletion) and one gap in already-accepted, unrelated §5 architecture: `HostCapabilityGrant` had no destination/`PeerHostId` scope. The latter was escalated and accepted as a Product Decision. New invariant `AUTH-005` added: every `HostCapabilityGrant` now targets exactly one `TargetHostId`, checked exactly on both the local-authorization and remote-authorization sides of §4c's outbound dual-authorization model, with matching delegation/role-preset/`DefaultGrantTemplate` updates. `AUTH-001` unweakened — it still governs type/scope validity between Host- and server-capabilities; `AUTH-005` adds the missing Host-identity scope.
- 2026-09-01 — third Codex review of PR #57 found two more gaps in mechanisms just built this session (fixed inline, no new invariants — a `PendingCredentialReplacement` trigger corrected to exempt a symmetric-pairing partner's unchanged credential, and `EnrollmentCode` moved to verifier-only persistence) and two gaps in already-accepted, unrelated architecture, both escalated and accepted as a Product Decision. Two new invariants added: `LOCAL-004` (local IPC gains server authentication via `LocalHostTrustDescriptor` and standard TLS before any secret or ordinary RPC crosses it, §3b — closing a named-pipe/Unix-socket-squatting exposure), `OWNER-002` (initial Owner establishment requires a privileged, `OsPrincipalRef`-bound `Host.Cli` bootstrap with a single-use `OwnerBootstrapSecret`, never mere OS-group membership, §2c). `LOCAL-001` clarified, not weakened, to state the one-Owner rule applies to an *initialized* Host, with an explicit `Uninitialized` pre-bootstrap state that exposes no ordinary authority.
- 2026-09-01 — fourth Codex review of PR #57 found two more gaps in mechanisms just built this session (fixed inline, no new invariants — `PAIR-004`'s unchanged-credential reconfirmation exemption in §4b-i restricted to `State == Active` rows specifically, with a matching-credential `PeerBound` row now correctly routed through §4b's existing crash/reconnect resumption path instead of being treated as reconfirmed `Active` trust; and `LOCAL-004`'s §3b credential-recovery claim — which cited a §2b operation that does not and was never meant to cover the Host's own machine credential — replaced with an actual, newly defined offline Host machine-credential-loss recovery operation, using the identical `Host.Cli` bootstrap/recovery privilege model §2b/§2c already established, that regenerates `HostIdentity.CurrentCredentialRef` and republishes `LocalHostTrustDescriptor` together, explicitly not claiming to restore already-paired remote peers, which independently re-pair through the existing §4a/§4b-i path) and one gap in already-accepted, unrelated §4a architecture (a Host with multiple paired peers rotating its single global mTLS credential has no staged/overlap mechanism, so an offline-at-rotation-time peer is stranded regardless of whether the Host switches immediately or waits) — escalated as a Product Decision, not yet resolved; no new invariant added pending that decision.
- 2026-09-01 — the escalated staged-rotation finding was accepted as a Product Decision and resolved. New invariant `IDENT-003` added: routine Host-credential rotation is staged across every `Active` peer (§4a-i) — a `HostCredentialRotation` proposes the new credential under the old, still-current one; each peer durably stages the new fingerprint as `PendingTrustedPublicKeyFingerprint` while continuing to accept the old one; the Host cuts over only once every remaining `Active` peer has staged (an offline peer either is waited for or is explicitly, audibly revoked by the Owner — never auto-revoked on a timeout); `LocalHostTrustDescriptor` (`LOCAL-004`) stages the same way for local clients. A separate, explicitly non-staged Owner-authorized emergency-compromise-replacement path exists for a suspected-compromised (not merely offline-inconvenient) old credential, which may strand an unreachable peer by design, requiring that peer to recover via the existing `PAIR-004`/§4b-i `PendingCredentialReplacement` flow — routine rotation, suspected compromise, and credential loss remain three distinct, non-interchangeable mechanisms. No `CapabilityGrant` changes at any step of routine rotation. `IDENT-001`, `PAIR-001`–`PAIR-004`, `LOCAL-004`, `AUTH-003`, and `SEC-001` are unweakened by this addition.
- 2026-09-01 — fifth Codex review of PR #57 found five findings: three were bugs in mechanisms built this session (fixed inline, no new invariants — a `FailedAttempts` rate limit added to `PendingLocalPrincipalEnrollment`'s `EnrollmentCode`, mirroring §4b's existing ten-attempt pairing-code lockout; `IDENT-003`'s §4a-i rotation corrected to dynamically add and stage a peer that reaches `Active` mid-rotation instead of freezing the peer set at step 1; `IDENT-003`'s cutover corrected to durably promote `HostIdentity.CurrentCredentialRef` before any old-key retirement, instead of leaving it stale) and two gaps in already-accepted, unrelated §1 architecture, both escalated and accepted as a Product Decision. Two new invariants added: `ARCH-002` (legacy `PalworldServerManager.Lan` is retained unchanged for the frozen WPF app; the new `Contracts` assembly is not a rename of it, and no v0.5 project depends on `Lan`, §1 — closing a gap where the original "`Contracts` is renamed/evolved from `Lan`" claim was unimplementable while `ARCH-001` keeps the WPF app frozen, since the frozen app's own `AppServices.cs` directly consumes `Lan` types), `CLIENT-003` (a new `PalworldServerManager.Client.Cli` project is the ordinary online command-line client, structurally a `Client.Avalonia` peer sharing the same `Client.Platform.Contracts` tree and `LocalPrincipal` credential model; `Host.Cli` loses its former "normal operation" mode entirely and becomes privileged offline bootstrap/recovery only, never an ordinary authenticated client — closing a gap where `Host.Cli`'s normal-mode dependency set had no path to a `LocalPrincipal` credential at all, so it could never actually satisfy §3a's local-IPC authentication requirement). `CLIENT-001`/`CLIENT-002` clarified, not weakened, to state their existing rules apply to every ordinary local client (`Client.Avalonia` and, now, `Client.Cli`), not `Client.Avalonia` alone.
