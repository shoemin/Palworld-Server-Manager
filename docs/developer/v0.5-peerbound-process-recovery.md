# Native PeerBound process recovery qualification

Trial reference: #44ap, within #44. `WindowsPeerPairingCrashQualification` runs inside the disposable Windows service account. Two explicitly simulated Hosts use separate fixture leases and real protected/native credentials. Their sole Owners are initialization fixtures, but neither peer-trust record is seeded. A test-only transactional activation hook records one effect per Host and creates no canonical grants.

The parent Host creates a short-lived native pairing invitation. Its child Host initiates the real address/code exchange through the selected guarded Windows SPAKE2 provider and actual TLS/gRPC. The shared `WindowsPeerProcessFixture` transfers exactly ten ASCII code bytes over redirected private standard input after a bounded public binary header/address. Codes are never converted to control strings, arguments, JSON configuration, public reports or diagnostics. Extracted byte arrays and the child's redacted-secret copy are zeroed/disposed after use. Reports contain only public identities, fingerprints, native container names, trust states and expiry metadata.

Both Hosts must independently commit PeerBound with the expected actual pins, original expiry and zero activation effects/grants. The parent explicitly terminates the still-running child before activation and waits for its exit. Only then may it reacquire the child fixture's lease and inspect durable PeerBound. The restarted child's public configuration omits the native provider, forcing the shared fixture's refusing factory. Its Host identity, own protected pin/native key name, peer pin and original binding expiry must remain unchanged. Actual pinned mutual-TLS activation and an idempotent retry must succeed with that refusing factory, independently commit Active on both Hosts, produce exactly one activation effect each and leave exactly one original PeerBound audit event. A final orderly exit and lease-held read verifies durability. No second PAKE or stored pairing code is available for recovery.

The shared infrastructure retains the [receipt process case](v0.5-peer-receipt-process-recovery.md). Its receipt/activation control commands carry public data only. The third command carries a code only for an explicitly native-enabled pairing fixture; unknown commands, oversized/truncated frames, non-loopback endpoints and incomplete provider selections fail. The actual process handle, PID and fresh instance distinguish lifetimes. A child watchdog and bounded parent waits prevent abandoned fixture processes from qualifying as a successful crash. Cleanup requires actual exit and complete Host generation shutdown before exact fixture native/protected deletion.

The Windows service CI job builds the same pinned native source through `build-spake2.ps1`. The integration script accepts `-PairingProviderPath`, computes a public SHA-256 digest, and passes path/digest to the privileged harness. The harness holds the source file against writes while checking and copying it, verifies the copy, and places it in a fresh explicit Administrator/SYSTEM-write, public-read/execute binary tree. The service and child use that copied absolute path plus expected digest; no ambient DLL search or external prebuilt component is used. Two real non-admin users must read the matching public binary while write-open and deletion fail. This is disposable test provisioning, not an installed-product provider configuration or release artifact.

A requested native provider requires its separate `PairingCrashQualified` readiness flag. CI always requests it. The older direct integration invocation without a provider still exercises its existing scope and leaves that flag false; it does not claim native pairing-process qualification. The original receipt case, native key/service restart, two-user local security and other service checks remain required. Exact passing/failed run IDs and two-review outcomes belong in the trial ledger.

This case qualifies process termination of the pairing initiator after both durable PeerBound commits, then activation recovery without another PAKE. It does not qualify termination before PeerBound, termination in the middle of a commit, the responder's corresponding crash boundary, power loss/reboot, physical multi-machine LAN or installed full-network enablement. Those remaining #44 requirements stay distinct. Accessibility remains waived for the isolated trial.
