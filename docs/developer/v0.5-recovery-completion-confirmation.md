# Exact recovery completion confirmation

Trial #28l supplies the trusted persistence seams for reading an outstanding local-Owner approval and recording that the peer acknowledged its completion. It uses the existing `PeerReplacementCompletions.ConfirmedUtc` field; no schema migration, transport, address, command queue or grant is added. The [receiving RPC](v0.5-recovery-completion-rpc.md) is qualified separately. The [fixed native sender](v0.5-recovery-completion-sender.md) validates an actual authenticated, correlated `Recorded`/`AlreadyRecorded` reply before calling this confirmation seam. The [fixed receiving offer extension](v0.5-recovery-completion-offer.md) also validates the actual approved peer's exact positive receipt attestation before confirmation. A `KeyMismatch`, unknown result or mismatched reply never qualifies confirmation.

`ReadPendingRecoveryCompletion` requires current actual TLS peer/local fingerprints, exact current relationship incarnation, an initialized Host and one active Owner. An existing marker must be uncanceled, match that incarnation and the exact current/actually presented peer key, and retain its original approved candidate and verified-binding provenance. Absent pending work returns no notice; an exact already-confirmed marker is read-only. A stale or invalid marker is refused. A durably staged different peer key cannot substitute for the approved current key. A pending rotation may coexist with confirming the still-current approved key; neither read nor confirmation promotes rotation or clears reconfirmation metadata.

The notice identifies the peer, original approval ID, approved peer fingerprint and current incarnation. The sender must retain that original approval ID across its exchange. `ConfirmAuthenticatedRecoveryCompletion` revalidates the same current proof and approval in a new immediate transaction; only `ConfirmedUtc` and an actual peer audit are written. It then verifies unchanged authorization revision, complete grant forests and all protected identity/credential/rotation/principal/trust/candidate/binding/receipt/incarnation/default rows, exact expected completion markers, current proof, final audit contents and cancellation. Any inconsistent late effect rolls back everything. Concurrent confirmations have one writer and read-only duplicates. A later or superseded approval cannot be confirmed using an older approval ID.

The marker's local fingerprint and approval timestamp remain historical. Qualified [own offline recovery](v0.5-offline-recovery-completion-continuity.md) changes the actual current local key and invalidates historical candidates while preserving an eligible approval marker. Confirmation therefore uses the actual current local key and original approved provenance; it does not require the candidate's diagnostic invalidation field to be empty or the historical local key to remain current. An [incoming receipt](v0.5-recovery-completion-receipt.md) may independently advance the relationship incarnation and carry the marker; a sender holding the previous incarnation must reconnect before confirming. Recording confirmation does not clear the local recovery flag, approve a replacement, revive old grants or authorize ordinary traffic.

Eight ordinary test groups cover exact pending/result/audit behavior and unchanged grant forests, absent/read-only duplicate handling, both forms of own recovery continuity, incoming-receipt incarnation races, thirteen changed-proof/unapproved-marker cases and later explicit re-pair, rejection of staged-key substitution with rotation preservation, eighteen late state/audit faults, concurrent single-winner confirmation and before/during-transaction cancellation. Fixtures invoke the existing canonical local Owner approval and recovery/receipt writers with explicit trusted proof objects; they do not qualify a complete real-TLS sending ceremony.

The awaited native sender has separate component qualification. [Generation-owned invocation](v0.5-recovery-generation.md) is now separately qualified. Opportunistic contact retry, public command initiation and full fresh-PAKE/two-Owner approval recovery acceptance remain #28 work. Creator permissions/limits remain unchanged; accessibility/screen-reader certification remains WAIVED, never PASS.
