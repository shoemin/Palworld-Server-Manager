# Rotation completion follows actual key retirement

Trial reference: #44as, within #44. The component acceptance audit found that #44an committed Completed before deleting Old. Architecture §4a-i requires the opposite order. The correction separates an irrevocable, durable retirement authorization from terminal completion; no peer predicate or current Owner check is weakened.

The existing all-current-peer proof gate runs under the immediate Host writer transaction after successful whole-generation shutdown. It checks actual Current New, the exact authenticated Owner, all nonrevoked relationships and their current-incarnation evidence, then records `RetirementAuthorized=1` and `HostRoutineRotationRetirementAuthorized` attributed to that Owner. Post-audit guards repeat authority, exact rotation, peer revision, evidence and cancellation checks. State remains CutOver and CompletedUtc remains null. This intent creates no capability or server authority.

The machine lease and full shutdown exclude other writers until reconciliation. Trust planning may release Old only for this authorized CutOver; New remains required and current. Reconciliation publishes New, retires native handles/material, deletes the protected Old secret and only then invokes post-deletion persistence. That callback atomically records RetiredUtc, Completed, CompletedUtc and a system `HostRoutineRotationCompleted` event referring to the rotation. Completion is performed by the system from the prior Owner authorization, including after restart; it does not pretend a fresh Owner request occurred during recovery. Post-audit identity/rotation/credential checks prevent contradictory completion. No process claims deletion merely from a public fingerprint or a database intent.

A publication, native retirement, protected deletion or final audit failure leaves retryable intent. Some physical deletion may already have succeeded; repeating missing-key deletion is idempotent. No listener can start while the reconciled snapshot still has a CutOver retirement intent. Explicit transition recovery and normal startup therefore finish reconciliation before serving. The privileged offline loss/compromise path supersedes the intent by clearing it and marking the rotation Aborted, preserving its independent recovery-required relationships.

Schema9 adds the checked intent flag. Historical schema2-8 metadata reads project false intent explicitly from the durable schema version; there is no exception fallback for malformed current-schema data. Retirement authorization requires schema9. An older Completed row whose Old credential still lacks RetiredUtc becomes CutOver with authorized intent and no CompletedUtc. This preserves its already committed eligibility, not a new Owner decision or proof of deletion. Old already recorded retired preserves its original Completed timestamp. Historical audits are retained, including premature completion events from old code; migration fabricates no deletion event. Invalid or ambiguous rotation metadata still fails closed under the planner rather than guessing which credential is authoritative.

Three new ordinary scenarios test all four failure boundaries with independently reopened reconciliation, atomic final-audit rollback and idempotence, old-schema upgrade with and without prior retirement, and offline compromise supersession. Existing full-peer/Owner/cancellation tests now distinguish intent from completion. Actual socket/generation tests require pending CutOver across cleanup failure and Completed after recovery.

The disposable Windows service fixture holds the real encrypted Old file open without delete sharing. Actual native retirement succeeds; protected file deletion fails through Windows. The fixture requires the file to remain, the native Old key to be absent, all listeners closed, and both CompletedUtc and completion audit absent. Releasing that file handle allows explicit recovery to delete the file, preserve usable original New material and record one terminal completion. Fixture cleanup requires successful whole-generation closure and its existing exact lease/path ownership. This is an actual OS deletion refusal and recovery, not a physical-machine reboot or power-loss claim.
