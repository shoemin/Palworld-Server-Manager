# Windows local security qualification

The Astra trial's final #42 integration uses the shipped Host, offline Host.Cli and ordinary Client.Cli executables on a disposable Windows runner. It refuses a pre-existing product service, group, data root or native-key grant. Two newly created non-admin users log on with separate profiles; neither is represented by a synthetic SID in these final ceremonies. The ordinary CLI uses its fixed product composition and each user's default DPAPI store.

[CI 34013057938](https://github.com/shoemin/Palworld-Server-Manager/actions/runs/34013057938), code/test commit `08bb1ed5986a102a0d4b72e7606c81d1889023b9`, passed both the ordinary test job and actual privileged integration. Local Release build had no warnings, all 217 ordinary self-tests passed and strict documentation validation passed. The trial ledger records the separate two-pass review and merge gates.

| #42 criterion | Evidence |
|---|---|
| Two users have distinct credentials and identities | Shipped CLI bootstrap/enrollment results match separately persisted native SID/public-key rows and separately reopened per-user stores |
| Transport access does not authorize registration | Group-eligible user starts the service but cannot authenticate or claim the intended user's bootstrap; principal count remains zero before intended completion |
| Client private key stays client-side | Actual helper returns only public verification material; Host receives public SPKI/proof, client graph excludes Host stores, and actual user attempts to read Host state/native private files fail; separate actual cross-user DPAPI tests remain required and pass |
| Exactly one persisted Owner | Actual bootstrap, rotation, active-target re-home, revoked-target re-home and restart each check the exact sole active Owner; former Owner authentication fails |
| Ordinary/remote RPC cannot replace Owner | Actual Owner and non-Owner attempts to revoke Owner fail; no ordinary Owner setter or remote recovery route exists; privileged tickets remain mandatory |
| Offline recovery respects exclusivity | Actual shipped offline executable refuses while service owns the lease; existing real held-lock/elevation tests also pass |
| Recovery is audited without secrets | Actual preparation/completion/revocation audit events are present; summaries contain no delivered enrollment codes; ordinary tests cover verifier/secret-safe fields and transaction rollback |
| Local IPC requires no remote TCP listener | Actual named-pipe server PID has no TCP endpoint before initialization and after the final Owner ceremonies |

Owner-authorized revocation survives restart and explicit re-enrollment preserves the target's identity while replacing its key. Rotation preserves Owner identity with a fresh key. Re-home to an active target preserves that target's existing key; re-home to a revoked target preserves identity with a fresh key. Protected handoff files are absent only after successful completion and durable client binding. Ordinary fault-injection tests separately cover lost replies, failed proof, failed confirmation and failed deletion; they are not described as actual machine failures.

Enrollment invitation output moves through fixture directories restricted to Administrator/SYSTEM and one intended recipient, then into the completion process through redirected standard input. Every helper confirms the other user's delivery marker is unreadable. Shared PASS/error files and CI logs never receive bearer output. The fixture removes per-command delivery files in `finally` and requires service/group/users/profiles/native grants and owned directories to be cleaned. The final run passed cleanup and retained the service activation ACL unchanged.

This qualifies the Windows local security boundary, not the whole milestone. Avalonia shares the same coordinator but feature screens and visual acceptance remain later work. No real Palworld, reboot, multi-machine remote pairing, Windows parity #55, Linux or release-artifact qualification is claimed here.
