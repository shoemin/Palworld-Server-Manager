# Fixed native recovery completion sender

Trial #28m connects the [fixed receiving RPC](v0.5-recovery-completion-rpc.md) to [exact pending/confirmation persistence](v0.5-recovery-completion-confirmation.md). One awaited Host-only call owns a fresh actual Windows mutual-TLS HTTP/2 transport and channel. It uses the fixed recovery hello and feature15, a 16KiB message bound and a 15-second cancellation deadline. Ordinary client, permission and rotation authentication are unchanged. The caller retains the authoritative Host lease and borrowed certificate until the entire call, including native callback/channel disposal, finishes.

Before TLS possession proof, the certificate predicate only reads whether the expected peer is Active and its exact current key matches. Recovery may remain independently required on this fixed intrinsic path. The completed native TLS callback then binds actual local/peer keys, the current local relationship incarnation and the exact outstanding approved marker. A staged different peer key cannot stand in for the approved current key. The sender retains that original proof; it never silently replaces a changed incarnation on an old connection. Native transport permits only one completed connection per instance.

After bounded exact-Host/explicit-feature negotiation, the sender rechecks the original current proof and pending marker. No pending work yields `NoPending` without a receipt request or new audit. Otherwise it sends the original approval ID and approved receiving peer fingerprint. It validates actual connection identity and exact receiving/approving Host IDs, approval ID, acknowledged key and closed reply result. Only `Recorded`/`AlreadyRecorded` calls the canonical confirmation writer. `KeyMismatch` never confirms; unknown, malformed or mismatched replies refuse. The canonical writer revalidates original keys/incarnation/approval and final state before commit. Network failure/cancellation leaves the durable obligation available for a fresh authenticated retry.

Each Host commits independently. If an incoming completion clears the local recovery flag while an outbound reply is held, the local incarnation advances and carries the eligible marker. The held outbound proof is stale and cannot confirm; a fresh connection can retry the same original approval against the peer's idempotent receipt. Own offline recovery similarly uses the actual current local TLS key while preserving the approval's historical local fingerprint. A peer that has not independently approved that new key still rejects it at real TLS admission. Confirmation creates no grants and does not itself clear the sender's independent recovery flag.

Eleven test groups exercise actual mutual completion and current configured Owner roots; own fresh-key recovery/history and old/unapproved-key refusal; lost reply/fresh exact retry; actual bidirectional receipt interleaving and stale-incarnation refusal; local revocation/key changes before send or confirmation; seven malformed/mismatch replies; bounded negotiation/no-pending/input handling; caller cancellation while a real native callback is held; the production deadline while a response is held; and eight concurrent native senders with one audit per effect. Response rewrites/holds are controlled Host-side test faults over real native TLS, not physical network-MITM or remote-hang qualification. Initial historical trust/verified binding is explicitly a fixture, followed by canonical local Owner approvals; this is not full native PAKE qualification.

The [Host generation](v0.5-recovery-generation.md) owns invocation through its existing traffic lifetime. The awaited sender and [reverse client](v0.5-recovery-completion-pull.md) are now invoked by the separately qualified [authenticated-contact coordinator](v0.5-recovery-contact-retry.md); [native repair](v0.5-native-repair.md) and [own-key recovery](v0.5-native-own-recovery.md) have separate genuine PAKE qualification. Public initiating commands remain #28 work. [Actual receiving-process crash and hang qualification](v0.5-recovery-process-faults.md) is now separately required and qualified in the Windows service harness. A caller must not treat deadline cancellation as proof that native cleanup has completed or release its borrowed credential before this call returns. Creator six/limits remain unchanged; accessibility/screen-reader certification remains WAIVED, never PASS. No installed deployment, physical Palworld, Windows parity, Linux production or release acceptance is claimed.
