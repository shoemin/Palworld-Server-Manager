# Scoped live unpair delivery

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28).

`PeerUnpairConnectionFactory.WithConnection` prepares a retained encrypted HTTP/2 connection while the peer is Active. It authenticates the actual completed Windows TLS identity, negotiates `PeerUnpair`, captures the current original peer/local fingerprints and relationship incarnation, and invokes a trusted Host callback. Preparation has a 15-second deadline. The callback is Host composition code, never a request-supplied callback or permission grant.

Connection preparation must be separate from the revoke command. `HostNetworkGeneration.WithPeerUnpairConnectionAsync` keeps the entire preparation, callback, send and transport cleanup within its existing traffic admission. Shutdown cancels that work and drains it before disposing the generation's certificate. The scoped connection cannot send after its callback returns. It is not an outgoing queue or a business-operation executor.

The canonical local/remote/received revocation result now records `PreviousIncarnation` as trusted Host metadata. `RequireCommittedUnpair` matches that source incarnation to the prepared connection, requires a changed result for the same peer and a strictly newer resulting incarnation, and checks the exact current clean tombstone plus the Host's current local credential. It is a read-only guard, not authentication for a new connection or authority to revoke anything. A fabricated result while trust remains Active, an unrelated/later transition, or a changed local credential cannot permit delivery. Old public peer-key evidence remains fixed in the already-authenticated connection; it is not reconstructed from the tombstone or request payload.

`PeerUnpairConnection.Send` makes at most one attempt. It validates the matching local commit, sends the [bounded receiving notice](v0.5-reciprocal-unpair-rpc.md) over its retained channel with a three-second deadline, validates both expected reply identities and the closed disposition, and rechecks the current local tombstone before reporting `Confirmed`. Any absent/invalid reply, cancellation, stale local state or transport failure is `Unconfirmed`; local revocation is already final. Further calls return `Unconfirmed` without another send. No delivery acknowledgement creates grants, audits, a new relationship or durable outgoing work.

No explicit new connection is opened by `Send`. The existing Windows transport rejects a second completed TLS identity, and its current-trust callback refuses a revoked peer if the underlying HTTP stack attempts to reconnect. This is not a claim that the HTTP stack makes zero attempted TCP reconnects. A replacement authenticated connection or ordinary-authentication bypass is never used for delivery.

Disposal marks the connection closed, cancels pending delivery, aborts HTTP and drains the send before its outer scope disposes the transport. Cleanup still proceeds if a cancellation callback fails. The existing transport drains callbacks that access Host state before returning from disposal. A cancellation or lost reply cannot undo either Host's committed revocation.

## Evidence and remaining integration

`LiveUnpairGuardTests`, `LiveUnpairConnectionTests` and the generation/rotation companion tests cover exact source/resulting incarnation and current-key guards, read-only refusal, actual two-store encrypted delivery with local-Owner/remote-peer audits, single-attempt/captured-scope refusal, uncommitted and later-transition refusal, actual transport disposal without a second authenticated exchange, concurrent disposal during a deliberately held Host-side HTTP response, unproven/PeerBound/canceled preparation and real generation shutdown with certificate/timer cleanup. The response hold is an explicit client-side adapter around actual Windows TLS, not a simulated remote-server hang presented as field evidence.

Preparation may independently observe and commit a legitimate staged New peer credential before a later feature check fails. A real rotation/TLS test with an explicitly altered feature reply verifies that the canonical promotion remains recorded while the callback is refused and no grants are issued; subsequent fresh preparation can revoke both sides. Preparation itself never revokes trust or grants authority. Fixture global cutover and artificial relationship restoration remain clearly bounded test inputs, not new full-rotation or Owner-repair acceptance claims.

The upcoming command coordinator must select only an already prepared connection, commit local revocation without waiting for connection establishment or peer acknowledgement, and expose delivery separately. Missing/offline/hanging-peer orchestration, complete local/remote command integration and full fresh Owner-approved re-pair remain later #28 units. Ordinary outgoing administration still requires the originating user's independent local permission. The six creator permissions/limits remain unchanged. Accessibility is **WAIVED, never PASS**; physical-PC/Palworld/parity/Linux/release qualification is not claimed.
