# Explicit current-credential confirmation

Trial reference: #44al, within #44. `ConfirmCurrentCredential` adds explicit peer capability12 with peer protocol1.10 and new immutable host/peer-security descriptor snapshots. Local protocol remains independent. This Active-only Host maintenance exchange supplies fresh evidence even when a peer already cleared the retained rotation ID associated with an earlier receipt. It does not depend on a claim inferred from the TLS handshake alone.

The rotating Host opens fresh pinned mutual TLS, negotiates the exact peer identity and capability, captures its local relationship incarnation, and prepares a fresh request for its exact current New credential and CutOver/Completed rotation. It sends a bounded request identity, Host identity, rotation identity and public fingerprint. The peer independently checks that the requesting Host is the actual authenticated peer, its requested New is both the actual presented key and durable Current, its own local credential is still current, and its negotiated relationship incarnation is unchanged. An unobserved Pending key, an Old-key request claiming New, PeerBound/recovery trust or a stale relationship cannot confirm. An unrelated later Pending key does not invalidate proof that the requested key is still Current.

The peer replies with the exact request and an explicit Confirmed result. This is a read-only current-trust statement, not a claim that it knows the other Host's full rotation history. It does not clear any retained rotation ID merely because it sent a reply. The existing completed-TLS observer may legitimately promote an already staged New before the request; that independent durable transition and ordinary receipt retry retain their established behavior.

The initiating Host rejects missing/mismatched correlation and every unknown result. Its immediate writer rechecks actual local Current/New, the exact current rotation, Active/non-recovery peer/current pin and the incarnation captured before requesting proof. Evidence and its public authenticated audit commit together, with the same guards and cancellation checked again after audit work. No transaction spans network. A state change, canceled operation, lost reply or failed audit leaves no new confirmation; a new bounded exchange can retry. Repeats for the same current incarnation are readonly.

Schema7 adds `HostRotationCurrentCredentialEvidence` separately from promotion evidence. Upgrade creates no rows. First promotion, staging and acknowledgement history remain unchanged. If the history row is absent, confirmation creates only the peer/rotation association with those historical timestamps null. A peer first paired under New never has a fictional promotion time recorded. Both kinds of evidence must still match the current relationship when the [final retirement transaction](v0.5-rotation-completion.md) evaluates them. No rotation is marked Completed and no protected key is deleted here.

The helper uses the existing fifteen-second deadline, fixed peer message limits, disabled proxy/redirect behavior, borrowed Host credential and whole-transport callback draining. Windows composition supplies the concrete transport; current-generation and transition helpers own the entire action and reject closed admission. There is no ordinary-client Host-key path, new local RPC, grant/default provider or installed remote enablement.

Seven new ordinary scenarios cover conservative upgrade, pre-cancellation and first-New repository binding without invented history; actual New-key TLS confirmation after a cleared legacy marker; retained-ID preservation and later ordinary receipt; capability/identity/malformed/PeerBound/recovery/Old/unobserved Pending refusal; corrupted correlation/unknown result/lost reply; changed local credential or relationship during the reply; and queued writer/audit/post-audit rollback with retry. Existing actual generation/cutover tests now confirm through both owned helper routes and check closed admission. Receipt-specific fixtures identify synthetic global cutover explicitly. Full388-case regression, native and service CI are recorded in the ledger; physical-LAN, process-crash, installed enablement and final retirement qualification remain separate.
