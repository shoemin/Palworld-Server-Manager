# Routine Host rotation preparation

Trial reference: #44i, within #44. This is the local durable preparation/staging-readiness/abort foundation. It does not send peer proposals, perform global cutover, retire an old active key or expose a local client RPC. Those later steps must enforce the complete staged-rotation protocol in the accepted architecture.

The trusted Host passes the result of actual local principal authentication to `HostCredentialStateRepository`. Each mutation rechecks that actor's Host UUID, principal UUID, native OS identity and exact current public verifier against the active Owner in the same write transaction. Being in an OS group or supplying an Owner UUID is not authorization. The Host must be initialized with exactly one Owner and a usable current public credential. Loss or suspected compromise still uses the existing privileged offline recovery path.

`PrepareRoutineRotation` accepts a stable request UUID. A retained request, including an aborted/completed one, returns its original identity and status. Otherwise an existing nonterminal rotation, including CutOver, is returned without creating a second rotation or credential. Concurrent requests serialize in SQLite. A fresh request reserves an opaque new reference and a Prepared row together with the local-Owner audit event; an audit failure rolls back all three. The old reference remains current and no grant or peer trust row changes.

Prepared has a reservation phase in which the new reference is known but its public fingerprint is still null. Startup reconciliation retains both references and publishes only the old credential during this phase. It never infers a fingerprint or treats this reservation as usable new material. Missing current fingerprints, missing/retired references, malformed non-null fingerprints and incomplete metadata after Prepared still fail closed. The [recoverable material coordinator](v0.5-rotation-material.md) creates or recovers and validates the reserved material, then records its public fingerprint with a fresh Owner check and transactional audit. Installed service orchestration remains later work.

`BeginRoutineRotationStaging` requires an unused, unretired new reference with valid public metadata different from the old fingerprint. It changes only Prepared to Staging and audits the transition, idempotently. The existing trust projection then makes that public fingerprint eligible for pending local-descriptor publication while continuing to select Old as current. This does not acknowledge that publication occurred, stage any peer, prove cutover eligibility or authorize presenting New. Those facts require their own later durable evidence.

`AbortRoutineRotation` accepts only Prepared, Staging or ReadyForCutover, with Old still current. Aborted retries are idempotent. CutOver and Completed cannot be aborted through this online path. Abort changes only the rotation state and audit; the existing quiesced reconciler owns descriptor removal and material deletion, recording retirement only after deletion succeeds. A reserved reference with no material can also be abandoned safely. The next deliberate request uses a different UUID/reference. Peer abort notice and live status reconciliation remain the later rotation transport's responsibility.

Three ordinary scenarios use independent SQLite transactions/connections to test twelve concurrent preparations, request replay and reopen, reservation retention, staging readiness and same-key refusal, stale Owner/native/key checks, audit rollback at every mutation, safe abort cleanup and a synthetic later-engine CutOver that blocks new preparation/abort and retains Old. Cleanup callbacks observe only public references; they are not claims of real key deletion or process-kill/reboot evidence. Existing Windows secure-store and service qualification remains separate. Full rotation, full #44 and field acceptance are incomplete.
