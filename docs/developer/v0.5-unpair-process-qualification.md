# Actual receiving-process unpair qualification

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28).

`WindowsUnpairProcessQualification` runs under the disposable Windows service account in the required service/multi-user job. Four cases each create two unique protected Host stores and native machine credentials. The receiving Host runs in a retained child process under its own exact Host lease. Initial verified bindings are explicit fixture inputs; real encrypted activation, the generation-owned coordinator, canonical local revocation and the actual receiving RPC then execute. Genuine PAKE and re-pair are separately qualified.

| Case | Actual receiving process | Expected result |
|---|---|---|
| 1 | Held before receipt, then killed | Local Revoked; remote Active; Unconfirmed |
| 2 | Canonical receipt commits; response bytes withheld; killed | Both Revoked; one remote receipt/audit; Unconfirmed |
| 3 | Handler hangs beyond the three-second client deadline | Local Revoked while child remains alive and Active; Unconfirmed |
| 4 | Normal reply, then killed | Both Revoked; Confirmed |

The local command returns before a held remote handler completes. Withholding uses a fixed non-expanding 16 KiB buffer, and the parent asserts that the actual notification task is still pending at the child barrier. The hung handler deliberately outlives client disconnection. A fixed public state probe verifies that the same child remains alive. The process watchdog and parent case deadline bound failure cleanup.

After termination, the parent acquires the released receiver lease and checks durable state. A fresh process must load the same protected/native identity and preserve the exact independent state, incarnation and audit counts. The sender cannot prepare a new unpair connection or resend the consumed notice. A stale activation attempt is refused; it cannot silently restore either relationship, replay activation effects or duplicate revocation. Unlike recovery-completion delivery, unpair does not queue a retry after local trust has been revoked. Missing remote receipt is an honest best-effort outcome, not permission to weaken the local tombstone.

Each case preserves the exact active Owner and creates no grants. Cleanup observes process exit and generation drain before acquiring the fixture lease and deleting fixture-owned native credentials and validated unique directories. The required service readiness record has a separate mandatory unpair qualification flag. All four cases run at each of the four service starts. These cases do not change the ordinary suite count; a concurrent recovery-admission defect found during qualification adds a separate regression, bringing that suite to 682. Full CI evidence is recorded in the trial ledger before acceptance.

These are disposable same-machine Windows process/network tests, not physical-PC, power-loss, live Palworld or field parity acceptance. No installed Host fault route or local privileged-probe PASS is claimed. [Protected local network actions](v0.5-local-trust-network-actions.md) now provide online unpair preparation and Owner recovery initiation. The [originating-user route](v0.5-originating-user-trust-route.md) now supplies independent local and remote administration checks; parent28 aggregate acceptance remains separate. Accessibility is **WAIVED, never PASS**.
