# Durable peer promotion receipts

Trial reference: #44p, within #44. `ConfirmRotationPromotion` is separately negotiated with `PeerRotationReceipt` capability 8, introduced at protocol 1.6. Immutable host-v1-6 and peer-security-v1-6 descriptors retain all earlier history. This completes the receipt exchange between the receiving peer and rotating Host; it does not implement global cutover, retirement or installed service scheduling.

The peer opens a fresh bounded Host-owned pinned mutual-TLS connection. Its ordinary completed-handshake observer can promote an already staged New key, including after lapse. The connection then negotiates the expected Host UUID and receipt capability. Only after actual observation does the peer read its retained RotationId and create a fresh correlated request on that same connection. Current local and remote fingerprints must match authoritative metadata. An unobserved pending key cannot be reported as promoted. No retained ID means there is no receipt pending; it does not invent or resend unrelated history. Feature failure may leave an independently valid observation durably promoted with its ID still available for later retry.

The rotating Host accepts receipts only from an Active, non-recovery peer whose actual presented key is still current in the same transaction. The request must identify this Host and an exact durable CutOver or Completed rotation whose New reference is the actual current local TLS credential. An Old-key status claim cannot satisfy this predicate. It records the first PromotedUtc and authenticated peer audit together, keyed by peer and rotation. [Relationship-specific provenance](v0.5-rotation-receipt-provenance.md) now binds that proof to the incarnation captured at authenticated negotiation. Repeats within that incarnation preserve the timestamp and event; a fresh receipt for a later incarnation updates separate evidence while preserving first-promotion history. Existing Staged/Acknowledged history remains untouched; a missing legacy row receives promotion history and current evidence without invented staging history. Completed rotations can still answer while a subsequent Prepared rotation retains the same current key, including after Old metadata is retired.

Only the exact echoed request and a closed recorded/already-recorded result allow the peer to clear its retained RotationId. The final transaction rechecks both actual current credentials, Active/non-recovery trust, absence of an unobserved pending key and the exact retained rotation. Concurrent clearing is idempotent; a different retained rotation is refused. Clearing and the remote-peer audit commit together. No cross-Host transaction is assumed: a lost reply after Host commit, failed peer audit, or reopened runtime/listener requires a new bounded exchange using the durable ID. The Host records proof once per current relationship and safely confirms repeats. Migrated legacy history receives no invented provenance; peers that already cleared their retained ID can use [explicit current-credential confirmation](v0.5-current-credential-confirmation.md) to obtain separate current evidence without inventing history.

The exchange is fifteen seconds with fixed message limits, HTTP/2, disabled proxies/redirects and Host-owned borrowed credentials. Wire and audit contain only public correlation metadata. The receipt does not change either Host's Current, rotation state, grants, defaults or key-retirement state. The cutover coordinator evaluates current peers and bounded acceptance inside its transaction; the [completion coordinator](v0.5-rotation-completion.md) separately evaluates every remaining relationship before releasing Old.

Seven ordinary scenarios exercise actual proposal delivery followed by genuine New TLS, same-connection observation and concurrent receipt, customized grant retention, real post-commit reply loss, each independent audit failure, runtime/listener reopen, forged correlation/unknown result, stale local credential/recovery, incomplete TLS proof, actual Old-key refusal, changed retained ID, missing negotiation/capability, wrong identity/rotation/fingerprint, fresh PeerBound denial and legacy absent history. Global CutOver/Completed/retired metadata is explicitly synthetic input. Reopen is not a process-kill/reboot claim. The concrete generation now implements global cutover and completion, and a separate [disposable Windows service case](v0.5-peer-receipt-process-recovery.md) qualifies actual receiving-process termination/restart with an undelivered receipt. For cumulative component evidence and downstream limits, see the [#44 acceptance inventory](v0.5-peer-component-acceptance.md).

[Dynamic peer-set freshness](v0.5-rotation-peer-set.md) and the [acceptance collector](v0.5-rotation-acceptance.md) now bind actual bounded acknowledgements to current local trust. The [cutover coordinator](v0.5-rotation-cutover.md) checks eligibility inside the final transaction and the [generation transitions](v0.5-host-generation-transitions.md) own complete listener orchestration. Historical acknowledgements are never sufficient for cutover. The [completion/retirement gate](v0.5-rotation-completion.md) now consumes current relationship evidence. Installed enablement and complete crash/physical qualification remain outstanding.
