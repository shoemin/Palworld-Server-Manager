# Owner-selected historical grant reissue

Trial reference: #45e. This is the ordinary canonical grant action used by the separately gated credential-replacement workflow after approval. It does not replace credentials, activate trust or prove replacement occurred. Parent #45 remains incomplete for failed-request auditing and Host dispatch; the complete credential-replacement flow is also separate. The [approved six-permission creator policy](v0.5-creator-grants.md) supplies the Host confirmation/grant seam; actual server-creation workflow integration remains downstream. [Authenticated remote grant writers](v0.5-remote-grants.md) add the trusted incoming peer repository paths; Host RPC/outbound integration remains separate.

The actual current local Owner selects historical Host and server root IDs for one currently Active, non-recovery peer. Each selected row must already be invalidated, have no parent and belong to that same PeerHostId. Missing, active, delegated, wrong-peer or duplicate per-type selections refuse. Owner authority is mandatory even when a non-Owner holds ManagePermissions or delegation rights. The pure policy calls the existing canonical IssueHost/IssueServer methods with a new ID, the exact historical capability/target/rights, current Owner as issuer and a null parent. The historical ID is audit context, never new provenance authority. Full ServerRef and separate typed forests preserve scope, including colliding UUIDs across types.

The Host writer copies the selection, checks fresh authenticated Owner proof and expected policy revision inside an immediate transaction, generates new IDs and validates the entire selection before writing. Each new grant has an actual-Owner CapabilityGrantReissued audit with a public batch ID and HistoricalGrant field; Source remains OwnerRoot. No verifier, native identity, credential or free-text label enters the audit. Final Owner/peer/proof/revision and exact new/old-row checks plus cancellation precede commit. An audit or authority change rolls back all new rows, audits and revisions together.

Old grants and delegated descendants remain unchanged and invalidated. Delegation must be deliberately established again by a holder of a new root through ordinary delegation rules. A stale lost-response retry refuses; a fresh, explicitly authorized Owner request may issue another new root, like ordinary grant issuance. Empty selections still check current Owner, peer and revision, but create no batch, audit or grant.

Seven pure/actual SQLite scenarios cover exact canonical roots, no descendant revival, separate Host/server IDs and targets, actual audit provenance, non-Owner and invalid selection refusals, inactive/recovery peers, second-entry audit and authority/history mutation rollback, eight competing writers, explicit fresh repeat, empty and cancelled calls. Initial test fixture correction cleared the pin when marking a peer Revoked, as the existing schema requires. These are engine/persistence tests with explicit synthetic identity fixtures, not actual replacement or installed operational evidence. No schema, wire, dependency or platform change. Accessibility is waived; physical Windows parity, Linux and release qualification remain downstream.
