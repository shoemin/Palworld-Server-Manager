# Windows SPAKE2 wrapper

Trial reference: #44a, within #44. This bounded unit implements the Host-side key-exchange boundary and authenticated identity messages. Later bounded units connect it to [first-contact transport](v0.5-peer-pairing.md), code-attempt coordination, durable trust and pinned activation. Rotation, local/service composition and canonical grants remain outstanding. Neither successful key confirmation nor a `VerifiedPairingIdentity` is management authority.

## Component and profile

The native component pins Pakery `4fa353417ddddfcaaf29f990404e1f48127167e3` with its reviewed P-256/SHA-256/HKDF/HMAC suite. `native/PalworldServerManager.Spake2/Cargo.lock` pins all dependencies. No Pakery `test-utils` feature is enabled. Windows x64 is the qualified target; other architectures and Linux are not asserted. Compiler: Rust 1.98.1, MSVC target, static CRT. The locally inspected DLL imports only Windows system libraries (`bcryptprimitives`, core synchronization API set, `KERNEL32`, `ntdll`).

Application profile v1 accepts exactly ten ASCII decimal digits, including leading zeroes, without whitespace or normalization. The [internal Host responder coordinator](v0.5-pairing-attempts.md) generates those digits uniformly with a CSPRNG and enforces the architecture's five-minute validity, ten wrong-attempt lockout, source backoff and single-use code/session policy. Future authenticated transport composition must use that coordinator; the wrapper itself does not expose a listener.

Both parties receive the same fresh 32-byte session nonce. Password scalar derivation is Argon2id v0x13 with 19,456 KiB memory, two iterations, one lane, 64-byte output and the nonce as salt, followed by the candidate's big-endian wide reduction. The nonce is public context, not an authentication credential. SPAKE2 role identities are the fixed strings `initiator` and `responder`; the agreed transport initiator takes A. AAD is ASCII `PalworldManager/SPAKE2-P256-v1` followed by the nonce. Both nonce and profile must be identical for confirmation to succeed. Host identities are authenticated separately after confirmation.

Every creation seeds standard ChaCha20 from 32 bytes supplied by Windows-backed `getrandom`; an entropy error rejects creation. Scalar generation remains the candidate's rejection sampling. No deterministic seed API exists in the production ABI. Keys and transcript state remain native. Caller-owned managed code buffers must be cleared by their owner after use; the provider clears its private copy. Zeroization reduces secret lifetime but does not promise erasure of all compiler/register/primitive-internal copies.

## Monotonic session boundary

`Created -> AwaitingConfirmation -> Confirmed`. Any malformed input, wrong-phase call, cryptographic failure or cancellation during an operation terminates that exchange. `Failed` and `Disposed` cannot be revived. A fresh exchange receives fresh randomness; retrying the failed handle cannot perform work or consume another native verification. The internal Host coordinator counts the terminal exchange failure once using its own attempt identity; repeated calls on the failed wrapper are not fresh guesses.

Initial messages are exactly 65-byte uncompressed P-256 points. Confirmation messages are exactly 32 bytes. The initiator sends its confirmation first; the responder releases its confirmation only after verifying the initiator. A responder receiving a key share returns no confirmation yet. The native map removes the session before processing and reinserts it only on success; errors and caught panics drop it. Handles are monotonically assigned 64-bit integers and never reused; exhaustion rejects creation. Creation and operations are serialized, with a 128-session bound that also limits concurrent memory-hard work. A poisoned mutex can be recovered because the failing session already left the map before mutation. Explicit close removes and drops state, never calls `zeroize()` followed by verification.

The managed provider uses one lock for session calls, cancellation checks, disposal and module lifetime. Caller buffers are copied before native calls. Disposal closes sessions before unloading the module; failed constructors cannot double-free it from a finalizer. Failed sessions close their native handle and leave the provider's tracking set. Callers must dispose successful sessions promptly; the internal Host responder coordinator owns expiry and disconnect cleanup for its exchanges.

Q44-1 is prevented by having no raw-key export or binding operation before confirmation. Q44-2 is prevented by terminal handle removal and exact confirmation lengths. Q44-3 is prevented by discarding the output after failed confirmation. All three are exercised through the managed production API.

## Authenticated identity binding

After confirmation, derive 32 bytes using HKDF-SHA256 with Ke as input, no salt, and ASCII info `PalworldManager/HostIdentityBinding/v1`. A binding payload is the nonempty Host UUID as 16 network-order bytes, a four-byte big-endian public-credential length, and canonical DER SubjectPublicKeyInfo for an ECDSA P-256 key. The public credential is limited to 1,024 bytes. No Host private key is passed into the wrapper.

The authentication tag is HMAC-SHA256 of ASCII `PalworldManager/BindingMessage/v1`, one role byte (0 for initiator, 1 for responder), and the payload. The wire binding appends the 32-byte tag. Verification uses the peer role, rejects reflection/substitution, validates the credential representation, and returns an immutable copy of the verified identity. The local binding must be created first, fixing the local UUID before any peer identity can be returned. Local and peer UUIDs cannot be equal. Repeated identical binding messages are idempotent; a different binding on the same exchange terminates it. The native session remembers the first local and peer payloads, so changing callers cannot retarget its identity.

This result proves the binding to the confirmed exchange; it does not prove a durable peer pin, mTLS possession, reciprocal activation or a capability grant. Those remain the Host coordinator/transport/state-machine responsibilities. Ordinary local clients have no reference path to the platform wrapper.

## Build and load

With the pinned Rust toolchain and existing MSVC x64 tools:

```powershell
$env:RUSTUP_TOOLCHAIN = '1.98.1'
./scripts/build-spake2.ps1
dotnet build PalworldServerManager.sln -c Release
dotnet run --project tests/PalworldServerManager.SelfTest -c Release --no-build -- --spake2-wrapper-probe "$PWD/build-logs/spake2-native/target/x86_64-pc-windows-msvc/release/palworld_spake2.dll"
```

The build emits the DLL, a SHA-256 component manifest and dependency notices under ignored `build-logs`. Build instructions/lockfiles are repeatable; bit-for-bit binaries across different compiler paths are not claimed. The managed provider requires an absolute path, an expected build-pinned digest and ABI 1. It locks the file against writes/deletion while hashing/loading it. The later Host composition must supply a protected installation path and trusted build manifest; a hash supplied by an attacker is not a trust anchor. No global DLL search or dynamic fallback is configured.

Regenerate dependency notices by saving `cargo metadata --locked --format-version 1 --filter-platform x86_64-pc-windows-msvc --manifest-path native/PalworldServerManager.Spake2/Cargo.toml` as JSON and passing that path and the destination notice path to `scripts/collect-spake2-notices.py`. The generator follows the reachable Windows dependency graph and preserves distinct notice texts; normalized trailing whitespace does not change license wording.

No native DLL is automatically deployed by this unit or loaded by the existing Host startup. Subsequent composition must copy the vetted component and notices into protected Host installation storage and retain this exact loading policy. The fixture-only entropy-failure build uses a different ABI marker; the production provider rejects it even with its correct file hash.

## Qualification evidence

These counts are separate from the ordinary self-test suite.

Existing full build/self-tests, actual Avalonia rendering/input, strict Docs and Windows CI remain required. The wrapper CI job explicitly builds production and entropy-failure artifacts and runs these checks. No mandatory field acceptance, timing audit, remote Host qualification or full #44 completion is inferred from unit results. Review A/B and exact validated heads are recorded in the trial ledger.
