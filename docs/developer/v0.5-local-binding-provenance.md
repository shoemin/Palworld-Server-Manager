# Local credential proof at first pairing

Trial reference: #44am, within #44. Schema8 records `PeerLocalBindingEvidence` only when a new verified PAKE binding creates a local PeerBound relationship. The record contains public peer identity, the actual local credential fingerprint, the relationship incarnation and the original binding time. No private material is stored here.

The authoritative immediate writer first verifies the actual local credential and, for locally initiated pairing, the exact authenticated Owner. It creates trust and pairing metadata, then captures the incarnation after both sets of triggers have run. Binding evidence and the existing PeerBoundCreated audit commit together. After audit work, the writer checks the local credential, incarnation, exact initiating Owner and new binding metadata again; any failure rolls back the whole new relationship. Each Host still commits independently, and neither PeerBound nor this evidence grants ordinary authority.

Migration creates an empty table. Existing pairing timestamps and local-fingerprint metadata are not retroactively certified. Resume, Active reconfirmation, recovery refusal and replacement-candidate paths neither create nor refresh this proof. Migration tests explicitly seed old-schema metadata; the newest production writer has no fallback that skips evidence on an unmigrated database.

Activation and verified routine peer-key promotion preserve the relationship incarnation. Recovery, revocation, unproved key changes and pairing metadata rewrites invalidate it according to the [existing provenance rules](v0.5-rotation-receipt-provenance.md). Evidence deliberately retains the original incarnation, so a return to the same identity and key cannot make stale proof current. The [final retirement gate](v0.5-rotation-completion.md) compares the current incarnation, actual local New fingerprint and current trust state inside its final writer transaction. A copied row or cached read cannot authorize retirement.

A peer first paired under New did not promote Old. This proof records that binding without creating a rotation, a rotation-peer history row or a fictional promotion timestamp. Legacy or invalidated proof can instead be resolved by an [explicit current-credential confirmation](v0.5-current-credential-confirmation.md). No completion transition, protected-key deletion, protocol addition or installed-service enablement is provided here.

Four ordinary scenarios cover conservative/idempotent/atomic upgrade, Owner binding and activation/routine continuity, stale evidence across recovery and replacement candidates, audit and final-context rollback with retry, a queued Owner change, and first binding under a changed local key without invented history. The guarded native PAKE scenario additionally verifies actual local fingerprints and current incarnations on both independently committed Hosts. This is not physical-LAN, process-crash or final retirement qualification.
