# Concrete Windows discovery configuration

Trial reference: #44ag, within #44. Trusted `WindowsHostComposition.CreateNetworkTransitions` accepts an optional explicit discovery UDP port. Null keeps discovery disabled. No port default or installed setting is selected, and installed `RunAsync` still starts the local-only generation. The mandatory Active hook remains required.

`CreateWindowsDiscoveryFactory` performs pure validation and creates a delegate without opening a socket. An enabled port must be 1–65535. Both peer and pairing TCP listener addresses must be IPv4 Any. This ensures that the advertised service ports listen on every eligible IPv4 LAN link used by the sender. Loopback, a single selected address, IPv6 Any and mapped IPv6 Any are refused for automatic discovery; they can still use manual routing with discovery disabled. The policy does not infer LAN membership from an address: concrete Windows hardware/source filtering remains mandatory.

The transition root deep-copies endpoint values before validation/capture. Every generation receives the fixed factory; generation startup still supplies stable Host identity, operational pairing protocol and actual bound TCP ports. The delegate constructs only `WindowsLanDiscoveryReceiver` and `WindowsLanDiscoveryBroadcaster` at the explicit UDP port and transfers their lifetime to `HostDiscoveryRuntime`. No caller-selected native policy, destination, sender implementation or port fallback enters this concrete path. Received hints remain unverified and cannot create trust/grants.

A port collision or permission/configuration failure propagates from initial receiver startup before any sender loop launches. Only the separately qualified clean native availability marker permits bounded retries; collision/permission errors are not in that set. Pre-cancellation refuses before receiver acquisition. Generation ownership, complete cleanup and transition failure behavior remain as qualified by the [generation integration](v0.5-generation-discovery.md) and [runtime](v0.5-host-discovery-runtime.md).

Two ordinary scenarios cover disabled/valid/invalid port and bind combinations, including IPv6/mapped/single-address refusal. The concrete factory is also invoked while a real exclusive Any-IPv4 UDP guard owns the configured port: native receiver bind failure must be retained, with no fallback, before sender launch. The same guarded setup proves pre-cancellation wins before binding, and exclusive rebinding after guard release verifies no leaked socket. These automated calls do not send physical broadcasts. Successful uncancelled concrete discovery startup and delivery across physical machines remain field evidence; component/runtime loopback tests do not supply that proof.

The [component acceptance inventory](v0.5-peer-component-acceptance.md) maps current orchestration, retirement and local initiation evidence and distinguishes installed/field limits. Installed enablement/default configuration and physical qualification remain downstream. This change adds no wire RPC, client UI, credential/persistence writer, Linux implementation or release action.
