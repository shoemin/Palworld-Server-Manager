# Exact-key recovery completion receipt

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28), architecture4b-i step7.

`GrantPolicyRepository.ReceiveAuthenticatedRecoveryCompletion` is a trusted Host persistence primitive for one fixed security action. Its caller must supply the original completed connection's actual peer and local key fingerprints, semantic peer identity and relationship incarnation. Request-body fingerprints or IDs cannot establish that proof. This component adds no transport admission, negotiated RPC or public command; ordinary authentication and authorization remain unchanged.

The receiver requires the current initialized Host and Owner structure, the actual current local credential, Active peer trust and the exact current relationship incarnation. The actual peer key must match the current trusted key or an already durably staged key with complete rotation metadata. A matching acknowledged fingerprint must equal this Host's current local key. A mismatched acknowledgement records a closed audit/result and changes neither recovery nor grants nor the receipt. An old connection whose own local-key proof is stale is refused before this comparison.

A matching acknowledgement clears only `PeerRecoveryRequired`, if set. It invalidates outstanding unapproved candidates with the canonical transaction timestamp before trust triggers and captures the new incarnation. It creates no grants, changes no default template and never revives invalidated grant history. The existing roots created by [local Owner approval](v0.5-owner-peer-replacement.md) become usable only through subsequent current authorization checks. Every existing grant is compared unchanged at the final transaction boundary.

Schema16 adds an empty bounded `PeerRecoveryCompletionReceipts` table: one latest record per peer, with the remote approval ID, actual peer/local fingerprints, source/resulting incarnation and receipt time. Its composite foreign key binds the resulting incarnation to that exact peer, and retiring that incarnation deletes the receipt. An exact retry on the original held proof or current resulting proof is read-only, with no additional audit or grant. A later distinct completion on a fresh connection may replace the bounded receipt; an old held proof then needs to reconnect. An already-clear recovery state records and confirms the same harmless no-op. No address or general command queue is stored, and migration backfills no authority or acknowledgement.

During this exact recovery-clear transition, an existing outgoing approval marker may carry its `CurrentIncarnation` forward only when its original current incarnation, approved peer key and uncanceled state match the pre-receipt relationship. Its approval/source incarnation and local fingerprint at approval stay historical. This prevents the incoming half of mutual completion from immediately stranding a still-valid outgoing approval. [Local offline recovery](v0.5-offline-recovery-completion-continuity.md) now supplies its own separate qualified continuity transition while preserving recovery.

The receipt preserves all staged rotation and reconfirmation metadata. A durably staged New peer key remains valid evidence after lapse, but the receipt does not promote it. After recovery clears, a fresh ordinary connection uses the existing canonical observation path to promote an actually presented New key. An Old-authenticated receipt cannot claim that New was observed or clear the rotation's separate reconfirmation requirement. The old source-incarnation proof stays stale for ordinary use after the recovery clear.

After its audit, the receiver rechecks authorization revision, unchanged grants, exact trust/candidate/proof/binding/pairing/unpair-receipt/approval-marker/recovery-receipt/incarnation rows, current local credential, receipt incarnation, audit contents and cancellation. A late inconsistent effect rolls back the entire transaction, including a maliciously induced recovery clear during mismatch auditing.

Nine persistence scenarios cover exact-key clearing without new grants, no-op and bounded duplicate behavior, mismatched/second-recovery keys, stale/foreign/revoked/PeerBound proof, Old and staged New rotation preservation, exact outgoing-marker carry, fourteen late-effect/audit rollback cases plus mismatch-clear rollback, concurrency/cancellation, and an empty migration with a cross-peer incarnation refusal. The fixtures explicitly supply database identities and trusted proof objects; they do not qualify a complete native TLS/PAKE-to-Owner-approval completion ceremony.

The [fixed native sender](v0.5-recovery-completion-sender.md) is separately qualified. Generation-owned invocation/retry coordination, public commands and full two-Host repair remain subsequent #28 work.
