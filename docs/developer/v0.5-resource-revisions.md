# Transactional editable-resource revisions

Trial reference: #46b. ConfigurationRevisionRepository compares the expected revision and persists an editable aggregate's database changes plus revision advance in one immediate Host SQLite transaction. Stale writes fail before the trusted action runs; there is no automatic retry, merge or command queue. This bounded concurrency seam does not expose a settings RPC or complete #46.

EditableResource combines a bounded code-defined aggregate name with the explicit HostTarget or ServerTarget from the [operation definitions](v0.5-operation-definitions.md). Canonical storage keys retain the target discriminator and complete Host/server identity. Separate aggregate names and equal profile IDs on different Hosts remain independent. Revisions use the existing ConfigurationRevisions table; missing means initial0, a successful write advances exactly once, and long exhaustion refuses. This API never deletes/resets revision history. Old unqualified rows are untouched; this is not a data migration. Canonical permission grants retain their separate AuthorizationRevision engine.

The caller holds the machine exclusivity lease. Read/write entry verifies the current initialized destination Host and its single active Owner; foreign targets refuse. This does not authenticate or authorize the initiating actor. The trusted Host database writer must check actual current actor/capability, mutate its own resource/audit within the supplied transaction, and return a mandatory read-only final validator for its current proof and exact effects. The repository owns transaction completion: callbacks must not commit, roll back or dispose the supplied connection/transaction, and the final validator must not write. The rollback guarantee assumes that trusted callback contract; this is not a sandbox for arbitrary callback code. Client requests cannot supply such callbacks or register aggregate kinds. A revision observation alone never supplies authority.

The repository compares before the action, rejects action-side revision changes, advances the token conditionally, runs the final validator, then rechecks current Host and exact revision/time before cancellation check and commit. Action, validator, SQL, malformed stored token, overflow, stale conflict or cancellation failures roll back the whole transaction. Nontransactional filesystem/process effects belong to the durable operation framework, not this database edit seam.

Six actual SQLite scenarios cover qualified resource separation and reopen, eight competing connections/one winner, stale-no-callback behavior, action/missing-validator/final-proof/cancellation rollback and retry,14 later revision-trigger faults across insert/update, invalid/noninteger/exhausted/missing storage and current Host refusal, committed WAL reader visibility and final Host change rollback. Payload/event tables and final proof refusal are explicit representative fixtures; they do not claim actual server settings, permission authentication or business audit integration.

The assembled lifecycle, workers, startup recovery, Activity contracts and installed lifetime are covered in [component acceptance](v0.5-operation-component-acceptance.md). No concrete destructive resume classification is invented. Accessibility WAIVED, never PASS; physical Windows parity/Palworld/Linux/release gates remain. The Astra trial used no external GitHub Codex reviewer. Astra was responsible for both implementation and technical review.
