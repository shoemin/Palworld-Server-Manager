# Windows LAN interface and source policy

Trial reference: #44aa, within #44. `WindowsLanInterfaceSource` supplies fresh, read-only observations for Windows LAN discovery. It correlates managed adapter GUID/index and preferred IPv4 unicast addresses with the native interface identity and connection state. A query failure, missing identity or changed index/GUID association cannot qualify an adapter. It neither opens a socket nor changes network settings.

Eligibility requires Windows-classified hardware with a physical connector, connected/enabled operational state, dedicated broadcast send/receive access, no tunnel and a known Ethernet or WLAN medium. Filter, endpoint, unauthenticated, disconnected, paused and low-power flags are excluded. Ethernet-looking names, private addresses and interface type alone are insufficient. Unknown physical media remain excluded; manual address entry remains available. The reader uses [GetIfEntry2](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-getifentry2) and the documented [MIB_IF_ROW2 fields](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/ns-netioapi-mib_if_row2), checked against the installed Windows SDK.

The neutral `LanDiscoveryLink` stores the observed LUID, GUID, index and IPv4 host/subnet as immutable values. It accepts prefixes 1–30 and excludes subnet endpoints, 0/8, loopback, multicast and class-E IPv4 addresses. It does not apply a blanket registry-based special-address filter; eligibility also depends on the observed hardware link and subnet. It computes a subnet-directed broadcast address and admits a received source only when the actual receiving interface index matches and the source is another allowed host in that subnet. Network, broadcast, self, out-of-subnet and IPv6 sources do not pass this IPv4 policy. Address objects returned to callers are independent copies. At most 256 address observations are considered, with duplicate links collapsed.

These are current observations, not persisted route identities or authentication. The later UDP owner must refresh policy as interfaces change, use actual packet interface/source information, constrain sends to eligible links and own shutdown. An interface index can be reused; callers must not reuse old observations as authority after a network change. No automatic VPN/non-LAN discovery, DNS-based trust, pairing secret, grant or trusted-Host mutation is introduced. Scoped IPv6 and other media require separate platform handling.

Three ordinary scenarios exercise subnet/source refusal, every interface flag combination and identity correlation, bounded observations, managed native-layout checks and real read-only Windows queries, including loopback and invalid-index cases. An independent C++ probe compiles the SDK's structure and checks its size, offsets and hardware/connector bit layout. Run `scripts/test-windows-lan-abi.ps1` and the self-test `--windows-lan-interfaces-probe`; isolated CI runs the SDK probe before the full ordinary suite. The first local SDK compilation needed explicit networking headers; the corrected probe passes. Tests do not broadcast or require an eligible physical NIC, so a VM with zero eligible links does not become physical-LAN field evidence.

The [unverified discovery directory](v0.5-host-discovery.md) remains separate from this platform policy and authoritative trust. The [owned Windows receiver](v0.5-windows-discovery-receiver.md) applies fresh policy to actual packet sources, and the [constrained sender](v0.5-windows-discovery-sender.md) rechecks each exact link after socket setup. Host composition, periodic broadcasting, locally authorized initiation, key retirement and remaining crash/multi-machine acceptance still follow. Linux remains gated on Windows parity.
