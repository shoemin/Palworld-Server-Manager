# Pinned rotation proposal delivery and acknowledgement history

Trial reference: #44o, within #44. `StageRotation` uses separately negotiated `PeerRotationProposal` capability 7 at protocol 1.5. Immutable host-v1-5 and peer-security-v1-5 descriptors preserve earlier snapshots. The Host sends only an already Owner-prepared immutable proposal; the ordinary client never owns this transport, key or direct remote route. This unit does not cut over Current, retire keys or implement the promotion-receipt exchange.

The outgoing Host reads its current pre-cutover proposal, creates a fresh random request ID and opens a new bounded pinned mutual-TLS HTTP/2 round. Negotiation must identify the expected peer and proposal capability. The actual local TLS key must be the proposal's Old key, and the proposal is rechecked before sending. The receiver requires Active, non-recovery trust on every request, binds proposal.HostId to the negotiated peer UUID and delegates completed actual peer/local TLS fingerprints to the staging transaction. Both the currently trusted peer key and the receiver's current local Host key must match. PeerBound, wrong UUID, stale local presentation, invalid identity/sequence and expired/replayed proposals cannot bypass the existing staging policy.

The receiver durably accepts through [ordered staging](v0.5-rotation-staging.md), with its own audit and deadline. It echoes the exact request and a closed result: staged, already staged, reconfirmation required or promotion receipt pending. Successful responses identify the exact proposed rotation; blocked results preserve the previously retained rotation and report zero current acceptance. Repeated proposals retain their original receiver deadline. Lapsed state and outstanding receipts cannot be overwritten. No grants/defaults/Current change.

Acceptance time is a bounded remaining duration computed from the receiver's own clock, never a UTC timestamp assumed comparable with the sender's clock. The sender validates the zero-to-thirty-minute range and subtracts its entire local monotonic elapsed exchange time, including connection, request and local recording time. The process-local result decreases conservatively and latches expiry/clock anomalies so they cannot revive a bound. It is not persisted or restored as authority across restart. Separate Hosts with unrelated UTC clocks still agree only on this conservative duration.

For an actual staged/already-staged reply, the sender's `RecordRoutineRotationPeerAcknowledgement` rechecks initialized current pre-cutover state, the immutable proposal, actual local Old and actual Active non-recovery peer key in one transaction. It records first Staged/Acknowledged timestamps in the existing per-peer history table with a remote-peer audit. Concurrent/repeated acknowledgements record one first event; audit failure rolls both back. A concurrent Owner abort refuses recording even if the other Host already staged. Missed abort delivery can then resolve through the peer's existing live status query.

**This history is not current cutover eligibility.** It only establishes that this peer acknowledged this rotation at least once. It never moves a rotation to ReadyForCutover, changes Current or deletes Old. The eventual global engine must freshly verify all remaining Active peers and their current acceptance bounds, resolve old-pinned PeerBound relationships and recheck dynamic trust. A previous timestamp, sender restart, wall-clock change or historical row cannot satisfy that gate by itself.

Six ordinary scenarios cover real concurrent proposal delivery with unrelated UTC clocks, exact retry deadlines, a genuinely lost post-response acknowledgement, sender audit rollback/retry and listener restart, lapsed/receipt blocks, capability and current identity gates, altered correlation/unknown enum/oversized duration, and concurrent abort followed by actual live status cleanup. A deterministic result test checks conservative elapsed-time expiry. The shared reply-fault fixture reads a real reply after completed TLS before altering or dropping it; it does not fabricate proof. Receipt-pending and Active preconditions are explicitly synthetic at setup, not a complete global rotation or physical/process-crash claim. Existing status fault tests also exercise that shared fixture.

Proposal acknowledgement history, bounded reply data and receiver staging are now available. Promotion receipt transport, fresh global cutover/retirement eligibility and orchestration, installed service/local initiation, automatic scheduling and complete integration/field qualification remain outstanding.
