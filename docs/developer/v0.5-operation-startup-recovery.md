# Explicit operation startup recovery

Trial reference: #46e. Startup recovery uses the [durable operation repository](v0.5-durable-operation-lifecycle.md) and [Host-owned workers](v0.5-host-owned-operation-workers.md). It applies trusted, code-defined handlers to the exact saved phase; it does not guess whether a concrete backup, restore, update or transfer is safe to resume. [Installed Host lifetime composition](v0.5-operation-host-lifetime.md) now owns the framework; installed Activity RPCs remain later vertical work.

An executor registration may provide explicit retry, resume and discard handlers for dispositions present in its definition. Registrations are immutable copies. Manual, unknown, duplicate and inapplicable handler declarations refuse. A missing handler never falls back to the ordinary executor. The kind author must advance the definition's semantic version when phase meaning changes; persisted fingerprints prevent a changed declaration from silently qualifying older work.

Construction inspects authoritative state. Existing nonterminal work blocks new admission until `ApplyStartupRecovery` has classified it. An empty startup is immediately usable. Initialization reads every current nonterminal Host/server record and runs only once per Host runtime; newly admitted or subsequently failed work is not swept into a retry loop. Manual, missing-handler, unknown/changed-policy and inconsistent state is held as Recovery Required. A terminal record still owning a lock also remains a recovery problem. Malformed persisted state fails closed, never by deleting evidence.

For an eligible record, preparation requires its exact current revision and declared disposition in the same transaction as the update. Retry resets only to the registered initial phase. Resume and discard retain the saved phase. The same operation ID, target and exact owned lock survive, while revision and heartbeat advance. Current Host/Owner checks, the handler's trusted current-authority callback before/after writes, definition qualification, exact effect checks and cancellation guard the commit. Stale, wrong/manual/unknown disposition, SQL faults or authority refusal cannot prepare work or dispatch its handler.

The chosen handler then runs as a tracked Host worker using the Host's own stop token. Discard must perform actual cleanup before explicitly committing its terminal phase; the framework never invents a Failed phase or releases its lock in a catch block. A failed preparation is held for recovery; a dispatch failure after preparation retains the prepared locked record. A handler that throws, stops or returns nonterminal retains state and becomes Recovery Required. Repeated initialization cannot retry it in the same runtime. Shutdown drains recovery tasks under the same ownership rules as ordinary tasks.

Recovery authority callbacks are trusted read-only Host code and cannot end their supplied transaction. Handlers retain responsibility for actual business authority, durable inputs, audit and awaited effects at each boundary. No client-supplied callback, implicit machine/admin authority, concrete destructive recovery policy or offline queue is introduced. Exactly one runtime belongs to the authoritative Host lifetime, outside replaceable listener generations; actual production integration must initialize recovery before exposing ordinary operation admission and retain the machine lease through worker drain.

Eight new ordinary scenarios verify exact preparation across both targets/scopes, six SQL faults and four authority/cancellation rollback cases with retry, all four dispositions in different phases of one kind on both targets, cleanup-before-release under either scope, missing/changed/manual/damaged state with no dispatch, concurrent initialization without repeated execution, shutdown retaining prepared state, and late authority refusal rolling back only that preparation while another eligible record recovers. The existing eight real process-kill cases now also run explicit startup recovery after their atomicity assertions: only committed nonterminal work invokes recovery, the ordinary executor never runs, and resolved work releases its lock. The focused probe runs these eight scenarios plus that expanded process scenario. These are representative SQLite/worker/process fixtures, not physical reboot, installed business RPCs or real Palworld acceptance.

No schema, grant, credential, wire/client dependency, platform or Linux production change. Accessibility WAIVED, never PASS; physical Windows parity/Palworld/Linux/release gates remain. The Astra trial used no external GitHub Codex reviewer. Astra was responsible for both implementation and technical review.
