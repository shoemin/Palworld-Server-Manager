# Host operation lifetime composition

Trial reference: #46g. One trusted lifetime owner now coordinates [workers](v0.5-host-owned-operation-workers.md) and [startup recovery](v0.5-operation-startup-recovery.md) in the installed Windows Host root. The owner belongs outside replaceable listener generations, under the authoritative machine lease. It copies trusted executor registrations and never chooses test handlers for product work.

The installed root creates its owner before exposing the local listener. If the Host is already initialized, the owner constructs one operation runtime and applies startup recovery before ready access. If the Host is still Uninitialized, bootstrap-only startup remains available: no operation runtime or Owner is manufactured. Future ordinary operation dispatch must obtain `GetReady`, which rechecks canonical Host identity and Owner cardinality after initialization and performs recovery before returning the runtime. Repeated/concurrent access returns that same runtime, never a generic recovery retry. Normal repository methods still independently require current authority at every mutation.

The current product registry is deliberately empty because concrete operation verticals have not been implemented. Existing valid-shaped unknown Host/server records and locks therefore remain Recovery Required. No legacy kind silently acquires the meaning of a representative test definition. Malformed startup state fails closed; the lifetime retains its failure and refuses repeated initialization until it is restarted after explicit repair. Any allocated runtime remains owned for shutdown cleanup.

When the installed Host stops or its listener exits, operation disposal starts before waiting for generation shutdown. This signals Host-owned work promptly even if a connection is observing it. Generation resources and actual worker tasks both finish before the enclosing machine lease is released. Startup exceptions after owner creation also dispose the owner through the enclosing asynchronous lifetime. A client disconnect or listener generation by itself does not own or dispose the operation runtime.

Five scenarios cover bootstrap-only state followed by canonical persisted Owner initialization and eight concurrent ready readers; copied registrations; explicit recovery once; an empty production registry retaining both target types; missing-state startup failure held despite fixture repair; concurrent shutdown/access with actual worker cancellation and retained unresolved locks; and an independent real writer lease unavailable throughout blocked worker drain and available after it completes. Representative setup uses the canonical identity repository but does not claim a new bootstrap credential ceremony. Required Windows service integration separately exercises the changed installed root, including real bootstrap and restart.

This installs framework ownership and startup classification, not concrete Palworld workers or Activity RPCs. Future business dispatch still needs explicit registrations, current caller authority, durable inputs, audits and suitable recovery semantics; [Activity contracts](v0.5-operation-activity-contracts.md) remain observations requiring authorized publication. Installed service remains local-only. No grant/creator, credential ceremony, schema migration, network enablement, UI or Linux implementation change. Accessibility WAIVED, never PASS; physical PCs/reboot, Palworld, Windows parity, Linux and release gates remain.
