# Protected local Owner replacement decisions

Trial reference: #28. The local listener offers `LocalOwnerPeerReplacement` (18) with local protocol1.16. `ReadPeerReplacements` and `ApprovePeerReplacement` require that explicit feature plus local principal security on the same runtime-owned, native-bound TLS connection. A capable older-minor client may negotiate the feature. Trust-management or permission-management capabilities never substitute for the actual current local Owner.

Inspection returns a keyset page of at most16 unapproved, noninvalidated candidates. Each contains only its replacement ID, semantic peer ID, expected historical state/pin, proposed public pin and original verification/expiry times. It includes expired rows that have not yet been invalidated; the expiry is displayed truthfully and the canonical writer still refuses them. The page carries the current authorization revision and a continuation only when another row exists. The Owner is checked inside the same transaction as projection, and again before the read commits. Successful reads create no grants or audits. Denied reads use the canonical bounded denial audit. The page is neither an approval permit nor an immutable multi-page snapshot, and does not assert that a candidate remains approvable.

Approval accepts only an exact replacement ID and expected authorization revision. The Host derives the actual current Owner from its existing authenticated session and calls [the canonical replacement writer](v0.5-owner-peer-replacement.md). That writer rechecks fresh verified pairing evidence, current keys/incarnation, expiry, trust state and absence of a staged pending key. It atomically invalidates the old exact grant forests and sibling candidates, binds the approved key, applies currently configured defaults as fresh Owner roots, and records the actual approval plus each default-grant audit and durable completion marker. No prior grant is revived.

The response describes only the local approval and its revision/incarnation, changed flag and grant counts. It does not confirm reciprocal delivery or clear the peer's independent recovery requirement. A refreshed retry of the same still-current approval is idempotent; stale policy returns `Aborted`, invalid/superseded/expired candidate returns `FailedPrecondition`, non-Owner returns `PermissionDenied`, and changed authentication returns `Unauthenticated`. Internal failures return constant text without database details. No network participates in the approval transaction.

Ten qualification groups cover actual local TLS/native identity, feature/backport and immutable wire history, anonymous/uninitialized/non-Owner/capability-only refusal, changed Owner/verifier/native identity, exact old-grant invalidation and fresh defaults, unrelated peer preservation, stale/expired/staged/revoked/unproven requests, bounded pages, malformed/stale input, audit rollback, concurrent single winner, and dispatcher cancellation/owned-runtime/facade lifetime. Prior peer state and verified-binding evidence are explicit fixtures. Separately qualified genuine PAKE and native repair remain distinct from these RPC fixtures.

Public recovery initiation, online unpair preparation, dual-authority remote administration routing and unpair-specific actual remote hang/drop remain parent28 work. No ordinary client receives a Host private key, no new remote Owner surface or UI is introduced, and no physical Palworld/Windows parity/Linux/release acceptance is claimed. Creator six/limits remain approved; accessibility is WAIVED, never PASS.
