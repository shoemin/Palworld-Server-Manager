# Fixed receiving recovery offers

Trial #28q adds `ReadRecoveryCompletionOffer` and `ConfirmRecoveryCompletionOffer` to the Host-owned recovery service. This is the receiving component needed to return a passive Host's pending acknowledgment on an authenticated connection. The production reverse client and automatic contact triggers remain separate #28 work.

The peer hello is protocol1.14. Explicit feature16 `PeerRecoveryCompletionOffer` and feature15 `PeerRecoveryCompletion` are both required for these two RPCs. Only the recovery hello advertises them; ordinary negotiation still grants neither. Existing feature15 senders remain compatible, and an explicitly capable older-minor backport is accepted. The immutable `host-v1-14.pb` and `peer-security-v1-14.pb` snapshots retain every earlier descriptor.

The query names only the offering Host. The receiver derives the other Host, both actual keys and original relationship incarnation from its own live, serialized HTTPS/HTTP2 connection. It calls the canonical pending-marker reader. A pending response contains the original Owner approval ID and the exact approved peer fingerprint; absence means no pending obligation. Reading an offer writes no state and does not confirm anything. It never derives a reverse listening address from the incoming TCP source port.

Confirmation is the authenticated approved peer's positive receipt attestation. The receiver requires exact offering/receiving Host IDs, the actual peer fingerprint, the original approval ID and a closed `Recorded` or `AlreadyRecorded` result. A mismatched key, `KeyMismatch`, unknown/default outcome or another approval cannot confirm. The canonical confirmation writer independently rechecks current Owner, keys, trust, incarnation, original approval provenance and final transaction/audit guards. Only the existing confirmed timestamp and peer audit change; grants and the offering Host's independent recovery flag remain unchanged. An exact duplicate returns `AlreadyConfirmed` without another audit.

This attestation has the same trust boundary as the existing sender's authenticated positive response. There is no new bearer token or generic remote authority. A peer cannot confirm another relationship's obligation. A malicious currently approved peer can already lie in its positive response; confirmation gives that peer no additional grant or recovery-clear capability on this Host.

Receiving a matching acknowledgment can advance the recipient's relationship incarnation. Any subsequent affected phase must establish fresh TLS proof; a held session cannot recapture the new incarnation. A future reverse client must preserve original approval correlation, pass a well-formed differing fingerprint through canonical mismatch auditing, retain durable obligations after lost replies, and own fresh transports under one bounded lifetime. No automatic retry or complete reverse-client qualification is claimed here.

Eight ordinary test groups cover immutable wire history and closed shapes; actual native TLS offer/local receipt/fresh confirmation and independent mutual recovery; malformed/failed/foreign approval refusal and one concurrent confirmation winner; missing features and capable backports; no-pending read-only behavior; original-session refusal after a recovery clear; late audit/Owner/grant/marker rollback and changed current authority; runtime/channel/cancellation/disposal boundaries; and actual staged-key refusal without rotation promotion. Historical binding setup and test-only caller remain explicit fixtures. The separate [native repair](v0.5-native-repair.md) and [simultaneous own-key recovery](v0.5-native-own-recovery.md) scenarios qualify their stated genuine PAKE lifecycles.

Public initiating commands and actual remote process/network hang/drop qualification remain #28 work. No generic queue, ordinary management endpoint, private-key provider change, new grant, Linux implementation, Windows parity or release acceptance is claimed. Accessibility/screen-reader certification remains WAIVED, never PASS.
