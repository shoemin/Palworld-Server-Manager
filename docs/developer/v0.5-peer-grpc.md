# Pinned Host-to-Host activation RPC

Trial reference: #44f, within #44. The trusted Windows Host composition root can construct an explicit peer gRPC listener with a required transactional Active hook. This unit connects durable PeerBound trust to actual mutual TLS and activation. [First-contact PAKE](v0.5-peer-pairing.md) has a separate endpoint. Installed service startup is unchanged until local initiation/authorization, rotation and the canonical #45 default hook are composed. This pinned endpoint exposes no ordinary management, operation forwarding, first-contact pairing or unpair/replacement RPC.

The listener uses the [qualified TLS profile](v0.5-peer-tls.md): required client certificate/private-key proof, P-256 public-key pins, TLS 1.2/1.3, HTTP/2 ALPN, no renegotiation or resumption, and a ten-second handshake limit. Kestrel owns the SslStream callback; its supported client-certificate validation hook invokes the shared pin/validity policy. Its later connection middleware reads the actual negotiated TLS protocol, ALPN and client certificate, rather than trusting a request fingerprint. The local fingerprint comes from the listener's borrowed credential. Empty production hosting loads no external URLs or development diagnostics, and only the explicit endpoint is bound. Limits are 128 connections, sixteen HTTP/2 streams per connection and sixteen KiB per message.

Handshake admission recognizes live current or already-authenticated pending peer keys. A UUID claim still has to match that actual TLS key during negotiation, and trust is reread for every later RPC. Recovery-required, revoked and expired PeerBound relationships fail closed, even on an existing connection. A recorded pending rotation key remains recognizable after its staging window, as required by the architecture. Unapproved replacement candidates are not recognized.

The additive `PeerTrustActivation` feature was introduced at protocol 1.2 and uses explicit major/minor negotiation, never the product version string. The current pinned endpoint advertises protocol 1.5 and separately gates [live rotation status](v0.5-rotation-status-rpc.md) behind `PeerRotationStatus` and [proposal delivery](v0.5-rotation-proposal-rpc.md) behind `PeerRotationProposal`; PeerBound cannot use that Active-only capability. Each actual connection owns its negotiation state and serializes requests. Failed or repeated negotiation cannot establish a different identity on that connection. `Activate` requires that capability and a current authenticated peer, then delegates exact connection identities and the received acknowledgment to the [transactional activation seam](v0.5-peer-activation.md). Unrecognized result values are refused. Errors are bounded and omit request/exception details; production request logging remains disabled.

`PeerActivationRpcClient` is internal to Host and uses `IPeerHttpTransportFactory`. The existing Windows composition root selects the concrete factory that borrows the Host credential; shared RPC orchestration never chooses a Windows implementation. The helper accepts a manual HTTPS root address without user information, query or fragment; proxying and redirects are disabled. Each attempt owns a fresh handler/channel and has a fifteen-second total deadline. The platform's post-handshake stream filter checks mutual proof, HTTP/2 and the actual local/remote certificate fingerprints. A second connection inside the same round is refused, requiring a fresh negotiation attempt instead of reusing stale connection state. Certificate owners retain their handles until all borrowing attempts/listeners finish.

The outbound Host negotiates, sends its durable acknowledgment, then commits locally only after receiving the peer's acknowledgment. The receiver can commit first; a lost reply leaves the initiator PeerBound until a new pinned connection retries safely. No distributed transaction or old pairing code is needed. The hook is still mandatory and has no production no-op implementation; #45 owns canonical default-grant issuance. Only a future locally authorized Host action may dispatch this internal helper on behalf of an ordinary client.

Five ordinary test scenarios run real Windows Kestrel/gRPC/HTTP2/mutual TLS with isolated synthetic CNG keys and two independent SQLite stores. They cover discarded replies and listener restart, connection negotiation and wrong UUID/feature/version, fresh recovery/expiry/revocation checks, actual wrong-key TLS causes, message limits/cancellation, a recorded staged key and explicit refusal to reuse one transport after a second TLS handshake. Test hooks record only fixture transaction effects. Keys are deleted after listener/connection disposal. These are actual loopback protocol tests; they do not establish first-contact PAKE, process-kill/reboot behavior, production service composition or multiple physical machines. Run `--peer-grpc-probe` or the full suite; the ledger records exact local/CI/review evidence.
