# Pure authorization and delegation foundation

Trial reference: #45a. This is the first bounded authorization unit after [#44 component acceptance](v0.5-peer-component-acceptance.md). This page covers the domain rules. Later slices add [transactional grants](v0.5-transactional-grants.md), [configured defaults](v0.5-configured-defaults.md), [presets](v0.5-canonical-presets.md) and [Owner historical reissue](v0.5-historical-grant-reissue.md). Parent #45 remains incomplete for creator grants, remote mutations, failed-request auditing and Host enforcement; complete credential-replacement integration is separate.

`Core.Authorization` contains only BCL domain types. Host grants have one explicit TargetHostId and a HostCapability; server grants have a ServerCapability and the complete ServerRef(AuthoritativeHostId, ServerProfileId). The common grant base has no interchangeable capability/scope field. Immutable constructors reject empty identities, unknown enum values, self/empty parent IDs, non-UTC timestamps and onward-delegation rights without delegation. LocalPrincipal and RemoteManager remain distinct actor kinds even when their UUID values happen to match.

The domain ServerRef is the same canonical two-part identity represented separately across the accepted assembly boundary. `Host.AuthorizationContractMapping` explicitly maps it to/from the existing Contracts.ServerRef and maps only the five accepted Host and seven accepted Server capabilities from the wire. Core does not reference Contracts/protobuf; ordinary clients still cannot reach Core. These value conversions confer no authority.

`AuthorizationPolicy` copies trusted facts for one authoritative Host: its identity, optional structural Owner, active local principals, Active non-recovery peers, and separate Host/server grant forests. No request-provided Owner/trust flag or grant DTO may build this snapshot. A null Owner represents uninitialized authority and denies every ordinary check. An initialized Owner must be an active local principal; the Host cannot be its own peer. Grant objects describe data only: each use follows the entire current lineage, checking active actors, invalidation, exact parent/grantor/target/capability and delegation rights until a current-Owner root. Missing parents, cycles, invalid roots or inactive ancestors deny. Owner's authority is structural and is not revoked by removing a grant subtree.

Canonical `IssueHost` and `IssueServer` return an authorized grant candidate without mutating the snapshot or a database. A null parent requires the structural Owner. A delegated candidate requires its issuing actor to hold the exact valid parent, that parent's CanDelegate, an identical capability and target, the exact parent ID, and CanDelegateOnwardDelegation for either child delegation right. Rights from a sibling grant cannot be combined. ManagePermissions authorizes its own inspection capability only; it neither substitutes for this predicate nor supplies Owner status. Grantees must be active. Duplicate IDs within the same typed forest refuse; the two storage-backed forest types remain separate even if a UUID is reused across them.

HostSubtree/ServerSubtree return immutable, cycle-bounded, exact descendant plans. They include only the requested root and its descendants in that typed forest, not everything ever issued by the same actor. These are effect plans, not transactional revocation. The subsequent persistence unit must rebuild the policy from current authoritative facts inside its writer transaction, revalidate the authenticated actor/revision and atomically commit canonical candidates or invalidation with audit. Reusing a stale immutable snapshot for a later write is expressly invalid.

`RemoteAuthorization` composes two independent policies. The initiating actor must be an active local principal; the local Host must regard the destination as Active. The local check uses the exact remote Host/server target. Independently, the remote Host checks RemoteManager(localHostId) against that same target and its own active-peer facts/grants. Even the local Owner needs the remote machine ceiling. Passing a remote actor as the initiating local user, a same-profile different-Host target, or a pending/inactive relationship refuses. These are pure trusted-fact checks and do not replace native local authentication, pinned mTLS or fresh transactional Host enforcement.

Six ordinary scenarios exhaust all nine parent/child combinations of the three valid rights profiles across every accepted capability, check cross-Host and cross-server collisions, sibling-right/capability substitution, forged/missing/cyclic provenance, exact typed subtrees and inactive-ancestor denial, structural Owner/uninitialized and ManagePermissions behavior, all four local/remote allow/deny combinations, immutable input/output snapshots, duplicate IDs and unknown wire/domain enums. They establish pure rules only, not operational remote execution or persisted audit/default behavior. The manual native CI condition includes astra/45-* so each candidate also receives existing Windows/PAKE regression qualification. No Linux, UI, grant storage migration, server operation or release action is introduced. Accessibility remains waived.
