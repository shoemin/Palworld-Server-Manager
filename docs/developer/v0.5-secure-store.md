# Host secure credential store — Astra #27

`ISecureCredentialStore` is a Host-side Platform.Contracts seam. Windows uses DPAPI `LocalMachine` with a protected NTFS DACL for the dedicated service, elevated Administrators and SYSTEM. The Product Owner explicitly approved that recovery access for the isolated trial on 2026-09-05; it resolves the earlier service-only wording in architecture §7. Ordinary users, activation-group members and ordinary clients have no file access. [Microsoft's DPAPI scope documentation](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.dataprotectionscope?view=net-8.0) confirms machine scope is not user isolation, so encrypted blobs must retain their ACL boundary.

The Host remains the sole online writer. The exceptional Host.Cli caller must first stop the Host and hold the same machine-wide exclusivity lease. The platform store does not create a competing lease or an online CLI escape hatch. Composition supplies the trusted Host root/service identity, never an RPC path or actor SID. The default composition names the #41 service/root. This storage slice itself executes no bootstrap, recovery, pairing or migration. The [offline coordinator](v0.5-offline-coordinator.md) now consumes it for bounded bootstrap/recovery; pairing and migration remain later work.

## Format and lifecycle

- Keys are case-sensitive 1–128 character ASCII identifiers (`A–Z`, `a–z`, digits, `.`, `-`, `_`), never paths or secret values. A domain-separated SHA-256 becomes the filename and DPAPI additional entropy, binding a ciphertext to its exact key. Renaming a blob to another key does not yield that credential.
- Files live under the provisioned Host root's `credentials` directory, independently of executable/version directories. A `PSM1` envelope contains machine-DPAPI ciphertext; no raw secret or private key enters SQLite. Values from zero through 1 MiB are supported; missing returns null, distinct from an empty value.
- Store creates a temporary file with its exact protected ACL in the creation call, writes encrypted bytes, flushes it and atomically replaces the destination name on the same volume. Cancellation before replacement and replacement failure preserve the last committed value. A crash can leave an encrypted temporary file named for that key hash; it is never adopted automatically. A later store/delete for the exact key validates and retires those interrupted writes too. In-process operations serialize by trusted root; the caller's machine lease excludes other writer processes. Directory metadata/power-loss durability is not overclaimed beyond the filesystem/DPAPI guarantees.
- Root/store/blob owners and complete ACLs are validated before use. Inherited/unprotected ACLs, outsiders, denies, missing service/recovery access, directories substituted for blobs and reparse paths fail closed. Unsafe state requires explicit privileged repair; ordinary reads do not normalize it. Privileged malicious races, hard-disk access, memory dumps and full machine-owner compromise are outside the accepted protection claim.
- Missing delete succeeds. Delete/replace is logical retirement, not guaranteed forensic secure erasure of filesystem snapshots or backups. Corruption, wrong-key ciphertext and unrecognized/plaintext legacy formats fail; there is no plaintext fallback or silent repair. Future migration must record rejection and require fresh pairing when a secret cannot safely migrate.
- Callers own input/returned byte buffers and must clear them after cryptographic use. The Windows implementation clears its internal plaintext copy and any decrypted result rejected on cancellation/size. Metadata and filenames contain no literal key string or secret value; hashes do not conceal predictable key names from guessing, and length/timing are not hidden.

## Secret-marked diagnostics

Wrap sensitive diagnostic values in `RedactedSecret` **before** they reach logging/audit/diagnostic payloads. Its default formatting and JSON converter emit `[REDACTED]`; it exposes no public material property for ordinary destructuring. Diagnostic deserialization is rejected. `CopyBytes()` is an explicit cryptographic-only escape requiring caller-owned clearing; disposing clears the internal copy. Do not log the exported array, its base64, a raw input buffer or an exception containing a secret. This mechanism protects marked data, not arbitrary caller misuse or a custom malicious serializer. Raw private material is never a persistence DTO field.

## Verification and Linux handoff

`SecureCredentialStoreContractTests.Run(factory)` has no Windows API dependency and covers lifecycle/reopen, case-sensitive keys, overwrite, cancellation, empty/missing and idempotent delete. Windows tests add ciphertext/plaintext rejection, wrong-key/tamper checks, size/path limits, unsafe ACLs, failed atomic replacement and secret JSON/formatting checks. Real Windows integration runs as a virtual service, then as an elevated offline lease holder, restarts the service, checks reciprocal read/write persistence, rejects symlinks and proves two non-elevated users cannot read/write/delete the blobs. Service replacement/update uses the retained stable root; no executable-local encryption state is required.

Linux production remains gated by #55. The contract needs no GUI/keyring or Windows type. Its accepted future baseline uses a service-owned permission-protected plaintext master-key trust anchor and encrypted application secrets; root/offline-disk limitations remain explicit. Optional TPM/systemd-creds protection is not silently made a baseline dependency.
