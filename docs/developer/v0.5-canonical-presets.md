# Canonical preset expansion

Trial reference: #45d. A named preset is presentation data containing explicit proposed grants. Its label is never an authorization primitive, persisted role or free-text audit field. Built-in UI recipe membership remains a UI concern; this engine checks the expanded entries through the [canonical authorization rules](v0.5-authorization-foundation.md) and [transactional grant repository](v0.5-transactional-grants.md). [Owner historical reissue](v0.5-historical-grant-reissue.md) provides the ordinary canonical grant action used after separately approved credential replacement. Remaining #45 failed-request audit and Host dispatch work is still incomplete; complete replacement integration remains separate. The [approved six-permission creator policy](v0.5-creator-grants.md) supplies the Host confirmation/grant seam; actual server-creation workflow integration remains downstream. [Authenticated remote grant writers](v0.5-remote-grants.md) add the trusted incoming peer repository paths; Host RPC/outbound integration remains separate.

HostGrantRequest and ServerGrantRequest are separate immutable shapes with a new grant ID, grantee, exact typed capability/target, delegation rights and optional source grant. They have no grantor, Owner flag or previously authorized snapshot. Empty/unknown identities, capabilities and duplicate per-type grant IDs refuse. Preset collections are copied and read-only. As with the storage forests, the same UUID may identify separate Host and server grant records without allowing a cross-type parent.

`AuthorizationPolicy.ExpandPreset` calls the existing IssueHost/IssueServer predicate for every entry against the original snapshot. An Owner applier produces independent Owner roots with null parents, irrespective of proposed delegated sources. A non-Owner must hold each exact source already in that snapshot, including its capability/target and delegation/onward rights. Earlier candidates cannot supply authority to later entries in the bundle. A label such as Host Administrator does not create permissions, and ManagePermissions does not replace per-entry delegation. Expansion returns immutable candidates without writing or changing the original policy.

`GrantPolicyRepository.ApplyPreset` checks current authenticated local identity and expected revision in an immediate writer transaction, validates the entire expansion before inserting anything, then writes each canonical grant and its actual-actor/provenance audit. A generated public batch ID correlates the audit records; it is neither a stored role nor a long-running operation identity. The label is omitted from audit and diagnostic output. Final actor, revision and exact persisted-row checks plus cancellation precede commit. Any invalid entry, failed audit or changed source/identity rolls back the entire bundle. An empty preset is a current-identity/revision-checked read-only no-op with no audit batch or permission removal.

Six pure/SQLite scenarios cover immutable typed proposals and Owner-root normalization, no within-bundle authority creation, mixed Host/server persistence and exact audit correlation, wrong source/target/capability/onward rights and ManagePermissions refusal after an otherwise valid entry, stale verifier proof, second-entry audit failure and actor/source mutation rollback, eight concurrent two-entry presets with one winner, exact later subtree invalidation and empty/cancelled behavior. No schema, transport, platform, UI or operation is introduced. Existing configured pairing defaults retain their separate canonical Active-time path. Accessibility is waived, not passed; installed operational, physical parity, Linux and release qualification remain downstream.
