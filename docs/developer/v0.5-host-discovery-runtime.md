# Owned Host discovery runtime

Trial reference: #44ae, within #44. `HostDiscoveryRuntime` owns periodic sending, receiver recreation and the unverified directory behind the neutral platform seams. Trusted composition supplies public HostId/protocol metadata and actual bound peer/pairing ports. The codec validates these fields; no secret, private credential, grant or authoritative writer enters this runtime. It does not negotiate protocol capabilities or authenticate advertised identities.

Startup validates before acquiring the first receiver. A successfully returned receiver transfers to the runtime, including when startup cancellation races construction. The factory must clean partial acquisition before throwing. Unknown startup failures propagate after acquired-owner cleanup; a known clean temporary availability failure allows startup with a delayed receive retry. The startup cancellation token applies until ownership is returned; the caller must own/dispose the returned runtime.

One serial receive loop owns one receiver at a time. Failed receivers are fully disposed before recreation. Only a top-level `LanDiscoveryUnavailableException` permits a fresh attempt after three seconds; a matching repeated Completion exception from receiver disposal is observed once. A different disposal failure becomes fatal, including a disposal-only unavailable marker. The loop never searches aggregate inner exceptions for a retry reason. Unexpected successful receiver completion, unknown errors and unrelated cancellation are fatal.

One serial sender loop awaits the entire broadcast round before a three-second delay. It also retries only the clean temporary marker. There is no overlapping send, catch-up scheduling, work queue, destination override or fallback interface. Socket acceptance is not remote delivery. Failed retries never make a discovery hint trusted. The native [receiver](v0.5-windows-discovery-receiver.md), [sender](v0.5-windows-discovery-sender.md) and [availability boundary](v0.5-discovery-availability.md) retain their own concrete filtering/cleanup obligations.

Stop closes directory admission and queries immediately. A separate stop signal begins receiver disposal without waiting for cancellation callbacks to run. This matters when a sender cancellation callback is blocked: cancellation callbacks are still awaited, but cannot prevent receiver shutdown from starting. A known fatal receive failure closes admission and stops the other loop before waiting for receiver disposal. The supervisor observes both loops, requests the same one-way stop when either fails, and completes only after the loops, receiver callbacks/disposal, in-flight sends and owner cancellation callbacks are drained. Concurrent/repeated disposal returns the same terminal result. Independent failures are retained together; identical exception objects are not duplicated at the supervisor boundary. There is no timeout-based claim of quiescence. Callbacks must not await disposal of their own owner.

Received packets enter the existing [directory](v0.5-host-discovery.md) only while admission is open. The trusted receiver supplies actual source information after LAN qualification; the directory keeps bounded, conflict-preserving, twelve-second monotonic hints. Snapshots contain only unverified values and closed-runtime queries refuse. Pairing still proves the code-confirmed Host identity against actual TLS before any zero-authority PeerBound record; discovery has no path to grants.

Six ordinary scenarios cover startup validation/failure/cancellation cleanup, metadata/source/expiry, controlled-clock retry spacing and fresh ownership, no overlapping/catch-up sends, blocked stop activity, fatal and simultaneous cleanup errors, and actual Windows loopback UDP plus exclusive port release. An initial blocked-cancellation test exposed delayed receiver-disposal initiation; the separate stop signal fixes it. All physical-LAN selection remains the production platform implementation's responsibility; loopback mechanics and synthetic faults are not field proof of adapter recovery or multi-machine discovery.

The [generation integration](v0.5-generation-discovery.md) now owns a configured runtime before readiness, supplies operational protocol/actual bound ports, observes unexpected completion and drains it before rotation/cutover. Installed service enablement remains separate. Local initiation/authorization, installed configuration, safe key retirement and full crash/physical acceptance remain outstanding. No new local RPC, UI, Linux implementation or release action is included.
