# Durable reciprocal activation

Trial reference: #44e, within #44. The activation partial of `PeerTrustRepository` implements each Host's local transaction after authenticated reciprocal identity evidence. Actual gRPC/local initiation composition, rotation and the #45 default-grant provider are still outstanding. Nothing opens a listener or automatically activates production trust in this unit.

`PrepareActivationAcknowledgement` reads durable PeerBound/Active trust and produces the sending Host UUID, recorded peer UUID and recorded public fingerprint. Merely sending it changes no state. The Host must send and receive these messages over completed pinned mutual TLS; a message DTO is not proof. The separate peer/local fingerprint arguments must come from that actual connection, never request fields or an earlier RPC's cached identity.

`AcceptActivationAcknowledgement` starts an immediate SQLite transaction. It checks the initialized Host/current credential and Owner cardinality, acknowledgment identities, exact local connection fingerprint, the live current or authenticated pending peer pin, recovery status, and original PeerBound deadline/local-binding proof. An unapproved replacement candidate is never a trusted pin. Unknown/revoked peers, expired pending trust, missing historical binding proof, changed local credentials and recovery-required relationships cannot activate. Ordinary activation cannot clear a recovery gate. Existing Active retries preserve grants and do not rerun the hook, even after the former pending deadline.

The local Active transition, required `IPeerActivationHook`, and public-only terminal audit commit in one transaction. A hook or audit failure rolls everything back. The deadline is checked again before commit so a slow hook cannot extend it. Expiry cleanup remains the existing scheduled-service seam, `ExpirePending`, which retains tombstones. Independent Hosts commit separately; one can be Active while the other's acknowledgment remains undelivered. Both can construct and retry acknowledgments from durable trust without an old PAKE code.

There is deliberately no production no-op hook. #45 must implement canonical configured-default issuance using the supplied connection and transaction, including its current authorization/provenance rules. It must not commit independently, make remote calls, or create effects outside that transaction. The required hook is a trusted Host component, never supplied by a remote request. No grant evaluator, template semantics or grant rows are implemented here. At most one committed initial activation invokes its hook; failed transactions may invoke it again during retry, with all prior database effects rolled back.

Four ordinary tests cover two independent SQLite stores with asymmetric progress, fresh connections and lost-reply retries; concurrent activation and atomic hook/audit rollback; identity/key/recovery/replacement/expiry refusals; and missing historical proof plus deadline crossing during a hook. Existing grants survive Active retries unchanged. Test hooks write only transaction-local fixture effects and are not production providers. Synthetic connection fingerprints qualify persistence semantics, not TLS, process-kill recovery or multi-machine gRPC. Actual TLS is separately qualified by #44d; complete #44 integration/field evidence remains required. Run `--peer-activation-probe` or the ordinary suite.
