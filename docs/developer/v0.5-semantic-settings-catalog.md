# Semantic settings catalog

Trial reference: #47. The additive Core `Settings` namespace introduces immutable `PalworldSettingDefinition` metadata and constant-code structured validation. It has no UI, transport, filesystem or Host dependency. The existing legacy schema remains unchanged and supplies canonical names, categories and descriptions; case-insensitive lookup returns the canonical known key. This component is consumed by later Host DTO mapping, not directly by ordinary clients.

The initial explicit semantic definitions follow accepted #36 examples: fast travel boolean, experience multiplier, DeathPenalty's four known choices, server player integer, Huge Egg time in hours, server name/description text and two password settings. Crossplay is known compound data with no invented exhaustive choices or destructive parser. Other recognized keys retain their baseline description as unclassified Raw; unknown keys also remain Raw. Neither prefixes nor a current string value infer semantics. Unsupported semantic editing returns `Unsupported`; the later document layer must preserve unchanged values, including future enum choices and compound tokens.

No range, step, default or restart rule is supplied without authoritative data. Numeric validation checks invariant syntax and finite representability, not game ranges. Integer validation does not invent a machine-integer or domain maximum. Negative values are not rejected without an established domain constraint. Typed text accepts punctuation/Unicode but no control characters or line breaks; serialization still belongs to the later project-owned document layer. Validation takes decoded semantic input, not a raw INI expression, and does not modify it. Choices are immutable and exact; booleans explicitly accept True/False without truthiness coercion.

Generic assignment to either password setting always returns `ExplicitSecretActionRequired`, including null/empty text. Sensitivity is nullable: unclassified Raw metadata has unknown sensitivity, never a false assertion that a future value is public. Later Host operations must distinguish unchanged, replacement and explicit clear and redact stored/default/effective secrets; only a positive nonsecret classification can authorize normal value presentation. A result holds only the setting key and a closed error code, never the submitted value. Core metadata supplies no installation default or effective-state observation.

The owner approved the later Host authorization mapping on 2026-10-10: `ViewServer` permits nonsecret `GetSettingsSchema`/`GetServerSettings` reads; `EditSettings` permits `SaveSettings`. Both use the exact `ServerRef`. Neither capability grants the other, so a fully navigable editor needs both. Remote requests independently require the originating user's corresponding permission and the receiving machine ceiling. Stored passwords remain hidden. This decision does not add an endpoint, grant or creator right to this Core component.

This bounded catalog component does not complete #47. The additive [preserved settings document](v0.5-preserved-settings-document.md) now composes the existing parser for lossless in-memory edits of supported source. Remaining established semantic definitions, Host mapping, protected read/save routes, file encoding, revision checks, stopped-state/operation ownership and durable save/recovery qualification remain mandatory. Existing legacy parser serialization trims token whitespace; it cannot itself be claimed as lossless unknown/comment preservation. Frozen WPF behavior is unchanged. No new UI, Linux or release claim is made; accessibility certification remains WAIVED, never PASS.

The Astra trial used no external GitHub Codex reviewer. Astra was responsible for both implementation and technical review.
