# Dynamic peer-set freshness for rotation

Trial reference: #44q, within #44. A rotation's peer set changes as trust is created, activated, recovered, promoted, expired or revoked. Comparing only current field values can miss a peer that changes and later returns to the same values while acknowledgements are collected. Migration 5 adds a durable monotonic `PeerTrustRevision`, with transaction-coupled triggers covering every insert, update and delete on `TrustedManagers` and `TrustedManagerPairings`.

The revision is local bookkeeping, not a peer acknowledgement or timestamp. Upgrade starts it at zero without changing existing trust, grants, deadlines, history or audit. Each subsequent affected row mutation advances it; even an update restoring identical values advances it. Multiple changes in one transaction can advance it multiple times. A rollback also rolls back every advance. Missing, invalid or exhausted revision state refuses affected trust writes before they can commit. The integer cannot wrap or silently become a floating-point value. Ordinary trusted writers need no separate call that could be forgotten.

`ReadRoutineRotationPeerSet` reads one consistent transaction containing the revision, an already Owner-prepared immutable pre-cutover proposal, and every non-Revoked peer. It validates initialized Host identity, Owner cardinality, current Old/proposal state, closed peer states, semantic peer IDs and public fingerprints. Recovery-required peers and unresolved PeerBound rows remain visible; an elapsed pending deadline is not silently treated as durable revocation. Existing expiry maintenance must actually resolve it. Missing legacy local-bound proof remains unknown, never inferred from the Host's current credential. Malformed pending deadlines and local self-peers are refused. The returned list is immutable.

This is public read-only context. It does not establish current cutover eligibility, create a permission token, collect remote proof, persist fresh acceptance bounds, move a rotation to Ready or change Current. The upcoming coordinator must obtain actual bounded acknowledgements, include peers activated after preparation, resolve pending relationships, and recheck both this revision and all other current predicates in its final transaction. A saved snapshot or a matching wall-clock timestamp never substitutes for that work. No-op or cosmetic trust updates may conservatively require a new collection.

Six ordinary scenarios cover additive schema-4 upgrade without invented evidence, rollback, identical-value ABA, pairing metadata insert/update/delete, concurrent peer creation, missing/invalid/exhausted counters, pending/recovery/legacy state, real observer audit rollback, immutable lists, unprepared/aborted proposals, invalid peer identity and initialized one-Owner scope. The existing schema-3 proposal-upgrade fixture is pinned to migration 4 so it continues testing its original boundary. Current-schema paths run all migrations. No process-kill/reboot or physical multi-machine evidence is claimed here. Fresh acceptance evaluation, global quiescent cutover/retirement, local/service composition and complete #44 qualification remain outstanding.
