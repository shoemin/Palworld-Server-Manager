# Owner recovery transactions

Astra #42d1 implements the persisted two-phase Owner recovery from [architecture section 2b](v0.5-architecture.md). It extends the [local enrollment transactions](v0.5-local-enrollment.md), preserving the existing schema and project graph. The [protected handoff foundation](v0.5-owner-handoff.md) supplies intended-user artifact delivery. The [offline coordinator](v0.5-offline-coordinator.md) implements privileged preparation and the [local security RPC adapter](v0.5-local-security-rpc.md) binds online completion. The [production Host service](v0.5-host-service-composition.md) exposes this adapter; [ordinary-client composition](v0.5-client-security-composition.md) is implemented and final multi-user recovery qualification remains #42d3c3; persistence fixtures do not satisfy those gates.

## Preparation and completion

Preparation methods belong exclusively to a trusted offline caller that must check actual Administrator privilege and hold the machine lease while Host is stopped. The online Host adapter has no method for preparing either ticket. Both preparations require an initialized Host with exactly one active Owner and accept only bounded future deadlines of at most 24 hours. They persist keyed verifiers, never raw secrets, and audit in the same transaction.

A rotation ticket captures the current Owner's principal ID, native identity and exact public key. Completion requires its correct secret and native identity, an unexpired/uninvalidated ticket, the same current Owner/key and a valid different P-256 public key. It replaces only that row's public key, consumes the ticket, invalidates dependent outstanding recovery tickets and audits atomically. The principal ID, Owner flag and Active state remain unchanged. The client's previous private key is not required; the intended-user handoff supplies the proof for this exceptional path.

A re-home ticket captures both the current Owner's ID/key and the exact target native identity's prior state: absent, Active with a particular ID/key, or Revoked with a particular ID and no key. The target must differ from the current Owner. First consumption rechecks both snapshots inside the writer transaction. An already-active replacement must submit its existing public key; a new or revoked replacement registers a fresh client-generated key. The transaction fully revokes the prior Owner, clears its key and Owner flag, applies the grant cascade, creates or reactivates/promotes the intended replacement, records its result ID, invalidates dependent tickets on both affected identities, verifies exactly one active Owner and audits. Other connections can observe only the committed state before or after this transaction.

The old Owner's held grants and their `DerivedFromGrantId` descendants are invalidated in both grant tables. Independent root grants previously issued by that Owner to other actors survive: `GrantedByActor` is attribution, not an extra provenance parent. Re-home grants no extra capability rows and never reactivates previously invalidated grants on its target. The Owner's new structural authority follows only its persisted Owner flag.

## Stale tickets and lost responses

Preparation does not silently cancel another still-valid recovery choice. When one completes, changing the Owner key or either re-home identity, it permanently invalidates other outstanding tickets dependent on those rows in the same transaction. This covers competing rotations, competing re-homes, rotation versus re-home, target revocation/reactivation, a formerly absent target becoming enrolled, and full ABA cycles where a key or target state later matches an old snapshot again. Snapshot comparisons remain additional fail-closed checks.

Correct consumed-ticket retries return the original principal ID indefinitely, even after expiration, later credential changes or another Owner re-home. They do not reinstall an old key or Owner, repeat the grant cascade or emit another completion event. Wrong secrets/native identities remain rejected. Client key generation and result binding must preserve the original key across lost responses, as required by the existing client credential-store contract.

The online adapter uses the independent secure-store HMAC key with distinct OwnerRotation/OwnerRehome purposes. It never reads a client private key, writes a new HMAC key or uses an old machine credential as proof for replacing that machine credential. Owner credential recovery and machine-identity loss/compromise recovery are separate flows; the latter is still offline-only composition work.

## Validation

Isolated tests use actual SQLite transactions and public-key authentication with synthetic native identities. They cover wrong/expired/malformed inputs, concurrent rotation consumption, audit-failure rollback, all three re-home target states, old-client denial and new-client authentication, indefinite retries without repeated effects, competing recovery choices, credential and target ABA, recovery after target enrollment, and independent-root versus descendant grant behavior in both grant tables. Offline preparation and online completion have distinct audit events without secrets. The handoff adapter has its own Windows integration checks; the offline coordinator has actual Windows privilege/lease checks, while the final multi-user recovery ceremony remains later qualification.
