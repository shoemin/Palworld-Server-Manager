# Durable pre-write permission denials

Trial reference: #45h. Authenticated permission-policy mutation refusals now produce a durable `PermissionPolicyDenied` audit event without committing any requested authority change. This covers local/remote direct grants, local/remote presets, Owner default configuration, Owner historical selection, Owner Host/server subtree invalidation and creator permission/new-identity checks before the confirmation callback. [Current capability-use evaluation](v0.5-capability-use.md) is now implemented; [authenticated Host dispatch](v0.5-authenticated-permission-dispatch.md) is implemented; the [component acceptance inventory](v0.5-authorization-component-acceptance.md) records the qualified engine; this is not a new RPC or operation executor.

The repository first validates actual current local or remote Host-owned proof and expected permission revision. Direct requests use existing closed HostGrantRequest/ServerGrantRequest value types; their grantor still comes only from the private evidence adapter. A private helper encloses only the authorization phase, before any requested write. It catches only its canonical UnauthorizedAccessException. No public caller can inject the helper, a validator, snapshot, actor kind or audit reason.

The denial record identifies the real LocalPrincipal or RemoteManager and a controlled action. Direct attempts include exact Host/full ServerRef, proposed grant ID, capability, grantee, requested source and delegation flags. Creator attempts identify the exact server/CreateServer prerequisite. Presets/defaults/historical/revocation attempts identify the local permission-policy Host resource, entry counts, selected peer or typed root ID as applicable; batch denial records do not claim individual candidate provenance or persist the recipe. No label, display name, path, native identity, verifier, fingerprint, secret or exception message is copied into audit. Successful grants continue to record full actual issuer/provenance separately.

Before committing a denial-only record, the helper rechecks current identity evidence, the unchanged permission revision, and every field of the exact saved audit row, then cancellation. Removed/changed audit data, current-proof/incarnation/credential changes or audit storage failure refuse and roll back the audit. An ordinary denial leaves the permission revision unchanged and rethrows the permission refusal only after its record commits. Concurrent denied requests may therefore record distinct denials against the same unchanged revision; stale requests still require refresh.

Failed authentication, malformed input, stale revision and cancellation are not recast as permission denials. Neither are exceptions after requested writes begin: successful grant/audit failures and creator callback failures retain full rollback. The helper never catches a callback's UnauthorizedAccessException to commit its metadata accidentally. Presets/historical selection validate all candidates before writes, so an otherwise valid earlier candidate cannot survive a later refusal. The separate activation-default hook remains inside its enclosing trust transaction; it never invokes this commit-owning helper. Existing pairing terminal audit/rollback remains authoritative there.

Six actual SQLite scenarios cover all eleven public pre-write entry paths, exact actor/target/redaction and no permission effects; authentication/malformed/stale/cancellation separation; audit failure/removal/mutation and late local/peer/Owner/incarnation/current-local-credential changes; partial-preset refusal and creator callback failure/duplicate finalization; eight concurrent denied requests followed by stale refusal and successful canonical issuance; late cancellation and success-audit failure. Existing preset/default/historical/remote tests now assert the exact added denial counts while preserving unchanged grant/revision/default/history assertions; full authorization and creator regression probes pass. Fixtures supply controlled authenticated evidence and do not prove installed permission RPCs, actual server execution, physical parity or release readiness. Accessibility is waived; Linux remains gated.

[Successful permission audit integrity](v0.5-successful-permission-audit.md) now verifies every newly written success record at the final transaction boundary, including earlier batch rows after later audits. Missing or altered records roll back the requested effects; they are not relabelled as policy denials.
