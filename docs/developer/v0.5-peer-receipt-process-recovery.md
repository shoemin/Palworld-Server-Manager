# Receiving-peer process recovery qualification

Trial reference: #44ao, within #44. The disposable Windows service runner now executes a real process termination/restart scenario through `WindowsPeerReceiptCrashQualification`. It is a qualification harness, with no product configuration, schema or protocol change.

Two explicitly simulated Hosts use distinct fixture leases on one Windows machine. Their identities, exact Owners and verified mutual bindings are fixture prerequisites using actual protected-material public fingerprints. A refusing PAKE factory ensures this case cannot be mistaken for proof of a PAKE crash boundary. Each Host uses the concrete Windows generation factory, service-account protected storage, native nonexportable TLS cache and actual loopback peer RPC. A transactional activation fixture records one effect and issues zero canonical grants.

The parent rotating Host and its receiver process activate through pinned mTLS. The sender prepares real New material, stages it and cuts over through the actual peer exchange. The receiver contacts New through an idempotent activation retry, durably promoting trust while retaining its undelivered RotationId. Sender completion must refuse. The parent then terminates only the child represented by its retained process handle, without graceful Host cleanup, and waits for actual exit. It reacquires the receiver's fixture lease before reopening its database. Current New, Active/non-recovery trust, retained RotationId, cleared pending-key metadata and zero grants must survive.

A fresh child starts from exactly the same protected root. Its public instance nonce and actual process handle distinguish process lifetimes even if Windows reuses a numerical PID. The actual HostId, protected public pin and native key-container name must remain stable. The ordinary authenticated receipt RPC delivers the retained ID; the sender records exactly one current-incarnation receipt and the receiver clears its ID durably. Successful graceful child exit is followed by a lease-held database check. Only then may sender completion succeed.

The control stream contains bounded public commands/reports only. No private key bytes, invitation code or client credential is exported into arguments, configuration or diagnostics. Config/root identity, actual service SID, a fixture-only database marker and non-reparse local ancestry are checked before opening the child Host. Parent-side access to the live receiver database is excluded; an explicit contended-lease assertion verifies this. Both process waits and control reads are bounded, and a child watchdog terminates a stranded fixture. Cleanup cannot delete borrowed material after a failed process exit or generation closure. Only exact newly created fixture paths and credential references are removed.

Service readiness requires a separate receipt-crash qualification flag, in addition to the existing rotation checks. The original main TLS fixture then publishes its own descriptor for the existing two-user/native-key/ACL checks. Passing run IDs belong in the trial ledger; ordinary self-tests do not execute or independently establish this privileged case.

This proves receiving-process recovery after durable New promotion with an undelivered receipt on a disposable service runner. It does not prove power-loss durability, reboot, physical multi-machine LAN behavior, a crash during PAKE or PeerBound creation, or installed full-network service enablement. Those remaining #44 acceptance items are tracked separately. SQLite process recovery is not a power-loss claim. Accessibility remains waived for this isolated trial.
