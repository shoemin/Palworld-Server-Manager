# Fresh credential replacement evidence

Trial reference: [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28). This implements the provenance prerequisite for the accepted [Owner replacement contract](v0.5-architecture.md#4b-i-credential-loss-pairing-the-pendingcredentialreplacement-gate-product-decision-2026-09-01-pair-004).

Schema 14 adds `PeerReplacementBindingEvidence`, keyed by the exact pending replacement ID. It records the original relationship incarnation, the local Host fingerprint verified in the pairing exchange, and that verification time. These public values come only from the existing trusted Host verified-binding primitive. They are neither wire-supplied approval tokens nor grants. The old incarnation is retained as historical provenance; it is not a foreign key that could silently rebind to a later relationship.

Candidate reuse requires matching peer state and pin, unexpired and unapproved status, no permanent invalidation, and evidence for the current incarnation and exact verified local fingerprint. Reuse retains the original deadline and emits no new audit or authority. Missing or mismatched evidence requires a new verified pairing result and a new candidate ID. Creation rechecks the exact candidate, proof and audit after all writes, the unchanged authorization revision, current local credential and target snapshot. The initiating local Owner, when present, is checked again before commit. A late change rolls back the transaction.

An additive migration creates no evidence for historical requests. It permanently invalidates unapproved legacy requests and preserves approved history. No migration restores trust or grants. Future Owner approval must require this fresh context in addition to all existing replacement conditions, including absence of a staged pending fingerprint; this unit does not expose approval.

Database triggers invalidate outstanding unapproved requests whenever the peer's trust state, current or pending key, rotation ID, recovery/reconfirmation state or relationship metadata changes; retiring an incarnation also invalidates its peer's requests. Changing the local Host identity/current credential, mutating the current credential metadata, or deleting that identity/credential invalidates outstanding requests as well. A later change back to identical values cannot undo the non-null invalidation marker. Trigger timestamps use SQLite UTC for diagnostic history; eligibility depends on the permanent marker, not timestamp ordering. Approved history is preserved by these triggers; explicit revocation/recovery retains its existing rules.

Canonical local, remote and received revocation invalidate their selected requests before updating trust. This preserves their exact transaction timestamp and final snapshot checks when the generic trust/incarnation triggers run. Grant provenance, actual actor auditing, local revision checks and separate Host transactions remain unchanged.

## Evidence and remaining work

Eight persistence scenarios cover durable exact context and concurrent idempotent reuse, six trust/staging/incarnation changes away and back, four local credential changes away and back, missing/mismatched proof refusal, schema 13-to-14 upgrade without backfill, unrelated and approved-history preservation, canonical revocation's exact timestamp, and sixteen late candidate/evidence/audit/authority faults with complete rollback. Active and transition fixtures are explicitly database test inputs, not proof of a completed Owner-approved re-pair or new PAKE construction. Existing full/native/Windows suites remain required.

Owner approval, fresh configured-default roots and durable exact-key recovery completion remain subsequent #28 units. The six creator permissions and limits are unchanged; accessibility certification is **WAIVED, never PASS**. No public command/UI, physical-PC/Palworld/parity/Linux/release qualification is claimed.
