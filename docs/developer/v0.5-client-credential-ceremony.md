# Durable client credential ceremonies

Trial #42d3a extends the current-user client credential store for bootstrap, additional enrollment, Owner rotation and re-home. `ILocalPrincipalCredentialCeremonyStore` records public Host/ticket/purpose/key-choice context and the prepared client key before any public-key submission. It never stores the handoff secret or a machine Host private credential. The later authenticated client protocol owns secret delivery, Host-result verification and handoff deletion; this storage foundation itself creates no Host authority.

The version 2 DPAPI envelope contains the current credential, at most one pending ceremony, the last completed public receipt and retired ticket contexts. A preparation retry in another process returns the same pending key. A different pending ceremony is refused rather than replacing recoverable material. Fresh rotation keeps the old current credential until confirmation. Existing-key reuse is available only for re-home and requires a bound current credential; the later client must select it from authenticated Host target-state evidence. A known current Host binding cannot silently switch to another Host.

Confirmation requires the exact context, returned principal and submitted public key. Rotation preserves a known principal identity; existing-key re-home does too. Current-key promotion, Host/principal binding, pending removal, completed receipt and retirement of the previous receipt persist in one atomic encrypted write. If the write fails before rename, the old state and pending key survive. If the response fails after rename, exact confirmation retry succeeds. A stale completion cannot overwrite a later ceremony or key. The last receipt supports immediate completed retries. Retired ticket contexts persist without old private keys and permanently refuse re-preparation: Host consumed-ticket retries confirm the original identity indefinitely without registering whatever public key accompanies a later retry. Generating a new client key for such a ticket would strand the client, so the client must remember these tombstones.

Before calling confirmation, the later client must also authenticate the returned principal using the prepared key over its Host-authenticated connection. An ID-only historical completion result does not prove the key is currently registered. This matters after a later recovery or loss of the client's previous local state; no storage primitive can reconstruct a lost private key from a ticket ID.

Only an explicit discard after authoritative terminal refusal may remove an unresolved pending key. Timeouts, disconnections, cancellation and lost responses are not grounds for discard. Discard preserves the current credential. Legacy creation/binding/deletion APIs cannot bypass pending state, and legacy binding cannot replace a ceremony-managed binding. Version 1 payloads remain readable and upgrade on the next write. An existing unbound key is preserved when preparing its first context because the old client may already have submitted it before losing the response; fresh rotation of a bound credential still generates a different key. Private buffers are cleared on internal failures and copied out with caller ownership; callers clear returned private material after use.

Ordinary tests exercise reopened/concurrent retries, fresh rotation, existing and fresh re-home, exact-context/key/result refusal, stale completion, explicit discard, version 1 upgrade, malformed state, cancellation and injected failures before and after rename. Actual Windows integration checks a pending real P-256 key across separate processes for one non-admin user, and proves a second user cannot decrypt current or pending keys even when the encrypted file is readable. These are storage checks; actual online Owner ceremonies remain #42d3b/c and full #42 is incomplete.
