# Restricted child launch qualification

Trial reference: #48. This test-only prerequisite evaluates a restricted copy of the existing virtual Windows service token. It does not implement or approve a production game launcher, a complete sandbox, process-tree recovery or real Palworld compatibility.

The explicit Windows integration harness creates its disposable service and read-only public executable tree. Inside that actual service, the fixture creates a synthetic private canary under its protected Host root, removes privileges from a copied token and applies restricting SIDs. A unique child SID is included in that copied token's default DACL so the child can access its own new objects. The shared logon SID is excluded from the restricting list.

Before granting temporary operational access to the disposable service's noninteractive window station, the fixture verifies that its name matches the token's exact authentication logon ID and rejects interactive and built-in shared service logons. Only the unique child SID receives the extra operational/read-control rights; it receives no station WRITE_DAC, WRITE_OWNER or DELETE rights. A new desktop has a separate service/unique-child ACL. The original station DACL is restored and read back before completion, even on failure; owned desktop and station handles are closed. No pre-existing user/system station, OS account or shared token privilege is changed. This fixture-owned grant is an experiment, not a selected production policy.

The child must execute, confirm its actual restricted virtual-service identity and read its public executable. It must be denied private-canary reading and DACL replacement, parent-process termination/thread creation/memory access/handle duplication/process creation/security-descriptor changes, and duplication of the parent token if limited process query is available. Bounded exit stages distinguish failure without logging submitted paths or private values. The parent requires native process termination and exit zero; successful process creation alone never counts as qualification. Cancellation and failure terminate only the owned child through its retained handle. Token, process, thread, desktop and private-file cleanup are mandatory. Every service start must produce a fresh positive readiness field.

The ordinary suite explicitly refuses to qualify this behavior outside a virtual service. CI must run the actual service fixture; a normal developer-session refusal is neither service evidence nor a product blocker. This test does not use real credentials or settings. A later production launcher still needs an explicit environment and handle policy, protected writable game paths, launch/descendant tracking, durable operation recovery and real Palworld/SteamCMD qualification.

Microsoft documents the two access checks for [restricted tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens) and recommends a separate desktop. [CreateProcessAsUser](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw) documents token privileges, desktop access, returned handles and the distinction between process creation and successful initialization. Those API properties motivate this experiment; only completed service results can establish its tested outcome.
