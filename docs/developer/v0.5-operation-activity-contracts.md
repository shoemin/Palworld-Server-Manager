# Operation Activity observation contracts

Trial reference: #46f. Contracts now describe a complete single-Host Activity snapshot, mapped from the [Host worker runtime](v0.5-host-owned-operation-workers.md) and [explicit startup recovery](v0.5-operation-startup-recovery.md). They add no installed endpoint, UI, authorization policy or operation command. Production Host lifetime composition remains subsequent #46 work.

Each operation retains its exact operation ID, kind, explicit Host/server target, phase, terminal flag, runtime status, optional recovery disposition, record revision and timestamps. Each lock separately retains its identity, owning operation ID, kind, explicit Host/server scope and acquisition time. A server-targeted operation holding a Host-wide lock remains a server target with HostScope; equal server profile IDs on different Hosts remain distinct. No synthetic server, phase inference, raw exception, actor credential or policy fingerprint is transported.

The snapshot's durable revision describes SQL state only. A worker can stop or fail while leaving its nonterminal record and lock untouched; its status then changes from Running to Recovery Required without advancing that revision. Consumers must use complete fresh snapshots and must not use durable revision as an unchanged-response condition, cache validator or stream cursor. Timestamps do not prove liveness. Neither a status nor a revision grants permission to mutate. Observational cancellation never cancels Host work.

The separate OperationActivity feature must be explicitly negotiated before mapping. Existing installed endpoints do not advertise it merely because its DTOs exist. A future publisher must authenticate the actual caller and enforce current permitted visibility before obtaining or publishing state, including independent local-user and destination-peer authorization for remote administration. This unit deliberately supplies no generic Host read capability or all-server inventory permission. Its mapper is trusted Host code, not an externally callable read API.

Client-side validation checks canonical nonempty identifiers, single-Host target/scope identity, duplicate operation/lock IDs, bounded kind/phase names, nonnegative revisions, UTC timestamp shape and closed status/recovery enums. Missing target/scope and unknown enum values refuse; they never mean idle or unlocked. Zero record revision and absent recovery/heartbeat remain representable for historical state. Validation is syntactic, not authority or business consistency proof. Inconsistent terminal locks and orphan locks remain visible alongside the recovery flag rather than being dropped to make the response appear healthy. A transport consumer must treat an invalid response as unavailable/recovery evidence, never an empty valid snapshot.

Five scenarios cover independent serialized readers, detached mutable DTO copies, both target types and valid independent scopes, equal-profile cross-Host distinction, malformed/unknown wire shapes, explicit negotiation, all four statuses/dispositions, unknown optional field preservation, canceled observations, runtime-only status changes with unchanged SQL revision, and retained terminal/orphan locks in real SQLite state. Focused validation also checks existing protocol descriptor evolution. These are contract/runtime tests, not installed Activity RPCs, physical PCs/reboot or real Palworld operation acceptance.

No schema, grant/default/creator, credential, client dependency, concrete destructive policy, offline queue, Linux or UI change. Accessibility WAIVED, never PASS; Windows parity/physical/Palworld/Linux/release gates remain. The Astra trial used no external GitHub Codex reviewer. Astra was responsible for both implementation and technical review.
