# Native responder crash with asymmetric durable trust

Trial reference: #44ar, within #44. `WindowsPeerResponderCrashQualification` runs under the disposable service identity with two simulated Hosts, distinct leases and actual protected/native credentials. The parent is the initiator; its child is the responder. Neither binding is seeded. Owner initialization and the single-effect activation hook remain explicit fixtures.

The child creates its actual native invitation. The parent requests it using the bounded fixture control protocol, receives public invitation ID/own endpoint metadata, exactly ten raw code bytes over redirected private stdout, and a public `invitation-ready` acknowledgement. The child sends that acknowledgement only after disposing its transient invitation/code copies; its actual coordinator legitimately retains the live invitation. The parent zeroes the raw read buffer before returning a redacted code wrapper and uses it only after the acknowledgement. Codes never enter arguments, configuration, JSON reports or diagnostics. Public report reading uses strict UTF8 over bounded raw byte reads through LF, with no StreamReader read-ahead that could decode private bytes into a text buffer. Existing private stdin code input remains available for the other native cases.

A role-explicit `VerifiedPairingBarrier` delegates every cryptographic operation to the selected native provider. The responder stops only after actual identity verification, before that result can return to its production Store caller. Its public phase must match the expected initiator Host/pin and show no local trust. At that moment the initiator must already have independently committed actual PeerBound, its exact pin/local binding, original expiry and current-incarnation binding evidence, but zero activation effects or canonical grants. The in-flight pairing call must still be incomplete.

The parent explicitly kills the live responder, awaits actual exit and settles its failed pairing call before disposing the retained code. The initiator's entire PeerBound record and binding evidence must remain identical. Under the reacquired child lease, the responder has no trust, incarnation, binding proof, binding audit, activation effect or canonical grants. Its real pin admission policy refuses activation, ordinary management and trust maintenance. This is a real asymmetric commit boundary, not a simulated distributed transaction or seeded repository state.

A fresh responder process reloads the same protected/native identity with no barrier and no trust. Its actual attempt to activate against the still-live initiator must fail with the nested TLS authentication cause; generic network errors cannot qualify. A new responder invitation then drives fresh actual native PAKE: the initiator must return ResumePeerBound with its unchanged original expiry/evidence, and the responder creates its first binding. Normal pinned activation and retry independently reach Active with one effect and one original binding audit per Host, zero canonical grants and unchanged initiator binding history. Final orderly child exit and leased reopening establish durability.

Failure cleanup first observes child exit and settles outstanding parent work. Host shutdown also cancels/drains any call that outlasted its bounded result wait before the remaining code wrapper is disposed. Native/protected deletion requires successful whole-generation closure and exact fixture path/lease ownership. The child watchdog bounds abandoned processes. No killed process is claimed to run graceful cryptographic cleanup.

Requested native service qualification additionally requires `ResponderCrashQualified`. The original precommit initiator, post-PeerBound restart-without-PAKE and retained-receipt cases remain independently required, together with two-user/native-provider/key protections and full cleanup. Provider-less runs make no native process claim. Exact passed/failed runs and both review passes belong in the ledger; ordinary tests alone do not execute this privileged case.

This targets the responder after real identity verification and before its writer, with an already-bound initiator. It does not establish a kill inside a database commit, power loss/reboot, physical multi-machine LAN, installed full-network enablement or release acceptance. Accessibility remains waived.
