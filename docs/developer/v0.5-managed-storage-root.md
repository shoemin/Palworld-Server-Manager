# Protected managed storage root

Trial reference: #48. The shipped privileged offline bootstrap prepares `%ProgramData%\PalworldServerManager\Servers` beside `Host`, `PublicTrust` and `OwnerHandoffs`. This prepares an empty storage container; it does not create/register servers, select game-process permissions, launch a game or issue creator grants. Owner rotation/rehome and machine recovery do not prepare or validate game storage, so storage problems cannot block those credential operations.

Preparation occurs after existing elevation, stopped-service and machine-exclusivity checks, before opening/migrating authoritative database state. Trusted test compositions may explicitly select an isolated storage root; the shipped CLI and RPCs expose no root-selection argument. All configured private/public/handoff roots must be disjoint from managed storage, including ancestor/descendant overlap. Local drive and no-reparse ancestor checks are required. Setup requires canonical path components and refuses device, dot, trailing-dot/space and tilde/short-name syntax; this is a fixed product storage convention, not a general folder picker.

The new root has protected permissions granting full control only to its exact virtual service SID, Administrators and SYSTEM. Its ancestors must remain privileged-owned and deny unprivileged replacement. No service grant is added to the product parent, and the private Host root is unchanged. Existing roots are validated without rewriting their ACLs or descendants; unsafe ownership, inheritance, extra/denied permissions, unsupported ACE forms, files or reparse roots are refused. Missing parents are not created implicitly. No recursive takeover or repair of existing game files is performed.

Creating a new protected root is idempotent preparatory filesystem work, not part of a database transaction. If later offline work is rejected or canceled, the safely prepared root can remain; it confers no application authority and contains no newly registered server. Uninstall continues preserving authoritative and server data.

Ordinary tests cover the policy and path boundaries. Actual disposable Windows integration must verify idempotent setup and unsafe-layout refusal, unchanged parent/private-root permissions, service write/bounded-read across four starts, two real nonadmin provisioning/read/write/create/delete refusals, shipped bootstrap composition and full cleanup. Ordinary policy tests alone do not qualify service access.

The read-only `IManagedStorageRoot` seam is for trusted Host composition. Validation is an observation, not a retained path handle or an authorization/operation permit. Individual server directories, game access, inventory binding, settings revision/save integration and process lifetime remain separate work. No local Owner, remote creator or ordinary user receives raw filesystem access from this change.
