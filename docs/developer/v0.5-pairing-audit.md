# Pairing outcome auditing and pending cleanup

Trial reference: #44h, within #44. `PeerPairingRpcRuntime` owns the terminal audit journal and periodic pending-trust maintenance. These use the existing Host database and machine-lease contract. Installed service startup and local invitation/initiator authorization remain later composition work.

`PairingAttemptFailed` and `PairingAttemptExpired` records contain only a Host-generated event UUID, original UTC occurrence time, closed event kind, affected local Host UUID and a fixed public summary. No code, session nonce, transcript, exception text, socket address or public/private credential is accepted by the persistence API. Actor fields are null: a failed exchange has not established a trusted remote actor. Event identity is idempotent; the first committed terminal outcome wins across timer/disconnect races and retry after an uncertain write response. A UUID collision with an unrelated audit event is refused. The authoritative initialized Host and one-Owner condition are checked in the write transaction. Unknown outcomes fail before writing.

The responder records failures from native initialization onward, including disconnect and failures after native identity verification but before durable storage. Unused invitation cancellation maps to Failed; invitation expiry maps to Expired. The outbound Host gives each admitted call its own local attempt identity and records failure if it did not reach durable storage. Native `IdentityVerified` remains a diagnostic handoff, never an Active or terminal success event. The existing `PeerBoundCreated`, `PeerActivated` and `PeerBoundExpired` events remain in the same transaction as their respective durable transition. A stream error after local persistence does not delete PeerBound or append a contradictory terminal failure. That pending relationship continues toward pinned activation or its original expiry; replacement/recovery cases retain their existing approval workflow.

Audit writes have a one-second SQLite busy timeout. On a write failure, the journal retains the public outcome and original timestamp for retry; it closes new invitation/transport admission and refuses new binding storage. The runtime exposes `AuditStorageUnavailable` to trusted composition. The sixteen shared inbound/outbound transport slots, sixteen retained invitations and closed admission bound outstanding records; a defensive sixty-four-record cap rejects overflow and permanently marks the runtime unhealthy, even after the retained records drain. A broken diagnostic consumer cannot suppress the owned database audit or prevent native cleanup. In-flight cryptographic sessions are disposed before terminal retry bookkeeping completes.

A one-second maintenance timer retries pending public records and expires abandoned PeerBound rows through the existing atomic tombstone/audit transaction. Startup runs the same cleanup before admission. Overlapping timer callbacks skip instead of accumulating behind a slow write. A rolled-back expiry stays PeerBound in storage but is already unusable by the live expiry check; cleanup resumes when the write succeeds. Successful retry and cleanup restore admission unless the defensive overflow latch was tripped. No original deadline is extended and no grants are created or resurrected.

Shutdown stops the coordinator, waits for the maintenance callback, retries pending records, and reports unavailable storage as a bounded exception after releasing owned resources. Callers must stop borrowing listeners/calls before disposing the runtime and dispose the native provider and credentials afterward. The installed-service integration must surface unhealthy status and shutdown failure. A process crash while an audit database is unwritable cannot make an unwritten record durable; the journal does not claim that guarantee or persist recoverable cryptographic state. Ordinary pre-PeerBound crash semantics still discard ephemeral attempts, while already-durable trust and its transactional audit survive independently.

Four ordinary scenarios cover duplicate/concurrent terminal records, closed outcomes and actor privacy, write-failure rollback/retry with original time, startup and later pending expiry with atomic audit rollback, defensive overflow/shutdown failure, and actual TLS/gRPC disconnect plus native-initialization failure and admission closure/recovery. The native pairing probe also verifies failed proof audits and injects an actual response-read failure after the genuine binding frame: local PeerBound remains with one creation audit and no false Failed event. The injection changes only the response read, not TLS, native confirmation or binding. This is loopback fault injection, not process-kill/reboot or multi-machine evidence.
