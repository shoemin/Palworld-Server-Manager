# Relationship-specific promotion evidence

Trial reference: #44ak, within #44. Schema6 adds a durable local incarnation for each trust relationship and separate promotion evidence keyed by rotation and peer. `PromotedUtc` remains the first historical receipt time; it alone cannot establish that today's relationship has resolved a rotation. This unit does not mark rotations Completed or permit key deletion.

`PeerRelationshipIncarnations` uses SQLite's positive AUTOINCREMENT identity, so committed incarnations are not reused after deletion/recreation. The Host's transactional triggers replace the incarnation on revocation, recovery boundaries, unproved current-key replacement, changed relationship timestamps and any pairing-metadata insert/update/delete (even an identical rewrite). Peer and pairing identities cannot be renamed in place. Missing incarnation metadata or sequence exhaustion refuses the mutation atomically. Rollback preserves the prior relationship and receipt evidence. Cosmetic names do not change the incarnation, nor does an unrelated peer's mutation.

Ordinary PeerBound-to-Active activation preserves continuity. The existing verified routine-promotion writer also preserves it: both states are Active/non-recovery, the prior stored Pending fingerprint becomes Current, the same retained rotation ID survives, and pending fingerprint/deadline/reconfirmation are cleared. Changes to recovery or relationship timestamps still invalidate independently. This exception is for trusted Host persistence of a verified staged credential; a wire DTO cannot choose an incarnation or write that transition. Future explicit replacement must create a new relationship, including rewriting its pairing provenance, even if the UUID/key happen to match. No replacement/grant-inheritance action is implemented here.

Authenticated peer negotiation captures the local incarnation from current trust and actual connection fingerprints. `ConfirmRotationPromotion` carries that captured value internally to the immediate writer, alongside the actual peer/local TLS pins. The writer requires the same current incarnation after acquiring the lock. A recovery/revocation/re-pairing change after negotiation cannot be hidden by returning to identical state or key values. A new connection can negotiate the current relationship and submit a fresh, explicitly correlated receipt through the existing protocol.

The writer preserves first `PromotedUtc` and existing staging/acknowledgement history, while attaching current `HostRotationPromotionEvidence` and its confirmation time in the same audit transaction. An exact current-incarnation repeat changes nothing; a fresh receipt for a later incarnation refreshes evidence and records a new authenticated event. Historical evidence for the prior incarnation remains distinguishable until refreshed; the [final retirement gate](v0.5-rotation-completion.md) compares it with the current relationship in its final writer transaction. Neither a cached snapshot nor this storage table is permission to retire a key.

Migration assigns incarnations to existing peers but leaves promotion evidence empty. It does not retrospectively associate a legacy receipt with today's relationship. A peer still retaining its rotation ID can resend normally; one that already cleared it can use the [explicit current-credential confirmation exchange](v0.5-current-credential-confirmation.md), which records separate truthful evidence. TLS alone, a migrated timestamp or an expired deadline cannot manufacture that proof.

Five ordinary scenarios cover conservative upgrade and atomic migration failure, actual repository activation/staging/promotion continuity, unrelated-peer independence, same-identity state reversal and pairing changes, delete/recreate non-reuse, queued stale receipt refusal, audit rollback, missing metadata/sequence exhaustion, and an actual New-key mutual-TLS connection whose negotiated relationship becomes stale. The last scenario re-negotiates and confirms successfully. Global cutover in these receipt fixtures is explicitly synthetic; these are not process-crash, physical-LAN, installed-service or final retirement acceptance tests.

[First-binding provenance](v0.5-local-binding-provenance.md) separately records the actual local credential and incarnation for new verified pairings. It never invents promotion history for a peer first paired under New.
