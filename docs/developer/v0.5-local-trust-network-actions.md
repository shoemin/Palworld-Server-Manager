# Protected local trust network actions

Trial reference: #28. A configured network generation offers `LocalPeerUnpairPreparation` (19) and `LocalOwnerPeerRecovery` (20) with local protocol1.17. Each action requires its own explicit negotiated feature plus local principal security on the original runtime-owned Windows native-identity/TLS connection. A capable older-minor client can negotiate either independently. Local-only composition advertises neither. Requests contain only the semantic peer Host ID and bounded hostname/IP plus port; no actor, Owner flag, approval, key or proof is accepted from the caller. Immutable1.17 descriptors preserve every older wire revision. The current peer protocol is1.15 after the separate [receiving administration extension](v0.5-peer-trust-administration-rpc.md).

`PreparePeerUnpair` checks the actual current local Owner or exact local-Host `ManageTrustedManagers` permission before any outbound contact and again before returning. It asks the existing [generation-owned unpair coordinator](v0.5-unpair-coordinator.md) to retain an actual authenticated Active peer connection. Preparation is optional and ephemeral: at most32 workers, two-minute retention, existing fifteen-second handshake bound and three-second eventual delivery bound. A false reply means this request did not prepare a new connection, including an already-prepared peer, capacity limit or failed contact. A true reply is a readiness observation, never authority or delivery confirmation. If final local authorization fails, that request cancels its own preparation outside SQL; the generation still owns actual worker cleanup.

[Local revocation](v0.5-local-peer-trust-rpc.md) independently rechecks its own current actor, authorization revision and exact relationship incarnation. It commits immediately, with or without successful preparation, before asking the coordinator for best-effort notification. No network work or cancellation callback runs inside its transaction. A missing/dropped/withheld remote response cannot undo or delay local revocation. No address, notice or offline command queue is persisted.

`CompletePeerRecovery` requires the actual current local Owner before contact, between the fixed confirmation and reverse-pull stages, and before reporting. Trust-management or permission-management grants do not substitute for Owner. One thirty-second cancellation bound covers both existing clients and their original proof/approval/incarnation checks. The response reports each direction separately using closed enums: confirmed, no pending, or key mismatch; reverse pull can also report unsupported. No-pending never means confirmed. This action cannot approve replacement, clear recovery by assertion, issue grants or revive old provenance. Only the existing independently authorized canonical receipt and confirmation writers may change state.

Remote receipt effects can commit while the originating Owner changes. The wrapper refuses the next stage and reply after the change; it cannot roll back an independently committed remote receipt. Existing intrinsic contact retry is separately authorized by canonical peer evidence. Neither action is triggered as a side effect of a denied ordinary administration request. The Host retains its machine key and owns all native traffic; ordinary clients never contact the peer as the machine identity.

Fixed trusted asynchronous methods run within the original local dispatcher and generation traffic lifetime; no synchronous permission facade escapes its scope. Cancellation and shutdown retain generation ownership until actual callbacks and transports finish. RPC failures use constant local messages. Invalid input, missing capability, stale authentication and denied permission are refused before contact; failed recovery contact leaves original approval evidence available for a later explicit retry.

The late-Owner barrier holds the actual receipt request before the peer handler, then changes the originating Owner verifier; the peer commits its independently authorized receipt while the wrapper refuses reverse pull. Historical verified-binding inputs are explicit fixtures. Genuine PAKE, native key repair, and actual receiving-process fault qualification remain separately documented.
