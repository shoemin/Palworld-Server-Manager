# Atomic rotation cutover and ordered local publication

Trial reference: #44s, within #44. The internal Host coordinator connects a [fresh acceptance collection](v0.5-rotation-acceptance.md) to the final SQLite transition and local trust publication. Its caller must retain the machine lease and quiesce all Host connections and competing mutations first. It never stops or resumes listeners itself, exposes no client RPC, and is not yet an installed service rotation action.

The coordinator verifies the current local Owner and exact immutable proposal, then validates the known New material through the existing protected-material seam. A known fingerprint cannot trigger regeneration. Before changing Current, it durably publishes Old as current with Pending New and the exact RotationId. Only then does the final immediate transaction run. It rechecks initialized Host/Owner/native identity/verifier, exact pre-cutover Old/New/proposal, the complete current peer set, and the collector's actual decreasing acceptance bounds against that same transaction's snapshot. PeerBound or recovery-required trust independently blocks. Historical acknowledgement timestamps cannot satisfy the callback. The callback is a trusted Host seam, never caller-supplied RPC data or a serialized permission token.

Current becomes New, New's activation time is recorded, and the rotation becomes CutOver together with the Owner audit in one transaction. Owner/proposal integrity, peer revision and remaining-time bounds are checked again after the audit, before commit. Any refusal, cancellation or audit error rolls the transition back. An exact already-CutOver retry is read-only and records no second transition; it does not need to recreate old acceptance bounds. No grants, peer trust, key-retirement metadata or HostId change.

After commit, a separate publication selects Current New and clears Pending. These two stores are never described as atomic. Failure before commit leaves Old authoritative; failure after commit leaves New authoritative and Old retained. The caller must remain quiesced on failure and reconcile authoritative trust before serving again. It must never restore Old merely because the file update failed. An in-process retry can finish publication even after the old collection's bounds expire. After restart, the existing unconditional startup reconciliation derives Current and Pending directly from durable state and retains both keys while CutOver remains unresolved. Neither path falsely declares old-key retirement complete.

Seven ordinary scenarios cover real multi-peer proposal acceptance followed by the actual transaction, genuine New-key TLS and durable receipts; custom grant retention; peer/Owner/proposal changes during publication; post-audit margin/cancellation and trigger changes; rollback; serialized committed retries; missing/mismatched material; each publication failure boundary; wrong collection scope; and zero-peer rotation. Material and publication boundaries use explicit fixtures here, and Active trust is synthetic setup. The tests assert publication order against authoritative state, not a new Windows filesystem, installed service, process-kill, reboot or physical multi-machine qualification. Full all-listener orchestration, local initiation, retirement, abort notifications and complete #44 integration/field acceptance remain outstanding.
