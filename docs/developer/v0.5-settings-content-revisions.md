# Settings content revision observations

Trial reference: #47. `ConfigurationRevisionRepository.ObserveContent` binds a trusted Host observation of bounded file bytes to the existing qualified editable-resource revision counter. It is an internal persistence seam; it does not read files, authorize a user or implement a settings RPC/save.

The Host computes a SHA-256 fingerprint of at most 4,194,308 owned bytes and stores it in its private database, associated with the resource and observed revision. Raw content is not stored. Fingerprints never become wire revision tokens, audit payloads or diagnostic output. Public revisions remain canonical nonnegative Int64 decimals.

The first observation establishes a new baseline by advancing the current counter, including when historical revision metadata already exists. Identical bytes at the same associated revision keep the counter and timestamp. Changed bytes advance it, including an observed A-to-B-to-A sequence. A generic database revision write makes an older content association stale; the next observation establishes another baseline. Timestamps record Host observation/commit time, not filesystem modification time or an effective running-game value. Missing or unreadable files have no observation in this seam.

Schema17 adds only `ConfigurationContentObservations`; it neither converts historical revision rows nor creates grants. Migration and schema-version advancement are one transaction. Observation updates use an immediate transaction, validate the initialized authoritative Host, check exact stored types/bounds, and recheck both metadata rows and current read authorization before commit. The read-only validator uses the supplied connection/transaction, runs before metadata changes and again before commit, and is mandatory even for unchanged bytes. It must not open a nested writer or call the separate transaction-owning capability API. This lets final authorization observe changes within this very transaction. Initial authorization before file access remains the caller's responsibility; caller-side denial auditing must run after rollback, not start a nested transaction. Failure, cancellation, invalid metadata or revision overflow leaves both rows unchanged. Overflow does not prevent an unchanged observation from returning the existing maximum revision.

The caller must retain the machine lease and serialize its ordered file-read/observe/save sequence. It must authorize the exact server before reading and supply a current read validator. This observation cannot freeze a file or prove a stopped process. Future save integration must freshly read/reconcile content before comparing the expected revision, hold the appropriate Host-owned operation lock and verified stopped lifetime, and use durable file-write recovery. A database transaction cannot roll back an external file write. Changes that occur and revert entirely between observations are not detected by content comparison.

Tests cover independent resources/Hosts and reopen, byte changes and bounds, concurrent observations, stale generic writes, final-proof/cancellation/trigger rollback, historical upgrade preservation, malformed storage and overflow. The existing generic database `Write` contract is unchanged. The [configured settings API](v0.5-configured-settings-api.md) consumes this seam through the authorized Host reader. No file writer consumes it yet.
