# v0.5 architecture: Manager Host and platform boundaries

This document is the deliverable for [#19 — Define Manager Host and Windows/Linux platform abstraction boundaries](https://github.com/shoemin/Palworld-Server-Manager/issues/19), the Gate B architecture item required by the [#17 accepted plan](https://github.com/shoemin/Palworld-Server-Manager/issues/17). It resolves the concrete engineering boundaries #20 (Windows) and #21 (Linux) implement against, so neither has to invent them mid-implementation.

Nothing here authorizes production implementation. It defines contracts, not code.

## 1. Project/assembly topology and dependency direction

Today's tree is three projects: `PalworldServerManager.App` (WPF), `PalworldServerManager.Core`, `PalworldServerManager.Lan`. The accepted #17 boundary list maps onto these new projects:

| Project | Role | May depend on |
|---|---|---|
| `PalworldServerManager.App` | **Frozen.** Existing WPF application, untouched except critical bug fixes. | (unchanged — Core, Lan as today) |
| `PalworldServerManager.Core` | Shared domain/application behavior: profiles, settings schema, SteamCMD, backups, process identity. Already has zero UI dependency — that invariant is preserved, not newly introduced. | BCL only |
| `PalworldServerManager.Contracts` | Renamed/evolved from `PalworldServerManager.Lan`, and **deliberately independent of `Core`** (see §4a — this was wrong in the prior revision of this document). Wire DTOs, protocol enums, gRPC service contracts, version/capability negotiation types. OS-neutral, transport-agnostic. | BCL + protobuf runtime only |
| `PalworldServerManager.Platform.Contracts` | OS-neutral interfaces: `IProcessPlatform`, `IPathPlatform`, `ISteamCmdPlatform`, `IServerLauncher`, `IHostServiceLifecycle`, `IBootStartPlatform`, `IClientLoginStartPlatform`, `ISecureCredentialStore`, `IShellIntegration`, `IUpdatePlatform`, `IPlatformDiagnostics`. | `Core` |
| `PalworldServerManager.Platform.Windows` | Windows implementations of the above. | `Platform.Contracts`, `Core` |
| `PalworldServerManager.Platform.Linux` | Linux implementations of the above. | `Platform.Contracts`, `Core` |
| `PalworldServerManager.Host.Persistence` | Owns the SQLite schema/migrations (§6), the machine-wide single-instance exclusivity lock primitive (§2), and repository/query code. Shared by `Host` and, only in bootstrap/recovery mode, `Host.Cli` (§5a) — neither talks to SQLite through any other path. | `Core` |
| `PalworldServerManager.Host` | The Manager Host service: composition root, local + remote endpoints, authorization enforcement, Core↔Contracts DTO mapping. | `Core`, `Contracts`, `Platform.Contracts`, `Host.Persistence`, and (at its single composition root only) `Platform.Windows` **or** `Platform.Linux` |
| `PalworldServerManager.Host.Cli` | Headless bootstrap/recovery CLI. Normal operation is a thin `Contracts`-speaking client of a running Host; bootstrap/recovery mode (§5a) uses `Host.Persistence` directly, gated by the same exclusivity lock. | `Contracts` (normal mode), `Core` + `Host.Persistence` + the relevant platform project (bootstrap/recovery mode only) |
| `PalworldServerManager.Client.Avalonia` | Avalonia desktop client (Windows + Linux). | `Contracts` **only** |
| `PalworldServerManager.SelfTest` | Existing self-test harness, expanded per §14. | Whatever it's testing |

**Dependency direction is one-way and enforced by this table**, not by convention: `Core` and `Contracts` never reference `Platform.*`, `Host`, `Host.Persistence`, or `Client.Avalonia`, and — critically — `Contracts` never references `Core` either, so nothing downstream of `Contracts` alone can reach a `Core` type transitively. `Platform.Windows`/`Platform.Linux` never reference each other. `Client.Avalonia` references **only** `Contracts` — it has no dependency path to `Core`, `Platform.*`, `Host`, or `Host.Persistence` at all, not merely a convention against using one. This is what makes "Avalonia is a management client, not the process/filesystem authority" structurally true.

`OperatingSystem.IsWindows()`-style branching is confined to exactly one place: `Host`'s composition root, choosing which platform project's implementations to register in DI at startup. Nowhere else in `Core`, `Contracts`, `Host`'s business logic, or `Client.Avalonia` should branch on OS.

## 2. Manager Host process/service boundary

- **Exactly one Host per physical PC**, running as a machine-wide service — Windows Service (SCM) or Linux daemon (systemd unit) — under a dedicated service identity, not a per-interactive-user process. This is deliberate: "one authoritative Host per PC" and "multiple local UI sessions must not create competing server authorities" both fail if Host runs per-user.
- Host acquires an OS-level exclusive lock (named mutex on Windows, a lock file with `flock` on Linux) on startup, owned by `Host.Persistence` (§1) and shared with `Host.Cli`'s bootstrap/recovery mode (§5a). A second launch attempt detects the running instance and exits rather than starting a competing instance. **[#26](https://github.com/shoemin/Palworld-Server-Manager/issues/26) remains an open, unresolved investigation — its actual root cause was never established, and nothing here claims to have found or fixed it.** What this design does independently: a single machine-wide, single-instance-locked Host removes the general class of competing-authority/multi-writer risk that a scenario like "two Manager processes running simultaneously" represents, regardless of whether that specific scenario was #26's actual cause. That's a reason to keep this design, not a claim about #26.
- Host owns **all** persistent state exclusively (§6). No other process — including `Host.Cli` once Host is running, and never `Client.Avalonia` — writes Host-owned files directly.
- Host exposes local IPC (§3) always, and a remote network listener (§4) only when remote management is enabled in Host settings. Both are served by the same in-process business logic — there is exactly one code path per operation, not a duplicated "local" and "remote" implementation.
- Host lifecycle is independent of `Client.Avalonia`'s lifecycle (§4 of the #17 plan, "Host lifecycle and safety"): closing the client disconnects a client, never stops the Host or any server it's running. Desktop Host defaults to boot-start off and idle-exits when nothing needs it; headless Linux Host defaults to boot-start on and simply stays running.

## 3. Local client transport

- **Windows**: `System.IO.Pipes` named pipe, fixed name scoped to the product (e.g. `PalworldServerManager.Host`), pipe ACL restricted to the local Administrators group plus the recorded Owner's SID — not "everyone," and not merely "whoever the service runs as." This is a **transport-level** restriction (defense in depth, §3a); it is not by itself the application-level authorization mechanism below.
- **Linux**: Unix domain socket at a fixed system path (e.g. `/run/palworldservermanager/host.sock`), `0660` permissions, owned by the Host's service group; authorized local OS users are added to that group during setup. Same defense-in-depth role as the Windows ACL.

### 3a. Local-caller identity — concrete mechanism, not an assumption

The prior revision of this document asserted "Host authorizes local connections by OS identity" without specifying how the connecting caller's OS identity is actually retrieved through the chosen Kestrel-hosted gRPC transport. That's not realizable as stated: whether Kestrel's named-pipe transport surfaces Windows pipe-impersonation identity, and whether its Unix-socket transport surfaces `SO_PEERCRED`, to the application layer in a simple, supported way is genuinely uncertain without an implementation spike — this document should not silently assume it works.

**Primary mechanism (the one this design formally depends on): an OS-file-ACL-gated local bootstrap credential.**

1. On startup, Host generates a random local bootstrap secret and writes it to a file whose OS-native permissions are set to exactly the authorized local principals — the recorded Owner's SID plus Administrators on Windows (NTFS ACL, restrictive parent directory); a dedicated OS group containing authorized local users on Linux (file mode `0640` or tighter, group ownership as above), under a system-owned path.
2. A local client — running as whichever OS user launched it — attempts to read that file. Success or failure is enforced entirely by the OS's own permission check, which both platforms guarantee reliably regardless of what the IPC transport layer does or doesn't expose.
3. The client presents the file's contents as a bootstrap credential over the local pipe/socket on connect; Host verifies it and, for the current connection, treats the caller as the local Owner (or, for a group-restricted variant, as "an authorized local user" — see below).
4. This is the same class of precedent used by other local daemon tools that gate a named-pipe/local-socket API via a token file rather than relying on transport-level peer-credential retrieval, chosen specifically because it does not depend on framework internals this document cannot verify with confidence.

This gives concrete, realizable answers to all three required distinctions:
- **Initial local Owner**: the OS user who completes initial setup is the only one with read access to the bootstrap secret at that point (the setup process itself runs interactively as them and provisions the ACL to their SID/group).
- **Explicitly authorized additional local users** (§5): adding a local OS user to the authorized group (Linux) or SID list (Windows ACL) — an explicit Owner action, not automatic — grants them read access to the bootstrap secret, and therefore the ability to authenticate as an authorized local caller.
- **Local users with no Manager authority**: simply never added to that group/ACL; the OS denies them the read, so they cannot construct a valid bootstrap credential at all — they never reach an authorization check to fail, the transport-adjacent credential is unobtainable in the first place.

**Required #20 preflight/contract-validation gate:** before building further Host authorization logic on top of it, #20 must run a standalone spike proving whether the *selected* Kestrel named-pipe/Unix-socket transport also exposes native peer identity (Windows SID via pipe impersonation or equivalent; Linux UID/GID via `SO_PEERCRED` or equivalent) reliably enough to use as a **defense-in-depth cross-check** against the bootstrap-credential claim (a mismatch between "the bootstrap secret says Owner" and "the transport says a different local user" should be rejected and logged as suspicious). This is optional hardening pending that spike's result — the design's actual authorization decision must never depend on it succeeding, since this document cannot commit to it being realizable through the chosen transport without that spike.

- Local and remote clients use the **same logical operation contracts** (`Contracts` project, §4) — local IPC and the remote network listener both speak the same RPC surface; only the transport and the auth-anchor (bootstrap credential vs. paired credential, §4a) differ.
- OS administrator/root has a separate emergency-recovery path (§5), not blanket day-to-day authority merely from running as root/Administrator.

## 4. Remote Manager ↔ Host protocol

**Selected: gRPC over TLS, hosted on Kestrel.** Kestrel/ASP.NET Core hosting is existing infrastructure (`ManagerLanHost` already depends on it) being evolved, not replaced. **gRPC itself is a genuinely new dependency, not a zero-cost addition**: it requires `Grpc.AspNetCore` (server), `Grpc.Net.Client` (client), and `Google.Protobuf` + `Grpc.Tools` (schema/codegen) — none of which the v0.4 codebase currently references (v0.4's REST endpoints use plain ASP.NET Core Minimal API, not gRPC). Recorded here explicitly as a new technology dependency, not implied to already be present.

Why gRPC specifically, evaluated against the actual requirements rather than convenience:
- **Protocol/capability negotiation** (§13) is naturally strongly-typed via protobuf service contracts and an explicit `Handshake` RPC, rather than something bolted onto a loosely-typed REST/JSON surface.
- **Streaming** is built in and is a real requirement here — Activity/log/metrics push (the #18 UI spec references this directly) needs server-streaming, which gRPC supports natively over the same connection as unary RPCs; a REST API would need a second mechanism (SSE/WebSockets) for the same job.
- Cross-platform .NET support (`Grpc.AspNetCore` / `Grpc.Net.Client`) is mature.

### 4a. Stable Host identity vs. authentication credential

The prior revision of this document defined a TLS certificate's fingerprint as *the* Host's identity. That's wrong: a certificate/key is an **authentication credential**, not the semantic identity of the physical Host, and conflating the two makes credential rotation indistinguishable from becoming a different Host. These are now two separate, explicitly related concepts:

```
HostIdentity     { HostId (ULID/GUID, generated once during machine Host
                    initialization, never changes for this physical PC's
                    life), CurrentCredentialRef (private-key reference into
                    ISecureCredentialStore, §7) }

TrustedManagers  { PeerHostId (stable, never changes),
                    CurrentTrustedPublicKeyFingerprint,
                    CredentialHistory[] (prior fingerprints + rotation
                    timestamps, retained for audit only),
                    DisplayName, MachineName (self-reported, cosmetic —
                    never security-relevant), FirstPairedUtc }
```

- **`HostId` is the project-owned, permanent identity** a physical Host is known by everywhere — `TrustedManagers` rows, `CapabilityGrant`s (§5), `AuditEvents` — all key on `PeerHostId`, never on a certificate fingerprint.
- **Credential rotation without changing `HostId`**: a Host may generate a new key pair and request rotation. The rotation request is authenticated under the **currently trusted** credential (signed by the old key) — since it requires already being trusted, an attacker without the old private key cannot rotate a victim's pinned credential out from under them. On successful verification, the peer updates `CurrentTrustedPublicKeyFingerprint` to the new value and appends the old one to `CredentialHistory`; `PeerHostId` is untouched.
- **Credential loss**: if the old private key is gone, rotation as above is impossible — there is no cryptographic way to prove "this is still the same Host" without it. The Host must go through the pairing bootstrap flow again (§4b) as if pairing for the first time, landing at the least-privilege default template (§5). The *only* way to carry the old `HostId`'s accumulated grants forward is a manual, explicit, audited Owner action — reusing the existing "Owner adoption/re-home" mechanism (§5) — never automatic, since automatic continuation would defeat the entire point of requiring proof of credential possession.
- **A previously trusted credential that has been revoked**: credential revocation and trust revocation are treated as the **same operation**, deliberately, rather than inventing a third "trusted-HostId-but-untrusted-credential" state — see §8. Partially trusting a `HostId` without trusting its current credential is a contradiction, because the credential is the only mechanism that proves you're actually talking to that `HostId`.

### 4b. Initial pairing bootstrap — MITM-resistant first contact

mTLS with pinned credentials (§4a) describes *post-pairing* authentication. It says nothing about how the first pin is established safely — and without that, an active man-in-the-middle during first contact could cause each side to pin the attacker's credential instead of the real peer's, defeating everything built on top of it. This subsection is that missing piece.

**Mechanism: a PAKE (Password-Authenticated Key Exchange) run over the one-time pairing code**, not a bare code comparison.

A PAKE protocol lets two parties who share only a short, human-enterable secret derive a strong session key *and* mutually authenticate, with the specific property this problem needs: an eavesdropper/relay who does not know the secret cannot complete the exchange or learn the derived key, and — critically — if a MITM relays between two honest parties without knowing the code, each side's independent PAKE run derives a **different** session key, so an explicit key-confirmation step (each side proving possession of its derived key, e.g. via a MAC over the exchange transcript) fails on at least one side, aborting *before* either side pins the other's long-term public credential. This is what makes "an active MITM cannot cause the user to pin the attacker's certificate" an actual property of the protocol rather than a hope.

Concrete requirements:

1. **One-time pairing secret/code**: sufficient entropy that the only viable attack is *online* guessing against a rate-limited endpoint, not offline transcript cracking — this reuses the existing, already-implemented v0.4 `PairingService` precedent (a short code, not a long key humans can't type) rather than inventing new numbers.
2. **Expiration**: the existing v0.4 precedent (5-minute validity) carries forward as the accepted baseline.
3. **Attempt/rate limiting**: the existing v0.4 precedent (10 wrong attempts locks out the current code entirely) carries forward, extended with server-side backoff per source address as defense-in-depth now that this surface is reachable over more than LAN broadcast.
4. **Replay prevention**: each PAKE run is bound to a fresh, single-use code and a fresh session nonce; a captured/replayed transcript from a prior (even successful) pairing cannot be reused to complete a new one.
5. **Mutual identity/key confirmation**: neither side commits to trusting the other's `HostId`/public credential until *both* sides' key-confirmation MACs succeed — a one-sided success (which is exactly what a MITM relaying without the code would produce on at most one side) aborts the whole exchange on both sides.
6. **What each side persists on success**: a new `TrustedManagers` row — `{ PeerHostId, initial CurrentTrustedPublicKeyFingerprint, DisplayName/MachineName as self-reported, FirstPairedUtc }` — written transactionally, only after key confirmation succeeds on both sides. Nothing is pinned on partial success.
7. **Behavior on failure** (wrong/expired code, key-confirmation mismatch): abort cleanly, no trust record written on either side, the attempt counts against the rate limit (item 3), and the UI reports "pairing failed" — never a partial or ambiguous trust state.
8. **Re-pair after credential loss/revocation**: identical to a first-time pairing — a fresh code, a fresh PAKE run. The only way prior grants carry forward is the manual Owner-adoption path noted in §4a, never automatically from the re-pair itself.

**No cloud PKI dependency**: the entire exchange is direct — LAN discovery response or manually-entered address, with the code communicated out-of-band (read aloud, typed on both sides) — never a third-party CA or an external pairing/relay service, consistent with the "explicitly not built" list at the end of this section.

**Capability/version negotiation:** a `Handshake` RPC is the first thing every connection does (local or remote) before any operational RPC is permitted. It exchanges `{ ProtocolVersion (major.minor), AppVersion, Capabilities[] }`. Feature availability is driven by capability flags the Host actually advertises, never by parsing/comparing app version strings (§13).

**Discovery and addressing:**
- Automatic discovery stays LAN-only, evolving the existing UDP broadcast `PeerDiscoveryService` to advertise a Host's `HostId` + protocol version instead of today's scheme.
- Non-LAN reachability (a VPN, a manually-routed private network) is manual address entry — host/IP plus port — never automatic.

**Explicitly not built:** no cloud relay/relay account service, no UPnP/NAT-PMP/automatic router configuration, no arbitrary remote shell, no general remote filesystem browsing API. The gRPC service surface (defined in `Contracts`, §1) only ever exposes the specific, enumerated Host operations in §1's contract list — there is no generic "execute" or "browse" RPC to misuse.

## 5. Authorization domain model

Concrete, project-owned types (not framework roles/claims):

`ManagerIdentity` below is the same concept as §4a's `TrustedManagers` row — a paired peer, keyed on its stable `PeerHostId`, never on its current credential fingerprint:

```
ManagerIdentity      { PeerHostId, DisplayName, MachineName, FirstPairedUtc }
HostCapability        enum { CreateServer, ManageHostSettings, ManageTrustedManagers,
                              ManagePermissions, GrantPermissions, GrantDelegationAuthority,
                              ManageHostUpdates, ... }
ServerCapability       enum { ViewServer, StartStopRestart, EditSettings, ManageBackups,
                              TransferExport, DeleteServer, ManageServerSharing,
                              GrantServerPermissions, ... }
CapabilityGrant       { GrantId, GranteePeerHostId, Scope (Host | ServerId),
                              Capability, CanDelegate: bool,
                              GrantedByPeerHostId, DerivedFromGrantId: GrantId?,
                              GrantedUtc }
```

Keying grants and identity on `HostId` rather than a credential fingerprint means a legitimate credential rotation (§4a) never disturbs a Manager's accumulated permissions — exactly the property conflating identity with credential would have broken.

- **Role presets are UI convenience only** — a preset (View Only / Server Operator / Server Administrator / Host Administrator) is a named bundle that creates several `CapabilityGrant` rows atomically. The persisted source of truth is always individual grants; presets are never themselves a stored authorization primitive.
- **Delegation is a separate right, not implied by holding a capability.** `CanDelegate` on a grant controls whether its holder may grant that same capability onward. Granting delegation authority is itself just another `CapabilityGrant` with `Capability = GrantDelegationAuthority`.
- **Provenance and cascade invalidation**: every grant records `DerivedFromGrantId`, forming a tree per capability rooted at a direct Owner-issued grant (`DerivedFromGrantId = null`). Revoking a grant transactionally revokes every grant whose `DerivedFromGrantId` chain passes through it. This is a precise, per-grant DAG traversal — not "revoke everything this Manager ever granted" — so unrelated grants issued through different authority are untouched.
- **Local Owner is not a data row.** It's an implicit, structural root of trust (the OS user who completed setup), always holding every capability, never expressed as a revocable `CapabilityGrant` — which is what makes it actually unrevokable by remote Managers rather than merely "protected by convention."
- **Configurable defaults for newly paired Managers**: a Host setting (`DefaultGrantTemplate`) that's applied — as ordinary root grants, `GrantedByPeerHostId = LocalOwner` — at the moment a new pairing completes. Changing the template later never retroactively rewrites grants already issued.
- **Explicit per-server sharing** is just `ServerCapability` grants scoped to a specific `ServerId`; a Manager's server inventory is exactly the set of servers where it holds `ViewServer`.
- **`ManageHostUpdates` is a distinct `HostCapability`** — not folded into `ManageHostSettings` — so update authority can be granted/withheld independently, per #17's explicit requirement.

Pairing (§4b) and authorization are enforced as genuinely separate steps in the request pipeline: a successful mTLS handshake proves *identity*; every subsequent RPC still independently checks the caller's `CapabilityGrant`s for that specific operation and scope. A freshly paired Manager with the least-privilege default template can authenticate perfectly well and still be told "denied" for everything until the Owner grants something.

### 5a. `Host.Cli` vs. Host-exclusive SQLite writer ownership

The prior revision of this document left "does `Host.Cli`'s bootstrap storage share the same SQLite database Host will later own exclusively" as an open question for #20/#21 to invent. That's a boundary decision this issue must fix, not implementation detail — resolved as follows.

**Invariant: while Host is running, Host is the sole writer of authoritative Host state, always.** This is structurally enforced, not just documented:

- **Normal/operational CLI mode** (Host is running): `Host.Cli` is a thin `Contracts`-speaking gRPC client over local IPC (§3), using the exact same operation surface Avalonia uses. It has **no direct database access whatsoever** in this mode.
- **Bootstrap/recovery CLI mode** (Host is not running — e.g. first-ever setup before any Host process has started, or emergency recovery while the Host service is down): `Host.Cli` first attempts to acquire the **same machine-wide exclusivity lock** Host itself uses (§2, owned by `Host.Persistence`). If the lock is already held, Host *is* running, and recovery mode refuses to proceed — it prints "Host is running; use normal CLI commands" rather than risking a concurrent writer. Only once the lock is successfully acquired does `Host.Cli` use `Host.Persistence`'s schema/repository code **directly** — the same code `Host` itself would use, not a separate ad hoc implementation — to perform the specific bootstrap/recovery action (initializing `HostIdentity`, resetting local Owner, etc.), then releases the lock.
- Every bootstrap/recovery-mode write is recorded in `AuditEvents` (§6), tagged as an offline-recovery action, written in the **same transaction** as the change itself using the same persistence code path — so it's auditable even though the Host process wasn't running to log it live.

This gives Host and CLI **no path to ever concurrently mutate the database**: the exclusivity lock is the single arbiter of who may write, and whoever holds it is provably the only writer — not "the only writer by convention."

## 6. Persistent Host state

Host owns a single embedded **SQLite** database under its machine-wide data directory, accessed only by the Host process (and, exclusively in bootstrap/recovery mode, `Host.Cli` — §5a) through `Host.Persistence` (§1).

Why SQLite over continuing the current JSON-file-per-concern approach: the new requirements — transactional cascade invalidation across many `CapabilityGrant` rows, revision/version tokens with atomic compare-and-reject, cross-client-visible operation locks, durable multi-phase recovery state — need real ACID transactions, which `File.WriteAllText`-per-file cannot provide. SQLite is zero-dependency (no separate service to install or fail, which matters for a headless single-machine tool), has mature first-class .NET support, and its single-file-plus-WAL model keeps the backup story as simple as it is today. **This is independently justified by the substantially greater complexity of v0.5's Host state on its own merits — it is not offered as, and does not claim to be, a fix for [#26](https://github.com/shoemin/Palworld-Server-Manager/issues/26), which remains an open, unresolved investigation with no established root cause.**

Logical tables/aggregates:

| Aggregate | Contents |
|---|---|
| `HostIdentity` | This machine's stable `HostId` (§4a), current credential reference (into `ISecureCredentialStore`, §7 — never the key bytes themselves), credential rotation history, setup timestamp |
| `ServerInventory` | Evolution of today's `servers.json` — profile identity, paths, ports, import provenance |
| `TrustedManagers` | Paired peer `ManagerIdentity` rows |
| `CapabilityGrants` | §5's grant rows |
| `AuditEvents` | Pairing/unpairing, grant/revoke, downstream revocation, Owner adoption, failed authorization, major remote admin actions, actor + affected Host/server, before/after state where practical — **never secrets** |
| `OperationRecords` | §10's durable operation/recovery state and §9's operation locks |
| `ConfigurationRevisions` | Revision/version tokens for optimistic concurrency (§9) on settings, permissions, sharing config, Host settings |
| `SecureCredentialReferences` | Opaque references/metadata pointing into the platform secure store — the actual secret bytes never enter this database |
| `MigrationRecords` | v0.4 → v0.5 migration audit trail (§ "v0.4 migration" in #17) |

## 7. Secure credential-storage abstraction

Coordinates directly with [#27](https://github.com/shoemin/Palworld-Server-Manager/issues/27). Contract (`Platform.Contracts`):

```csharp
interface ISecureCredentialStore
{
    Task StoreAsync(string key, ReadOnlyMemory<byte> secret, CancellationToken ct);
    Task<byte[]?> RetrieveAsync(string key, CancellationToken ct);
    Task DeleteAsync(string key, CancellationToken ct);
}
```

- **Windows**: DPAPI (`ProtectedData.Protect`) at **machine scope**, not user scope — Host runs as a machine-wide service (§2), so user-scoped DPAPI (tied to an interactive profile) is the wrong primitive here. Machine scope also matches "one Host identity per physical PC": only that machine's OS installation can decrypt it.
- **Linux**: session-based keyrings (gnome-keyring/kwallet via Secret Service) are explicitly rejected as the *primary* store, because they require an active desktop session and headless unattended boot is a hard requirement. Instead: a locally-generated master key file, `0600` permissions, owned by the Host's dedicated service account. This is the same practical trust model most unattended Linux daemons already rely on for their own secrets (comparable to how `sshd` protects its host keys via file permissions).

  **Threat-model boundary, stated precisely rather than implied:**
  - **Protects against**: ordinary/non-privileged local users (denied by file permissions), accidental disclosure through normal file browsing, appearing in logs/audit/diagnostics (enforced separately, below), and a naive backup script that respects file permissions.
  - **Does not protect against**: a privileged root user on the same machine, or an attacker with offline access to the raw disk (booting from external media, mounting the disk elsewhere). A colocated software key protected only by filesystem permissions provides **no** resistance to either — the permission check is enforced by the running kernel, not by anything cryptographically tied to something the attacker lacks. This baseline must not be described as hardware-backed or offline-disk-resistant, because it is neither.
  - **Optional stronger mitigation**: TPM-backed sealing (binds the key to specific machine hardware/boot state, and can resist offline-disk-copy attacks even against a root-level attacker in some configurations) or `systemd-creds` where it integrates with TPM — offered as an enhancement layered on top of the floor above, not claimed as the baseline.
  - This baseline still satisfies #27's actual requirements: no *recoverable plaintext* secret in ordinary Host state (true — reading it requires OS-level access, not a text editor); unattended headless boot remains possible (true — no interactive unlock needed); no secrets in logs/audit/diagnostics (true, enforced separately below). It does not, and is not represented as, defending against a root-level or offline-disk attacker.
- Secrets never appear in `AuditEvents`, logs, or diagnostic bundles — this is enforced at the logging/serialization layer (a `[Secret]`-style marker on any DTO field that must never be logged, checked by a self-test, not by developer discipline alone).
- v0.4 → v0.5 migration never widens exposure: if a v0.4 secret (e.g. today's plaintext outbound LAN token) can't be migrated into the new model safely, migration stops and reports it rather than silently carrying the weaker format forward.

## 8. Trust revocation architecture

Coordinates directly with [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28).

As established in §4a, **credential revocation and trust revocation are the same operation** — there is no partial "trust the `HostId` but not its current credential" state, since the credential is the only thing that proves you're talking to that `HostId` at all.

- **Online two-sided unpair**: initiator deletes its local `TrustedManagers` row (keyed on `PeerHostId`, §4a) and sends an authenticated `RevokeTrust` RPC over the still-valid mTLS connection; the peer does the same on receipt. Both sides cascade-invalidate dependent `CapabilityGrant`s per §5's DAG traversal.
- **Offline revocation** is structurally simple under the pinned-credential trust model (§4a): trust is a local allow-list keyed on `HostId` with a pinned current-credential fingerprint, not a CA-issued certificate anyone could still present. Deleting the `TrustedManagers` row **is** the revocation — the next connection attempt from that peer fails TLS trust validation immediately (its credential no longer matches anything pinned), with no CRL/OCSP/tombstone-propagation machinery required. This is exactly the elegance the certificate-pinning choice in §4a was made for.
- **Re-pairing** always starts a fresh pairing bootstrap (§4b) — a revoked peer regains nothing by simply reconnecting; it has to re-earn a new `HostId`↔credential pin through the full MITM-resistant flow and starts back at the least-privilege default template (§5), not its old grants (unless manually adopted by the Owner, §4a).
- **Local Owner** can always revoke any remote Manager. A remote administrator may revoke another remote Manager only if explicitly granted that authority under §5's model — revocation itself is gated by the same capability system it operates on.

## 9. Concurrency contracts

- **Revision tokens**: every mutable aggregate that can be edited by more than one actor (server settings, `CapabilityGrant` sets, sharing config, Host settings) carries a monotonically increasing `RevisionId`. Write RPCs must submit the revision they last read; the Host compares it inside the same transaction as the write and rejects with a `StaleWriteConflict` result — never a silent overwrite.
- **Per-server operation locks**: an `OperationLock` row `{ ServerId, OperationKind, AcquiredUtc, OwningOperationId }`, acquired transactionally before an exclusive/destructive operation begins. This is a direct, durable generalization of the existing in-memory `CriticalOperationTracker` — same proven concept (a lease held for an operation's duration, released on completion or exception), now a database row instead of process memory, which is exactly what's needed once more than one client (local and remote) can be watching the same server.
- **Lock visibility**: because the lock is a database row rather than in-process state, every connected client — local or remote — querying operation/Activity status sees the same lock, satisfying "lock visibility to multiple clients" directly.
- **Operation lifetime independent of the initiating client**: the lock and its `OperationRecord` (§10) belong to the operation, identified by its own `OperationId`, not to the client connection that started it. If that client disconnects mid-operation, the Host-side work and its lock continue exactly as they do today when a `SendServerWindow` is closed mid-transfer (the lease is released only when the operation itself finishes or fails) — same principle, now durable and multi-client-visible instead of single-process.

## 10. Durable operation/recovery model

`OperationRecord { OperationId, Kind, ServerId, Phase, StartedUtc, LastHeartbeatUtc, RecoveryDisposition }`.

Phases are **specific to each operation kind**, not a generic state machine — e.g. a Backup operation might declare `{ Started, SourceSnapshotted, ArchiveWritten, Verified, Completed }`. Each operation kind's implementation declares, per phase-transition, which of these applies on recovery:

- `SafeToRetryFromStart` — nothing durable happened yet, just restart it.
- `SafeToResumeFromPhase` — durable, idempotent-from-here work exists; continue from the recorded phase.
- `RequiresManualReview` — ambiguous/partial durable state; do not guess.
- `SafeToDiscard` — partial artifact exists but is worthless; clean it up and mark failed.

**Not every interrupted operation is assumed resumable** — that classification is explicit, per operation kind, per phase, decided by the code that implements that operation, not inferred generically. On Host startup, every non-terminal `OperationRecord` is scanned and its declared disposition applied; anything landing in `RequiresManualReview` surfaces as an explicit "Recovery Required" item in Activity rather than being silently resumed, silently discarded, or reported as if the server were simply idle.

## 12. Core Palworld settings metadata seam

`Core` already models Palworld's INI settings with unknown-key preservation (`PalworldConfigParser`, `PalworldSettingSchema`). That model is extended, not replaced: `Core` owns `PalworldSettingDefinition` records — key, display name, description, category, semantic editor kind, min/max/step/unit/default, validation rules, enum choices, restart-required-if-actually-known.

`Host` exposes this to clients through the protocol boundary, never by `Client.Avalonia` referencing `Core` directly:

```
GetSettingsSchema(serverId) -> SettingDefinition[]
GetServerSettings(serverId, revision) -> { values[], revision }
```

Avalonia renders controls purely from the returned schema + values (§9 of the #18 UI spec's semantic-control table maps `EditorKind` values directly to Avalonia control types) — it never needs to know Palworld's INI format exists. Unknown/future INI keys keep flowing through exactly as `PalworldConfigParser` already preserves them today; they're exposed to the UI through an Advanced/raw surface rather than discarded or guessed at.

## 13. Protocol compatibility policy

`ProtocolVersion = { Major, Minor }`, advertised in every `Handshake` (§4).

- **Major** version mismatch is incompatible and the connection is refused with a clear, specific error naming both versions — **unless** an explicit compatibility range says otherwise (a deliberate, documented exception such as "major 2 also accepts major 1 read-only clients"), never guessed or assumed from app version strings.
- **Minor** version evolution is strictly **additive** — a minor bump may add new fields/RPCs/capabilities, never remove or repurpose an existing one. Removing or changing the meaning of anything requires a major bump.
- **Protobuf field numbers are never reused**, even for fields later removed; removed fields are marked `reserved` in the `.proto` schema rather than freed for reuse — this is what lets an old message on the wire never be silently misinterpreted by a newer schema, or vice versa.
- **Unknown/new optional fields are tolerated safely** — protobuf's default forward-compatible behavior (an older parser ignores fields it doesn't recognize) is relied on deliberately, not worked around.
- **Unknown/new enum values must never accidentally authorize behavior.** An older client or Host encountering a capability/permission enum value it doesn't recognize must treat it as **deny/unknown**, never default-permit — this is the one place "ignore what you don't recognize" (the general forward-compatibility rule above) is deliberately *not* applied, because for an authorization-relevant enum, silently ignoring an unrecognized value in the permissive direction is a privilege-escalation bug waiting to happen.
- **Two-layer gate on every feature**: an operation executes only when *both* protocol-major compatibility holds *and* the specific capability was negotiated in `Handshake` — compatibility alone doesn't imply a feature is available, and capability advertisement alone doesn't bypass a major-version incompatibility.
- **App/product version strings are informational only** — displayed to the user, never consulted for authorization or compatibility decisions. `ProtocolVersion` and `Capabilities[]` are the only inputs to those decisions.
- Handshake is mandatory on **every** connection, local or remote, before any operational RPC is accepted — there's no "trusted because it's local" bypass of version/capability negotiation, only a different auth anchor (§3a vs §4a).

## 14. Testability

Contracts this section leaves stable enough to write **before** #20 needs them (these tests are #20's deliverable, not #19's — #19 only has to make them meaningful to write):

1. **Capability-grant DAG invalidation** — pure-logic unit tests: revoking a grant cascades exactly to its dependents and no further.
2. **Revision/stale-write conflict** — a concurrent write with a stale revision token is rejected, not merged or overwritten.
3. **Operation-lock acquire/release/cross-client visibility** — two simulated clients observe the same lock state; lock survives the initiating client disconnecting.
4. **Recovery-disposition classification** — simulate a Host crash at each declared phase of a representative operation kind and assert the correct disposition is chosen (never assume resumable by default).
5. **Local IPC parity** — the same logical Host contract test suite runs against both the Windows named-pipe and Linux Unix-socket transports and produces identical client-observable behavior.
6. **Handshake/version negotiation** — compatible minor-version connects and correctly hides newer capabilities from an older client; incompatible major-version is refused with a clear error.
7. **Secure-credential-store round-trip per platform** — store/retrieve/delete, plus a redaction assertion that no `[Secret]`-marked field ever reaches `AuditEvents`, logs, or diagnostics.
8. **Pairing bootstrap MITM resistance** (§4b) — a simulated relay-without-the-code attempt must fail key confirmation on at least one side and result in no trust record on either side; expired/wrong-code/rate-limit-exceeded attempts must behave identically.
9. **Credential rotation and loss** (§4a) — a rotation signed by the current credential succeeds and preserves `HostId`/grants; an unsigned/incorrectly-signed rotation attempt is rejected; simulated credential loss correctly requires full re-pairing rather than silently continuing.
10. **`Host.Cli`/`Host` writer exclusivity** (§5a) — a bootstrap/recovery-mode CLI invocation while Host holds the exclusivity lock must be refused, never silently allowed to proceed.

These extend the existing `PalworldServerManager.SelfTest` harness pattern rather than introducing a new, separate test framework.
