# v0.5 architecture: Manager Host and platform boundaries

This document is the deliverable for [#19 — Define Manager Host and Windows/Linux platform abstraction boundaries](https://github.com/shoemin/Palworld-Server-Manager/issues/19), the Gate B architecture item required by the [#17 accepted plan](https://github.com/shoemin/Palworld-Server-Manager/issues/17). It resolves the concrete engineering boundaries #20 (Windows) and #21 (Linux) implement against, so neither has to invent them mid-implementation.

Nothing here authorizes production implementation. It defines contracts, not code.

## 1. Project/assembly topology and dependency direction

Today's tree is three projects: `PalworldServerManager.App` (WPF), `PalworldServerManager.Core`, `PalworldServerManager.Lan`. The accepted #17 boundary list maps onto these new projects — **`PalworldServerManager.Lan` itself is retained, not folded into anything new; see the note below the table (Product Decision, 2026-09-01, `ARCH-002`)**:

**Dependency direction is one-way and enforced by this table**, not by convention: `Core` and `Contracts` never reference `Platform.*`, `Client.Platform.*`, `Host`, `Host.Persistence`, `Client.Avalonia`, or `Client.Cli`, and — critically — `Contracts` never references `Core` either, so nothing downstream of `Contracts` alone can reach a `Core` type transitively. `Platform.Windows`/`Platform.Linux` never reference each other, and neither do `Client.Platform.Windows`/`Client.Platform.Linux`. **`Client.Avalonia` and `Client.Cli` each have no dependency path to `Core`, Host-side `Platform.*`, `Host`, or `Host.Persistence` at all** — their only OS-abstraction dependency is the same separate, `Core`-independent `Client.Platform.Contracts` tree, which exists specifically because a prior revision of this document put `IHostActivation` in the Host-side `Platform.Contracts` (which depends on `Core`) while simultaneously claiming `Client.Avalonia` depends on `Contracts` only — a real contradiction, now fixed by giving ordinary local clients their own, structurally separate platform-contracts boundary. **Neither ordinary client depends on legacy `PalworldServerManager.Lan` either** (`ARCH-002`) — that dependency belongs solely to the frozen `App`. This is what makes "Avalonia and the CLI are management clients, not the process/filesystem authority" structurally true.

`OperatingSystem.IsWindows()`-style branching is confined to exactly three places, each a single composition root: `Host`'s (choosing `Platform.Windows` or `Platform.Linux`), `Client.Avalonia`'s own, and `Client.Cli`'s own (each of the latter two choosing `Client.Platform.Windows` or `Client.Platform.Linux` independently, at their own separate composition roots). Nowhere else in `Core`, `Contracts`, `Host`'s business logic, or either ordinary client's own business logic should branch on OS.

**`Core`'s one explicit legacy carve-out (Product Decision, 2026-09-01, `ARCH-001` governs).** `Core` is not *literally* BCL-only during the v0.5 transition. Verified against the actual repository: `Core.csproj` currently references `Velopack` 1.2.0, and `Core`'s `VelopackUpdateBackend` is constructed directly by the **frozen** `App/AppServices.cs`. `ARCH-001` freezes the WPF app untouched; that app cannot be modified to consume a relocated update backend, so `Core` keeps this one dependency for as long as the frozen app needs it. Rules: no *new* v0.5 Host/Avalonia feature may consume `VelopackUpdateBackend` — new Host update behavior uses `IUpdatePlatform` (§11) instead; the existing legacy updater is not moved or refactored merely to make `Core` dependency-pure; the carve-out is removable only once the frozen WPF app itself is retired under a separately authorized future change. This is a documentation correction only — no production source, `Core.csproj`, or `AppServices.cs` change.

**Legacy `Lan` and new `Contracts` coexist; `Lan` is never renamed (Product Decision, 2026-09-01, `ARCH-002`).** A prior revision of this document described `Contracts` as "renamed/evolved from `PalworldServerManager.Lan`" — verified against the actual repository, that's not implementable while `ARCH-001` keeps the WPF app frozen: `App.csproj` directly references both `Core` and `Lan`, and the frozen `AppServices.cs` directly constructs/consumes `Lan` types including `LanCoordinator`. Renaming `Lan` into `Contracts` would either break the frozen app (which needs `Lan`'s current, `Core`-dependent shape) or force the new, deliberately `Core`-independent `Contracts` assembly to inherit dependencies this design excludes it from. Fixed: `Lan` and `Contracts` are two separate projects with distinct roles, both present in the v0.5 tree (see the table above) — `Lan` stays exactly what it is today, solely for the frozen app; `Contracts` is new, from scratch, and no new v0.5 project depends on `Lan`. The conceptual product/protocol evolution from v0.4 LAN functionality to the new wire contracts may still be discussed historically; the assembly/project relationship is not a rename, and no v0.5 architecture text should imply otherwise. `Lan` is retirable only once the frozen WPF app itself is retired under a separately authorized future change — the same removability condition `ARCH-001`'s `Core`/Velopack carve-out already uses, applied here to a second legacy dependency the frozen app needs.

**Privileged `Host.Cli` and ordinary `Client.Cli` are separate projects with separate privilege domains, never one mixed-authority process (Product Decision, 2026-09-01, `CLIENT-003`).** A prior revision of this document gave `Host.Cli` a "normal operation" mode as a thin `Contracts`-speaking client of a running Host — but `Host.Cli`'s normal-mode dependency set (`Contracts` alone) had no path to `ILocalPrincipalCredentialStore` (declared client-only), so it could never actually satisfy §3a's per-principal signed-challenge requirement for ordinary local-IPC operations; it also risked mixing `Host.Cli`'s privileged offline recovery authority into the same process as ordinary online client authentication. Fixed by separating the two privilege domains into two projects, not by giving `Host.Cli` a credential store: **`Host.Cli` becomes offline privileged-only** (see its table row above) — Host stopped, actual Administrator/root, exclusivity lock held, for the specific enumerated recovery/bootstrap operations only (§5a), never an ordinary authenticated Manager client, never a bypass of `LocalPrincipal` authorization. **`Client.Cli` is the new ordinary online command-line client** (see its table row above), a `Client.Avalonia` peer in every structural sense: same `Client.Platform.Contracts` dependency tree, same `LocalPrincipal` credential model (§3a), same server-authenticated local-IPC route (§3b), no Administrator/root bypass for being a CLI. §2c's Owner-bootstrap flow is the concrete two-phase illustration of this split: `Host.Cli` (offline, privileged) prepares the bootstrap material in phase 1; `Client.Avalonia` **or** `Client.Cli` (ordinary, online, as the intended OS account) completes it in phase 2 — never `Host.Cli` itself acting online.

## 2. Manager Host process/service boundary

- **Exactly one Host per physical PC**, running as a machine-wide service — Windows Service (SCM) or Linux daemon (systemd unit) — under a dedicated service identity, not a per-interactive-user process. This is deliberate: "one authoritative Host per PC" and "multiple local UI sessions must not create competing server authorities" both fail if Host runs per-user.
- Host acquires an OS-level exclusive lock (named mutex on Windows, a lock file with `flock` on Linux) on startup, owned by `Host.Persistence` (§1) and shared with `Host.Cli`'s bootstrap/recovery mode (§5a). A second launch attempt detects the running instance and exits rather than starting a competing instance. **[#26](https://github.com/shoemin/Palworld-Server-Manager/issues/26) remains an open, unresolved investigation — its actual root cause was never established, and nothing here claims to have found or fixed it.** What this design does independently: a single machine-wide, single-instance-locked Host removes the general class of competing-authority/multi-writer risk that a scenario like "two Manager processes running simultaneously" represents, regardless of whether that specific scenario was #26's actual cause. That's a reason to keep this design, not a claim about #26.
- Host owns **all** persistent state exclusively (§6). No other process — including `Host.Cli` once Host is running, and never `Client.Avalonia` or `Client.Cli` (`CLIENT-003`) — writes Host-owned files directly.
- Host exposes local IPC (§3) always, and a remote network listener (§4) only when remote management is enabled in Host settings. Both are served by the same in-process business logic — there is exactly one code path per operation, not a duplicated "local" and "remote" implementation.
- Host lifecycle is independent of `Client.Avalonia`'s lifecycle (§4 of the #17 plan, "Host lifecycle and safety") — the same holds for `Client.Cli` (`CLIENT-003`), which didn't exist when #17's plan was written but is architecturally just another ordinary local client: closing the client disconnects a client, never stops the Host or any server it's running. Desktop Host defaults to boot-start off and idle-exits when nothing needs it; headless Linux Host defaults to boot-start on and simply stays running.

### 2a. Desktop Host activation — a bounded, non-Administrator start path

The accepted combination — desktop boot-start off by default, but opening Avalonia starts/connects to the Host as needed — was asserted in the prior revision without defining how an ordinary user starts a dormant machine-wide service. A normal desktop user must not need broad Administrator/root authority every time the Host happens to be stopped; that would either force boot-start always-on (contradicting the accepted default) or force an elevation prompt on ordinary use (a bad, and telling, sign that the model is wrong).

**Windows**: the installer configures the Host's Windows Service security descriptor **once, at install time**, granting `SERVICE_START` (and `SERVICE_QUERY_STATUS`) — and *only* those rights, never `SERVICE_ALL_ACCESS` or general service-control authority — to a single dedicated local security group (e.g. `PalworldServerManager Users`), not to individual SIDs. This deliberately avoids the ordinary Host process ever needing to rewrite its own service DACL at runtime, which it should not be trusted to do. Authorizing a new local principal is then an ordinary Windows administrative action — adding that OS account to the dedicated group (`net localgroup` / Local Users and Groups) — which itself requires actual local Administrator privilege to perform, same as adding any user to any Windows security group; the product does not need, and does not introduce, its own privileged mechanism for this. Group membership grants only the OS-level right to *attempt* to start the service; it is not application-level authorization — that's still §3a's separate `LocalPrincipal` credential check, so being in the group without a registered credential still connects to nothing useful.

**Linux desktop**: the exact OS-native mechanism (a polkit rule scoped to this one systemd unit, a narrowly-scoped `sudoers` rule, or an equivalent distro-supported delegation) is a **#20/#21 implementation decision**, validated by their preflight against the actual target distributions — this document does not assert a specific mechanism such as a custom polkit action, since Palworld Server Manager does not (yet) own a privileged helper that would make inventing one meaningful. What this document fixes is the **required property**: some bounded, OS-supported mechanism must let an authorized local principal (a member of the same OS group used for `LocalPrincipal` Linux identity, §3a) start specifically this one unit — never a blanket "manage all units" grant, and never general root/sudo.

**Neither mechanism grants general Administrator/root authority** — both are scoped to "start this one specific service," nothing more. `IHostActivation` (`IsHostRunningAsync()`, `RequestStartAsync()`) lives in the **client-side** `Client.Platform.Contracts` (§1, §11) — not Host-side `Platform.Contracts` — since it's exclusively a `Client.Avalonia` concern and Host-side `Platform.Contracts` depends on `Core`, which `Client.Avalonia` must never reach. It is deliberately kept separate from `IHostServiceLifecycle` (§11, Host-side), which remains the full install/start/stop/status surface used by installer/administrative tooling and does require full privilege.

**Client flow**: on startup (or on losing its local IPC connection), `Client.Avalonia` first attempts to connect over local IPC (§3); on failure, it calls `IHostActivation.RequestStartAsync()` through the bounded per-OS mechanism above (running as the ordinary logged-in user, no elevation prompt), then retries the local IPC connection with backoff until Host comes up or a timeout is reached. **This retry-as-dormant behavior applies only to an absent endpoint (§3b case A) — an endpoint that exists but fails local TLS authentication (§3b case B) is a security failure, not a "still starting up" signal, and is never retried as if it were.** Host's own idle-exit decision (§2, unchanged) remains something Host does to itself under the accepted desktop policy — there is no corresponding client-side "stop" permission to define, since a client never tells Host to stop.

**Required #20 validation**: the actual non-elevated start/connect path — an ordinary authorized local user, with no Administrator/root privilege, successfully starting a dormant Host and connecting — must be explicitly validated end to end, not assumed from the mechanism's description alone.

### 2b. Owner immutability and emergency recovery

§3a establishes that no ordinary operation — remote, or local from any `LocalPrincipal` other than the Owner acting through the exceptional path below — can ever change who the Owner is. This subsection defines the one exception precisely, so "unrevokable" doesn't quietly become "no recovery is possible if the Owner's own credential or OS account is lost."

- **Remote actors can never revoke, demote, or replace the local Owner.** There is no RPC, no `CapabilityGrant`, and no protocol message that touches `IsOwner` — it is not part of the remote-facing operation surface (`Contracts`, §1) at all.
- **Ordinary local operations cannot either**, even from a `LocalPrincipal` holding `ManagePermissions` (§5) — `IsOwner` is not a grantable or editable field through any normal Host RPC.
- **OS Administrator/root emergency recovery** is the sole exception, and is deliberately bounded: it is available only through `Host.Cli`'s bootstrap/recovery mode (§5a) — meaning **Host must be offline and the machine-wide exclusivity lock held** by the recovery operation, gated by actual OS root/Administrator privilege at the point of use. It can:
  - **Rotate the Owner's credential**, re-registering a new public key for the existing Owner `LocalPrincipalId`, if the Owner's client-side private key is lost but the original OS account still exists — **as a two-phase flow, the same shape §2c's initial bootstrap already establishes (Product Decision, 2026-09-01, fresh evidence during this round's review)**. A prior revision of this bullet said only "re-registering a new public key," with no defined path for that new key to actually be generated and delivered — and, since `Host.Cli` holds no `LocalPrincipal` credential and never runs online (`CLIENT-003`), there was no way for the recovered Owner to authenticate afterward without one. Fixed:
    - **Phase 1 — privileged preparation**, identical conditions to this whole path (Host stopped, exclusivity lock held, actual Administrator/root): `Host.Cli` creates a `PendingOwnerCredentialRotation { LocalPrincipalId, OsPrincipalRef, SecretVerifier, ExpiresUtc, ConsumedUtc? }` bound to the existing Owner's `LocalPrincipalId` and `OsPrincipalRef`; generates a high-entropy, single-use secret, storing only a keyed verifier — never the raw secret, the same pattern `OwnerBootstrapSecret` already establishes (§2c, §7); delivers the raw secret through the same OS-protected, SID/UID-restricted handoff mechanism §2c already defines.
    - **Phase 2 — intended-user completion**, entirely online, no privileged `Host.Cli` process involved (`CLIENT-003`): the Owner runs `Client.Avalonia` **or** `Client.Cli` as that OS account, authenticates the local Host first (§3b, `LOCAL-004`), reads the handoff, generates a **fresh** `LocalPrincipal` keypair client-side through `ILocalPrincipalCredentialStore` — replacing whatever was lost — and submits the pending secret plus the new public key over that authenticated channel. Host, in one atomic transaction: verifies the secret against the stored verifier; consumes it exactly once; re-registers `PublicVerificationKey` on the **existing** Owner row (same `LocalPrincipalId`, `IsOwner` and `State` unchanged); records the audited completion (`AuditEvents`, §6, same same-transaction pattern as everywhere else in this section). The client persists the resulting binding as a `LocalPrincipalClientCredential` (§3a) exactly as any other credential-issuing flow does. **If the response is lost after this transaction commits, presenting the same secret again is an idempotent retry, not an error** (§2c's identical fix, cross-referenced there) — Host recognizes the already-consumed, still-verifier-matching secret and simply confirms success again (`LocalPrincipalId` is already known from `PendingOwnerCredentialRotation` itself, unlike bootstrap) without re-registering anything a second time.
  - **Re-home Owner status** to a different `LocalPrincipal`, if the original OS account itself no longer exists (deleted Windows/Linux account) — **also a two-phase flow (Product Decision, 2026-09-01, fresh evidence during this round's review), for the same reason "Rotate" above needed one.** A prior revision of this bullet said only "setting it on a new one," implicitly assuming a *different, already-enrolled* `LocalPrincipal` exists to promote — but on a normal single-user installation, the deleted account *was* the only enrolled principal, so there is no other row to promote, ordinary enrollment (§3a) requires an Owner to authorize it and the Owner is exactly who's unavailable, and `Host.Cli` still has no credential store to bootstrap one directly. Fixed to cover both cases with one mechanism:
    - **Phase 1 — privileged preparation**, identical conditions: `Host.Cli` identifies the intended **replacement** Owner by exact new `OsPrincipalRef` (Administrator/root-selected, exactly like §2c's initial bootstrap — never "whoever connects first"); creates a `PendingOwnerRehome { NewOsPrincipalRef, SecretVerifier, ExpiresUtc, ConsumedUtc?, ResultLocalPrincipalId? }`; generates a single-use secret, storing only a keyed verifier; delivers it through the same OS-protected handoff mechanism as above.
    - **Phase 2 — intended-user completion**, entirely online, no privileged `Host.Cli` process involved: the new Owner runs `Client.Avalonia` **or** `Client.Cli` as that OS account, authenticates the local Host first, reads the handoff, and submits the pending secret together with a public key — either a **freshly generated** one (the common, single-user case, where no prior `LocalPrincipal` for this account exists) or their **existing** enrolled principal's current one (the multi-user case, where this account was already an ordinary, non-Owner principal). Host, in one atomic transaction: verifies the secret; consumes it exactly once; creates a new `LocalPrincipal` row **or** locates the existing one for that `OsPrincipalRef` (never both); sets `IsOwner = true`, `State = Active` on that row; **fully revokes the old, now-orphaned row using §3a's already-established `LocalPrincipal` revocation procedure (`LOCAL-003`) — never merely clearing its `IsOwner` flag (Product Decision, 2026-09-01, fresh evidence during this round's review).** A prior revision of this step only cleared the old row's `IsOwner`, leaving it `State = Active` with its `PublicVerificationKey` still registered and any `CapabilityGrant`s it independently held untouched — since native SID/UID cross-checking is explicitly optional (§3a), anyone still transport-eligible and holding a copy of that departed account's credential could keep authenticating as that now-meaningless identity and exercising whatever survives. Fixed: the same transaction that clears `IsOwner` also sets `State = Revoked`, clears `PublicVerificationKey`, and cascade-invalidates that row's `CapabilityGrant`s — exactly `LOCAL-003`'s already-defined revocation, applied here rather than re-invented. Exactly one active Owner ever exists at any point either side of the operation, never zero and never two simultaneously, regardless of whether the new Owner was previously enrolled — and the displaced identity is durably tombstoned, not left dangling. **Records that (created-or-located) `LocalPrincipalId` on the `PendingOwnerRehome` row as `ResultLocalPrincipalId` and returns it to the completing client**, which persists it together with its private key as a `LocalPrincipalClientCredential` (§3a) — a prior revision of this step created the row but never returned its ID for the client to bind against, exactly the gap already fixed for Rotate above and for §2c's initial bootstrap; the freshly re-homed Owner authenticates on its very next connection using that persisted binding, in the single-user case exactly as much as the multi-user one. **If the response is lost after this transaction commits, presenting the same secret again is an idempotent retry** — exactly §2c's fix, cross-referenced there — returning the same recorded `ResultLocalPrincipalId` without repeating the row-creation-or-location, `IsOwner` transfer, or old-row revocation a second time.
- This is an **exceptional, audited** operation: recorded in `AuditEvents` via the same `Host.Persistence`-mediated, same-transaction pattern §5a already established for offline recovery writes, even though Host wasn't running to log it live.
- §5a's earlier description of `Host.Cli`'s recovery actions as "resetting local Owner, etc." was ambiguous; it now means precisely this operation, not an undefined catch-all.

### 2c. Privileged initial Owner bootstrap (Product Decision, 2026-09-01, `OWNER-002`)

A prior revision of this document let the *first* enrollment case — establishing the initial Owner — happen with no gate beyond §3a's transport-level group ACL: "the initial Owner's keypair is generated and its public half registered during initial Host setup... no separate approval needed." That's a real gap: since group membership is the *only* check, and Owner status is structurally unrevokable once set (§2b), the first authorized-group member to reach initial setup — not necessarily the person actually meant to be Owner — permanently claims the role, and the native SID/UID cross-check that might otherwise help (§3a) is explicitly optional, never guaranteed. This subsection closes that gap.

**Machine initialization state.** `HostBootstrapState: Uninitialized | Initialized`. A brand-new Host starts `Uninitialized`; it becomes `Initialized` exactly once, atomically, at the moment described below, and never reverts.

**While `Uninitialized`, a Host has zero normal Manager authority surface.** It exposes only the minimum local bootstrap-completion operation (below) — no remote network listener for ordinary management, no starting/managing Palworld servers, no `CapabilityGrant` issuance, no settings/backups/transfers/or any other normal RPC. There is nothing for an unauthorized connection to do even if it reaches local IPC.

**Phase 1 — privileged preparation.** `Host.Cli` initializes the machine offline (§5a, `CLIENT-003`) — Host stopped, the machine-wide exclusivity lock held, gated by actual OS Administrator/root privilege at the point of use, exactly the same privilege/lock/offline conditions §2b's Owner-recovery operation already requires. It:

1. initializes `HostIdentity` if it does not already exist, generating the machine's own `HostId` and its first credential through the accepted secure-store mechanism (§4a, §7);
2. publishes `LocalHostTrustDescriptor` (§3b) so the local channel is authenticable from the very first client connection;
3. identifies the intended initial Owner by **exact** `OsPrincipalRef` — not "whoever connects first";
4. creates exactly one `PendingOwnerEnrollment` bound to that `OsPrincipalRef`;
5. creates a high-entropy, single-use `OwnerBootstrapSecret`;
6. stores only a keyed verifier of that secret in authoritative Host state — never the raw secret, the same "store a verifier, never the bearer secret itself" pattern §3a's `EnrollmentCodeVerifier` already established;
7. delivers the *raw* secret through an OS-protected handoff **outside** ordinary Host persistence and outside `ISecureCredentialStore` (that store is for secrets *Host itself* later retrieves; this is a one-time value handed to a specific *person* who has no Host-issued credential yet to protect it with) — Windows: an ACL restricting the handoff artifact to the intended SID; Linux: ownership/mode restricting it to the intended UID. Shared product-group membership is deliberately **not** sufficient for this handoff, unlike ordinary transport access (§3). Exact handoff artifact name/location/format is a #20/#21 implementation detail; the required property — readable only by the intended OS principal, by an OS-enforced mechanism, not an application-level check — is fixed here.

The raw `OwnerBootstrapSecret` is never logged, never written to `AuditEvents`, never stored recoverably in ordinary SQLite, expires, is single-use, and is deleted from the handoff artifact once successfully consumed.

**Phase 2 — intended-user completion**, performed by the intended local user, entirely online, with **no privileged `Host.Cli` process involved** (`CLIENT-003`):

1. runs `Client.Avalonia` **or** `Client.Cli` (an ordinary local client, not `Host.Cli`) as the intended OS account;
2. obtains their protected bootstrap handoff via `IOwnerBootstrapHandoffReader` (§1, §3a — readable only because they *are* that OS account);
3. authenticates the local Host **first**, using §3b's server-authenticated channel — the same requirement §3b fixes for every other local exchange applies here too, not as an afterthought;
4. generates their `LocalPrincipal` keypair **client-side**, through `ILocalPrincipalCredentialStore` (§3a), exactly like any other principal's key;
5. submits the one-time bootstrap secret, their public verification key, and the bootstrap request, over that authenticated channel;
6. receives the resulting `LocalPrincipalId` in Host's response and persists it together with its private key as a `LocalPrincipalClientCredential` (§3a) — the same binding step every other principal's enrollment already performs — after which it authenticates on every subsequent connection exactly like any other `LocalPrincipal`.

Host then, in one atomic transaction: verifies the presented secret against the stored `PendingOwnerEnrollment`'s verifier; consumes it exactly once; creates the initial Owner `LocalPrincipal` (`IsOwner = true`, `State = Active`, the submitted public key registered); sets `HostBootstrapState = Initialized`; records the audited bootstrap completion (`AuditEvents`, §6) — the same same-transaction audit pattern §2b's offline recovery already uses; **durably records the resulting `LocalPrincipalId` on the `PendingOwnerEnrollment` row itself (`ResultLocalPrincipalId`, alongside `ConsumedUtc`)**; returns the new `LocalPrincipalId` to the completing client (step 6 above).

**Completion is retryable if the response is lost, without ever repeating the underlying transaction (Product Decision, 2026-09-01, fresh evidence during this round's review).** A prior revision of this flow had no answer for the connection dropping *after* the transaction above commits but *before* its response reaches the client: the client never learns its `LocalPrincipalId` and can never construct a `LocalPrincipalClientCredential` to authenticate with, yet `HostBootstrapState = Initialized` and the consumed `PendingOwnerEnrollment` make the bootstrap RPC permanently unusable for a second attempt — the only Owner row that exists becomes unusable by anyone, recoverable only through a full privileged offline recovery (§2b) that shouldn't have been necessary. Fixed: if the **same** secret is presented again against an **already-consumed** `PendingOwnerEnrollment` (verified against the still-retained `SecretVerifier`, not cleared merely because it was already used once) and the record's `ExpiresUtc` window hasn't lapsed, Host does not error and does not repeat the creation transaction — it simply returns the already-recorded `ResultLocalPrincipalId` again, a safe, idempotent read. A secret that doesn't match, or a retry attempted after `ExpiresUtc`, is rejected exactly as a first-time attempt would be. **The same idempotent-retry treatment applies to §2b's `PendingOwnerCredentialRotation` and `PendingOwnerRehome` completions below** — both share this exact one-time-secret-then-respond shape, and a lost response after either one's transaction commits is exactly as recoverable-without-repeating-the-transaction as this case, for the identical reason.

**After initialization**: exactly one active Owner exists, matching `LOCAL-001`'s clarified statement below; the initial-bootstrap RPC is permanently disabled — `HostBootstrapState = Initialized` is itself the gate, not a runtime check that could be raced; no other group member, having failed to be the one who completed the original bootstrap, can replay or race their way into becoming Owner; a *second* bootstrap attempt after initialization can never succeed, full stop. Any *future* Owner credential or OS-account loss uses the existing, unchanged offline Owner-recovery path (§2b) — this bootstrap flow exists only for the machine's very first Owner, never as an ongoing recovery mechanism.

**If bootstrap expires before completion** (the `PendingOwnerEnrollment`/`OwnerBootstrapSecret`'s own bounded lifetime, an implementation-level policy value like `PeerBound`'s pending window, §4b), the Host remains `Uninitialized` and a fresh Administrator/root-authorized `Host.Cli` bootstrap is required — nothing silently lets a different, unintended caller become Owner instead.

## 3. Local client transport

- **Windows**: `System.IO.Pipes` named pipe, fixed name scoped to the product (e.g. `PalworldServerManager.Host`), pipe ACL restricted to connect-access for the **same dedicated local security group** used for service-start authorization (§2a) — the group every authorized `LocalPrincipal`'s OS account is a member of — plus local Administrators for recovery/troubleshooting convenience. A prior revision of this document scoped the pipe ACL to "Administrators plus the Owner's SID only," which contradicted allowing any other authorized local principal to connect at all; this is the fix. This is a **transport-level** restriction (defense in depth, §3a) — connect-access via group membership alone grants nothing; the application-level credential check below (§3a) is what actually authenticates *which* principal is connecting.
- **Linux**: Unix domain socket at a fixed system path (e.g. `/run/palworldservermanager/host.sock`), `0660` permissions, owned by the same dedicated OS group. Same defense-in-depth role as the Windows ACL.
- **Neither the pipe ACL nor the socket permissions authenticate that the *server* is genuinely the Host (Product Decision, 2026-09-01, `LOCAL-004`).** Group-membership connect-access is a transport-level filter on who may *attempt* a connection — it says nothing about who *created* the endpoint. §3b closes that gap with server authentication on top of this transport.

### 3a. Local-caller identity — persistent per-principal model, client credential separate from Host verifier

The prior revision of this document authorized *any* local connection presenting one shared bootstrap secret, and separately described that secret in a way that implied it was ultimately just another entry in Host's own (machine-service-scoped) `ISecureCredentialStore` — which would mean an interactive user's own credential had to be readable from a store designed for Host's service-account-only secrets. Both problems are fixed by an **asymmetric, per-principal keypair model**, distinguishing what the client holds from what Host holds.

```
LocalPrincipal   { LocalPrincipalId (stable, generated once per authorized
                    local user), OsPrincipalRef (Windows SID / Linux UID,
                    recorded at authorization time — a claim to be cross-
                    checked per below, never solely trusted on its own),
                    IsOwner: bool (true for exactly one row on an
                    Initialized Host — §2c's privileged bootstrap or
                    §2b's Owner recovery are the only two paths that
                    can ever set it; never by any ordinary operation),
                    State: Active | Revoked
                    (durable lifecycle state, §3a "Revocation" below —
                    independent of OS-group membership), PublicVerificationKey?
                    (this principal's current public key when State = Active;
                    not secret, safe to store in ordinary Host persistence,
                    not ISecureCredentialStore; cleared/unset while Revoked),
                    DisplayName, CreatedUtc }
```

- **Each `LocalPrincipal` has its own keypair, generated client-side, never Host-side, through a concrete contract**: `ILocalPrincipalCredentialStore` in `Client.Platform.Contracts` (§1, §11) — **shared by every ordinary local client, `Client.Avalonia` and `Client.Cli` alike (Product Decision, 2026-09-01, `CLIENT-003`), never by `Host.Cli`**, which holds no `LocalPrincipal` credential of any kind:

  ```csharp
  interface ILocalPrincipalCredentialStore
  {
      Task<bool> HasCredentialAsync(CancellationToken ct);
      Task<LocalPrincipalKeyPair> CreateAndStoreAsync(CancellationToken ct);
      Task<LocalPrincipalPrivateKey?> LoadAsync(CancellationToken ct);
      Task DeleteAsync(CancellationToken ct);
  }
  ```

  This governs only the **current OS user's own** credential — it has no operation that could reach any other principal's key or any Host machine credential, structurally matching "never expose Host machine credentials." Its Windows implementation (`Client.Platform.Windows`) uses DPAPI at **`CurrentUser` scope** (the correct scope here, unlike Host's `LocalMachine`-scoped DPAPI, §7: `Client.Avalonia` and `Client.Cli` are interactive/invoked per-user processes, not a machine-wide service, so per-user protection is both correct and sufficient). Its Linux implementation (`Client.Platform.Linux`) uses an appropriate persistent interactive-user secret store (e.g. the desktop session's Secret Service keyring where available) — with the exact fallback behavior where no such keyring is available left as a #20/#21 Linux-implementation decision, since desktop-Linux credential-storage availability varies more across environments than Host's uniform headless/service scenario (§7). Either way, this credential only ever needs to be available while that person is actively using `Client.Avalonia` or `Client.Cli`; there is no headless-unattended-boot requirement for it, unlike Host's own secrets. The private key **never leaves the client machine and is never transmitted to Host, stored in Host's `ISecureCredentialStore`, or written to `Host.Persistence` in any form.**
- **The client-side identity binding, made explicit (Product Decision, 2026-09-01, `CLIENT-003`)**:

  ```
  LocalPrincipalClientCredential { LocalPrincipalId, PrivateKey }
  ```

  After any enrollment or bootstrap succeeds, the client persists this binding — the `LocalPrincipalId` Host assigned, together with the private key `ILocalPrincipalCredentialStore` already protects — so it knows *which* principal it authenticates as on every subsequent connection, not merely that it has *some* keypair. This does not change the asymmetric challenge/response model above; it makes the client side of that model's identity binding concrete and implementable. `Client.Avalonia` and `Client.Cli` use the **same** `LocalPrincipalClientCredential` for the same OS user — never a separate identity per client application.
- **Host stores only the public verification key**, in the ordinary `LocalPrincipals` table (§6) — not a secret, so it needs no special protection beyond the table's own integrity, unlike the machine-scoped secrets in `ISecureCredentialStore` (§7).
- **Authentication is a challenge/response, not presenting a shared value.** On each local IPC connection, Host issues a fresh nonce; the client signs it with its private key; Host verifies the signature against the stored `PublicVerificationKey` for the claimed `LocalPrincipalId`. This maps every connection to exactly one principal without either side ever transmitting the private key itself.
- **Enrollment** (registering a principal's public key) happens two ways. **The initial Owner's enrollment is a privileged, gated bootstrap, not an unconditional first-connection claim (Product Decision, 2026-09-01, `OWNER-002`) — see §2c for the complete flow.** A prior revision of this section said the initial Owner's keypair was simply "registered during initial Host setup... no separate approval needed," which — since the only gate was §3a's own transport-level group ACL below — let the first authorized-group member to connect permanently claim the structurally-unrevokable Owner role. §2c fixes this: initial Owner establishment requires a privileged `Host.Cli` bootstrap bound to an exact, Administrator/root-selected `OsPrincipalRef`, a single-use `OwnerBootstrapSecret` delivered through an OS-protected handoff, and completion over §3b's server-authenticated channel — never mere OS-group membership.

  **For every other principal — a new non-Owner principal, or reactivating a `Revoked` one — OS-group/ACL membership is transport eligibility only, never application-level enrollment or re-enrollment authority (Product Decision, 2026-09-01, `LOCAL-003`).** §2a's platform-level authorization (Windows group / Linux group equivalent) still gates who can even *attempt* local IPC at the transport layer, and remains useful defense-in-depth — but it is not, by itself, sufficient to create or reactivate a `LocalPrincipal`. Enrollment additionally requires an explicit, Host-side, **Owner-created** authorization record:

  ```
  PendingLocalPrincipalEnrollment { EnrollmentId, OsPrincipalRef,
                      EnrollmentCodeVerifier (a keyed HMAC/hash of the
                      generated EnrollmentCode, never the code itself —
                      see below), ExistingLocalPrincipalId? (set when
                      this reactivates a Revoked principal rather than
                      creating a new one), CreatedByOwnerLocalPrincipalId,
                      ExpiresUtc, ConsumedUtc?, FailedAttempts (Product
                      Decision, 2026-09-01, fresh evidence during this
                      round's review — see below), ResultLocalPrincipalId?
                      (Product Decision, 2026-09-01, fresh evidence during
                      this round's review — see below) }
  ```

  Properties: Owner-created only, for v0.5 (no delegated identity-management capability exists yet — see below); bound to exactly one `OsPrincipalRef`; single-use; bounded expiration; audited (`AuditEvents`, §6). **`OsPrincipalRef` alone does not authenticate the connecting party.** The shared transport-level group ACL (§3) proves only "some authorized group member is connecting," not "the specific person the Owner intended"; without a reliably available native peer-identity cross-check (below — not guaranteed on every platform/transport), any other group member who can discover or guess a pending `OsPrincipalRef` could otherwise consume someone else's enrollment with their own key. The fix reuses the pattern §4b's pairing bootstrap already established for exactly this class of problem: the Owner communicates a freshly generated `EnrollmentCode` **out-of-band** to the intended person (the same "read aloud, typed on both sides" channel §4b uses, never transmitted over local IPC in the clear ahead of time) — the enrolling client must present the matching `EnrollmentCode`, not merely claim the `OsPrincipalRef`, for Host to consume the record. **The raw code is never persisted.** `EnrollmentCode` is a bearer secret exactly like a password, so it gets the same treatment as any other secret under §7's threat model, not the plaintext-in-ordinary-persistence treatment a public verification key gets: Host stores only `EnrollmentCodeVerifier`, a keyed HMAC/hash of the code computed using key material held in `ISecureCredentialStore` (§7) — the same reason `LocalPrincipal` stores only a *public* verification key and never the private one (§3a), applied here to a symmetric secret instead of an asymmetric keypair. A copy of the ordinary SQLite database therefore reveals no usable code, consistent with §7's "no recoverable plaintext secret in ordinary Host state" requirement, and `EnrollmentCodeVerifier` is covered by the same `[Secret]`-marker redaction enforcement (§7) as everything else that must never reach `AuditEvents`, logs, or diagnostics. The next time `Client.Avalonia` **or** `Client.Cli` (`CLIENT-003`) runs as that OS account and attempts local IPC, finding no local keypair yet, it generates one and presents the public half **together with the `EnrollmentCode`**; Host recomputes the HMAC over the presented code and consumes the matching, unexpired `PendingLocalPrincipalEnrollment` **atomically** with registering the key, rejecting a correct key with a wrong or missing code exactly as it would a wrong pairing code. **A wrong-code attempt is rate-limited, not merely rejected.** A prior revision of this paragraph specified expiration and single-use consumption but no failed-attempt limit — unlike §4b's pairing code, which explicitly locks out after ten wrong attempts, a short, read-aloud `EnrollmentCode` presented with an attacker-controlled key would otherwise be guessable online, by any other transport-eligible group member, before it expires. Fixed the same way: each `PendingLocalPrincipalEnrollment` tracks `FailedAttempts`, incremented on every wrong-code presentation against it; on reaching the same bound §4b's pairing code already uses (ten), the record is locked out — rejecting even a subsequently correct code — for the remainder of its `ExpiresUtc` window, exactly mirroring §4b's existing lockout, requiring the Owner to issue a fresh enrollment (a new code, a new record) rather than silently extending the guessing window. If `ExistingLocalPrincipalId` was set, this reactivates that principal (`State: Revoked -> Active`, new `PublicVerificationKey` registered) rather than creating a new row — see "Revocation" below for what reactivation does and does not restore. **Either way, the consumption response returns the (new-or-reactivated) `LocalPrincipalId` to the enrolling client (`CLIENT-003`)**, which persists it together with its private key as a `LocalPrincipalClientCredential` (above) — the same binding §2c's Owner bootstrap performs, generalized to every enrollment path. **The consumption records that `LocalPrincipalId` as `ResultLocalPrincipalId` on the `PendingLocalPrincipalEnrollment` row, and a lost response is recoverable the same idempotent way §2c's bootstrap completion already defines (Product Decision, 2026-09-01, fresh evidence during this round's review)** — presenting the same, correct, already-consumed code again (rather than a wrong or missing one) returns the same `ResultLocalPrincipalId` again, bounded by `ExpiresUtc`, without a second registration; this is the fourth and last of the mechanisms sharing this exact one-time-secret-then-respond shape (alongside §2c's bootstrap and §2b's Rotate/Re-home) to need it, all fixed the same way for the same reason. **`ManagePermissions` does not imply this authority** — issuing a `PendingLocalPrincipalEnrollment` is Owner-only, exactly like `DefaultGrantTemplate` editing (§5); a future delegated identity-management capability is a separate Product Decision, not implied here.
- **The initial local Owner is persisted, not pretended not to exist.** The OS user who completes initial setup gets a `LocalPrincipal` row with `IsOwner = true`. "Unrevokable" is enforced by the *authorization rule*, not by omitting the record: no ordinary operation — remote, or local from any other `LocalPrincipal`, including one holding `ManagePermissions` — can ever change any row's `IsOwner` flag; the only path that can is the exceptional Owner-recovery operation defined in §2b. Authorization code never evaluates the Owner's authority through the revocable `CapabilityGrant` mechanism (§5) at all — `IsOwner = true` is checked directly and always grants everything, so there is no grant for anyone to revoke.
- **Explicitly authorized additional local users** get their own `LocalPrincipal` row (`IsOwner = false`), their own distinct keypair (never the Owner's), and — separately, via §5's authorization model — whatever `CapabilityGrant`s the Owner (or someone the Owner delegated to) chooses to give them. A non-Owner local principal may hold real capability scope without ever becoming Owner.
- **Revocation is durable and OS-group-independent (Product Decision, 2026-09-01, `LOCAL-003`).** Revoking a non-Owner principal sets `State = Revoked` and clears `PublicVerificationKey` — the row itself is **retained**, not deleted, so the semantic identity persists across revocation. Revocation cascade-invalidates that principal's current `CapabilityGrant`s using the existing subtree/provenance rules (§5) — every other principal's keypair and grants are untouched, since each is independent. Revocation **does not depend on removing the OS account from the dedicated group** — removing OS-group membership remains useful transport-level defense-in-depth on top of this, but application-level revocation is fully effective on its own, closing the gap where a still-group-member revoked user could otherwise just regenerate a keypair and reconnect. A `Revoked` principal cannot self-reactivate merely because its `OsPrincipalRef` can still reach local IPC — reconnecting with a freshly generated keypair authenticates nothing without a matching `PendingLocalPrincipalEnrollment` (above), and Host has none for a `Revoked` principal until the Owner explicitly issues one. Reactivating a `Revoked` principal restores the same semantic `LocalPrincipalId` and lets it authenticate again — it **never** automatically restores the `CapabilityGrant`s revocation removed; any new authority is granted explicitly, afterward, through the ordinary grant-issuance model (§5).
- **Local users with no Manager authority** simply have no `LocalPrincipal` row and no registered key at all — there's nothing for them to sign a challenge with, so they never reach an authorization check to fail.
- **Native SID/UID cross-check**: if #20's preflight (below) finds that the chosen Kestrel transport reliably exposes native peer identity, Host cross-checks the transport-reported identity against the connecting principal's stored `OsPrincipalRef` as defense-in-depth — a mismatch is rejected and logged as suspicious.
- **OS administrator/root emergency recovery** is a distinct, exceptional operation, not ordinary `LocalPrincipal` authority — see §2b.

**Required #20 preflight/contract-validation gate** (unchanged in spirit from prior revisions): #20 must run a standalone spike proving whether the *selected* Kestrel named-pipe/Unix-socket transport exposes native peer identity reliably enough to use as the cross-check described above. The design's actual authorization decision never depends on that spike succeeding — the per-principal signed-challenge mechanism is what this design formally commits to.

- Local and remote clients use the **same logical operation contracts** (`Contracts` project, §4) — local IPC and the remote network listener both speak the same RPC surface; only the transport and the auth-anchor (per-principal signed challenge vs. paired remote credential, §4a) differ.

### 3b. Authenticated local Host channel (Product Decision, 2026-09-01, `LOCAL-004`)

§3a proves *which `LocalPrincipal`* is connecting. It never proves the other direction: that the process on the other end of the named pipe or Unix socket is genuinely the Host. A prior revision of this document left that gap open — and it's a real, exploitable one: named-pipe and Unix-socket names have no built-in server-identity guarantee, so while the Host is dormant (§2, the documented desktop default) and `Client.Avalonia` is between calling `IHostActivation.RequestStartAsync()` (§2a) and the real SCM-managed Host actually claiming the endpoint, another member of the same dedicated authorization group could pre-create an endpoint with the same fixed name — a well-known class of local-IPC squatting attack — and either directly capture whatever the client sends next (an `EnrollmentCode`, an `OwnerBootstrapSecret`, §2c) or relay a live session to the real Host once it starts, completing it as the victim. This subsection closes that gap.

**The local RPC connection is server-authenticated and integrity-protected before a client sends anything sensitive.** Concretely, before transmitting an `EnrollmentCode` (§3a), initial-Owner bootstrap material (§2c), a `LocalPrincipal` authentication signature (§3a), any credential or other secret material, or any ordinary management RPC, the channel itself must already provide server authentication, confidentiality, and integrity — **standard TLS** over the selected local stream (named pipe on Windows, Unix domain socket on Linux), not a custom application-level cryptographic protocol. The exact .NET/Kestrel wiring for local-transport TLS is a #20 implementation detail; the required security property — server-authenticated, confidential, integrity-protected — is fixed here.

**The TLS server credential is the existing Host machine identity credential (§4a), never a new one.** Reusing `HostIdentity`'s own credential means the same identity that's already the anchor for remote peer trust also anchors local trust — one credential, one rotation/recovery story, not two. The Host's **private** key never leaves the Host process; this was already true for remote mTLS (§4c, §7) and stays true here.

```
LocalHostTrustDescriptor { HostId, CurrentHostCredentialFingerprint,
                    PendingHostCredentialFingerprint?, PendingRotationId?
                    (§4a-i, `IDENT-003` — set only while a routine
                    credential rotation is staged; both null otherwise) }
```

- **Public identity material only** — no secret ever appears in this descriptor; it exists specifically so a client can verify without needing anything Host must protect.
- **Writable only by**: privileged bootstrap/recovery (`Host.Cli`, offline, Administrator/root, exclusivity lock — §2b, §2c, §5a), or the authoritative Host service itself when performing an *authorized* credential rotation (§4a) — never by an ordinary client, never by an unprivileged local process.
- **Readable by** any local user permitted to use the Manager client — this is why it cannot live inside the Host-exclusive SQLite database (§6, `PERSIST-001`/`HOST-002`: Host is the sole reader/writer of that store): `LocalHostTrustDescriptor` is a separate, machine-readable public artifact Host publishes alongside its database, not a row inside it. Exact file format/location is a #20/#21 implementation detail.
- **Both Windows and Linux follow this same rule** — no platform-specific exception to public-readability or privileged-only-writability.
- **Neither `Client.Avalonia` nor `Client.Cli` ever receives the Host private key** — each only ever reads the public `LocalHostTrustDescriptor`, exactly the same boundary §4c already established for remote credentials, now stated for the local case too.

**Client behavior, before pinning:** the client loads `LocalHostTrustDescriptor`, connects, and verifies the TLS server credential's fingerprint against `CurrentHostCredentialFingerprint` — or, while a routine rotation is staged (§4a-i, `IDENT-003`), also accepts a match against `PendingHostCredentialFingerprint` — for the expected `HostId`, reloading the descriptor fresh on each connection rather than caching one fingerprint indefinitely. This is the same pin-then-verify shape §4a's remote credential model already uses, applied locally.

**Client authentication is unchanged, and happens *inside* this now-authenticated channel.** §3a's per-principal signed-challenge mechanism is not replaced by this — a shared channel-level credential is not a substitute for per-principal client authentication, any more than remote mTLS being authenticated replaces the local-authorization/remote-authorization dual check in §4c. This closes the *server*-authentication gap; §3a already closes the *client*-authentication one.

**Connection-outcome semantics — two cases, never conflated:**

- **A. Endpoint absent, or connection refused.** The Host may simply be dormant — `IHostActivation.RequestStartAsync()` (§2a) applies as already documented, and the client retries with backoff.
- **B. Endpoint exists, but local TLS authentication fails** (fingerprint mismatch, untrusted credential, or any TLS-layer trust failure). **This is a security failure, never treated as case A.** The client does not send any secret, does not send a `LocalPrincipal` signature, does not proceed with any ordinary RPC, and does not silently retry as if the Host were merely starting up. It surfaces an explicit local-endpoint-authentication error to the user. A relay that cannot terminate the authenticated TLS session on the real Host's behalf — including a byte-for-byte proxy — cannot learn or modify the traffic flowing through it once this check is in place; this is what actually closes the named-pipe-squatting scenario, not merely making it harder.

**Credential rotation and recovery keep the descriptor consistent.** A routine, staged Host credential rotation (§4a-i, `IDENT-003`) updates `LocalHostTrustDescriptor` **twice, not once**: first adding `PendingHostCredentialFingerprint`/`PendingRotationId` while staging (§4a-i step 4), then, only once every remaining `Active` remote peer has also staged the new credential, promoting it to `CurrentHostCredentialFingerprint` and clearing the pending fields at global cutover (§4a-i step 5) — a client is never left pinning a value the Host itself has already superseded, and never told mid-rotation that only the new credential is acceptable while a remote peer might still legitimately be relying on the old one. Exact atomic-replacement mechanics (e.g. write-new-then-rename) for either update are a #20/#21 implementation detail; the required property — a client is never told to accept an unpinned credential merely because rotation or recovery occurred, and always accepts whichever of `Current`/`Pending` the Host is actually presenting during a staged window — is fixed here.

**`HostIdentity.CurrentCredentialRef` (SQLite) and `LocalHostTrustDescriptor` (a separate file) can never be updated as one atomic transaction, and every mechanism that touches both must say so explicitly (Product Decision, 2026-09-01, fresh evidence during this round's review).** A prior revision of the Host machine-credential-loss recovery operation below claimed to update both "in one atomic transaction" — that's impossible by construction, since §6 already establishes `LocalHostTrustDescriptor` as deliberately *outside* the Host-exclusive SQLite database, so no single database transaction can span both stores. If the process crashes between the two writes, the two stores disagree about which credential is current. Fixed with a general rule every such mechanism relies on: **`HostIdentity.CurrentCredentialRef` in SQLite is the sole authoritative source of truth; `LocalHostTrustDescriptor` is always a derived publication of it, never the other way around.** `HostIdentity.CurrentCredentialRef` is updated first, as its own ordinary SQLite transaction (already atomic on its own). Before Host serves **any** local IPC connection — on every startup, not merely after a crash — it compares the fingerprint implied by `HostIdentity.CurrentCredentialRef` against `LocalHostTrustDescriptor.CurrentHostCredentialFingerprint`; a mismatch means an interrupted republish, and Host republishes the descriptor from the authoritative SQLite value before accepting any connection, closing the gap deterministically rather than leaving it to chance. This reconciliation is idempotent and cheap enough to run unconditionally, not merely when a crash is suspected. §4a-i's own step 5 cutover already writes both in this same order (`CurrentCredentialRef` first, descriptor second, per that step's own text) and is covered by this same reconciliation rule — it is stated once, here, rather than redefined separately for each mechanism that needs it.

**The same startup reconciliation also covers the descriptor's `Pending*` fields against `HostCredentialRotation`, not merely `Current` against `HostIdentity` (fresh evidence a round later — this rule's scope was too narrow as first written).** A prior revision of this rule compared only the *current* fingerprint, which a crash during `HostCredentialRotation`'s own **Abort** step (§4a-i) does not disturb — `Abort` never touches `HostIdentity.CurrentCredentialRef` at all, so a crash between marking `State = Aborted` (SQLite) and republishing the now-cleared descriptor (a separate file) would pass the *current*-fingerprint check with no mismatch found, silently leaving the descriptor's abandoned `Pending*` fields in place indefinitely — exactly the exposure the Abort fix exists to close, just reopened via a crash instead of a missing step. Fixed: the same unconditional startup check also compares the descriptor's `PendingHostCredentialFingerprint`/`PendingRotationId` against the latest `HostCredentialRotation` record for this `HostId`: if that record's `State` is `Aborted` or `Completed` (no rotation genuinely in progress) but the descriptor still carries non-null `Pending*` fields, Host clears them before serving any connection; if `State` is `Staging`/`ReadyForCutover` (a rotation genuinely in progress) but the descriptor's `Pending*` fields don't yet reflect `NewCredentialRef`'s fingerprint, Host (re-)publishes them to match. Both directions of this check are unconditional on every startup, exactly like the `Current`-fingerprint check beside it — never merely triggered when a crash is suspected.

**Host machine-credential-loss recovery, defined precisely (Product Decision, 2026-09-01, fresh evidence during this round's review).** A prior version of this subsection claimed "§2b's privileged offline recovery" replaces a lost/corrupted Host machine credential and refreshes the descriptor — that was wrong: §2b's recovery operation rotates or re-homes only the **Owner's `LocalPrincipal`** keypair, and §5a scopes `Host.Cli`'s bootstrap/recovery-mode writes to exactly §2c's initial-Owner bootstrap or §2b's Owner-credential operation — neither touches `HostIdentity.CurrentCredentialRef` at all. With no defined operation for this case, a lost/corrupted Host machine key would have permanently locked out local TLS (§3b) with no recovery path. This subsection closes that gap, using the same privilege model §2b/§2c already established rather than inventing a new one:

- Performed only through `Host.Cli`'s existing bootstrap/recovery mode (§5a) — Host stopped, the machine-wide exclusivity lock held, gated by actual OS Administrator/root privilege at the point of use, the same conditions §2b's Owner recovery and §2c's initial bootstrap already require.
- Generates a fresh key pair through the accepted secure-store mechanism (§4a, §7); updates `HostIdentity.CurrentCredentialRef` to reference it, in its own SQLite transaction; republishes `LocalHostTrustDescriptor` (§3b) with the new fingerprint as the following, separate step — **never claimed as one atomic transaction spanning both stores, since that's impossible (above)**. If `Host.Cli` crashes between the two writes, the general startup-reconciliation rule above republishes the descriptor from the now-authoritative SQLite value before Host ever serves a connection — a client is never left pinning a value Host itself has already superseded, the same property ordinary rotation guarantees above, now also true for the loss/recovery case, and now also true across a crash mid-recovery.
- Recorded in `AuditEvents`, tagged as an offline-recovery action, in the **same SQLite transaction as the `HostIdentity.CurrentCredentialRef` update** — the same same-transaction offline-audit pattern §2b/§5a already use; the descriptor republish is a separate step (above) and isn't part of this transaction, since it can't be.
- **Does not, and cannot, restore trust with already-paired remote peers by itself.** A lost Host machine key means rotation-under-the-old-key (§4a) is impossible for the remote side too, exactly as §4a's existing "Credential loss" bullet already describes — this recovery operation only re-establishes the *local* side (a fresh `HostIdentity` credential and a consistent `LocalHostTrustDescriptor`); each already-paired remote peer independently detects the mismatch on its next connection attempt and the Host must re-pair with it via a fresh §4b bootstrap, landing at that peer's §4b-i `PendingCredentialReplacement` gate (since the `HostId` is unchanged and already known to that peer) — requiring that peer's own local Owner approval before trust resumes, exactly as already specified. No new remote-trust mechanism is introduced here; this operation only fixes the local-channel half of credential loss, and existing peers do not silently regain trust merely because the Host's own database recognizes its new key.

## 4. Remote Manager ↔ Host protocol

**Selected: gRPC over TLS, hosted on Kestrel.** Kestrel/ASP.NET Core hosting is existing infrastructure (`ManagerLanHost` already depends on it) being evolved, not replaced. **gRPC itself is a genuinely new dependency, not a zero-cost addition**: it requires `Grpc.AspNetCore` (server), `Grpc.Net.Client` (client), and `Google.Protobuf` + `Grpc.Tools` (schema/codegen) — none of which the v0.4 codebase currently references (v0.4's REST endpoints use plain ASP.NET Core Minimal API, not gRPC). Recorded here explicitly as a new technology dependency, not implied to already be present.

Why gRPC specifically, evaluated against the actual requirements rather than convenience:
- **Protocol/capability negotiation** (§13) is naturally strongly-typed via protobuf service contracts and an explicit `Handshake` RPC, rather than something bolted onto a loosely-typed REST/JSON surface.
- **Streaming** is built in and is a real requirement here — Activity/log/metrics push (the #18 UI spec references this directly) needs server-streaming, which gRPC supports natively over the same connection as unary RPCs; a REST API would need a second mechanism (SSE/WebSockets) for the same job.
- Cross-platform .NET support (`Grpc.AspNetCore` / `Grpc.Net.Client`) is mature.

### 4a. Stable Host identity vs. authentication credential

The prior revision of this document defined a TLS certificate's fingerprint as *the* Host's identity. That's wrong: a certificate/key is an **authentication credential**, not the semantic identity of the physical Host, and conflating the two makes credential rotation indistinguishable from becoming a different Host. These are now two separate, explicitly related concepts:

```
HostIdentity     { HostId (ULID/GUID, generated once during machine Host
                    initialization, never changes for this physical PC's
                    life), CurrentCredentialRef (private-key reference into
                    ISecureCredentialStore, §7) }

TrustedManagers  { PeerHostId (stable, never changes),
                    State: PeerBound | Active | Revoked (§4b's
                    already-established pairing states, plus Revoked —
                    a row is retained, never deleted, once it has
                    reached PeerBound; see §8),
                    CurrentTrustedPublicKeyFingerprint? (cleared, not
                    merely stale, once Revoked),
                    PendingTrustedPublicKeyFingerprint?,
                    PendingRotationId?, PendingRotationExpiresUtc?
                    (§4a-i, `IDENT-003` — a staged, not-yet-observed
                    routine rotation this peer has durably accepted
                    alongside the current fingerprint, bounded by an
                    explicit deadline; all three null outside an
                    in-progress rotation),
                    PendingReconfirmationRequired: bool (§4a-i step 6,
                    `IDENT-003` — set when `PendingRotationExpiresUtc`
                    lapsed without observation; `PendingTrustedPublic
                    KeyFingerprint`/`PendingRotationId` are retained,
                    not cleared, while this is set, so the local
                    Owner's explicit approval can promote the
                    already-verified fingerprint directly, preserving
                    grants — never cleared by mere elapsed time alone),
                    CredentialHistory[] (prior fingerprints + rotation
                    timestamps, retained for audit only),
                    DisplayName, MachineName (self-reported, cosmetic —
                    never security-relevant), FirstPairedUtc }
```

- **`HostId` is the project-owned, permanent identity** a physical Host is known by everywhere — `TrustedManagers` rows, `CapabilityGrant`s (§5), `AuditEvents` — all key on `PeerHostId`, never on a certificate fingerprint.
- **This same credential anchors trust on two channels, not two separate credentials (Product Decision, 2026-09-01, `LOCAL-004`).** `CurrentCredentialRef` is used both as the mTLS credential for remote peer authentication (§4c) *and* as the TLS server credential local clients verify against `LocalHostTrustDescriptor` (§3b). One identity, one rotation/recovery story — rotating or recovering the Host credential (below, and §2b/§2c) updates both `TrustedManagers`-facing trust and `LocalHostTrustDescriptor` together, never one without the other.
- **Routine credential rotation without changing `HostId` is staged across every trusted peer (Product Decision, 2026-09-01, `IDENT-003`) — see §4a-i.** A Host may generate a new key pair and request rotation. Every rotation request is authenticated under the **currently trusted** credential (signed by the old key) — since it requires already being trusted, an attacker without the old private key cannot rotate a victim's pinned credential out from under them. **A prior revision of this bullet had a peer update `CurrentTrustedPublicKeyFingerprint` immediately on verifying a single rotation request** — that's only safe for a Host with exactly one trusted peer; a Host with several `Active` peers, some of them offline at rotation time, cannot safely have some peers already expecting the new credential while others still only trust the old one, whichever order the Host switches in. §4a-i defines the required staged, overlap-safe mechanism instead. `PeerHostId` is never touched by rotation, staged or otherwise.
- **Credential loss**: if the old private key is gone, rotation as above is impossible — there is no cryptographic way to prove "this is still the same Host" without it. The Host performs a completely fresh pairing bootstrap (§4b) with a fresh code. **But a fresh pairing that ends up claiming this same, already-known `HostId` cannot simply complete normally to `Active`** — the peer already has a `TrustedManagers` row and grants keyed on that exact `HostId`, and letting an unauthenticated new credential silently step into that identity's shoes (either by colliding with the row or updating it in place) would silently hand the old grants to whoever holds the new key, defeating the entire point of requiring proof of credential possession. §4b-i defines precisely what happens in this case: a bounded, zero-authority `PendingCredentialReplacement`, requiring explicit local Owner approval before the new credential is trusted for anything.
- **A previously trusted credential that has been revoked**: credential revocation and trust revocation are treated as the **same operation**, deliberately, rather than inventing a third "trusted-HostId-but-untrusted-credential" state — see §8. Partially trusting a `HostId` without trusting its current credential is a contradiction, because the credential is the only mechanism that proves you're actually talking to that `HostId`.

### 4a-i. Staged multi-peer Host credential rotation (Product Decision, 2026-09-01, `IDENT-003`)

`IDENT-001` still holds: `HostId` is the stable semantic identity; the credential rotating here is only the authentication material, never identity, and no CA/root-leaf hierarchy is introduced. But §4a's single-peer rotation bullet assumed a Host with one relationship to keep in sync — a Host with **multiple** `Active` peers, some possibly offline at rotation time, cannot safely have the Host switch its one global credential immediately (an offline peer, still pinning the old fingerprint, is stranded the moment it reconnects and sees the new one presented) or wait for every peer before ever telling anyone (a peer that already updated to expect the new credential sees the Host still presenting the old one, which looks like a downgrade). This subsection defines the required staged, overlap-safe flow that avoids both failure modes for **routine** rotation, where the old credential is still trustworthy — never for credential **loss** (§4a's own bullet, `PAIR-004`/§4b-i, unchanged) or suspected **compromise** (below) — these three cases are not interchangeable.

**`HostCredentialRotation`**, owned by the Host initiating rotation (persisted, §6):

```
HostCredentialRotation { RotationId, OldCredentialRef, NewCredentialRef,
                    State: Prepared | Staging | ReadyForCutover | CutOver
                    | Completed | Aborted, StartedUtc }
```

Exact field/table layout (e.g. whether per-peer staging status is a child table or embedded) is a #20/#21 implementation detail; the state names above are illustrative, not a fixed enum this document requires verbatim — the required property is that the Host can durably determine, for every currently-`Active` peer, whether that peer has staged the new credential yet. **This set is not a snapshot frozen at step 1** — see step 2's newly-activated-peer rule below.

**1. Prepare.** The Host generates `NewCredentialRef` through the accepted secure-store mechanism (§4a, §7) and secures it, but does **not** yet present it anywhere — `OldCredentialRef` remains the Host's only presented credential, on both the local (§3b) and remote (§4c) channels. Both credentials belong to the same, unchanged `HostId`.

**2. Stage to every `Active` peer, with a bounded acceptance window.** For each `Active` `TrustedManagers` peer, the Host — authenticated with the **old**, still-current credential — sends a rotation proposal: `HostId`, `RotationId`, the new public credential/fingerprint, and sufficient anti-replay/version information. The peer verifies its trust for that `HostId` is `Active`, the presented old credential matches its own `CurrentTrustedPublicKeyFingerprint`, and the proposal isn't stale or replayed — then durably records `PendingTrustedPublicKeyFingerprint = New`, `PendingRotationId = RotationId`, and `PendingRotationExpiresUtc` (an explicit, bounded deadline — an implementation-level policy value, same category as `PeerBound`'s own pending-trust window, §4b) **while leaving `CurrentTrustedPublicKeyFingerprint` unchanged** — the peer now accepts *both* the old and the new credential as valid for this `HostId`, for this specific `RotationId`, **until that deadline**, and sends back an idempotent, durable acknowledgment. A peer receiving a validly-signed proposal with a *different* `RotationId` than one it may already be staging (a fresh attempt after an aborted one, below) always overwrites its existing `Pending*` fields with the new proposal's — never rejected merely for already having stale pending state from a prior attempt. **No `CapabilityGrant` changes, no re-pairing, no `DefaultGrantTemplate` application, and no `HostId` change occur at this or any later step** — this is purely a credential-material update to an already-`Active`, already-authorized relationship.

**Newly-activated peers join an in-progress rotation automatically.** A prior revision of this subsection implicitly treated "every `Active` peer" as a set fixed at step 1 — but an ordinary pairing (§4b) can reach `Active` *while* a rotation is `Staging`/`ReadyForCutover`, and that peer's activation pins only `Old` (rotation isn't complete, so `Old` is still the Host's only presented credential) without ever being staged, since it wasn't part of any original snapshot — stranding it the moment cutover happens. Fixed: whenever a pairing reaches `Active` while `HostCredentialRotation` is in a non-terminal state, the Host atomically, as part of that same activation, adds the new peer to the in-progress rotation and stages it exactly as step 2 above (proposal signed by `Old`, `PendingTrustedPublicKeyFingerprint`/`PendingRotationId` durably recorded before the peer is told activation is complete) — never left implicitly trusting only `Old` with no staged path to `New`.

**3. Cutover rule — never strand a reachable peer, never wait forever on an unreachable one, and never cut over on a stale acknowledgment.** The Host must not present `New` as its normal credential until **every currently-`Active` peer** — including one that reached `Active` after the rotation began, per the newly-activated-peer rule above — has a **currently-unexpired** `RotationId`-matched acknowledgment (`PendingRotationExpiresUtc` in the future, step 2/6) — not merely one received at some point in the past. **This distinction is required, not cosmetic (Product Decision, 2026-09-01, fresh evidence during this round's review).** A prior revision of this rule checked only whether an acknowledgment was *ever* received: if peer A stages early but peer B stays offline long enough for A's own `PendingRotationExpiresUtc` to lapse, A stops accepting `Old`-or-`New` ambiguity for ordinary authentication (step 6) — but the Host, having recorded A's *original* acknowledgment, would still treat A as "staged" once B finally reconnects, cutting over and stranding A, in direct conflict with `IDENT-003`'s own core requirement. Fixed: cutover eligibility is re-evaluated against every peer's **current** acknowledgment state at the exact moment cutover is attempted; a peer whose acknowledgment has gone stale counts the same as an unstaged peer for this purpose — it blocks cutover until it re-establishes trust through the grant-preserving local-Owner reconfirmation a lapsed deadline now requires (step 6 — a stale acknowledgment can no longer be refreshed by a bare re-proposal, since that channel is exactly what an attacker holding a copy of `Old` could also use), or until the Owner explicitly revokes it instead of waiting for that. An offline `Active` peer, or one with a stale acknowledgment, therefore blocks graceful cutover. **"Unexpired" requires a minimum remaining margin before cutover, not merely a future timestamp at the exact instant checked (fresh evidence beyond the stale-acknowledgment fix itself, same round).** A prior revision of this fix checked only `PendingRotationExpiresUtc > now` — but if the last blocking peer stages and cutover proceeds within, say, milliseconds of *another* already-staged peer's own deadline, that other peer's window can lapse (step 6) in the gap between the eligibility check and that peer actually observing `New` in a live connection, stranding an `Active` peer exactly as before, just through a narrower timing window instead of an unbounded one. Fixed: cutover requires every peer's `PendingRotationExpiresUtc` to exceed *now plus a minimum required margin* — an implementation-level policy value, same category as the deadline duration itself — not merely to be in the future by any amount; a peer within that margin of expiring is treated as not-yet-eligible for cutover purposes, giving it (or the Host, via a fresh proposal before the original deadline actually lapses) room to actually complete promotion before its window can close mid-cutover. This is a deliberate choice the local Owner makes explicitly, not something the Host resolves automatically: **wait** for that peer to (re)stage normally, or **explicitly revoke/unpair it** through the existing, audited trust-revocation rules (§8) to unblock rotation without it. **Rotation never auto-revokes a peer on a timeout** — an `Active` peer that simply hasn't reconnected yet is never silently dropped merely to finish someone else's rotation. A peer that staged `New` and then went offline does **not** block cutover on that basis alone — but if enough time passes that its own acknowledgment goes stale before cutover actually happens, it reverts to blocking, exactly like any other peer with a stale or missing acknowledgment.

**Abort, reachable only before cutover.** The Host may abandon an in-progress rotation any time before step 5. On abort: `HostCredentialRotation.State = Aborted` is set locally, immediately; for every peer that had staged (durably acknowledged), the Host best-effort sends an authenticated (signed by `Old`, still current — abort happens only pre-cutover) notice causing that peer to immediately clear its `Pending*` fields, idempotently reverting it to trusting only `Old`, exactly as before staging began. A peer that cannot be reached for this notice is not left indefinitely stranded on the abandoned `New` — its own bounded `PendingRotationExpiresUtc` (step 2) lapses regardless and clears its `Pending*` fields the same way, whether or not the explicit notice ever arrives. **A subsequent, fresh rotation attempt always uses a new `RotationId`** — a peer still holding stale `Pending*` state from the aborted attempt (notice not yet delivered, or deadline not yet lapsed) simply has it **overwritten** by the new proposal, per step 2's overwrite rule; it is never rejected as "occupied," and no manual cleanup is required before starting over. **Abort also republishes `LocalHostTrustDescriptor` with its `Pending*` fields cleared, and retires the abandoned `NewCredentialRef` (Product Decision, 2026-09-01, fresh evidence during this round's review).** A prior revision of this paragraph addressed only remote peers, leaving the descriptor exactly as step 4 published it if abort happened afterward — but the descriptor's `Pending*` fields, unlike a remote peer's, were never given a bounded expiry at all (§3b's fresh-read-per-connection design makes that unnecessary for the *ordinary* staged-then-cutover case, but does nothing to bound an *abandoned* one), so a local client would keep accepting the abandoned `New` fingerprint **indefinitely** — anyone who obtained a copy of that never-adopted key could authenticate a squatted local endpoint with no deadline at all. Fixed: aborting clears `LocalHostTrustDescriptor.Pending*` in the same step as the remote-peer notice, exactly reverting local trust to `Current` only; the abandoned `NewCredentialRef` private key material is retired through the ordinary secure-store lifecycle (§7) immediately on abort — unlike `Old`'s retirement (step 6), nothing ever depended on this key, so there's no peer to wait on.

**4. Local client trust stages too.** The Host's credential is dual-purpose (§4a, `LOCAL-004`) — it is also the TLS server credential `LocalHostTrustDescriptor` (§3b) publishes for local clients. Before global cutover, the descriptor's own `PendingHostCredentialFingerprint`/`PendingRotationId` fields (§3b) are populated the same way a peer's `Pending*` fields are in step 2. A local client verifies the connecting TLS server credential's fingerprint against **either** `CurrentHostCredentialFingerprint` **or**, while set, `PendingHostCredentialFingerprint` for the expected `HostId` — never only the current one during a staged window — reloading the descriptor on each new connection rather than permanently caching a single pinned value from a prior session. This is the same `HostId`, the same descriptor, the same trust anchor — staging never creates a second local Host identity.

**5. Global cutover.** Once every currently-`Active` peer (step 3) has durably staged `New` and the local descriptor recognizes it (step 4), the Host, in this order — **`HostIdentity.CurrentCredentialRef`/`HostCredentialRotation.State` (SQLite, one transaction) always precede the `LocalHostTrustDescriptor` republish (a separate file, never atomic with the SQLite write — §3b's general reconciliation rule covers any crash between the two)**: **sets `HostIdentity.CurrentCredentialRef = NewCredentialRef`** and marks `HostCredentialRotation.State = CutOver`, together, in one SQLite transaction — a prior revision of this step never actually promoted the canonical credential reference defined in §4a/§6, only started presenting the new key and updating the public descriptor, which left `HostIdentity` itself still pointing at `Old` even after cutover; fixed so the durable source of truth and the credential actually being presented are never out of sync — begins presenting `New` as its credential on every channel (local §3b and remote §4c alike) using that same now-current reference; updates `LocalHostTrustDescriptor.CurrentHostCredentialFingerprint = New` and clears its `Pending*` fields as the following, separate step. `HostId` is unchanged throughout; remote authorization stays keyed on `PeerHostId` and each peer's existing `CapabilityGrant`s exactly as before — **routine rotation rewrites or reissues no grant**. A peer that happened to be offline at the exact moment of cutover (having already staged `New` per step 2) reconnects successfully afterward with no further action, since it already durably trusts `New`.

**6. Peer-side completion, bounded acceptance of `Old`, and old-key retirement gated on every peer resolving.** When a peer, in any live connection after cutover, actually observes the Host presenting `New`, it **promotes** `PendingTrustedPublicKeyFingerprint` to `CurrentTrustedPublicKeyFingerprint`, clears both `Pending*` fields, appends the old fingerprint to `CredentialHistory`, and stops accepting `Old` for ordinary authentication from that point on — idempotently, so observing `New` twice changes nothing further. A peer that staged `New` but has not yet, in a live connection, actually seen it presented **continues accepting `Old` for ordinary authentication only until its own `PendingRotationExpiresUtc` deadline (step 2)** — not indefinitely. **Bounding this window is required, not optional (Product Decision, 2026-09-01, fresh evidence during this round's review).** A prior revision of this step let a peer accept `Old` for as long as it took to reconnect, with no deadline; retaining `OldCredentialRef` at the Host (the round's own prior fix, below) does not by itself protect that peer, because anyone holding a copy of `Old` obtained from *anywhere* — a backup, a disk image, any source outside this mechanism's control, not merely the Host's own copy — remains fully able to authenticate to that specific peer with the relationship's existing grants for as long as the peer keeps accepting `Old` with no limit. This is the same routine-rotation threat model §4a already accepts (rotation is authenticated by possession of the current credential; step 7 exists precisely for when that assumption breaks) — the fix here is bounding routine rotation's own exposure window to something finite, consistent with every other pending/staged state in this document (`PeerBound`, `PendingLocalPrincipalEnrollment`, `PendingCredentialReplacement`), never a defense against an already-*known*-compromised `Old` (that remains step 7's distinct job). **When the deadline lapses without promotion, the peer stops accepting `Old`-authenticated messages entirely — including a fresh staging proposal, not merely ordinary RPC.** A prior revision of this step let a lapsed peer still accept a *new*, freshly-signed staging proposal from "the Host" as a lightweight resync path — but that exception is exactly as forgeable as everything else `Old`-signed: an attacker holding a copy of `Old` can construct that "fresh proposal" too, naming an **attacker-controlled** key as the proposed `New`, and the unsuspecting peer would durably stage it, then promote it on a later "observation" the same attacker also controls — completing a full, silent, *permanent* takeover of the relationship with its existing grants intact, using nothing but the same copied key round 8's bounded window exists to contain in the first place. Limiting `Old` to "ordinary RPC only" does not bound its authority if it can still be used to *replace itself* indefinitely. Fixed: once the deadline lapses, resuming trust with that peer via a **bare, freshly-signed re-proposal** is never again accepted — signature-only proof is exactly what round 8's bounded window exists to stop trusting indefinitely.

**Resuming a lapsed-but-already-verified rotation preserves grants; it is not treated as an unproven-identity replacement (Product Decision, 2026-09-01, fresh evidence a round later).** A prior revision of this fix routed a lapsed peer through §4b-i's full `PendingCredentialReplacement` gate — but that gate exists for a genuinely **unproven** claim (an unknown credential appearing out of nowhere, possibly attacker-controlled), and its approval semantics reflect that: it invalidates the relationship's existing `CapabilityGrant` roots and applies the Host's *currently configured* `DefaultGrantTemplate` fresh (§4b-i steps 2 and 5) — appropriate when identity itself is in question, but wrong here, since the peer *already cryptographically verified* this exact `New` fingerprint at staging time (step 2), while `Old` was still unambiguously trustworthy — the only thing that lapsed is the bounded time window, not the proof. Routing a merely-slow, otherwise-legitimate peer through that gate would silently strip its customized grants and replace them with whatever `DefaultGrantTemplate` currently says — directly contradicting this section's own repeated promise that **routine rotation changes no `CapabilityGrant`, ever**. Fixed with a narrower, grant-preserving gate instead of the credential-loss one: on lapse, the peer retains its already-verified `PendingTrustedPublicKeyFingerprint` (rather than discarding it) and durably records `PendingReconfirmationRequired = true`, surfaced to that peer's local Owner (Activity/audit, same visibility as any other pending item). **The local Owner's explicit approval — required precisely because a bare `Old` signature alone is no longer sufficient once the window has lapsed, the same underlying reason §4b-i's gate exists — directly promotes the already-verified fingerprint to `CurrentTrustedPublicKeyFingerprint`**, exactly as step 6's own observation-triggered promotion above does, clearing `Pending*`/`PendingReconfirmationRequired` and appending `Old` to `CredentialHistory`. `TrustedManagers.State` remains `Active` throughout; the row is never re-created; `CapabilityGrant`s are **never** invalidated or reissued by this path — Owner approval here reconfirms an already-proven credential material update, not a new identity claim. The Owner may instead simply revoke the peer (§8, the same choice step 3 always offers) rather than reconfirming, if the delay is no longer wanted. This is deliberately distinct from, and narrower than, `PendingCredentialReplacement` — a genuinely **unproven** claim (credential loss, §4a's own bullet; suspected compromise, step 7 above; or any peer that never durably staged this `RotationId` at all before its window lapsed) still requires the full replacement gate and its grant-reset semantics, unchanged. **This narrower gate is available only for the exact fingerprint that peer itself already durably verified before lapsing** — it confers no authority to accept an arbitrary, never-staged credential, which is exactly why it doesn't reopen round 8's forgery concern: an attacker holding only a copy of `Old` was never able to get anything into this peer's `Pending*` in the first place without first passing step 2's live, pre-expiry verification, which happens on the Host's own initiative, not on demand from an untrusted-until-proven caller. **The Host may retire (delete) `OldCredentialRef`'s private key material — and only then mark `HostCredentialRotation.State = Completed` — only once *every* remaining `Active` peer has either confirmed promotion, had its own deadline lapse (meaning it no longer accepts `Old` for ordinary authentication regardless), or been explicitly revoked by the Owner (§8); `CutOver` (step 5) and `Completed` are therefore genuinely distinct states.** An Owner facing a peer that never reconnects may explicitly revoke it (the same choice step 3 already offers for a peer blocking cutover) to unblock retirement sooner, rather than waiting out every deadline.

**7. Emergency compromise replacement — a distinct, non-staged path, and never authenticated by `Old`.** The flow above (steps 1–6) assumes `Old` is still trustworthy and only availability, not security, is at stake. **If `Old` is suspected compromised, availability must not override security — and, critically, nothing signed by `Old` can be trusted as proof of anything anymore, for *any* peer, reachable or not.** A prior revision of this step said reachable peers are "staged and promoted as above" — but "as above" (steps 2/6) authenticates the proposal *using* `Old`'s signature, and an attacker who has actually compromised `Old` can produce an identical, validly-signed proposal; a peer has no way to distinguish the Owner's genuine emergency replacement from the attacker's own forged one under the very key just declared untrustworthy. Accepting either would let the attacker rotate the relationship to an attacker-controlled key while silently preserving its existing grants — exactly the failure `PAIR-004`/§4b-i's `PendingCredentialReplacement` gate already exists to prevent. Fixed: compromise replacement is an ordinary, Owner-authorized operation on a **running** Host (unlike §2b/§2c/§3b's offline `Host.Cli` recovery operations, which apply only when the Host cannot authenticate itself at all) that immediately generates and presents a new credential everywhere — but **every** peer, reachable or not, re-establishes trust the same way a credential-**loss** peer does: a fresh pairing bootstrap (§4b) landing at §4b-i's `PendingCredentialReplacement` gate, requiring that peer's own local Owner's explicit approval, never an old-key-authenticated fast path for peers that happen to be online at the time. **Prior grants never silently transfer through an unproven credential**, here any more than anywhere else in this document. This operation is explicitly audited (`AuditEvents`, §6), distinctly from ordinary staged rotation. From a peer's perspective, emergency compromise replacement and credential loss are now the *same* recovery mechanism — they differ only in why the Host initiated it (a stolen key vs. an unrecoverable one), never in how a peer re-establishes trust.

**Three distinct cases, never conflated**: routine rotation (this subsection, `Old` trustworthy, staged, **each individual peer** either promotes within its own bounded window or, if it lapses, requires local-Owner reconfirmation of the *already-verified* fingerprint — step 6 — never a bare re-proposal and never a grant-invalidating replacement, since identity was never in question here, only timing), suspected compromise (immediately above, `Old` untrustworthy, force-cutover, **every** peer — reachable or not — re-pairs through §4b-i, since nothing signed by `Old` can be trusted as proof for anyone once it's compromised, and existing grants are correctly invalidated because identity genuinely cannot be proven continuous), and credential **loss** (§4a's own bullet and §4b-i, `Old` unrecoverable, the Host itself has nothing left to stage with, so it re-pairs with every peer from scratch, same grant-invalidating gate for the same reason). Compromise and loss converge on the identical, grant-invalidating peer-side re-pairing mechanism, since both genuinely leave identity unproven; a routine-rotation peer whose own bounded window merely lapses is deliberately **not** routed through that same mechanism, precisely because its identity and its proposed credential were both already cryptographically verified before the window closed — only a human confirmation of *timing*, not identity, is missing. All three triggers, and what a peer does about each, remain distinct — never bare-signature-sufficient once a window has closed, but not automatically grant-invalidating either, unless identity itself is genuinely unproven.

**Crash/recovery.** `HostCredentialRotation` state, and each peer's `Pending*` fields, are durable specifically so a Host-process crash at any point does not require restarting the whole rotation from `Prepared`: a crash after `New` is generated but before any peer is staged resumes from `Staging` with no peer yet having accepted `New`, nothing to undo; a crash after some but not all peers have staged resumes staging only the remainder; a crash after every remaining peer has staged but before cutover resumes directly at cutover eligibility; a crash during or immediately after the local-descriptor update (step 4) is recovered the same write-then-verify way §3b's ordinary descriptor consistency already requires; a crash immediately after global cutover leaves `HostCredentialRotation.State = CutOver` durably recorded, so a restarted Host does not re-present `Old` or repeat cutover, but does resume waiting on whichever remaining peers haven't yet confirmed promotion or been revoked, exactly as before the crash; a crash specifically between step 5's SQLite write (`CurrentCredentialRef`/`State = CutOver`) and its separate `LocalHostTrustDescriptor` republish is exactly what §3b's general startup-reconciliation rule exists for — the restarted Host republishes the descriptor from the now-authoritative SQLite value before serving any local connection, never left presenting `New` while the descriptor still claims `Old`; a crash after every remaining peer has confirmed (or been revoked) but before the old key is actually deleted resumes directly at retirement, never re-entering any earlier phase. **A peer's `PendingRotationExpiresUtc` deadline (step 6) requires no special crash handling of its own** — it's a plain durable timestamp, evaluated by comparison against the current time whenever relevant, exactly like every other bounded-expiration field in this document; there is no separate "deadline-tracking" process to crash mid-operation. **Completion is never inferred from in-memory state alone**, and the Host must never reach a state where it presents `New` while any currently-`Active` peer — including one that joined the rotation after it began, per the newly-activated-peer rule above — has never persisted `New`, except via the explicit, audited emergency-replacement path above.

### 4b. Initial pairing bootstrap — MITM-resistant first contact

mTLS with pinned credentials (§4a) describes *post-pairing* authentication. It says nothing about how the first pin is established safely — and without that, an active man-in-the-middle during first contact could cause each side to pin the attacker's credential instead of the real peer's, defeating everything built on top of it. This subsection is that missing piece.

**Corrected security property.** A prior revision of this document overstated the guarantee, claiming a transparent relay necessarily causes the two honest peers to derive different keys. That's not the right framing — a relay that faithfully passes bytes through without knowing the code and without modifying anything learns nothing and grants itself nothing; it is not by itself a successful impersonation, and a PAKE run through a purely passive relay between two honest parties who both know the real code can still complete normally. **The actual required property is**: an attacker who does *not* know the one-time pairing code cannot (a) successfully complete an authenticated PAKE session *as* either party, (b) terminate a genuine session and substitute their own, or (c) cause either peer to bind its `HostId` to a credential the attacker controls. This is what a PAKE with active-attacker security (not merely passive-eavesdropper security) actually guarantees, and it's the correct, precise statement of why first contact is safe.

**Mechanism: SPAKE2 (RFC 9382)** — the construction actually appropriate to this problem's roles, not treated as interchangeable with augmented variants. A prior revision suggested "SPAKE2+ or an OPAQUE-class equivalent" as if these were freely swappable with plain SPAKE2. They are not: **SPAKE2+ and OPAQUE are augmented PAKEs**, purpose-built for a client authenticating to a server that stores a password *verifier* rather than the password itself, specifically so a server-side database compromise doesn't reveal the password — that model requires an explicit registration phase and genuinely asymmetric prover/verifier roles. **This pairing scenario has neither**: two Hosts, symmetric peers, sharing the *same* ephemeral one-time code, discarded after minutes, with no persistent password database on either side to protect from compromise. **SPAKE2 — the direct, symmetric construction — is what actually fits**, and is the required baseline. SPAKE2+/OPAQUE remain available *only* if #20 deliberately introduces genuine asymmetric registration semantics into some future variant of this flow (it does not do so here); this document does not invent a custom protocol either way, and the exact library implementing SPAKE2 is a #20 decision made with current engineering guidance.

**Identity binding — one specific, standard mechanism, not left ambiguous.** `HostId` + long-term public credential are exchanged in an explicit message **after** SPAKE2 key confirmation succeeds, authenticated (MAC'd, using a key derived from the completed exchange's shared secret) so that only someone who actually derived that shared secret — impossible without the code, per the corrected security property above — could have produced a valid binding message. This is the standard way real protocols layer identity exchange on top of a completed PAKE: the *confirmed key*, not the raw PAKE transcript itself, authenticates what comes after.

**Pairing state machine — local states, no cross-machine atomicity, and no grants before reciprocal confirmation.** Each side runs its **own local** state machine; there is no distributed transaction spanning two Hosts, and neither side may assume the other has reached any particular state at any particular time. A prior revision let one side reach `Active` (and apply `DefaultGrantTemplate`) independently, arguing this was always safe because defaults are least-privilege — **that argument doesn't hold, because `DefaultGrantTemplate` is itself configurable** (§5) and could be set to something non-trivial. The fix is an explicit intermediate state: identity is verified and durably recorded *before* either side treats the trust as usable, and usability requires evidence the *other* side reached that same point too.

```
Created -> PAKEAuthenticated -> PeerBound -> Active   (this side's own local states)
                |
                v
           Expired / Failed   (reachable from any non-terminal state)
```

- **`Created`**: a pairing attempt has started locally (code generated on one side, about to be entered on the other); no cryptographic exchange has occurred yet. Exists only in this side's process memory.
- **`PAKEAuthenticated`**: SPAKE2 key confirmation succeeded, *on this side*, entirely **in-memory** — not written to durable storage (see crash behavior below).
- **`PeerBound`**: this side received and verified the peer's authenticated identity-binding message (per above) — it now has cryptographic proof of the peer's `HostId` and public credential. **This fact may now be durably recorded** (unlike the two states before it): a `TrustedManagers` row is written with the peer's identity, but explicitly marked not-yet-active — **no `CapabilityGrant`s are created from `DefaultGrantTemplate` yet, and the peer's identity is not usable for any authorization decision at this state.** Because the identity is now durably known, further communication with this peer no longer needs the ephemeral PAKE code at all — it proceeds over ordinary ephemeral-free authenticated mTLS using the now-known, now-pinned credential.
- **`Active`**: reached only after this side has **reciprocal evidence** that the peer also reached `PeerBound` — an explicit activation-acknowledgment message, sent and received over the mTLS channel now available (see `PeerBound` above), confirming "I have verified and durably recorded your identity too." Only on receiving that acknowledgment does this side apply `DefaultGrantTemplate` (creating real `CapabilityGrant`s) and mark the `TrustedManagers` row active. The acknowledgment exchange is **idempotent and retryable**: resending or re-receiving it never creates a second set of grants, and either side can keep retrying delivery (using the already-durable, already-verified `PeerBound` credential) if the first attempt is lost to a network interruption, with no time pressure from the original short-lived code.
- **`Expired` / `Failed`**: terminal, reachable from any non-terminal state including a `PeerBound` that never receives reciprocal confirmation within a bounded pending window (longer than the original 5-minute code window, since `PeerBound` reflects durably verified identity, not an ephemeral exchange — an implementation-level policy value, not fixed by this document). Cleanup removes the pending `TrustedManagers` row; no grants were ever created, so nothing to unwind.

Requirements this state machine must satisfy:

1. **No privilege before `Active`, and asymmetric completion is safe by construction — now true regardless of `DefaultGrantTemplate` content.** `Created` and `PAKEAuthenticated` grant zero authorization and exist only in memory. `PeerBound` is durable but still grants zero authorization — no `CapabilityGrant`s exist for this peer yet, so it doesn't matter what `DefaultGrantTemplate` contains. Only `Active`, reached solely via reciprocal acknowledgment, ever creates real grants. A window where one side is `PeerBound` and the other hasn't caught up yet is normal, expected, and genuinely unprivileged either way — not merely "unprivileged because the default happens to be minimal."
2. **Idempotent finalization**: verifying the same identity-binding message twice, or receiving the same activation acknowledgment twice, each commits their respective transition at most once.
3. **Crash/reconnect semantics, by phase**: `Created`/`PAKEAuthenticated` remain in-memory only — **a Host process crash discards them unconditionally**, and the user starts a fresh attempt with a new code, exactly as before. `PeerBound`, once durably recorded, **survives a process crash and can complete to `Active` without repeating the PAKE exchange at all** — it resumes via ordinary authenticated mTLS reconnect using the peer credential already verified and pinned at `PeerBound`, retried until the activation acknowledgment succeeds or the pending window (item below) expires.
4. **Bounded pending lifetime at both stages**: an attempt not reaching `PeerBound` before the original short code-validity window (existing v0.4 `PairingService` precedent — 5 minutes) simply times out from `Created`/`PAKEAuthenticated`. A `PeerBound` state not reaching `Active` within its own, longer pending-trust window is cleaned up the same way. Either case requires starting over from `Created` with a fresh code — a `PeerBound` state is never resurrected with a stale code after its own window lapses.
5. **Rate limiting**: the existing v0.4 precedent (10 wrong attempts locks out the current code) carries forward for the `Created`→`PeerBound` phase, extended with server-side backoff per source address now that this surface is reachable over more than LAN broadcast.
6. **Replay prevention**: each attempt is bound to its own single-use code and session nonce; a captured transcript from one attempt (even a successful one) cannot be replayed to authenticate a different attempt.
7. **Audit**: `AuditEvents` records a pairing attempt's terminal outcome (`Active` or `Expired`/`Failed`) without recording the code or session cryptographic material — including attempts that stalled at `PeerBound` and never reached reciprocal confirmation.

**Re-pair after credential loss/revocation** (§4a, §8): always a fresh attempt from `Created` with a fresh code — never a resumption of a prior attempt. If the claimed `HostId` is genuinely new (no existing `TrustedManagers` row for it), the ordinary state machine above applies unchanged, ending at `Active` with the currently configured `DefaultGrantTemplate`. If the claimed `HostId` already exists, see §4b-i — the fresh pairing does not simply complete to `Active`.

### 4b-i. Credential-loss pairing: the `PendingCredentialReplacement` gate (Product Decision, 2026-09-01, `PAIR-004`)

`IDENT-001` still holds: `HostId` remains the stable semantic identity, separate from its credential. But a peer that already trusts a `HostId` cannot tell "the real Host lost its key and is re-proving itself" apart from "an attacker is claiming someone else's `HostId`" from the PAKE/identity-binding exchange alone — proof of *continuity* requires the old credential (§4a's rotation path), which by definition isn't available here. This subsection defines what happens instead.

**Trigger, corrected to exempt an unchanged peer.** During §4b's identity-binding step, the peer verifies the incoming `HostId` + public credential as usual. Because pairing is symmetric, this same fresh-pairing exchange runs on **both** sides even when only *one* of the two Hosts actually lost its credential — the *other* side's identity and credential are completely unchanged, and must not be disturbed just because its unaffected partner happened to trigger a fresh bootstrap. The check on each side is therefore:

- **No existing `TrustedManagers` row for that `HostId`** (in any state): genuinely new peer — the ordinary state machine applies, ending at `Active` with the currently configured `DefaultGrantTemplate`.
- **An existing `Active` row, and the presented public credential exactly matches `CurrentTrustedPublicKeyFingerprint` already pinned for it**: **this is not a replacement candidate at all** — the peer's identity and credential are unchanged (this is the *other* Host's side of a partner-initiated fresh pairing, or an ordinary reconnection), so the exchange simply reconfirms the existing `Active` trust and touches nothing — no new `PendingCredentialReplacement`, no grant disturbance, no Owner approval needed. **This reconfirmation exemption requires `State == Active` specifically (Product Decision, 2026-09-01, fresh evidence during this round's review) — a matching credential on a row that is only `PeerBound` does not qualify.** A `PeerBound` row that never reached reciprocal activation (§4b — e.g. a crash after durably persisting `PeerBound` but before the acknowledgment) still carries **zero ordinary authority** per §4b's own rule ("asymmetric completion is safe by construction"); silently treating a matching-credential re-attempt against it as reconfirmed `Active` trust would grant real authority (`DefaultGrantTemplate`) without the reciprocal confirmation §4b requires. Instead, a fresh attempt presenting the same already-pinned credential against an existing `PeerBound` row is exactly the crash/reconnect case §4b's Requirements item 3 already defines: it resumes via ordinary authenticated mTLS reconnect using the credential already verified and pinned at `PeerBound`, retried toward the reciprocal activation acknowledgment — **not** treated as reconfirmed `Active` trust (there is no `Active` trust yet to reconfirm), and **not** routed into `PendingCredentialReplacement` either (the credential itself hasn't changed, so there is nothing to replace). It simply continues the existing `PeerBound` → `Active` path §4b already defines, with no new mechanism needed.
- **An existing row, and the presented credential differs from the pinned fingerprint, and does not match an authenticated-rotation request signed by the *previously* trusted key** (§4a): reaching `PeerBound`-equivalent verification does **not** proceed to durably record a fresh `TrustedManagers` row or continue toward `Active`. Instead it creates:

```
PendingCredentialReplacement { PeerHostId, CandidatePublicKeyFingerprint,
                    VerifiedUtc, ApprovedByOwnerLocalPrincipalId?,
                    ApprovedUtc?, ExpiresUtc }
```

**Zero ordinary authority while pending.** A `PendingCredentialReplacement` candidate can authenticate the pairing exchange itself, but has no `CapabilityGrant`s, is not `Active` trust, and cannot exercise any ordinary management operation (§4c). The existing trusted credential and the existing peer's `CapabilityGrant`s are **not** silently transferred, disturbed, or made available to the candidate merely because verification succeeded — verification proves possession of a new key, not authorization to inherit an old identity's authority.

**Explicit local Owner approval, one audited transaction.** A local Owner must explicitly approve the replacement. Approval is a single audited (`AuditEvents`, §6) local transaction that:

1. retires the old trusted-credential binding for this `PeerHostId`;
2. invalidates the old peer's existing `CapabilityGrant` roots and their normal downstream provenance subtrees (§5's existing cascade-invalidation rule — no new mechanism needed here);
3. binds the new credential to the same, unchanged `PeerHostId`;
4. establishes `Active` trust for the (now-replaced) relationship;
5. applies the Host's **currently configured** `DefaultGrantTemplate` (§5) as fresh Owner-root grants — never the prior grants, and never necessarily the shipped factory least-privilege value.

Prior grants do not silently reactivate at any point in this flow.

**Owner adoption/re-home, defined concretely.** This is the mechanism §5 refers to by name: **after** a credential replacement above, the Owner may separately, deliberately choose to reissue selected prior permissions as **new** Owner-root grants to that same `PeerHostId` — an ordinary grant-issuance action (§5), audited, never automatic, and never a resurrection of the invalidated grants themselves. Old downstream *delegated* grants (anything with `DerivedFromGrantId != null` under the old roots) are **not** revived by adoption/re-home either — if still appropriate, they must be re-established through the ordinary delegation mechanism (§5) by whoever now holds the reissued root grant.

**Un-approved candidates expire** the same way a `PeerBound` state does (§4b) — a bounded pending window, cleaned up with no grants ever having existed to unwind.

**No cloud PKI dependency**: the entire exchange is direct — LAN discovery response or manually-entered address, with the code communicated out-of-band (read aloud, typed on both sides) — never a third-party CA or an external pairing/relay service, consistent with the "explicitly not built" list at the end of this section.

**Capability/version negotiation:** a `Handshake` RPC is the first thing every connection does (local or remote) before any operational RPC is permitted. It exchanges `{ ProtocolVersion (major.minor), AppVersion, Capabilities[] }`. Feature availability is driven by capability flags the Host actually advertises, never by parsing/comparing app version strings (§13).

**Discovery and addressing:**
- Automatic discovery stays LAN-only, evolving the existing UDP broadcast `PeerDiscoveryService` to advertise a Host's `HostId` + protocol version instead of today's scheme.
- Non-LAN reachability (a VPN, a manually-routed private network) is manual address entry — host/IP plus port — never automatic.

**Explicitly not built:** no cloud relay/relay account service, no UPnP/NAT-PMP/automatic router configuration, no arbitrary remote shell, no general remote filesystem browsing API. The gRPC service surface (defined in `Contracts`, §1) only ever exposes the specific, enumerated Host operations in §1's contract list — there is no generic "execute" or "browse" RPC to misuse.

### 4c. Outbound remote connections are Host-owned, never client-owned

Every section above establishes *that* remote connections are authenticated mTLS/gRPC and *how* a Host's identity/credential work — but a prior revision of this document never actually said **which process opens the outbound connection to a remote peer**, leaving a real gap: if `Client.Avalonia` (or, now, `Client.Cli`, `CLIENT-003`) opened it directly, it would need the local Host's own private credential to authenticate as that Host — directly contradicting the already-established rule that no ordinary local client ever receives Host machine credentials (§4a, §7). This subsection closes that gap.

**The routing model, always — for either ordinary local client:**

```
Client.Avalonia or Client.Cli
    -> local Manager Host, over local IPC (§3, already established)
        -> remote Manager Host, over authenticated mTLS/gRPC (§4)
            -> remote Host executes the operation locally, as sole authority for its own server state
```

Neither `Client.Avalonia` nor `Client.Cli` **ever** opens a connection to a remote peer Host directly, and neither receives, reads, or handles the local Host's private credential at any point — that credential (§4a, protected by Host-side `ISecureCredentialStore`, §7) never leaves the Host process. Concretely, the **local machine-wide Host** — not either client — owns:

- all outbound remote connections (initiating, maintaining, reconnecting);
- the machine's own `HostId` and private credential;
- executing the Host-to-Host pairing protocol itself (§4a, §4b) as one of the two cryptographic participants;
- the local record of remote trust state (`TrustedManagers`);
- mTLS credential rotation and revocation (§4a, §8);
- remote protocol/capability negotiation (`Handshake`, §13).

**Pairing is Host-to-Host even when a person initiates it from an ordinary client.** Clicking "Pair with new Manager" in Avalonia (or invoking the equivalent `Client.Cli` command) sends a request over local IPC to the local Host; the *local Host* — not the client — then runs the actual PAKE exchange and identity binding (§4b) directly against the peer Host. The client only ever sees pairing *status* (in progress / awaiting reciprocal confirmation / `Active` / failed), reported back to it by the local Host over the same local IPC channel already established for everything else.

**The dual-authorization invariant** — this is the specific, required rule closing the actual security gap:

> A remote Host's `CapabilityGrant` to a `PeerHostId` represents the **maximum** authority available to that paired machine as a whole. It is never automatically exercisable by every local OS user on the machine holding that identity.

**This entire invariant presupposes `Active` trust, never merely `PeerBound`.** §4b already establishes that `PeerBound` grants zero authorization by construction — no `CapabilityGrant`s exist for a `PeerBound`-only peer on either side. Restated explicitly here because it is a prerequisite for the operation to even attempt outbound routing, not just a fact about how grants happen to be populated: `PeerBound` permits only pairing-finalization/activation-recovery traffic over the relationship, never ordinary management, and both the initiating and the destination Host require `Active` trust for the specific `PeerHostId` involved before either side does any local- or remote-authorization work below.

Concretely, for any outbound remote operation initiated via `Client.Avalonia` or `Client.Cli`:

1. **Local authorization first, and only once the destination trust is `Active`.** The local Host requires its trust record for the destination `PeerHostId` to be `Active` (§4b) — a merely `PeerBound` relationship carries zero grants by construction and is not usable for ordinary management, per §4b's requirements — before it even attempts to forward the request. Given that, the local Host checks whether the initiating `LocalPrincipal` (§3a) holds a `CapabilityGrant` (§5) authorizing this specific operation. For a **server-level** operation, that's the **exact same** grant model already defined for local-server operations, since a remote server that's been shared into this machine's view is a `ServerRef` (§4d) in this Host's own `CapabilityGrants`/inventory, exactly like a local one. For a **Host-level** operation (`CreateServer`, `ManageHostSettings`, `ManageHostUpdates`, etc.) targeting the remote peer, the held `HostCapabilityGrant`'s `TargetHostId` (`AUTH-005`) must **exactly equal** the destination `PeerHostId` — a grant targeting `ThisHostId`, or targeting a *different* remote peer, does not authorize this destination, even though `HostCapabilityGrant` is Host-wide *by type*, since #19's Product Decision now makes it Host-wide *by type, for exactly one target Host*, never every Host the grantee happens to have a same-capability grant for. If the initiating `LocalPrincipal` isn't locally authorized for this specific destination, or the destination trust isn't `Active`, the local Host denies the request **without ever contacting the remote peer** — an unauthenticated or unprivileged local user cannot use the machine's remote identity merely by being able to connect locally, and a user authorized only for a *different* Host cannot exercise that authority against this one.
2. **Remote authorization, independently, second — also gated on `Active`.** Only if step 1 passes does the local Host use its own outbound mTLS connection (its own `HostId`/credential, §4a) to send the operation request to the remote peer Host. The **remote** Host first requires its own local trust record for the connecting `PeerHostId` to be `Active` — the same `PeerBound`-carries-no-authority rule applies symmetrically on the receiving side, since a peer that hasn't reached reciprocal confirmation has no `CapabilityGrant`s to evaluate in the first place. Given `Active` trust, the remote Host independently evaluates its **own** `CapabilityGrant`s for `GranteeActor = RemoteManager(local HostId)` — for a Host-level capability, the remote Host's own grant has `TargetHostId = ` the remote Host's **own** `ThisHostId` (per `AUTH-005`, every `DefaultGrantTemplate`-issued grant is scoped that way, §5) — it does not know or care about the initiating machine's internal `LocalPrincipal`s, only about what it itself granted to that paired machine identity as a whole. This is exactly why the remote grant is a *ceiling*, not a guarantee: the local machine's own local-authorization policy (step 1), now itself scoped per destination `HostId`, can independently restrict which of its local principals may exercise up to that ceiling **for which specific remote Host**, and can grant different local principals different subsets of it for different destinations — the remote side never needs to know or mirror that internal policy.
3. Only if **both** checks independently pass does the remote Host execute the operation, remaining the sole executor/authority for its own server's process/filesystem/profile state throughout, exactly as already established for locally-initiated operations on locally-owned servers.

Exact local-side capability granularity for "which specific operations require this check" is left to #20, as an ordinary extension of the already-defined grant model — the invariant above, not the granularity, is what this issue fixes. **How a remote server's identity is represented is not left to #20** — see §4d immediately below, which this document fixes now.

### 4d. Canonical host-qualified server identity

A prior revision of this document let every reference to a shared/remote server stay a bare `ServerId` — "a remote server that's been shared into this machine's view is still just a `ServerId` in this Host's own `CapabilityGrants`/inventory," with the actual cross-Host representation deferred to #20. That's a boundary decision this issue must fix, not implementation detail: #17 already requires remote server identity to be collision-safe and Host-qualified, and a bare `ServerId` cannot be, since two different Hosts are free to assign the same `ServerProfileId` to unrelated servers.

**The fix — a project-owned, always-Host-qualified identity:**

```
ServerRef { AuthoritativeHostId, ServerProfileId }
```

- **Every server identity that crosses a Host boundary is a `ServerRef`, never a bare `ServerId` or `ServerProfileId`.**
- **Local server** (this Host is authoritative for it) = `ServerRef(ThisHostId, ServerProfileId)`. Even though `AuthoritativeHostId` is trivially `ThisHostId` for a Host's own servers, the field is still present and populated — not omitted — so a local server and a remote-shared server are the same shape everywhere they might appear together (a unified inventory view, §6).
- **Remote server** (a peer Host is authoritative for it, shared into this Host's view via §4c) = `ServerRef(RemoteHostId, ServerProfileId)`.
- **Identical `ServerProfileId` values minted independently by two different Hosts remain distinct** — they differ in `AuthoritativeHostId`, so nothing conflates them, collides them in a set, or lets one silently shadow the other in a unified view.
- **Every place this document defines a per-server data shape uses `ServerRef`, not `ServerId`**: `ServerCapabilityGrant`'s target (§5), local authorization checks (§4c), the routing decision itself (§4c — which peer, if any, a given `ServerRef` even resolves to), `OperationLock`/`OperationRecord` (§9, §10 — Activity/operation state), `AuditEvents` (§6), and the settings-metadata RPC surface (§12) whenever it crosses a Host boundary in the remote-management path.
- **Neither `Client.Avalonia` nor `Client.Cli` ever reconstructs a server's identity from its display name** — a duplicate or renamed `DisplayName` across Hosts must never cause a client to conflate two distinct `ServerRef`s or misroute an operation; `ServerRef` is what identity comparisons, not the display string, are actually keyed on.

This does not itself decide the exact wire representation (a single composite field vs. two separate protobuf fields, string-encoding of `AuthoritativeHostId`, etc.) — that remains an ordinary #20 implementation detail, same as any other DTO shape. What #20 does *not* get to invent is *whether* cross-Host server identity is qualified at all, or *by what* — both are fixed here.

## 5. Authorization domain model

Concrete, project-owned types (not framework roles/claims):

`ManagerIdentity` below is the same concept as §4a's `TrustedManagers` row — a paired peer, keyed on its stable `PeerHostId`, never on its current credential fingerprint. Grantees/grantors throughout are `ActorRef` (§5b) — either a `LocalPrincipal` or a `RemoteManager(PeerHostId)`:

```
ManagerIdentity      { PeerHostId, DisplayName, MachineName, FirstPairedUtc }
HostCapability        enum { CreateServer, ManageHostSettings, ManageTrustedManagers,
                              ManagePermissions, ManageHostUpdates, ... }
ServerCapability       enum { ViewServer, StartStopRestart, EditSettings, ManageBackups,
                              TransferExport, DeleteServer, ManageServerSharing, ... }
```

**`CapabilityGrant` is type-safe by construction, not a generic Host-or-Server bag** — a prior revision gave every grant a generic `Scope (Host | ServerId)` field regardless of capability type, which allowed nonsensical states like a `CreateServer` or `ManageHostUpdates` grant scoped to a specific `ServerId`. Fixed as two distinct grant shapes:

```
HostCapabilityGrant   { GrantId, GranteeActor: ActorRef, Capability: HostCapability,
                              TargetHostId: HostId (§4a — required and always
                              present, exactly one authoritative Host; ThisHostId
                              for local authority, a specific PeerHostId for
                              remote — not a generic Scope field, and not
                              "implicitly Host-wide" the way a prior revision
                              of this document had it: Host-wide by *type*
                              (never server-scoped) is still true, but that is
                              orthogonal to being scoped to exactly one target
                              Host — see AUTH-005),
                              CanDelegate: bool, CanDelegateOnwardDelegation: bool,
                              GrantedByActor: ActorRef, DerivedFromGrantId: GrantId?,
                              GrantedUtc }

ServerCapabilityGrant { GrantId, GranteeActor: ActorRef, Capability: ServerCapability,
                              Target: ServerRef (§4d),
                              -- required and always present: no Host-wide ServerCapability
                              -- grant exists. Host-qualified, not a bare ServerProfileId —
                              -- see §4d for why an unqualified id is not collision-safe.
                              -- (A fleet-wide "AllServers" scope was considered and
                              -- deliberately not introduced here — see "Unresolved" below.)
                              CanDelegate: bool, CanDelegateOnwardDelegation: bool,
                              GrantedByActor: ActorRef, DerivedFromGrantId: GrantId?,
                              GrantedUtc }
```

A `HostCapabilityGrant` can only derive another `HostCapabilityGrant` for the *same* `TargetHostId` — never `Host A -> Host B` (`AUTH-005`); a `ServerCapabilityGrant` can only derive another `ServerCapabilityGrant` for the *same* `ServerRef` — the full host-qualified tuple, not merely the same `ServerProfileId`, since two different Hosts may otherwise reuse the same profile id for unrelated servers (§4d). **A derived grant can never change capability type, and `CreateServer`/`ManageHostUpdates`/other Host-level capabilities can never become server-scoped — not as a rule to remember, but because there is no field to put a `ServerRef` into on a `HostCapabilityGrant` at all.**

Keying grants and identity on `HostId`/`LocalPrincipalId` rather than a credential fingerprint means a legitimate credential rotation (§4a) never disturbs an actor's accumulated permissions — exactly the property conflating identity with credential would have broken.

- **Role presets are UI convenience only** — a preset (View Only / Server Operator / Server Administrator / Host Administrator) is a named bundle that creates several grant rows atomically. The persisted source of truth is always individual grants; presets are never themselves a stored authorization primitive.
- **The delegation predicate is exact, not "holding a capability implies granting it."** A grant carries two independent booleans:
  - `CanDelegate` — the holder may create new grants of *this same* `Capability` for other actors.
  - `CanDelegateOnwardDelegation` — the holder may set `CanDelegate = true` (and/or `CanDelegateOnwardDelegation = true`) on grants derived from this one. This is deliberately a **separate, stricter** right from `CanDelegate` itself, so that "may delegate X" and "may let others re-delegate X" are independently controlled — matching #17's "delegation rights are separately controlled" requirement precisely.

  **Exact predicate** — actor A, holding grant `G` (of either type) for `Capability: X` with `G.CanDelegate == true`, may create a new grant `G'` for `Capability: X` for actor B if and only if:
  1. `G.CanDelegate == true` (the base gate — A could not create *any* onward grant of X otherwise).
  2. **Type/scope match, not a subset check**: if `X` is a `HostCapability`, `G'` is a `HostCapabilityGrant` and `G'.TargetHostId` must equal `G.TargetHostId` exactly (`AUTH-005`) — a `HostCapabilityGrant` targeting `Host A` can only derive another grant targeting that exact same `Host A`, never `Host B`, even if the delegating actor separately happens to hold a same-capability grant targeting `Host B` too; each `TargetHostId` is its own independent delegation lineage. If `X` is a `ServerCapability`, `G'.Target` must equal `G.Target` exactly as a full `ServerRef` (§4d) — `AuthoritativeHostId` and `ServerProfileId` both — a `ServerCapabilityGrant` is already maximally specific, so "narrowing" collapses to "the same server on the same Host, never a different one." Comparing only `ServerProfileId` would be wrong: two different Hosts can independently mint the same profile id for unrelated servers.
  3. `G'.DerivedFromGrantId = G.GrantId` — recorded exactly, the real source grant, not merely "some grant A happens to hold."
  4. `G'.CanDelegate` may only be `true` if `G.CanDelegateOnwardDelegation == true`.
  5. `G'.CanDelegateOnwardDelegation` may only be `true` if `G.CanDelegateOnwardDelegation == true`.

  Rules 4–5 are what make it **structurally impossible** for an actor who can delegate X but was never given the *right to delegate the delegation right itself* to manufacture a `CanDelegate = true` grant downstream — every grant they issue is forced to `CanDelegate = false`, full stop.

  **`ManagePermissions` (`HostCapability`) is deliberately not part of this predicate at all.** A prior revision left it ambiguous whether broad "manage permissions"-style capabilities factored into "may actor A issue this exact grant." They do not — `ManagePermissions` governs a separate, narrower class of administrative actions (**viewing** the full grant/delegation graph across all actors; other permission-*inspection* UI), never the act of creating a specific grant, and — per the fix below — **not** editing `DefaultGrantTemplate` either. **There is exactly one authoritative answer to "may A issue this downstream grant to B": the five-part predicate above, and only that.** The prior `ServerCapability.GrantServerPermissions` enum value is **removed** — its name actively invited the exact ambiguity this correction closes (it read as if it independently authorized granting server permissions, duplicating what `CanDelegate` on the specific capability already governs), so it's deleted rather than kept as a confusing near-duplicate.

  **Closing the `DefaultGrantTemplate` bypass.** A prior revision let `ManagePermissions` edit `DefaultGrantTemplate`, which is applied as Owner-root grants (`DerivedFromGrantId = null`) the moment a new pairing reaches `Active` — an alternate path that could manufacture authority (e.g. `ManageHostUpdates`) an actor holding only `ManagePermissions` could never grant directly through the five-part predicate above. **Fixed by the simpler of the two options this document considered: `DefaultGrantTemplate` modification is Owner-only.** No delegated capability, including `ManagePermissions`, authorizes editing it — only the structural `IsOwner` check (§3a) does, the same mechanism that makes Owner status itself unrevokable. This closes the gap completely rather than through a more complex per-entry provenance-tracking scheme: since only the Owner (who can already grant anything, by definition) can ever configure it, there is no path where the template could contain a grant its configurer wasn't independently allowed to issue.
- **Provenance and cascade invalidation, precisely a tree (forest), not a DAG.** `DerivedFromGrantId` is a single nullable reference — each grant has **at most one** provenance parent, so the structure is a set of trees (a forest), each rooted at a grant with `DerivedFromGrantId = null`. Revoking a grant transactionally revokes every grant in the subtree rooted at it — a precise per-subtree operation, not "revoke everything this actor ever granted." (A future design could intentionally allow multiple provenance parents, making this a true DAG — that is not this design.)
- **Owner root-grant representation** uses the persisted `LocalPrincipal` Owner actor (§3a, §5b): a root grant (`DerivedFromGrantId = null`) has `GrantedByActor = LocalPrincipal(OwnerLocalPrincipalId)`. The Owner's *own* authority is never itself a grant (§3a); grants the Owner issues to others are. **A `HostCapabilityGrant` root grant still requires an explicit `TargetHostId`** (`AUTH-005`) — Owner authority is structural and unconditional, but the grants the Owner *issues*, including to a non-Owner local principal for local-Host administration, are not exempt from destination scoping merely because the Owner issued them.
- **Configurable defaults for newly paired Managers**: a Host setting (`DefaultGrantTemplate`), **modifiable by the Owner only** (see above), applied — as ordinary root grants, `GrantedByActor = LocalPrincipal(OwnerLocalPrincipalId)` — at the moment a new pairing reaches `Active` (§4b/§4c). **The shipped factory `DefaultGrantTemplate` is least-privilege; a Host's *currently configured* `DefaultGrantTemplate` may differ from that factory default**, since the Owner is free to change it (and only the Owner, per above). Activation always applies whatever is currently configured at that moment — never an assumed-least-privilege factory value — which is precisely why the pairing state machine (§4b) cannot treat "defaults are safe" as a reason to skip reciprocal confirmation. Changing the template later never retroactively rewrites grants already issued. **Every `HostCapabilityGrant` a `DefaultGrantTemplate` produces for a newly-`Active` `RemoteManager` targets `TargetHostId = ThisHostId`** (`AUTH-005`) — these grants represent what that peer may now do to *this* Host, never an ambiguous "every Host," and there is no other Host a fresh pairing could sensibly grant authority over. A **genuinely new** `HostId`'s pairing lands at this same currently-configured template directly, the ordinary way. Credential-loss re-pairing for an **already-known** `HostId` does not — see §4b-i's `PendingCredentialReplacement` gate: explicit Owner approval applies this same currently-configured template (with the same `TargetHostId = ThisHostId` scoping) as fresh Owner-root grants, and never silently restores a peer's prior grants; carrying old permissions forward afterward requires the explicit, audited Owner adoption/re-home step §4b-i defines concretely.
- **Role-preset application is validated per entry, not applied blindly.** A preset (View Only / Server Operator / Server Administrator / Host Administrator) expands into several individual grants; each one is checked against the five-part predicate above using the *applying* actor's own current grants, exactly as if that grant were being issued individually. An entry the applier isn't independently authorized to issue is not created — a preset can never grant its applier's own authority beyond what they could already grant one capability at a time. **Every `HostCapability` entry a preset expands to gets an explicit `TargetHostId`** (`AUTH-005`), validated per entry against the applying actor's own `TargetHostId`-scoped authority for that same Host — applying a preset for administering Host B never grants authority over Host C, even if the applier separately holds broad authority over Host C too.
- **Explicit per-server sharing** is just `ServerCapabilityGrant`s; a Manager's server inventory is exactly the set of `ServerRef`s (§4d) where it holds `ViewServer`.
- **`ManageHostUpdates` is a distinct `HostCapability`** — not folded into `ManageHostSettings` — so update authority can be granted/withheld independently, per #17's explicit requirement.

Authentication and authorization are enforced as genuinely separate steps in the request pipeline, for both actor kinds: a successful mTLS handshake (remote, §4a) or signed local challenge (local, §3a) proves *identity*; every subsequent RPC still independently checks the caller's grants for that specific capability and scope. A freshly paired Manager, even with the Host's currently configured `DefaultGrantTemplate` at its most permissive, can authenticate perfectly well and still be told "denied" for any capability that template doesn't actually include.

### 5a. `Host.Cli` vs. Host-exclusive SQLite writer ownership

The prior revision of this document left "does `Host.Cli`'s bootstrap storage share the same SQLite database Host will later own exclusively" as an open question for #20/#21 to invent. That's a boundary decision this issue must fix, not implementation detail — resolved as follows.

**Invariant: while Host is running, Host is the sole writer of authoritative Host state, always.** This is structurally enforced, not just documented:

- **`Host.Cli` has exactly one mode: privileged, offline bootstrap/recovery (Product Decision, 2026-09-01, `CLIENT-003`).** A prior revision of this section also gave `Host.Cli` a "normal operation" mode — a thin `Contracts`-speaking gRPC client over local IPC, using the same operation surface as ordinary clients, while Host is running. That's removed: `Host.Cli` never runs while Host is running at all, has no online client behavior, no `LocalPrincipal` credential, and never authenticates as, or substitutes for, an ordinary local client. Ordinary online command-line management is `Client.Cli`'s role (§1) — a structurally separate project with no privileged-recovery authority of any kind.
- **Bootstrap/recovery mode** (Host is not running — e.g. first-ever setup before any Host process has started, or emergency recovery while the Host service is down) is therefore `Host.Cli`'s *only* mode: it first attempts to acquire the **same machine-wide exclusivity lock** Host itself uses (§2, owned by `Host.Persistence`). If the lock is already held, Host *is* running, and `Host.Cli` refuses to proceed — it prints "Host is running; privileged recovery is unavailable while Host holds the exclusivity lock" rather than risking a concurrent writer, and falls back to nothing, since it has no other mode to fall back to. Only once the lock is successfully acquired does `Host.Cli` use `Host.Persistence`'s schema/repository code **directly** — the same code `Host` itself would use, not a separate ad hoc implementation — to perform the specific bootstrap/recovery action: initializing `HostIdentity` and creating the `PendingOwnerEnrollment`/`OwnerBootstrapSecret`/`LocalHostTrustDescriptor` for privileged initial Owner bootstrap (§2c, `OWNER-002`), the Owner credential-rotation/re-homing operation defined precisely in §2b, or the Host machine-credential-loss recovery operation defined precisely in §3b — then releases the lock.
- Every bootstrap/recovery-mode write is recorded in `AuditEvents` (§6), tagged as an offline-recovery action, written in the **same transaction** as the change itself using the same persistence code path — so it's auditable even though the Host process wasn't running to log it live.

This gives Host and CLI **no path to ever concurrently mutate the database**: the exclusivity lock is the single arbiter of who may write, and whoever holds it is provably the only writer — not "the only writer by convention." `Client.Cli`, having no dependency path to `Host.Persistence` at all (§1), was never a party to this concern in the first place — it reaches the database only indirectly, the same way `Client.Avalonia` does, by asking the running Host to act on its behalf over authenticated local IPC.

### 5b. Actor model for grants and audit

`CapabilityGrant` (§5) and `AuditEvents` (§6) must represent *both* kinds of actor without pretending one is the other:

```
ActorRef = LocalPrincipal(LocalPrincipalId) | RemoteManager(PeerHostId)
```

A `LocalPrincipal`'s Owner authority is never itself a `CapabilityGrant` row (§3a); grants the Owner *issues* — to a non-Owner `LocalPrincipal` or to a paired `RemoteManager` — are ordinary `CapabilityGrant` rows with `GrantedByActor = LocalPrincipal(OwnerLocalPrincipalId)`. Everywhere this document says "Manager" as a grantee/actor, read it as `ActorRef`, covering both local principals and remote Managers uniformly — including in every `CapabilityGrant`/`ManagerIdentity` field named `...PeerHostId` above, which should be read as the `RemoteManager` case of `ActorRef` for grants issued to a paired peer, and as `LocalPrincipal` for grants issued to a local user.

## 6. Persistent Host state

Host owns a single embedded **SQLite** database under its machine-wide data directory, accessed only by the Host process (and, exclusively in bootstrap/recovery mode, `Host.Cli` — §5a) through `Host.Persistence` (§1).

Why SQLite over continuing the current JSON-file-per-concern approach: the new requirements — transactional cascade invalidation across `CapabilityGrant` trees, revision/version tokens with atomic compare-and-reject, cross-client-visible operation locks, durable multi-phase recovery state — need real ACID transactions, which `File.WriteAllText`-per-file cannot provide. SQLite has mature first-class .NET support and needs no separate database *service process* to install, configure, or keep running (unlike Postgres/MySQL), which matters for a headless single-machine tool. **This is independently justified by the substantially greater complexity of v0.5's Host state on its own merits — it is not offered as, and does not claim to be, a fix for [#26](https://github.com/shoemin/Palworld-Server-Manager/issues/26), which remains an open, unresolved investigation with no established root cause.**

**Correcting "zero-dependency" framing.** SQLite is not a zero-dependency choice: the .NET SQLite provider (e.g. `Microsoft.Data.Sqlite`, exact package selection left to #20) and its native SQLite runtime binary are a genuine new product dependency, recorded here explicitly rather than implied away. "No separate service to install" is true and is the actual point in SQLite's favor; "no new dependency at all" is not, and this document does not claim it.

**Correcting the backup assumption.** With WAL mode enabled (needed for the concurrent-reader/single-writer behavior this design relies on), a live database's true on-disk state spans the main `.db` file plus `-wal`/`-shm` files; naively copying just the `.db` file while Host is running can produce a corrupt or stale snapshot missing not-yet-checkpointed WAL contents. Any Host-state backup/snapshot mechanism must use SQLite's own consistent-snapshot facilities — its online backup API (exposed in .NET as `SqliteConnection.BackupDatabase` or equivalent) or `VACUUM INTO` — while the database remains live, never a raw filesystem copy of the `.db` file alone. This document fixes that requirement; it does not design #22's actual backup/packaging UX.

## 7. Secure credential-storage abstraction

Coordinates directly with [#27](https://github.com/shoemin/Palworld-Server-Manager/issues/27). Contract (`Platform.Contracts`):

```csharp
interface ISecureCredentialStore
{
    Task StoreAsync(string key, ReadOnlyMemory<byte> secret, CancellationToken ct);
    Task<byte[]?> RetrieveAsync(string key, CancellationToken ct);
    Task DeleteAsync(string key, CancellationToken ct);
}
```

- **Windows**: DPAPI (`ProtectedData.Protect`) at **machine scope**, not user scope — Host runs as a machine-wide service (§2), so user-scoped DPAPI (tied to an interactive profile) is the wrong primitive here. **Machine scope alone is not per-service isolation**: any process running with sufficient machine-level privilege on that Windows install can call `ProtectedData.Unprotect` at machine scope on *any* blob it can read, regardless of which service "owns" it conceptually. DPAPI machine-scope encryption is therefore paired with restrictive NTFS ACLs on the actual encrypted-blob storage location — readable only by the Host's specific service account, not by "any sufficiently privileged process." **This ACL pairing meaningfully raises the bar against an ordinary local process or a different, unprivileged service running on the same machine — it does not, and cannot, protect against a genuinely privileged local Administrator/`SYSTEM`-level attacker**, who can take ownership of the file, reset its ACL, and read it; Windows' security model does not meaningfully contain Administrator/`SYSTEM` privilege against itself on the same machine. This is stated explicitly to keep the Windows threat-model boundary parallel to the Linux one below: v0.5 protects ordinary at-rest application secrets against non-privileged local users and other unprivileged processes; it does not claim protection from a fully privileged local machine owner on either platform.
- **Linux**: session-based keyrings (gnome-keyring/kwallet via Secret Service) are explicitly rejected as the *primary* store, because they require an active desktop session and headless unattended boot is a hard requirement. Instead, a two-tier model:
  - **Tier 1 — the master key**: a locally-generated key file, `0600` permissions, owned by the Host's dedicated service account. This file **is plaintext key material** — it is the trust anchor itself, not something further encrypted, protected only by OS file permissions. It must not be described as "non-recoverable plaintext"; it is straightforwardly recoverable by anyone with sufficient OS access to read it (root, or offline disk access — see the threat-model boundary below).
  - **Tier 2 — application secrets**: paired-Manager credentials, private keys, and other sensitive material in `SecureCredentialReferences`/ordinary Host persistence are **encrypted at rest using the Tier 1 master key** — so a compromise of ordinary Host state *alone* (a copy of the SQLite database without the separately-permissioned master key file) does not expose secrets. Only possession of both, or of the master key specifically, does.
  - This is the same practical trust model most unattended Linux daemons already rely on for their own secrets (comparable to how `sshd` protects its host keys via file permissions) — a plaintext root key, permission-protected, with everything else encrypted under it.

  **Threat-model boundary, stated precisely rather than implied:**
  - **Protects against**: ordinary/non-privileged local users (denied by file permissions), accidental disclosure through normal file browsing, appearing in logs/audit/diagnostics (enforced separately, below), and a naive backup script that respects file permissions.
  - **Does not protect against**: a privileged root user on the same machine, or an attacker with offline access to the raw disk (booting from external media, mounting the disk elsewhere). A colocated software key protected only by filesystem permissions provides **no** resistance to either — the permission check is enforced by the running kernel, not by anything cryptographically tied to something the attacker lacks. This baseline must not be described as hardware-backed or offline-disk-resistant, because it is neither.
  - **Optional stronger mitigation**: TPM-backed sealing (binds the key to specific machine hardware/boot state, and can resist offline-disk-copy attacks even against a root-level attacker in some configurations) or `systemd-creds` where it integrates with TPM — offered as an enhancement layered on top of the floor above, not claimed as the baseline.
  - This baseline still satisfies #27's actual requirements: no *recoverable plaintext* secret in ordinary Host state (true — reading it requires OS-level access, not a text editor); unattended headless boot remains possible (true — no interactive unlock needed); no secrets in logs/audit/diagnostics (true, enforced separately below). It does not, and is not represented as, defending against a root-level or offline-disk attacker.
- Secrets never appear in `AuditEvents`, logs, or diagnostic bundles — this is enforced at the logging/serialization layer (a `[Secret]`-style marker on any DTO field that must never be logged, checked by a self-test, not by developer discipline alone).
- v0.4 → v0.5 migration never widens exposure: if a v0.4 secret (e.g. today's plaintext outbound LAN token) can't be migrated into the new model safely, migration stops and reports it rather than silently carrying the weaker format forward.
- **`EnrollmentCode` (§3a), `OwnerBootstrapSecret` (§2c), and the Owner-credential-rotation and Owner-rehome secrets (§2b) are bearer secrets covered by the same `[Secret]`-marker redaction as everything above, but none go through `ISecureCredentialStore` itself** — that interface is for secrets *Host* later retrieves for its own use; these are one-time values handed to a *person* who has no Host-issued credential yet to protect them with. All follow the "store a verifier, never the value" principle instead: ordinary Host persistence holds only a keyed hash/HMAC (computed using `ISecureCredentialStore`-protected key material), and the raw value exists only transiently — communicated out-of-band for `EnrollmentCode` (§3a, mirroring §4b's pairing code), or delivered through an OS-ACL'd handoff artifact readable only by the intended `OsPrincipalRef` for `OwnerBootstrapSecret` and both §2b Owner-recovery secrets alike — never through this store, and never recoverable from a copy of ordinary Host state.

## 8. Trust revocation architecture

Coordinates directly with [#28](https://github.com/shoemin/Palworld-Server-Manager/issues/28).

As established in §4a, **credential revocation and trust revocation are the same operation** — there is no partial "trust the `HostId` but not its current credential" state, since the credential is the only thing that proves you're talking to that `HostId` at all.

- **Revocation retains a durable tombstone, never deletes the `TrustedManagers` row (Product Decision, 2026-09-01, fresh evidence during `PAIR-004` review).** A prior revision of this section had revocation delete the row outright — that broke §4b-i's own trigger, which requires an *existing* row to recognize a same-`HostId` re-pairing attempt as a credential replacement rather than a genuinely new peer; deleting the row on revocation would let a later re-pairing with that exact `HostId` be misclassified as new and receive fresh default grants with no Owner approval, silently defeating the replacement gate this same round just built. Fixed the same way `LOCAL-003` fixed the analogous problem for `LocalPrincipal`: revocation sets `State = Revoked` and clears `CurrentTrustedPublicKeyFingerprint` — the row, and the fact that this `HostId` was once trusted, persists. **Revocation also clears any in-progress staged-rotation fields (`PendingTrustedPublicKeyFingerprint`/`PendingRotationId`/`PendingRotationExpiresUtc`/`PendingReconfirmationRequired`, §4a-i, `IDENT-003`)** — including the Owner-driven revocation an unreachable peer receives specifically to unblock a stalled rotation (§4a-i step 3), and one the Owner chooses instead of reconfirming a lapsed-but-already-verified rotation (step 6) — so a tombstoned row never retains a dangling pending credential from a rotation it will never complete.
- **Online two-sided unpair**: initiator sets its local `TrustedManagers` row (keyed on `PeerHostId`, §4a) to `State = Revoked` and clears its pinned fingerprint, then sends an authenticated `RevokeTrust` RPC over the still-valid mTLS connection; the peer does the same on receipt. **Both sides cascade-invalidate every `CapabilityGrant` in the subtree rooted at that actor's grants, per §5's tree traversal, in the same transaction as the state change** — revocation is never "row updated, grants cleaned up later, maybe."
- **Offline revocation** is structurally simple under the pinned-credential trust model (§4a): trust is a local allow-list keyed on `HostId` with a pinned current-credential fingerprint, not a CA-issued certificate anyone could still present. Setting `State = Revoked` and clearing the pinned fingerprint **is** the revocation — the next connection attempt from that peer fails TLS trust validation immediately (its credential no longer matches anything pinned), with no CRL/OCSP machinery required; the row's continued existence is the tombstone, not a re-introduced "still trusted" signal. **This same transaction also cascade-invalidates the peer's `CapabilityGrant`s (§5)** — orphaned grants surviving a state change, evaluable again if that `HostId` ever reconnects, is exactly the silent-restoration failure mode this whole Product Decision exists to close.
- **Re-pairing** always starts a fresh pairing bootstrap (§4b) — a revoked peer regains nothing by simply reconnecting; it has to re-earn a new `HostId`↔credential pin through the full MITM-resistant flow. A genuinely new `HostId` — no `TrustedManagers` row in any state — lands at the Host's *currently configured* `DefaultGrantTemplate` (§5) directly — not necessarily its shipped factory least-privilege value. If the peer instead re-presents the *same* `HostId`, in **any** existing state including `Revoked` (rather than a fresh one), that hits the §4b-i `PendingCredentialReplacement` gate, not an ordinary fresh pairing — zero authority until the local Owner explicitly approves the replacement, never its old grants (unless separately, deliberately adopted by the Owner afterward, §4b-i).
- **Local Owner** can always revoke any remote Manager. A remote administrator may revoke another remote Manager only if explicitly granted that authority under §5's model — revocation itself is gated by the same capability system it operates on.

## 9. Concurrency contracts

- **Revision tokens**: every mutable aggregate that can be edited by more than one actor (server settings, `CapabilityGrant` sets, sharing config, Host settings) carries a monotonically increasing `RevisionId`. Write RPCs must submit the revision they last read; the Host compares it inside the same transaction as the write and rejects with a `StaleWriteConflict` result — never a silent overwrite.
- **Per-server operation locks**: an `OperationLock` row `{ Server: ServerRef (§4d), OperationKind, AcquiredUtc, OwningOperationId }`, acquired transactionally before an exclusive/destructive operation begins. This is a direct, durable generalization of the existing in-memory `CriticalOperationTracker` — same proven concept (a lease held for an operation's duration, released on completion or exception), now a database row instead of process memory, which is exactly what's needed once more than one client (local and remote) can be watching the same server.
- **Lock visibility**: because the lock is a database row rather than in-process state, every connected client — local or remote — querying operation/Activity status sees the same lock, satisfying "lock visibility to multiple clients" directly.
- **Operation lifetime independent of the initiating client**: the lock and its `OperationRecord` (§10) belong to the operation, identified by its own `OperationId`, not to the client connection that started it. If that client disconnects mid-operation, the Host-side work and its lock continue exactly as they do today when a `SendServerWindow` is closed mid-transfer (the lease is released only when the operation itself finishes or fails) — same principle, now durable and multi-client-visible instead of single-process.

## 10. Durable operation/recovery model

`OperationRecord { OperationId, Kind, Server: ServerRef (§4d), Phase, StartedUtc, LastHeartbeatUtc, RecoveryDisposition }`.

Phases are **specific to each operation kind**, not a generic state machine — e.g. a Backup operation might declare `{ Started, SourceSnapshotted, ArchiveWritten, Verified, Completed }`. Each operation kind's implementation declares, per phase-transition, which of these applies on recovery:

- `SafeToRetryFromStart` — nothing durable happened yet, just restart it.
- `SafeToResumeFromPhase` — durable, idempotent-from-here work exists; continue from the recorded phase.
- `RequiresManualReview` — ambiguous/partial durable state; do not guess.
- `SafeToDiscard` — partial artifact exists but is worthless; clean it up and mark failed.

**Not every interrupted operation is assumed resumable** — that classification is explicit, per operation kind, per phase, decided by the code that implements that operation, not inferred generically. On Host startup, every non-terminal `OperationRecord` is scanned and its declared disposition applied; anything landing in `RequiresManualReview` surfaces as an explicit "Recovery Required" item in Activity rather than being silently resumed, silently discarded, or reported as if the server were simply idle.

Split into two separate interface sets in two separate projects (§1), matching the corrected dependency graph — Host-side interfaces may reference `Core` domain types; client-side interfaces deliberately never do.

### 11a. Local server-folder path lookup (client-side shell launch, Product Decision, 2026-09-01, `PLATFORM-002`)

"Open server folder" is client-side, not Host-side, for the same reason §2 makes Host a background service: launching Explorer or `xdg-open` requires an interactive desktop session, which a Windows Session-0 service or a headless Linux daemon simply doesn't have — for a local caller, and there is no meaningful session to launch into at all for a *remote* one. The existing v0.4 behavior works today only because it launches Explorer from the interactive WPF UI process, not a service.

**The model**: Host owns authoritative knowledge of where a server's data lives and who's authorized to see it; `Client.Avalonia`'s own interactive session owns actually opening a folder.

1. Only a **local** desktop client may request this, and only for a server whose `ServerRef.AuthoritativeHostId == ThisHostId` (§4d) — never for a remote-shared server.
2. Host exposes a narrow, **local-IPC-only** RPC that, given a `ServerRef` satisfying (1) and the same authorization already required for other operations on that server (§3a, §5), returns the known local data-directory path — nothing else. This is not a generic browse-filesystem RPC, not a user-supplied arbitrary-path lookup, and it does not exist on the remote network listener (§4) at all.
3. `Client.Avalonia` receives that authorized local path and invokes `IClientShellIntegration` (§11) in its own current interactive user session — never Host, and never a background/service context.
4. A remote or headless server offers no meaningful local "open folder" action at all; `Client.Avalonia` does not send a remote server's filesystem path anywhere for shell launching, and does not attempt this operation for a non-local `ServerRef`.
5. No user-session broker is introduced for v0.5. The existing "no generic file-browser API, no remote filesystem browsing" rules (§4b) are unaffected — this narrow, single-purpose, local-only path lookup is not a browsing capability.

## 12. Core Palworld settings metadata seam

`Core` already models Palworld's INI settings with unknown-key preservation (`PalworldConfigParser`, `PalworldSettingSchema`). That model is extended, not replaced: `Core` owns `PalworldSettingDefinition` records — key, display name, description, category, semantic editor kind, min/max/step/unit/default, validation rules, enum choices, restart-required-if-actually-known.

`Host` exposes this to clients through the protocol boundary, never by `Client.Avalonia` or `Client.Cli` referencing `Core` directly:

```
GetSettingsSchema(server: ServerRef) -> SettingDefinition[]
GetServerSettings(server: ServerRef, revision) -> { values[], revision }
```

Like every other RPC on the protocol boundary, these take a `ServerRef` (§4d), never a bare id — the routing model (§4c) means these calls can reach a remote Host through the local one, and the target must stay unambiguous once more than one Host is in play.

Avalonia renders controls purely from the returned schema + values (§9 of the #18 UI spec's semantic-control table maps `EditorKind` values directly to Avalonia control types) — it never needs to know Palworld's INI format exists. Unknown/future INI keys keep flowing through exactly as `PalworldConfigParser` already preserves them today; they're exposed to the UI through an Advanced/raw surface rather than discarded or guessed at.

## 13. Protocol compatibility policy

`ProtocolVersion = { Major, Minor }`, advertised in every `Handshake` (§4).

- **Major** version mismatch is incompatible and the connection is refused with a clear, specific error naming both versions — **unless** an explicit compatibility range says otherwise (a deliberate, documented exception such as "major 2 also accepts major 1 read-only clients"), never guessed or assumed from app version strings.
- **Minor** version evolution is strictly **additive** — a minor bump may add new fields/RPCs/capabilities, never remove or repurpose an existing one. Removing or changing the meaning of anything requires a major bump.
- **Protobuf field numbers are never reused**, even for fields later removed; removed fields are marked `reserved` in the `.proto` schema rather than freed for reuse — this is what lets an old message on the wire never be silently misinterpreted by a newer schema, or vice versa.
- **Unknown/new optional fields are tolerated safely** — protobuf's default forward-compatible behavior (an older parser ignores fields it doesn't recognize) is relied on deliberately, not worked around.
- **Unknown/new enum values must never accidentally authorize behavior.** An older client or Host encountering a capability/permission enum value it doesn't recognize must treat it as **deny/unknown**, never default-permit — this is the one place "ignore what you don't recognize" (the general forward-compatibility rule above) is deliberately *not* applied, because for an authorization-relevant enum, silently ignoring an unrecognized value in the permissive direction is a privilege-escalation bug waiting to happen.
- **Two-layer gate on every feature**: an operation executes only when *both* protocol-major compatibility holds *and* the specific capability was negotiated in `Handshake` — compatibility alone doesn't imply a feature is available, and capability advertisement alone doesn't bypass a major-version incompatibility.
- **App/product version strings are informational only** — displayed to the user, never consulted for authorization or compatibility decisions. `ProtocolVersion` and `Capabilities[]` are the only inputs to those decisions.
- Handshake is mandatory on **every** connection, local or remote, before any operational RPC is accepted — there's no "trusted because it's local" bypass of version/capability negotiation, only a different auth anchor (§3a vs §4a).

## 14. Testability

Contracts this section leaves stable enough to write **before** #20 needs them (these tests are #20's deliverable, not #19's — #19 only has to make them meaningful to write):

1. **Capability-grant tree invalidation** — pure-logic unit tests: revoking a grant cascades exactly to the subtree rooted at it and no further.
2. **Delegation predicate, including type-safety and the template bypass** — the exact §5 five-part predicate: an actor with `CanDelegate=true, CanDelegateOnwardDelegation=false` can create grants for others but can never produce a `CanDelegate=true` downstream grant, under any input; a `HostCapabilityGrant` can never derive a `ServerCapabilityGrant` or vice versa; a `HostCapabilityGrant` can never derive a grant for a *different* `TargetHostId` (`AUTH-005`) — including when the delegating actor separately holds a same-capability grant for that other Host too; a `ServerCapabilityGrant` can never derive a grant for a *different* `ServerRef` — including two grants that happen to share a `ServerProfileId` but differ in `AuthoritativeHostId`; `DerivedFromGrantId` always records the real source grant used; `ManagePermissions` alone never authorizes issuing a specific grant *or* editing `DefaultGrantTemplate`; only `IsOwner` authorizes the latter; a role preset containing an entry the applier isn't independently authorized to issue creates every other entry but not that one.
3. **Revision/stale-write conflict** — a concurrent write with a stale revision token is rejected, not merged or overwritten.
4. **Operation-lock acquire/release/cross-client visibility** — two simulated clients observe the same lock state; lock survives the initiating client disconnecting.
5. **Recovery-disposition classification** — simulate a Host crash at each declared phase of a representative operation kind and assert the correct disposition is chosen (never assume resumable by default).
6. **Local IPC parity** — the same logical Host contract test suite runs against both the Windows named-pipe and Linux Unix-socket transports and produces identical client-observable behavior.
7. **Handshake/version negotiation** — compatible minor-version connects and correctly hides newer capabilities from an older client; incompatible major-version is refused with a clear error; an unrecognized authorization-relevant enum value is treated as deny, never permit.
8. **Secure-credential-store round-trip per platform** — store/retrieve/delete, plus a redaction assertion that no `[Secret]`-marked field ever reaches `AuditEvents`, logs, or diagnostics.
9. **Pairing local-state machine and crash behavior** (§4b) — an attempt that never reaches `Active` (wrong/expired code, failed key confirmation, rate-limit exceeded) grants zero authorization; a simulated Host-process crash during `Created`/`PAKEAuthenticated` discards that in-flight state entirely and a fresh attempt with a new code succeeds normally; a `PeerBound` state durably survives a simulated Host-process crash and completes to `Active` via ordinary mTLS reconnect **without** repeating the PAKE exchange; a `PeerBound` state with a non-trivial configured `DefaultGrantTemplate`, sitting unacknowledged, grants zero authorization until the reciprocal activation acknowledgment is actually received; receiving that acknowledgment twice (a retried/duplicated message) commits the resulting grants at most once.
10. **Credential rotation and loss** (§4a) — a rotation/staging proposal signed by the current credential is accepted and preserves `HostId`/grants; an unsigned/incorrectly-signed proposal is rejected; simulated credential loss correctly requires full re-pairing rather than silently continuing; a fresh pairing claiming a genuinely new `HostId` completes normally, while one claiming an already-known `HostId` produces a `PendingCredentialReplacement`, not an `Active` trust relationship. (The staged multi-peer rotation flow itself is covered in detail by item 34, `IDENT-003`.)
11. **`Host.Cli`/`Host` writer exclusivity** (§5a, `CLIENT-003`) — a `Host.Cli` invocation while Host holds the exclusivity lock must be refused, never silently allowed to proceed, and never falls back to any ordinary-client behavior, since `Host.Cli` has none.
12. **Per-principal local identity and credential separation** (§3a) — two distinct `LocalPrincipal` keypairs map to two distinct `LocalPrincipalId`s on a signed-challenge connect; a signature from a non-authorized/`Revoked` principal's key is rejected; Host's stored data for a principal contains only the public verification key, never anything resembling private key material.
13. **Desktop Host activation** (§2a) — an ordinary authorized local user with no Administrator/root privilege, a member of the dedicated local group, can start a dormant Host through `IHostActivation` and connect; a local user not in that group cannot even attempt the start.
14. **Owner immutability and recovery** (§2b) — no remote RPC and no ordinary local grant (including via `ManagePermissions`) can change any row's `IsOwner`; the offline recovery operation (Host stopped, exclusivity lock held) correctly rotates the Owner's credential or re-homes `IsOwner` to a new principal, leaving exactly one `IsOwner=true` row in every case, verified transactionally.
15. **Outbound remote routing and dual authorization** (§4c) — a `LocalPrincipal` with no local grant for a given remote-server operation is denied by the local Host without any outbound connection being attempted (simulated/mocked, to prove the remote peer was never contacted); a `LocalPrincipal` with local authorization but where the remote peer's `CapabilityGrant` to this machine's `PeerHostId` doesn't cover the operation is denied by the *remote* side despite passing locally; only when both checks independently pass does the operation succeed; neither `Client.Avalonia`'s nor `Client.Cli`'s own test surface ever has access to a Host private credential to assert against. **For a Host-level operation, a `LocalPrincipal` holding a `HostCapabilityGrant` targeting Host B is denied — without any outbound connection attempted — when the destination is Host C, even for the identical `Capability`** (§4c, `AUTH-005`); holding the capability for `ThisHostId` never authorizes it against any remote Host.
16. **`ILocalPrincipalCredentialStore` round-trip per client platform** — create/store/load/delete for the current OS user's own credential; a second, different `LocalPrincipalId`'s credential is never returned by another principal's load call; nothing resembling Host machine credential material ever appears in this store's data; `Client.Avalonia` and `Client.Cli`, run as the same OS user, load the same `LocalPrincipalClientCredential` (`CLIENT-003`) — never two different identities for one person.
17. **`LocalPrincipal` revocation and reactivation** (§3a) — revoking a non-Owner principal sets `State = Revoked`, clears its key, and cascades its current grants without affecting other principals; a `Revoked` principal's OS account remaining group-member does not by itself restore any authority; reconnecting and generating a fresh keypair without a matching `PendingLocalPrincipalEnrollment` authenticates nothing; **a keypair presented with the correct `OsPrincipalRef` but a wrong or missing `EnrollmentCode` is rejected — knowing/guessing the `OsPrincipalRef` alone is never sufficient to consume another party's pending enrollment**; an Owner-issued `PendingLocalPrincipalEnrollment` reactivates the same `LocalPrincipalId` (`State: Revoked -> Active`) but never restores the grants revocation removed; the enrollment record's underlying registration happens exactly once — a wrong code or an expired record is always rejected, but presenting the **same, correct** code again after the record is already consumed (simulating a lost response) idempotently returns the same `ResultLocalPrincipalId` again rather than erroring or registering a second time, bounded by `ExpiresUtc`. **The persisted `PendingLocalPrincipalEnrollment` row never contains the raw `EnrollmentCode` in a form readable without `ISecureCredentialStore`-protected key material** — a redaction assertion equivalent to §7's `[Secret]`-marker check, and a direct read of the ordinary SQLite tables never yields a usable code. **Wrong-code attempts against one `PendingLocalPrincipalEnrollment` are rate-limited**: `FailedAttempts` increments on each wrong-code presentation, and on reaching the same ten-attempt bound §4b's pairing code already uses, the record is locked out for the remainder of its `ExpiresUtc` window — asserted by simulating repeated wrong-code guesses and confirming a subsequently *correct* code is still rejected once the bound is reached, never merely that incorrect codes fail individually.
18. **`PendingCredentialReplacement` Owner-approval flow** (§4b-i) — a fresh pairing claiming an already-trusted `HostId` without valid rotation proof produces a zero-authority candidate that cannot exercise any operation and does not disturb the existing trusted credential or grants; approval requires an explicit local-Owner action and is rejected for any other actor; approval atomically retires the old credential binding, invalidates the old grant roots/subtrees, binds the new credential, establishes `Active` trust, and applies the currently configured `DefaultGrantTemplate` as fresh grants — never the prior ones; a subsequent Owner adoption/re-home action can reissue selected prior permissions as new root grants but never revives old downstream delegated grants automatically; an unapproved candidate expires with no grants ever having existed. **A `Revoked` `TrustedManagers` row (§8) still triggers this gate on the next same-`HostId` pairing attempt — it is never misclassified as genuinely new** — and revocation itself (online or offline) cascade-invalidates the peer's grants in the same transaction as the state change, leaving nothing orphaned to re-evaluate later. **A symmetric fresh-pairing exchange where only the *partner* Host lost its credential never produces a `PendingCredentialReplacement` on the unaffected side, but only once that side is actually `Active`** — a presented credential that exactly matches the already-pinned fingerprint on an `Active` row reconfirms `Active` trust and disturbs nothing; the identical matching-credential case against a row still only `PeerBound` (e.g. a simulated crash after `PeerBound` persisted but before reciprocal activation) does **not** get reconfirmed as `Active` and does **not** open a `PendingCredentialReplacement` either — assert it instead resumes toward `Active` via the ordinary `PeerBound` crash/reconnect path (item 9); only an actually-*different*, non-rotation-proven credential triggers the gate.
19. **Local server-folder path lookup** (§11a) — the local-IPC-only path-lookup RPC succeeds only for a `ServerRef` with `AuthoritativeHostId == ThisHostId` and only for a caller holding the same authorization already required for other operations on that server; it is denied (never silently no-op'd) for a remote `ServerRef`; the RPC does not exist on the remote network listener at all; `Client.Avalonia`'s test surface never attempts to invoke shell-launch behavior from anything but its own interactive-session code path.
20. **`HostCapabilityGrant` destination scoping** (§5, `AUTH-005`) — a `TargetHostId`-scoped grant authorizes only that exact `HostId`, never a different one, including the local `ThisHostId` itself when the grant targets a remote peer, and vice versa; delegation of a `HostCapabilityGrant` can never change `TargetHostId`, even when the delegator independently holds a same-capability grant for a different target; `DefaultGrantTemplate` activation and `PendingCredentialReplacement` approval (§4b-i) both produce `HostCapabilityGrant`s scoped to `TargetHostId = ThisHostId`, never left ambiguous or omitted; role-preset expansion validates each `HostCapability` entry's `TargetHostId` against the applying actor's own authority for that same Host.
21. **Named-pipe/Unix-socket squatter** (§3b, `LOCAL-004`) — a local endpoint that exists but cannot prove the pinned Host identity (simulated attacker-created endpoint) causes the client to send **no** `EnrollmentCode`, **no** `OwnerBootstrapSecret`, and **no** `LocalPrincipal` signature — assert none of these ever leave the client process toward an unauthenticated endpoint.
22. **Local TLS pin mismatch** (§3b) — a fingerprint mismatch against `LocalHostTrustDescriptor` fails closed as an explicit local-endpoint-authentication security error; assert it is never classified as the Host-dormant case, never silently retried as one, and no client-side activation flow (§2a) is triggered by it.
23. **Real Host, both layers in order** (§3b, §3a) — against the genuine Host, local TLS authentication succeeds first, and only then does the `LocalPrincipal` signed-challenge exchange proceed; a client that skips or short-circuits the TLS step never reaches a state where its challenge signature is even evaluated.
24. **Enrollment/bootstrap secret confidentiality in transit** (§3b) — `EnrollmentCode` and `OwnerBootstrapSecret` submission is observable only in cleartext-equivalent terms *inside* the TLS-protected channel in a test harness that decrypts for assertion purposes; a simulated passive observer of the raw transport-level bytes recovers neither value.
25. **Initial-bootstrap race** (§2c, `OWNER-002`) — with a `PendingOwnerEnrollment` bound to OS principal X pending, a connection attempt from a different, otherwise-transport-eligible group member Y is rejected and produces no `LocalPrincipal` with `IsOwner = true`; only X's presented, verifier-matching secret succeeds.
26. **Bootstrap handoff readability** (§2c) — the platform-protected handoff artifact is readable by the intended SID/UID and not by another ordinary local account under the platform's own permission model (a Windows ACL check / a Linux ownership-and-mode check, not an application-level gate).
27. **Bootstrap secret persistence** (§2c, §7) — ordinary Host state (a simulated database copy) contains only `OwnerBootstrapSecret`'s keyed verifier, never a recoverable raw value; the same redaction assertion used for `EnrollmentCodeVerifier` applies here.
28. **`Uninitialized` Host authority surface** (§2c) — every ordinary operation (server start/stop, settings, backups, grant issuance, remote listener/administration) is denied while `HostBootstrapState = Uninitialized`; only the minimum local bootstrap-completion path is reachable.
29. **Successful bootstrap is atomic** (§2c) — one consumption of a valid `PendingOwnerEnrollment` produces, in the same transaction, exactly one `LocalPrincipal` with `IsOwner = true, State = Active` and `HostBootstrapState = Initialized`; no intermediate state is observable where one holds without the other.
30. **Bootstrap replay with a wrong secret is rejected; replay with the correct, already-consumed secret is an idempotent retry, not a second Owner** (§2c) — presenting a *different* or incorrect secret against an already-consumed `PendingOwnerEnrollment` is rejected and creates no side effect, exactly as a first-time wrong attempt would be; presenting the **same, correct** secret again (simulating a lost response) returns the identical `ResultLocalPrincipalId` from before, mutates no state, and creates no second `LocalPrincipal` or second `IsOwner = true` row — asserted by confirming exactly one `LocalPrincipal` row exists after both the original success and the retry.
31. **Bootstrap expiry** (§2c) — an expired, never-completed `PendingOwnerEnrollment` cannot establish Owner even with a correct secret; the Host remains `Uninitialized`, and only a fresh privileged `Host.Cli` bootstrap can proceed. An expired **and already-consumed** `PendingOwnerEnrollment` also refuses the idempotent-retry path (item 30) once `ExpiresUtc` has passed, even with the correct secret — the retry window is bounded, not indefinite.
32. **Post-initialization bootstrap lockout** (§2c) — once `HostBootstrapState = Initialized`, the initial-bootstrap RPC path cannot create or replace any `LocalPrincipal`'s `IsOwner`, under any input, including a resubmitted or freshly-generated bootstrap attempt; only §2b's distinct offline-recovery path can ever change Owner after initialization.
33. **Host machine-credential-loss recovery** (§3b) — the offline recovery operation is refused unless Host is stopped and the exclusivity lock is held under actual Administrator/root privilege, exactly like §2b/§2c; on success, `HostIdentity.CurrentCredentialRef` changes durably in SQLite and `LocalHostTrustDescriptor`'s fingerprint is republished to match as a separate, following step (never claimed as one cross-store transaction — see item 33a for the crash case); a local client connecting after both steps complete re-pins and authenticates successfully with no manual intervention; a simulated already-`Active` remote peer that still pins the *old* fingerprint is **not** silently restored — it fails its own local TLS-equivalent trust check on next contact and requires the ordinary §4a "credential loss" → §4b-i `PendingCredentialReplacement` re-pairing flow, with that peer's local Owner approval, same as any other credential-loss case.
33a. **Startup reconciliation between `HostIdentity.CurrentCredentialRef` and `LocalHostTrustDescriptor` is unconditional, not merely crash-triggered** (§3b) — a simulated crash between the SQLite `CurrentCredentialRef` write and the descriptor republish, on either the machine-credential-loss recovery path (§3b) or `IDENT-003`'s own cutover (§4a-i step 5), leaves the two stores briefly disagreeing; on the next Host startup, before any local IPC connection is served, Host detects the mismatch by comparing SQLite's value against the descriptor and republishes the descriptor to match SQLite — asserted directly, not merely inferred from a client eventually succeeding; a startup with **no** crash and **no** mismatch performs the same comparison and republishes nothing, confirming the check is unconditional rather than conditional on suspecting a crash occurred.
33b. **Startup reconciliation also covers the descriptor's abandoned `Pending*` fields, not merely `Current`** (§3b) — a simulated crash between `HostCredentialRotation.State = Aborted` (SQLite) and the Abort flow's descriptor republish (§4a-i "Abort") leaves `LocalHostTrustDescriptor.Pending*` still naming the abandoned `New`, with `Current` unchanged and therefore no mismatch on the `Current`-only check alone; assert the extended startup check independently detects this (`State = Aborted`/`Completed` but non-null descriptor `Pending*`) and clears the descriptor's `Pending*` fields before serving any connection, asserted directly rather than merely inferred from a client eventually failing to authenticate with the abandoned key. The symmetric case — `State = Staging`/`ReadyForCutover` genuinely in progress, but the descriptor's `Pending*` don't yet reflect `NewCredentialRef` — is also reconciled by (re-)publishing them to match, on the same unconditional startup check.
34. **Staged multi-peer Host credential rotation** (§4a-i, `IDENT-003`) — with two `Active` peers A and B: A stages the new credential while B is offline, and the Host **must** remain on the old credential (asserted directly, not merely inferred from A's own state); A, having staged, still accepts the old credential in a live connection **and** accepts the new one for the pending `RotationId`; B reconnects and stages, at which point cutover becomes eligible; a peer that stages and then goes offline does not block cutover once every other remaining `Active` peer has staged **and A's own acknowledgment is still unexpired at the moment cutover is attempted** (see item 34d for the expired case), and that peer reconnects successfully with the new credential later; an Owner explicitly revoking an unreachable, unstaged peer removes it as a blocker through the ordinary revocation cascade (§8) and it cannot silently regain trust afterward; duplicate rotation proposals and duplicate staging acknowledgments are idempotent and produce no duplicate trust or grant state; a proposal with the wrong `HostId`, an old-credential signature that doesn't match the peer's actually-pinned fingerprint, or a stale/mismatched `RotationId` is rejected; **no `CapabilityGrant` is created, modified, or removed at any step of routine rotation**; `LocalHostTrustDescriptor` recognizes both the current and pending fingerprint before cutover, and a local client connects successfully both immediately before and immediately after cutover with no manual re-trust step; a simulated Host-process crash and restart at every persisted rotation phase (prepared-not-staged, partially-staged, fully-staged-not-cutover, during/after the local-descriptor update, immediately after cutover) resumes deterministically from persisted state, never from memory alone; the emergency compromised-credential replacement path force-cuts-over without waiting on an offline peer, and **every** peer — including one that was `Active` and fully reachable at the moment of replacement — is left needing to re-pair through §4b-i rather than silently continuing to trust the Host on the strength of a signature under the now-compromised `Old` key; a simulated attacker who still possesses `Old` and forges a staging/promotion message during compromise recovery is rejected exactly like any other unauthenticated `PendingCredentialReplacement` attempt, never accepted as a legitimate in-progress rotation. **A new peer that reaches `Active` via ordinary pairing while a rotation is in progress is automatically added to the rotation and staged, and does not block cutover any differently from a peer present at rotation's start; that new peer is never left pinning only `Old` with no path to `New`.** After cutover, `HostIdentity.CurrentCredentialRef` is asserted to actually equal `NewCredentialRef` — not merely that the Host presents `New` on the wire — and a subsequent Host restart or a second rotation initiated afterward succeeds using that promoted reference, never failing to authenticate because the canonical reference was left pointing at already-retired key material.
34a. **Old-key retirement is gated on every peer resolving, not merely cutover** (§4a-i step 6) — with two `Active` peers A and B: A observes `New` and promotes immediately after cutover, B remains offline; assert `OldCredentialRef`'s private key material is **not** deleted while B has neither promoted, had its deadline lapse, nor been revoked, however long that takes; B eventually reconnects before its deadline, observes `New`, and promotes — only then does retirement become eligible for B's share, and once every peer has resolved one way or another, `HostCredentialRotation.State` transitions to `Completed` (distinct from, and strictly after, `CutOver`); alternatively, the Owner explicitly revokes B instead of waiting — B's share of retirement-eligibility is satisfied immediately, without B ever promoting.
34b. **A peer's acceptance of `Old` is bounded by `PendingRotationExpiresUtc`, never indefinite, and never renewable by a bare `Old` signature once lapsed** (§4a-i step 2/6) — a simulated adversary presenting a copy of `Old` to peer B **before** B's deadline lapses successfully authenticates an ordinary operation using the relationship's existing grants (an accepted, bounded-window consequence of B legitimately still trusting its own currently-pinned credential, exactly matching §4a's already-accepted routine-rotation threat model); the **same** adversary presenting `Old` to peer B **after** the deadline has lapsed with no promotion is rejected for ordinary authentication/RPC, even though B has not promoted and has no record of `New` — closing the previously-unbounded exposure window. **Critically, a simulated adversary presenting a *forged fresh staging proposal* — signed with the same copied `Old`, naming an attacker-controlled key as the proposed `New` — to peer B after B's deadline has lapsed is also rejected outright, never staged, never promotable**, even though the signature is validly under `Old`: once lapsed, resuming trust with B requires the local-Owner reconfirmation gate (§4a-i step 6, item 34e) for B's *already-verified* fingerprint specifically — never a signature-only proposal naming a *different* key, which is rejected exactly like an unauthenticated `PendingCredentialReplacement` attempt — asserted directly by attempting exactly this forged-proposal attack and confirming it produces no staged state and no promotable credential.
34c. **Aborting an in-progress rotation clears staged peers' `Pending*` state and the local descriptor's, and a subsequent rotation is never blocked by leftovers** (§4a-i "Abort") — with peer A staged and peer B offline (unstaged) when the Host aborts before cutover: `HostCredentialRotation.State = Aborted` is set immediately; A receives an authenticated abort notice and its `Pending*` fields are cleared, reverting it to trusting only the original `Old`; a simulated failure to deliver that notice to A leaves A still eventually reverting once its own `PendingRotationExpiresUtc` lapses, with no permanent stranding on the abandoned credential either way; B, never having staged, is unaffected. **`LocalHostTrustDescriptor.Pending*` is also cleared as part of the same abort, asserted directly** — a local client connecting after abort accepts only `CurrentHostCredentialFingerprint`, never the abandoned `New`, even indefinitely far in the future, since the descriptor's own pending fields have no independent expiry to fall back on; the abandoned `NewCredentialRef` private key material is retired immediately, not held for any peer. A fresh rotation attempt started afterward uses a new `RotationId`; presenting it to A (whether or not A's abort notice or deadline-expiry has happened yet) **overwrites** any stale `Pending*` state from the aborted attempt rather than being rejected as occupied.
34d. **Cutover revalidates every peer's acknowledgment at the moment it's attempted, with a required minimum margin, never trusting a stale or nearly-stale one** (§4a-i step 3) — with peer A staging early and peer B staying offline long enough for **A's own** `PendingRotationExpiresUtc` to lapse before B finally reconnects and stages: assert cutover does **not** proceed merely because both peers acknowledged at *some* point in the past — A's now-expired acknowledgment blocks cutover exactly like an unstaged peer would, asserted directly (not merely inferred from A's own state); resolving A's stale acknowledgment requires the grant-preserving local-Owner reconfirmation gate (item 34e) and A's local Owner's explicit approval (item 34b — a bare re-proposal is never sufficient once lapsed), after which cutover proceeds with both A and B genuinely current; alternatively the Owner explicitly revokes A instead. **Additionally**: with A's acknowledgment still technically unexpired but within the required minimum margin of expiring at the moment B finally stages, assert cutover still does **not** proceed on A's account — A counts as not-yet-eligible until either it re-stages with a fresh deadline or the Owner revokes it, closing the race where cutover could otherwise complete a hair's-breadth before A's own window lapses. A peer whose acknowledgment is re-validated as current, with adequate margin, at the moment cutover is attempted is never wrongly treated as expired merely because it staged early relative to a slower peer.
34e. **Lapsed-but-already-verified rotation reconfirmation preserves grants; it is never routed through the credential-loss/compromise gate** (§4a-i step 6) — with peer B's `PendingRotationExpiresUtc` lapsed without observation: assert B's `PendingTrustedPublicKeyFingerprint`/`PendingRotationId` are **retained**, not cleared, and `PendingReconfirmationRequired = true`; B's local Owner explicitly approves resuming, and assert the already-verified fingerprint is promoted directly to `CurrentTrustedPublicKeyFingerprint` with `TrustedManagers.State` remaining `Active` throughout and **every existing `CapabilityGrant` for that peer unchanged** — neither invalidated nor reissued, in direct contrast to item 18's `PendingCredentialReplacement` assertions, where approval explicitly does both; a simulated Owner instead choosing to revoke B (rather than reconfirm) proceeds through the ordinary revocation cascade (§8) exactly as elsewhere. A control case — a peer that never durably staged this `RotationId` at all before some other trigger (credential loss, compromise, or a wholly different, never-verified fingerprint) — is confirmed to still require the full grant-invalidating `PendingCredentialReplacement` gate (item 18), never this narrower one, since this gate is available only for a fingerprint the peer itself already cryptographically verified before lapsing.
35. **Legacy `Lan`/new `Contracts` project isolation** (§1, `ARCH-002`) — the frozen `App` project still references `PalworldServerManager.Lan` unchanged, and the frozen app's actual behavior consuming `Lan` types (e.g. `LanCoordinator`) is untouched; `Contracts` has no dependency, direct or transitive, on `Core` or on legacy `Lan`; every new v0.5 project (`Host`, `Host.Persistence`, `Host.Cli`, `Client.Avalonia`, `Client.Cli`, every `Platform.*`/`Client.Platform.*` project) has no dependency, direct or transitive, on legacy `Lan` — an architecture-guard test asserting this fails the build if any of these projects gains a `Lan` reference.
36. **`Client.Cli` dependency isolation and authentication parity** (§1, `CLIENT-003`) — `Client.Cli` has no dependency path to `Core`, `Host`, `Host.Persistence`, or any Host-side `Platform.*` project, mirroring the existing `Client.Avalonia` check; run as a given OS user with a valid `LocalPrincipalClientCredential`, `Client.Cli` successfully authenticates and executes an ordinary Host operation exactly like `Client.Avalonia` run as that same user would; run without a valid credential (none enrolled, or a deleted/corrupted one), `Client.Cli` cannot execute any ordinary Host operation — the same signed-challenge rejection §3a already requires, exercised through the CLI; no code path in `Client.Cli` obtains a Host machine private credential or reaches `Host.Persistence` directly, by construction (no dependency exists to do so) and by runtime assertion.
37. **Two-phase Owner bootstrap via `Client.Cli`** (§2c, `CLIENT-003`) — phase 1 (privileged offline `Host.Cli` preparation) succeeds identically regardless of which ordinary client will complete phase 2; phase 2 completed by `Client.Cli`, run as the intended OS account, succeeds using the same steps §2c defines (authenticate local Host first, generate keypair client-side, submit secret + public key) with **no** `Host.Cli` process involved in this online phase; the bootstrap-completion response's `LocalPrincipalId` is persisted by `Client.Cli` as a `LocalPrincipalClientCredential` together with its private key, and a subsequent, separate `Client.Cli` invocation authenticates successfully using that persisted binding with no re-bootstrap; `Client.Avalonia` and `Client.Cli` are interchangeable for phase 2 — whichever one completes it, the result is the same `LocalPrincipal` with `IsOwner = true`.
38. **Two-phase Owner credential-loss recovery** (§2b) — phase 1 (`Host.Cli`, offline, Administrator/root, exclusivity lock) creates a `PendingOwnerCredentialRotation` bound to the existing Owner's `LocalPrincipalId`/`OsPrincipalRef` and delivers a secret through the same protected handoff §2c uses; phase 2, completed online by `Client.Avalonia` or `Client.Cli` as that OS account with **no** `Host.Cli` process involved, generates a fresh keypair client-side and submits it with the secret; on success, the **existing** `LocalPrincipal` row's `PublicVerificationKey` is replaced (same `LocalPrincipalId`, `IsOwner` still `true`) — never a new row, never a second Owner; the old, lost private key is never required and never recoverable; a wrong secret is rejected and leaves the existing key untouched; **presenting the same, correct, already-consumed secret again (simulating a lost response) returns the same success outcome again without re-registering anything a second time** — asserted by confirming the row's `PublicVerificationKey` is unchanged by the retry itself; a retry attempted after `ExpiresUtc` is rejected even with the correct secret; the recovered Owner authenticates successfully on the very next connection using the newly persisted `LocalPrincipalClientCredential`.
39. **Two-phase Owner re-home, single- and multi-user** (§2b) — **single-user case**: the deleted Owner account was the only enrolled principal; phase 1 targets a brand-new `OsPrincipalRef`; phase 2, completed by that account via `Client.Avalonia` or `Client.Cli`, generates a fresh keypair and submits it with the secret; a new `LocalPrincipal` row is created with `IsOwner = true`, and the old (now-orphaned) row is fully revoked (`State = Revoked`, `PublicVerificationKey` cleared, its `CapabilityGrant`s cascade-invalidated — `LOCAL-003`'s procedure, not merely `IsOwner` cleared) in the same transaction. **Multi-user case**: the target `OsPrincipalRef` already has an ordinary, non-Owner `LocalPrincipal`; phase 2 submits that principal's existing public key rather than generating a new one; no duplicate row is created, `IsOwner` is set on the existing row, and the old row is fully revoked the same way in the same transaction. Both cases: exactly one `IsOwner = true` row exists at every point before, during (mid-transaction is never observable), and after the operation — never zero, never two; the old row is durably `Revoked`, never left `Active` with a still-usable key; a simulated reconnection attempt using the old row's original credential, from a still transport-eligible group member, is rejected — `Revoked` denies it regardless of group membership; a wrong secret is rejected and leaves both rows' state untouched; **presenting the same, correct, already-consumed secret again (simulating a lost response) returns the same `ResultLocalPrincipalId` again without creating a second row, re-transferring `IsOwner`, or re-revoking the old row a second time** — asserted by confirming both rows' state is unchanged by the retry itself; a retry attempted after `ExpiresUtc` is rejected even with the correct secret.

These extend the existing `PalworldServerManager.SelfTest` harness pattern rather than introducing a new, separate test framework.

## 15. Summary for #20/#21

Nothing above is implemented by this document. What #20 (Windows) and #21 (Linux) each get from it, without having to invent it themselves mid-implementation:

- The exact project topology and dependency direction, including **both** the `Contracts`/`Core` split and the new client-side `Client.Platform.*` tree, which together structurally keep `Client.Avalonia` and `Client.Cli` from ever reaching `Core` — closing the contradiction where `IHostActivation` previously lived in a `Core`-dependent project (§1). `Core`'s one explicit, bounded legacy carve-out for the frozen WPF app's existing Velopack/`VelopackUpdateBackend` dependency is also resolved here — not silently contradicted by a "BCL only" claim, and not something #20 needs to move or work around (§1). **Legacy `Lan`/new `Contracts` non-rename, resolved**: `Lan` is retained unchanged, solely for the frozen `App`; `Contracts` is a genuinely new, from-scratch, `Core`-and-`Lan`-independent assembly; no v0.5 project depends on `Lan` (§1, `ARCH-002`).
- **`Host.Cli`/`Client.Cli` privilege split, resolved**: `Host.Cli` is privileged offline bootstrap/recovery only — never an ordinary online client, never a `LocalPrincipal` credential holder, never a bypass of local-client authorization; the new `Client.Cli` is an ordinary online command-line client, structurally a `Client.Avalonia` peer (same `Client.Platform.Contracts` tree, same `LocalPrincipal` credential model, same server-authenticated local-IPC route), and either ordinary client may complete initial Owner bootstrap's online phase — never `Host.Cli` itself (§1, §2c, §5a, `CLIENT-003`).
- Host is one machine-wide service, single writer, single-instance-locked (§2) — a deliberate reduction of general competing-authority/multi-writer risk, independent of and not claiming to resolve #26, which remains an open investigation.
- A bounded, non-Administrator path for an ordinary user to activate a dormant desktop Host, with install-time-only DACL/group provisioning on Windows and an explicitly-deferred-to-#20/#21 distro-appropriate mechanism on Linux (§2a); precise Owner immutability and exceptional offline recovery/re-homing semantics (§2b). **`LocalPrincipal` lifecycle, resolved**: OS-group/ACL membership is transport eligibility only, never enrollment or re-enrollment authority; revocation is durable (`State: Active | Revoked`, row retained) and independent of OS-group removal; non-Owner enrollment and reactivation both require an explicit, Owner-created, single-use `PendingLocalPrincipalEnrollment`, consumed only with a correctly presented out-of-band `EnrollmentCode` — the shared group ACL and a claimed `OsPrincipalRef` alone are never sufficient; reactivation never auto-restores prior grants (§3a).
- Local IPC transport with a corrected, non-contradictory ACL policy, and an asymmetric per-principal client-credential/Host-verifier identity model — the client's own OS-native per-user credential protection, never Host's machine-scoped secret store — plus the required #20 preflight gate (§3, §3a). **Local server authentication, resolved**: local IPC is server-authenticated and integrity-protected via standard TLS using the existing Host machine credential and a public `LocalHostTrustDescriptor`, before any secret or ordinary RPC crosses it — closing the named-pipe/Unix-socket-squatting exposure, with an explicit, never-conflated distinction between "Host is dormant" and "local authentication failed" (§3b, `LOCAL-004`).
- **Privileged initial Owner bootstrap, resolved**: the first Owner is established only through an Administrator/root-authorized `Host.Cli` operation bound to an exact `OsPrincipalRef`, a single-use `OwnerBootstrapSecret` delivered via OS-ACL'd handoff — never ordinary product-group membership — and a `HostBootstrapState` gate that permanently disables the bootstrap path once consumed; an `Uninitialized` Host exposes no ordinary Manager authority at all (§2c, `OWNER-002`). **Owner credential-loss recovery, resolved**: the same offline-preparation/online-completion two-phase shape now defines exactly how the *existing* Owner's lost credential is actually replaced — a `Host.Cli`-prepared, single-use secret and an online client-generated keypair, never a public key that was supposed to materialize with no defined path to get there (§2b).
- The remote protocol technology (gRPC/TLS) and its actual new dependencies (§4); a stable `HostId` kept separate from rotatable authentication credentials (§4a); a role-appropriate SPAKE2 pairing bootstrap with a corrected security property, an explicit authenticated identity-binding mechanism, and a local-only state machine — now with an explicit `PeerBound` state so configured, non-trivial default grants are never usable before reciprocal activation confirmation, alongside the honest, deliberately simple process-crash-discards-unfinished-cryptographic-state rule for the states before it (§4b). **Credential-loss trust replacement, resolved**: a fresh pairing claiming an already-known `HostId` produces only a zero-authority `PendingCredentialReplacement`, never an automatic `Active` trust or an automatic inheritance of the old peer's grants — explicit local Owner approval is required, and the previously-undefined "Owner adoption/re-home" mechanism now has a concrete, audited definition (§4b-i). **Staged multi-peer credential rotation, resolved**: routine rotation of the Host's single global credential is no longer a single immediate switch — every remaining `Active` peer, and the local `LocalHostTrustDescriptor`, durably stages the new credential alongside the still-valid old one before the Host ever cuts over, so an offline peer is never stranded by a rotation it didn't witness live and a peer that already staged never sees a stale credential either; a suspected-compromise emergency path exists separately and, since nothing signed by the compromised key can be trusted as proof for anyone, every peer re-establishes trust through the same fresh-pairing/Owner-approval gate credential loss already uses — never an old-key-authenticated fast path for whichever peers happen to be reachable (§4a-i, `IDENT-003`).
- **Who owns outbound remote connections, resolved**: the local machine-wide Host, never `Client.Avalonia` or `Client.Cli` — neither of which ever receives a Host private credential — including that pairing itself is Host-to-Host even when triggered from either ordinary client, and the dual local-authorization-then-remote-authorization invariant, now explicitly gated on `Active` (never merely `PeerBound`) trust on both sides, for every outbound remote operation (§4c).
- **Canonical, collision-safe cross-Host server identity, resolved**: `ServerRef { AuthoritativeHostId, ServerProfileId }`, used everywhere a server identity crosses a Host boundary or appears in a unified local/remote inventory — grants, routing, operation locks/records, audit, and the settings-metadata RPC surface — not left to #20 to invent (§4d).
- A type-safe authorization model — `HostCapabilityGrant` and `ServerCapabilityGrant` as distinct shapes, an exact delegation predicate, `ManagePermissions` explicitly excluded from that predicate *and* from `DefaultGrantTemplate` editing (Owner-only, closing a real grant-manufacturing bypass), validated role-preset application, a redundant capability name removed, and the structure correctly described as a tree/forest (§5). **Host-capability destination scoping, resolved**: every `HostCapabilityGrant` now targets exactly one `TargetHostId` (`AUTH-005`) — closing the gap where a single local grant would otherwise satisfy outbound authorization against *every* paired remote Host rather than the one it was actually meant for.
- A unified local/remote actor model for grants and audit (§5b).
- Explicit `Host.Cli`/Host SQLite-writer-exclusivity ownership, not left for #20/#21 to invent — `Host.Cli` now has exactly one mode, privileged offline bootstrap/recovery, so there is no second "normal mode" left to reconcile with Host's own writer exclusivity (§5a, `CLIENT-003`).
- The persistence technology (SQLite, with an honest dependency and WAL-safe-backup framing) and schema shape (§6).
- The secure-credential contract, per-OS strategy, and an honest, now-symmetric threat-model boundary on both platforms (neither claims protection from a fully privileged local machine owner), coordinated with #27 (§7).
- The revocation mechanics, aligned with the `HostId`/credential model, coordinated with #28 (§8) — including how a same-`HostId` re-pairing attempt diverts into §4b-i's `PendingCredentialReplacement` gate rather than an ordinary fresh pairing, and why revocation retains a durable `Revoked`-state tombstone rather than deleting the `TrustedManagers` row, so that gate can never be bypassed by simply deleting the evidence a peer was ever trusted.
- Concurrency/locking contracts generalizing the proven `CriticalOperationTracker` pattern (§9).
- The durable recovery model and its explicit non-assumption of resumability (§10).
- The full platform-interface list, correctly split across Host-side and client-side projects, including the concrete `ILocalPrincipalCredentialStore` client-side credential contract (§11). **Interactive shell launching, resolved as entirely client-side**: Host has no shell-launch interface at all — a Windows Session-0 service and a headless Linux daemon can't meaningfully own one — `Client.Avalonia`'s `IClientShellIntegration` handles both its own diagnostic folder and, given a Host-authorized local path, a local server's data folder; Host exposes only a narrow local-IPC-only path lookup for an already-known local server, never a remote one (§11, §11a).
