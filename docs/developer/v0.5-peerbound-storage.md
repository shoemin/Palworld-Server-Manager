# Durable pending peer trust

Trial reference: #44c, within #44. `PeerTrustRepository` is a trusted Host persistence primitive after cryptographic identity verification. A fingerprint argument alone proves nothing: later Host transport composition must supply only actual verified bindings, retain the machine-wide lease, and enforce local authorization. This unit does not expose an RPC, activate trust, apply grants, approve replacements or implement rotation.

The repository checks the initialized local Host identity, exactly one active Owner, and the current non-retired Host credential inside its transaction. A binding made under a local credential that changed before persistence is rejected. New peer UUID/public-fingerprint bindings create `TrustedManagers.State = PeerBound`, a thirty-minute pending deadline, the local public fingerprint used in the exchange, and a redacted audit event in the same SQLite transaction. No private credential, pairing code, nonce or session key enters these tables. PeerBound grants no management authority.

Concurrent and repeated matching bindings retain the original pin and deadline. An existing PeerBound remains PeerBound and must resume through the later pinned mTLS activation path. A matching Active peer only reconfirms existing trust; no new grant or default application occurs. A recovery-required relationship remains blocked even with a matching peer fingerprint. A different credential or any claim against a Revoked tombstone creates an unapproved, zero-authority `PendingCredentialReplacement` capturing the existing state and current fingerprint. Matching unexpired candidate retries reuse that candidate without extending its deadline. They never replace the trusted pin.

Expired PeerBound relationships become retained Revoked tombstones. Current and staged peer pins and recovery flags are cleared; outstanding replacement candidates are invalidated, including previously approved records, so a later state cycle cannot revive them. Expiry and its audit event commit together. A failed audit write rolls back the entire transition. The thirty-minute pending window is independent of the five-minute ephemeral code window. These durable deadlines use UTC and are evaluated by the Host's clock; the later service must schedule cleanup and check the deadline again during activation. `Read` returns a snapshot and is not an authorization decision.

Schema migration 3 adds public pairing metadata. Prior PeerBound rows receive deadlines based on their original creation time. The migration deliberately leaves the verified local fingerprint absent because old rows do not establish that proof; they cannot be silently resumed through this repository, and expire to tombstones. An invalid historical timestamp fails migration instead of inventing a new deadline. No old pin becomes Active during upgrade.

Offline Host-credential recovery now marks both Active and PeerBound relationships as recovery-required and invalidates old replacement candidates in its existing transaction. This propagates the existing recovery rule to newly implemented pending-trust storage; old pending relationships cannot resume using a replaced local credential. Owner approval, fresh recovery pairing, live mTLS proof and the recovery-completion acknowledgment remain later work.

Five ordinary test scenarios cover durable reopening and concurrent idempotent writes, zero grants and credential replacement routing, tombstone expiry and candidate invalidation, audit-trigger rollback and competing credentials, prior-schema migration without fabricated proof, and the offline-recovery interaction. Fixture keys/fingerprints are public test values, not cryptographic evidence. The accepted native pairing tests remain separate. Run the ordinary suite or `--peer-trust-probe`; exact qualification and two-pass review records live in the trial ledger. Actual multi-Host activation/crash qualification is still outstanding.
