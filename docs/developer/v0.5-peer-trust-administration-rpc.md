# Receiving peer trust administration

Trial reference: #28. The normal peer listener offers explicit `PeerTrustAdministration` (21) with peer protocol1.15. Recovery-only negotiation offers only its two existing intrinsic features and cannot enable administration, even when requested. The local protocol is now1.18 after the separate [originating-user route](v0.5-originating-user-trust-route.md). Additive host1.18 and peer1.15 descriptor snapshots retain all earlier schemas. Product version and pairing alone authorize nothing.

`ReadManagedPeerTrust` and `RevokeManagedPeerTrust` enter the original runtime-owned native TLS session once through the existing synchronous peer permission dispatcher. The dispatcher requires both ordinary peer negotiation and feature21 before any request-level credential observation. Its original peer/local fingerprints, semantic peer and incarnation feed canonical ordinary authentication. Current Active, non-recovery trust and exact destination `ManageTrustedManagers` are required again by the repository. A receiving machine grant is only one ceiling: the sending Host must independently authorize its originating local principal before contact. The [originating-user route](v0.5-originating-user-trust-route.md) supplies those independent checks.

Normal native negotiation can independently record a valid staged-key presentation. Once an original session exists, an administration request missing feature21 does not trigger further observation. A permitted request may record a legitimate staged-key promotion before a stale or denied command fails. The caller must refresh the resulting authorization revision; this separate security transition creates no grant and does not make the command succeed.

Read requests name the exact authoritative Host, optional keyset cursor and limit up to16. The existing private trust projection is shared by local and remote actor adapters, preserving local behavior. Current proof and destination permission are checked in the same transaction as the read, with final proof/revision checks before commit. Replies contain only public IDs, closed trust state, incarnation, public fingerprints and recovery status, with a current authorization revision and bounded continuation. Every reply fits16KiB. Reads create no authority or success audit; denied capability use retains canonical audit identity. Pages are observations, not execution permits or multi-page snapshots.

Revoke requests name the authoritative Host, selected peer, expected authorization revision and incarnation. The existing canonical remote writer commits only that relationship's clean tombstone, exact grant subtrees, pending replacements and bounded audit. It cannot target a local Owner. Unrelated roots/relationships remain intact. Stale revision returns `Aborted`; changed target incarnation returns `FailedPrecondition`. Malformed input returns `InvalidArgument`, denied capability `PermissionDenied`, and changed original proof `Unauthenticated`. Missing/corrupt authoritative data and other internal errors return constant text without database detail.

A successful reply describes the receiving Host's local commit only. Existing prepared notification can run after commit, never blocking it. Selected-peer retries with refreshed revision/incarnation are idempotent while the actor remains authorized. Intentional self-revocation uses only the canonical exact actor-equals-target final tombstone rule. The old authenticated session cannot issue ordinary retries or become current again after an artificial same-key later relationship. No remote Owner/replacement approval, generic queue, new grant/default/creator writer or distributed transaction is introduced.

Nine qualification groups cover real native TLS and explicit older-minor feature negotiation, actual recovery-only refusal, machine permission denial and wrong scope, exact descendant removal with unrelated roots/Owner preserved, self-revocation and old-session refusal, stale/malformed/Owner-target refusals, bounded pages and corrupt projections, current proof/non-Active changes, audit rollback, runtime ownership and cancellation. Historical verified Active/staged relationships are explicit fixtures. The separate request-level feature/rotation-order case uses a controlled original-session dispatcher fixture; actual native negotiation independently promotes a valid pending key and is tested separately. This is receiving qualification, not the originating local-user route or physical-PC acceptance.

The separately qualified [originating local route](v0.5-originating-user-trust-route.md) enforces its independent exact-destination permission before contact and before sending. No ordinary client may hold the Host key or directly act as that machine. No new installed remote enablement, UI, physical Palworld/Windows parity, Linux or release qualification is claimed.
