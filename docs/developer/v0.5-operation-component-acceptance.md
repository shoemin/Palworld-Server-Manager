# Host operation framework component acceptance

Trial reference: #46h. This assembles the reusable #46 framework from the accepted [definitions](v0.5-operation-definitions.md), [resource revisions](v0.5-resource-revisions.md), [durable lifecycle](v0.5-durable-operation-lifecycle.md), [workers](v0.5-host-owned-operation-workers.md), [startup recovery](v0.5-operation-startup-recovery.md), [Activity contracts](v0.5-operation-activity-contracts.md) and [installed lifetime](v0.5-operation-host-lifetime.md). The experiment ledger records exact qualification and final acceptance. Concrete backup/restore/SteamCMD/transfer, UI and Linux remain outside #46's authorized scope.

## Issue acceptance criteria

| Current #46 criterion | Evidence and boundary |
|---|---|
| Stale writes reject instead of overwriting | ConfigurationRevisionRepository compares inside the immediate transaction before the trusted action. Operation transitions/heartbeats compare exact record revision. Competing writers, late faults, cancellation, exhaustion and rollback/retry tests cover both seams. |
| Two clients observe the same lock | OperationActivityTests independently serialize complete snapshots. OperationCrossHostTests keeps two live destination/origin Host fixtures and two independent contract consumers; both see the exact destination lock for HostScope and ServerScope. These are representative consumers, not installed Activity RPCs. |
| Conflicting operations cannot run concurrently | OperationLockPolicy declares the fixed symmetric hierarchy; repository acquisition and record creation commit together. Concurrent Host/server admissions yield exactly one conflicting winner, while independent server or different-Host work can coexist. |
| Safe read-only status remains possible where modeled | Repository/runtime/Activity reads acquire no operation lock, do not advance revisions and preserve exclusion while workers remain held. Damaged/orphan lock evidence stays visible; malformed state refuses instead of becoming idle. |
| Initiating-client disconnect does not cancel or lose Host work | Worker and cross-Host tests cancel the initiating admission/wait token while actual Host-owned tasks remain Running and their exact locks remain. The combined test covers HostTarget/HostScope, ServerTarget/ServerScope and ServerTarget/HostScope. Only explicit resolution releases the lock. |
| Recovery classification is explicit per operation phase | Immutable kind definitions declare phases, edges and dispositions with version/fingerprint qualification. A mixed-kind fixture assigns all four dispositions to different phases on both target types. Explicit trusted handlers apply retry/resume/discard; manual or missing handlers stay held. |
| No generic resume-everything behavior | Missing/unknown/changed policy, inconsistent state, failed preparation or failed initialization cannot choose the ordinary executor or retry in a loop. Startup is one-time per runtime. An empty product registry preserves unknown work as Recovery Required. |
| ServerRef prevents equal-profile cross-Host collisions | Core target/scope values and persisted keys retain authoritative Host ID. A refuses a B-targeted admission without recording or dispatching it. B owns its operation/lock; A can run independent work with the same profile ID. Finishing B does not release A's lock. |

The additional authorized scope is also present: durable OperationRecord persistence and schema12 qualification, operation identity independent of initiating connection, all-target startup inspection, explicit Recovery Required state, immutable Activity DTO history and explicit feature negotiation. No offline command queue, generic cancellation command or implicit recovery authority is introduced.

The installed Windows root owns one operation lifetime outside its listener generation and under the machine lease. Bootstrap-only startup remains valid before an Owner exists; future ordinary operation access must obtain the lifetime's ready runtime. Shutdown signals operations before awaiting generation shutdown and drains actual workers before releasing the lease. Lifetime tests cover concurrent initialization, failure hold and real lease retention; privileged Windows integration separately verifies the changed installed root's actual bootstrap, restart, native security and multiple-user behavior.

## Responsibilities of later verticals

The product registry is currently empty. Concrete operations must supply durable business inputs, a declared lock requirement, phase semantics/version, explicit suitable recovery handlers, actual current caller authority and audit/effect validation at each boundary. Repository callbacks are trusted Host code, not client-supplied commands or a sandbox. Configuration revision transactions can roll back database effects; filesystem/process operations need their own durable effect/recovery design.

Activity contracts and trusted mapping do not install an endpoint or grant read authority. A publisher must authenticate the actual caller and enforce permitted current visibility, including independent originating local-user and destination peer ceilings for remote administration. Wire snapshots preserve status and lock evidence; their durable SQL revision is not an Activity freshness cursor because worker status can change without a database write. Future client RPCs must not treat a failed/invalid observation as an empty healthy snapshot.

The assembled evidence is framework qualification with representative operations and serialized consumers. It does not claim real Palworld execution, installed business/Activity RPCs, physical PCs/reboot, Windows feature parity, Linux or release acceptance. Accessibility/screen-reader certification remains WAIVED, never PASS. The six approved creator grants and their limits remain unchanged.
