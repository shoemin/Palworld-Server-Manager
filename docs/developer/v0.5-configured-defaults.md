# Owner-configured pairing defaults

Trial reference: #45c. This unit implements configured templates and their canonical application at the existing Active transition. The [typed foundation](v0.5-authorization-foundation.md) and [transactional grant repository](v0.5-transactional-grants.md) remain authoritative. Later engine slices add [presets](v0.5-canonical-presets.md) and [Owner historical reissue](v0.5-historical-grant-reissue.md). Remote mutations, creator grants, failed-request auditing and incoming Host dispatch remain incomplete; complete credential-replacement integration is separate.

The shipped factory template has no grant entries, matching #17's denial of server inventory, creation, administration, permission management and delegation for a freshly paired Manager. An Owner-configured empty template is represented distinctly from never-configured factory state. A configured template may contain broader authority, so activation always reads the current configuration inside its own transaction. Pairing does not bypass reciprocal activation simply because the factory defaults are empty.

Core template entries are immutable, closed Host/server capability shapes with copied read-only collections, exact server identities and validated delegation rights. Duplicate capability/target entries refuse. Host entries materialize with explicit TargetHostId=ThisHostId. Server entries target an exact ServerRef on this authoritative Host; there is no all-servers or foreign-Host default scope. Templates are configuration data, never persisted roles or independently usable grants.

Schema11 adds singleton configuration identity/Owner/time metadata and two typed entry tables. The initial state creates no grants and contains no configured entries. All template mutations advance the existing authorization revision through triggers with the same missing/exhausted-counter refusal as schema10. Configuring requires current authenticated local proof, the expected revision and structural Owner authority in an immediate writer transaction; ManagePermissions cannot substitute. Replacing the template and its closed-field audit commit atomically with a new configuration identity. Post-audit Owner, revision and exact-content checks reject changed authority. Existing grant rows are not rewritten.

`CreateDefaultActivationHook` supplies the real mandatory `IPeerActivationHook`. It uses the connection and transaction already owned by PeerTrustRepository, without a nested connection, commit or external effect. After that repository changes PeerBound to Active, the hook checks current Host/Owner/peer facts and reads the current configured template. Each entry is issued through the canonical Owner-root rule with a new grant ID, the exact target, null parent and current Owner as GrantedByActor. The automatic audit records the actual initiating local Owner or RemoteManager, true Owner issuer, peer grantee and configuration identity. PeerTrustRepository supplies that caller provenance from its authenticated path; the hook never invents a local request or accepts a request-body actor claim. The enclosing PeerActivated event records the trust transition.

The hook returns a separate validator for each call. PeerTrustRepository requires that validator, invokes it after its own trust audit, then checks the original pairing deadline, current initiating Owner when applicable, and cancellation before committing. The real validator rechecks revision, current Owner/Active peer, exact template metadata and every newly persisted grant. Failure rolls back trust, grants, revisions and both audits together. Synthetic historical test providers return explicit fixture-only guards; there is no production no-op provider or optional guard fallback. The already-Active retry returns before applying any template, so retries and later configuration edits never retroactively mint or rewrite grants.

Eight ordinary scenarios cover immutable/unknown/duplicate shapes, schema10 upgrade with zero grant effects, factory versus configured-empty state, Owner-only configuration even against ManagePermissions, current-at-activation semantics, exact grant/audit provenance and no retroactivity, inner/outer audit failure or authority mutation rollback, deadline and cancellation including a slow final guard, missing guard refusal, simultaneous activations sharing a provider, and independent two-Host commits. They use actual SQLite transactions and explicitly synthetic identity/trust fixtures. Existing native/service regression qualification remains separate; this unit does not claim a new installed management RPC or physical Windows parity. Accessibility remains waived, not passed. Linux and release gates remain downstream.
