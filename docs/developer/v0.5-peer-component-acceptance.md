# Host transport and pairing component acceptance

Trial reference: #44as, completing the isolated #44 component audit. The [trial ledger](../experiments/astra-v0.5.0-trial.md) records both reviews, exact validated commits and acceptance. This inventory does not close the canonical issue or change its Project state. It covers the current #44 issue body under the owner's isolated-trial authorization.

The component provides Host-owned first-contact PAKE and pinned gRPC/TLS, stable Host identity, durable zero-authority PeerBound, reciprocal activation, current-key-authenticated rotation, local Owner initiation, and the required manual-address/LAN foundation. A mandatory transactional Active hook is present; the capability/default engine is now covered by the [component acceptance inventory](v0.5-authorization-component-acceptance.md). No ordinary server-operation forwarding is enabled by this component.

## Contract evidence

| Current #44 acceptance criterion | Implementation and concrete evidence |
|---|---|
| An attacker without the code cannot bind its credential to a peer HostId. | The [guarded SPAKE2 provider](v0.5-spake2-wrapper.md) authenticates both immutable public identities. `Spake2WrapperTests` exercises wrong code, reflection, replay and HostId/key/MAC substitution using the real native provider. `PeerPairingRpcTests.Native` additionally rejects a valid native binding for the wrong actual TLS credential and a valid binding followed by forbidden trailing frames. First-contact TLS proves possession; only code-confirmed identity matching the actual TLS SPKI reaches storage. |
| Created, PAKEAuthenticated and PeerBound grant no ordinary authority. | `PairingAttemptCoordinator` holds only ephemeral exchange state. `PeerTrustRepository` writes public trust, original deadline and binding provenance without grants. `PeerTrustTests`, `PeerActivationTests`, native RPC and service process cases inspect both canonical grant tables. Pending trust is identity state, never an authorization decision. |
| PeerBound permits only activation/recovery traffic. | `PeerTransportAuthentication` denies unknown purposes, ordinary management and trust maintenance for PeerBound. `PeerTlsTests.TrustPurposes` and `PeerSecurityRpcTests` exercise purpose and per-RPC state checks. Recovery-required or unapproved replacement state is refused; the finalization label is no shortcut through the independent Owner replacement gate. |
| The normal remote path requires Active trust. | Fresh Host-side purpose admission requires Active for ordinary management; the service rechecks live trust on each authenticated RPC. Active is only the prerequisite to #45's independent capability checks. No server-operation forwarding or client-held machine identity is supplied in #44. |
| Persistence never assumes a transaction spanning two Hosts. | The initiating PAKE stream commits before sending its own binding; the responder verifies that binding and EOF before its separate commit. Real result-loss tests and `PeerActivationTests.ReciprocalReopenAndLostReply` retain independent local state. The [asymmetric responder crash](v0.5-peer-responder-process-crash.md) preserves the initiator's original record, deadline, incarnation and binding evidence while the responder has no binding. |
| A pre-PeerBound crash discards ephemeral state; durable PeerBound can resume over pinned mTLS. | The [native precommit initiator case](v0.5-peer-precommit-process-crash.md) kills the actual process after native verification but before Store and requires fresh pairing. The [post-PeerBound case](v0.5-peerbound-process-recovery.md) restarts with the same protected/native identity and a provider that refuses PAKE, then activates successfully over pinned TLS. The asymmetric responder case independently requires fresh pairing on the unbound side and resumes the original pending record on the other. |
| Activation retries are idempotent. | The mandatory hook, trust transition and audit share one local transaction. Ordinary tests exercise concurrent retries, reopen, asymmetric completion, hook/audit failure, deadline and Owner/cancellation changes. Actual post-PeerBound and responder process cases produce one fixture activation effect and one original binding audit per Host, with zero canonical grants. No production no-op hook exists. |
| Machine private credentials never appear in ordinary client processes, diagnostic test surfaces or logs. | Host-owned DPAPI storage, protected native nonexportable CNG handles and generation-owned borrowers retain the machine key. Real two-user service tests refuse ordinary-user access to protected/native material. Client dependency tests and protected local Owner RPC qualify the boundary. Public process reports contain identities/pins and bounded status only; transient pairing codes use exact-length private control pipes, never arguments, JSON or logs. These codes are not machine private credentials. |

## Additional authorized scope

[Rotation preparation](v0.5-rotation-preparation.md), [material recovery](v0.5-rotation-material.md), [staging](v0.5-rotation-staging.md), [proposal transport](v0.5-rotation-proposal-rpc.md), [reconfirmation](v0.5-rotation-reconfirmation.md), [cutover](v0.5-rotation-cutover.md), [receipts](v0.5-rotation-receipt-rpc.md) and [completion](v0.5-rotation-completion.md) preserve stable HostId and require current-credential proof. Peer revision and relationship-incarnation checks prevent stale evidence from authorizing a later relationship. Actual New presentation is required for promotion; expired staging does not invent that proof or revoke genuine Old trust. The retained receipt survives an [actual receiving-process restart](v0.5-peer-receipt-process-recovery.md). Routine rotation changes no capability grants; loss and suspected compromise retain their distinct privileged offline recovery and peer-local replacement gates.

The audit found and corrected one real ordering gap: [retirement now precedes Completed](v0.5-rotation-retirement-ordering.md). Durable retirement authorization permits retry after partial cleanup, but terminal completion requires native and protected deletion. A real Windows sharing lock exercises protected deletion refusal after native retirement; listeners stay closed, and recovery preserves original New. Earlier tests expecting premature Completed do not qualify the corrected order.

The [Host generation](v0.5-host-network-generation.md) and [transition coordinator](v0.5-host-generation-transitions.md) own all listeners, outgoing TLS callbacks, borrowed credentials, attempt/audit timers and optional discovery. Failed shutdown never supplies a usable quiescence handoff. Manual-address and bounded discovery hints select a destination, never prove identity. Actual datagrams, Windows adapter ABI, lifetime and protected local Owner initiation tests qualify this foundation. Local initiation uses the same authenticated per-user boundary before the Host performs peer work.

## Evidence limits and next work

The disposable service tests simulate separate Hosts with distinct identities, protected roots, native containers and leases on one Windows runner. They use real TLS, native PAKE, OS users, process termination and restart. They do not claim separate physical PCs, power loss, reboot, or a kill inside every possible database commit. Database audit/transaction rollback and representative pre/post/asymmetric process boundaries are separate evidence, not interchangeable labels.

`WindowsHostComposition` exposes the full trusted network composition and mandatory Active hook. The installed `RunAsync` remains local-only pending complete authorization/configuration integration. This component acceptance does not claim a finished installed pairing UI or operational remote administration. The [component acceptance inventory](v0.5-authorization-component-acceptance.md) covers canonical grants/defaults and the dual local/remote authorization engine; #28 supplies unpairing; operation slices supply forwarding; #54 supplies Manager UI. These are excluded work or downstream dependencies in the current issue bodies, not circular prerequisites for the #44 component.

The final Windows parity gate #55 and broader validation #23 retain their explicit integration/field requirements. Unavailable physical/reboot evidence is FIELD EVIDENCE REQUIRED there; neither Linux's hard Windows-before-Linux gate nor release qualification is released here.
